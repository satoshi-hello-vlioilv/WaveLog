# tests — 回帰テスト

```
tests/run_all.sh      # 一括実行(これだけ覚えればよい)
```

以前はサンドボックスの作業用フォルダにしか無く、セッションが変わるたびに
消えていた。安全網が揮発する状態ではリファクタリングに着手できないため、
リポジトリへ常設した(docs/REFACTORING_PLAN.md フェーズ0)。

## 実行

```bash
tests/run_all.sh
```

ランナーが前後処理まで面倒を見る:

1. **パス設定マスタを退避** → 検証用フィクスチャ(`db/test_fixture/`)へ
   差し替え → サーバー再起動
2. **1本ごとに作業予定を種データへ戻す** → テスト実行
   (アクセスモードはグループごとに切り替え)
3. **退避した値へ必ず復元** → サーバー再起動
   `trap ... EXIT INT TERM` で登録しているので、Ctrl+Cや異常終了でも戻る。

2の「戻す」が要るのは、テストが並べ替え・ロック・予定追加でフィクスチャを
書き換えるため。戻さないと次のテストが前の並び順を引き継ぎ、さらにその結果が
ファイルに残るので**次の実行は前の実行の続きから始まる**。行を位置で掴む
テストが、単体では通るのに通しで回すと落ちる原因になっていた。

共有スケジュールDBは、gitが持つ原本ではなく`db/test_fixture/work/`へ作った
**作業用コピー**を使う(ランナーが毎回作り直す)。原本を直接書き換えると、
テストを回すたびに追跡ファイルが変わり`git status`が汚れ続ける。
仕掛・品質データは読み取り専用なので原本のまま。

3の復元は以前は手作業で、**戻し忘れると以降の起動が検証用DBを読み続ける**
事故になっていた(CLAUDE.mdにも注意事項として書かれていた運用)。人間の記憶に
頼らずランナーが担保する。

退避した値は`tests/.saved_paths.json`にも書き、復元できたら消す。`trap`は
プロセスが死ぬときにしか走らないので、**コンテナごと落ちる**ような終わり方だと
復元されないまま残る。その状態で次の実行が「今の値」を退避すると、退避される
のは検証用フィクスチャのパスで、本来の設定が上書きで永久に失われる(実際に
起きた)。ファイルが残っていたら前回が復元前に終わった証拠なので、次の実行は
そちらを真として復元する。

テストが異常終了して閉じ損ねたChromiumも、1本ごとに掃除する
(`--user-data-dir=/tmp/playwright_chromiumdev_profile` で絞るので、
Playwrightが起動したものだけが対象)。残った画面は設備の編集セッションを
掴んだままハートビートを打ち続けるため、後続のスケジュール系テストが
「編集中です」で連鎖的に落ちる — 実際に1本のFATALから8本が落ちた。

### 一部だけ実行する

引数にテスト名を並べると、それだけを実行する(拡張子は省略可)。
前後のパス退避・復元はそのまま効く。

```bash
tests/run_all.sh test_screport test_sccat
```

### 変更したファイルに関係するものだけ実行する（§9.103）

```bash
tests/run_all.sh --changed          # git の変更 → 関係するテストだけ
python3 tests/pick_tests.py --why   # 何がどの規則で選ばれたかを見る
python3 tests/pick_tests.py backend/routes/logs.py   # ファイルを直接指定
```

`tests/pick_tests.py` の対応表（変更ファイル → テスト）で絞り込む。
**通しの代わりではない。** 「関係ない」と判断する根拠はその手書きの表しか
ないので、表が間違っていれば見落とす。**コミット前は必ず通しで回すこと。**
直したそばから回せる折り返しを作るための道具で、安全網を薄くする道具ではない。

決めごとは3つ:

- **分からないものは全部回す。** 当たる規則が無いファイルを「関係なし」と
  読むと、道具が黙って安全網を外す。
- **土台を触ったら全部回す**(`base.js` / `index.html` / `app.py` /
  `backend/config.py` / `run_all.sh`)。
- **安い静的検査は常に混ぜる**(`test_patchlint` / `test_globallint` /
  `test_dskeylint` / `test_csslint` / `test_docindex`)。変更したファイルからは
  辿れない種類の崩れを見るため。

テストやソースを足したら対応表にも足す。`tests/test_pick.py` が
「実体の無いテスト名」「どの規則からも呼ばれないテスト」「どの規則にも
当たらないソース」の3つを見張っているので、忘れると落ちる。

## テストを書くときの約束

出力の形式はランナーが集計に使う。守らないと件数が合わなくなる。

- 各検証は行頭 `PASS: ` / `FAIL: ` で1行出す
- 例外は `FATAL` を含めて出し、終了コードを非0にする

### 後始末は `finally` に置く(重要)

テストは**共有のフィクスチャDBを書き換える**。後始末を怠ると次のテストを
巻き込む。実際に起きた事故:

| 残したもの | 起きたこと |
|---|---|
| アクセスモード | `test_nav.js`がscheduleのまま終了 → 後続の`test_master.js`（旧`test_p11.js`）が読み取り専用で落ちた（§9.249 ④で`test_nav.js`はモードを切り替えなくなった） |
| 編集セッション(ロック) | `test_wkfast.js`がロックを握ったまま終了 → `test_cols.js`が「他端末が編集中」の画面になった |
| 追加した作業予定 | 実行のたびに増え続け、描画が遅くなって固定待ちのテストが時間切れになった |
| バックアップ行 | 残骸が計画外実績として合成され、別テストの表示内容が変わった |
| 測定レコード(共有DB) | 消したつもりが**遅れて届いた共有で復活**し、L0001に身に覚えのない実績が残って`test_scdrop`が落ちた（通しで1回だけ再現）|
| 列レイアウト(`timeline:テスト設備A`) | `lotNo`を非表示のまま残したせいで、**次の実行**の`test_orphan.js`が「実績がスケジュールに出ない」で3件落ちた |

したがって、テストが作ったもの(予定・バックアップ行・マスタ行)は
**必ず`finally`で消し、モードは`edit`へ戻す**。
ロットNo等の識別子は実行ごとに一意にする(過去の失敗で残った行と
取り違えて消してしまうため)。

**測定レコードは「消えるまで確かめる」。** 共有(`shareRecord`)は画面を
待たせずに送るので、1回消しただけでは**後から届いた登録で復活する**ことが
ある。消す→数える→残っていたらもう一度、を数回まで繰り返す
(`test_mcore.js`/`test_msteps.js`のcleanup)。また**画面のidと保存側の
記録IDは違う**(設備名が前に付く)ので、末尾一致で消す。

**「見せ方」の設定はマスタDBに残り、実行をまたいで生き延びる。**
共有スケジュールDBは作業用コピーを作り直し、作業予定は1本ごとに
`reseed`で戻すが、列レイアウトマスタ・スケジュール内容表示マスタは
`db/master.sqlite3`にそのまま残る。**壊れ方が遠いので原因に辿り着けない**
——内容欄とは何の関係も無い`test_orphan.js`が落ち、しかも本体の変更を
疑って探すことになる(行の題名はロット番号を出す内容セルなので、隠すと
探せなくなる)。ランナーは開始時に`resetcontent`で検証用設備ぶんを白紙へ
戻すが、**テスト側の`finally`を省いてよい理由にはならない**(同じ実行の
中で後続のテストを巻き込むのは防げない)。

### 待ち方

**固定待ちは実行時間の半分を占める。** 実測(§9.133): 101本1,989件で16.3分の
うち、`waitForTimeout`等の固定待ちが373箇所・**7.8分**あった。速い画面では
無駄に待ち、遅い画面では足りない。手当てした3本の実績:

| テスト | 前 | 後 | 何に置き換えたか |
|---|---|---|---|
| `test_wkfast` | 29秒 | 6秒 | 可否の「?」が消えるまで(`settleFlags`) |
| `test_scale` | 25秒 | 8秒 | 取得が静まるまで(`quiet`)。7画面×1.8秒を数えるだけに使っていた |
| `test_waiting`(+旧waiting2) | 29秒 | 10秒 | 画面が出来上がるまで／覆いが出て閉じるまで |

**残っている上位**(固定待ちの合計): `test_startwork` 17.9秒 /
`test_uiux` 15.6秒 / `test_theme` 14.4秒 / `test_nav` 13.9秒 /
`test_scbalance` 13.7秒 / `test_orphan` 13.4秒 / `test_listcache` 13.0秒 /
`test_scperm` 12.9秒 / `test_screorder` 12.7秒。

**速くしたら「同じものを見ている」ことを数で確かめる**(§9.102)。早すぎて
画面が出来ていないと、**数える対象が減っただけで全部PASSする**。
`test_scale`には「数えた部品が360件を下回らない」を入れてある。

**同じ待ちは `tests/lib/wait.js` で名前を付けて呼ぶ**（§9.324 R5）。書き写しを
減らすためで、置き換えの型はこの5つ:

| 道具 | 何を待つか | 置き換えた固定待ち |
|---|---|---|
| `W.booted(page)` | 起動の覆い（`app-booting`）が外れた | `waitForSelector('#openSchedule')`＋1200ms |
| `W.openSchedule(page,EQ)` | 設備の行→その設備のタイムライン→作業可否の落ち着き | 2200ms＋1500ms |
| `W.until(page,fn,arg)` | 画面の条件（＋350msの落ち着き） | モーダルが開く／並びが変わる等の900〜2500ms |
| `W.poll(fn,pred)` | **サーバーの答え**が条件を満たす（書込のあとの取り直し） | 「3500ms待ってからGET」 |
| `W.opSave(page)` | 操業データ項目の窓が閉じて「保存しました」が出た | `#opdSave`のあとの1500ms |

**押す前に前の合図を消すこと**（`opSave`は`#opLayoutState`を空にしてから押す）
——前回の「保存しました」が残っていると、押した瞬間に条件が真になって何も待たない。
**わざと遅らせた応答を待つ時間は残す**（`test_scsave`の4000ms。時間そのものが
検証の材料）。**どこに固定待ちが残っているかは `python3 tests/wait_report.py`**
（本ごとの合計と件数。`tests/wait_report.py test_x`で1件ずつ）。

置き換えた7本の実績（単独・PASS数は同じ・3回連続で同結果）:

| テスト | 前 | 後 |
|---|---|---|
| `test_scinsert` | 36秒 | 22秒 |
| `test_scstop` | 23秒 | 11秒 |
| `test_startwork` | 21秒 | 6秒 |
| `test_scsave` | 30秒 | 14秒 |
| `test_opui` | 42秒 | 35秒 |
| `test_oppad` | 35秒 | 32秒 |

**単独で回せない網は直したかどうかを単独で確かめられない**（§9.325 ②）——
`test_startwork`／`test_sctimecols`は「完了」の行を前のテストの記録に頼っていた。
材料は自分で置くこと。



`waitForTimeout` の固定待ちは**フィクスチャが育つと必ず落ちる**。
実際に`test_cols.js`/`test_split_layout.js`と内容欄のテスト(当時の
`test_content_apply.js`。いまは`test_sccontent.js`)が
これで落ちた。描画の完了そのものを `waitForFunction` / `waitForSelector`
で待つこと。

**固定待ちは所要時間にそのまま乗る。** `run_all.sh`が1本ごとの秒数と
上位10本を出すので、遅い本はまずここを疑う。実測(2026-08-12)では
`test_scperf`が34秒のうち**31秒が固定待ち**、`test_fit`が70秒のうち
**58秒が固定待ち**だった(§9.102)。

**固定待ちは、速い画面では無駄に待ち、遅い画面では足りない。** 待っている
対象を名指しできれば時間は要らない。`test_fit.js`は3つに置き換えて
70秒→35秒になった。

| 待っているもの | 置き換え |
|---|---|
| レイアウトの確定(CSS変数の付け替え等) | `requestAnimationFrame`2回 |
| 画面ぶんの取得の完了 | 取得中の数を数え、止まってから一定時間静かなら次へ |
| モーダルの出現 | `waitForSelector` |

**速くしたら「同じものを見ている」ことを確かめる。** 「見つからない」ことを
確かめるテストは、早すぎて何も描けていなくても素通りする。`test_fit.js`では
(1)画面ごとの要素数を新旧で突き合わせて全12画面一致を確認し、(2)本物の
溢れをCSSへ一時的に注入して検出できることを確かめた。**両方PASSは証拠に
ならない。**

「何も起きないこと」を確かめる検証(例: 画面へ戻っても再取得しない)は、
待たないと確かめられないように見えるが、**2つに分けると速くなる**。

```js
const SETTLE=350;                                   // 取りこぼしを拾う短い落ち着き
const until=async(fn,ms=15000)=>{
  await page.waitForFunction(fn,null,{timeout:ms}).catch(()=>{});
  await page.waitForTimeout(SETTLE);
};
await page.click('#openSchedule');
await until(()=>document.querySelectorAll('.sc-row-line').length>0);
```

画面が組み上がるのを**条件で**待ち、そのあと短く落ち着かせる。
`test_scperf`はこの形で**34秒→11秒**になった(検証内容は同じ11件、
3回連続で同結果)。**落ち着きを0にしないこと**——描画の直後に飛ぶ
要求を数え損ねる。

### 前提は「他のテストの残骸」に頼らず自分で作る

`test_audit` / `test_nav` の作業可否の索引の検証は、長いあいだ
**`test_sccat` が残した実績行**(`ZZZZ1`/`ZZZZ2` = 仕掛に無いロット)に
暗黙に頼っていた。`test_sccat` はこの2本より**後**に走るので、効いていたのは
前回の実行の残骸であり、それが表示範囲(直近N時間)に入っているかどうかで
結果が変わっていた。直前に流していれば通り、間が空くと落ちる。
**実行履歴で結果が変わる安全網は安全網にならない。**

必要な前提はテストが自前で用意して自前で消す。仕掛に無いロットの予定は
`tests/orphan_lot.js` の `addOrphanPlan()` で作れる(`remove()` で消す)。

**同じ依存がまだ2本残っている**(§9.132で判明): `test_wkbg` の
「判定材料が揃う前は『?』で出す」と `test_theme` の「実績のある行に削除
ボタンが出る」は、**測定バックアップ(`db/records.sqlite3`)に実績が
1件以上あること**に暗黙に頼っている。実績を空にすると、この2本だけが
**コードを1行も変えていないのに落ちる**(実測: 空で4件FAIL → 実績を
入れ直すと52/52 PASS)。実績を作るのは `test_screport` / `test_startwork` /
`test_share` / `test_orphan` で、いずれもこの2本より**後**に走るため、
効いているのは前回の実行の残骸。**新しい端末やクリーンな置き場では落ちる。**
直すなら、この2本が自前で実績を作って自前で消す形にする。

**逆に、実績をむやみに消さないこと。** ランナーの起動時に
「検証用設備の実績を白紙へ戻す」を入れてみたが、上の依存のせいで
`test_wkbg`・`test_theme` が落ちるようになったので取り消した。
異常終了した実行が残した実績を落としたいときだけ、手で
`python3 tests/reset_records.py` を使う(消すのは検証用設備の行だけ)。
使ったあとは、この2本が落ちることを承知しておく——実績を作るテスト
(`tests/run_all.sh test_screport test_startwork`)を1度流せば戻る。

### 依存する前提

- 設備マスタに `テスト設備A` / `テスト設備B` があること
- 仕掛フィクスチャの `残仕掛設備ｺｰｽ` が `テスト設備A ...` で始まること
  (作業可否フラグの検証で使う)
