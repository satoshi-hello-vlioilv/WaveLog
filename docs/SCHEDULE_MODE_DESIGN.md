# スケジュールモード 詳細設計

作業スケジュール(作業順・所要時間・メンテナンス計画)を設備ごとに管理し、
「何時間後にどの作業を行うか」を可視化する機能の設計書。

対象読者はこのコードを実装・変更する人。全体構成は `docs/ARCHITECTURE.md`、
機能一覧は `README.md` を参照。

---

## 1. 目的と範囲

### 1.1 解きたい課題

現状、次に何を流すかは紙・口頭・個人の記憶で管理されており、

- 「今の作業はあと何分か」「次は何か」が作業者以外から見えない
- メンテナンス・段取り替えをどこに差し込めば無理がないか判断できない
- 所要時間の見積が「だいたい1本◯時間」の一律感覚で、品種・材料による
  重い/軽いの差が計画に反映されない

### 1.2 本機能で実現すること

1. **スケジュールモード**を起動時のモードとして追加する(編集可能/閲覧に次ぐ第3のモード)。
   閲覧モードの動作(測定データ・マスタへの書き込み禁止)に加え、作業予定の編集だけを許可する。
2. スケジュールモードの端末から、**仕掛一覧の行を選んで設備ごとの作業順に並べる**。
   メンテナンス・休止も同じ列に差し込める。
3. **過去の作業実績から品種・材料ごとの負荷率(換算係数)を統計的に算出**し、
   予定1件ごとの所要時間を推定する。
4. 稼働カレンダー(就業時間帯・休日)を考慮して**予定開始/終了時刻を展開**し、
   「◯時間後」をタイムラインで表示する。編集モードの測定端末からも読み取り専用で見える。

### 1.3 本機能の範囲外(今回やらないこと)

- 自動最適化(納期・段取り最小化による自動並べ替え)。順序は人が決める。
  負荷率はあくまで「人の判断材料としての時間の見える化」に使う。
- 設備をまたぐ負荷平準化・振り分け。予定は設備ごとに独立した1本の列とする。
- 予定の承認ワークフロー・履歴差分。単一書き込み者(§4)を前提とし、監査列のみ持つ。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 予定 / エントリ | 設備の作業列に並ぶ1件。種別は「作業」「メンテナンス」「休止」 |
| 作業列 (キュー) | ある設備の、順序付きの予定の並び |
| アンカー | 時間展開の起点時刻。通常は現在時刻、着手中の作業があればその実開始時刻 |
| 展開 (ETA展開) | 順序+所要見積+稼働カレンダーから予定開始/終了時刻を算出すること |
| 負荷率 / 換算係数 | ある因子水準(例: 用途名=「缶材」)が所要時間を平均の何倍にするかの係数 |
| 因子 / 水準 | 因子=用途名・製造材質など。水準=その因子の具体値 |
| 基準時間 T0 | ある設備の、全因子を中立(係数1.0)としたときの1件あたり所要時間 |

## 3. モード設計

### 3.1 3モードの定義

| モード | 内部値 | 測定データ・マスタへの書込 | 作業予定への書込 | 想定端末 |
|---|---|---|---|---|
| 編集可能モード | `edit` | 可 | 不可(読み取りのみ) | 設備の測定端末 |
| 閲覧モード | `view` | 不可 | 不可(読み取りのみ) | 参照専用端末 |
| **スケジュールモード** | `schedule` | **不可** | **可** | 工程管理・班長の端末 |

スケジュールモードは**閲覧モードの上位互換ではない**。測定データ・マスタへの
書き込みは閲覧モードと完全に同じく禁止で、作業予定という別ドメインの書き込み
だけが開く。これにより「計画担当の端末が誤って測定データを触る」経路を
最初から作らない。

作業予定の**読み取り**は3モードすべてで可能。編集モードの測定端末から
スケジュールが見えること自体が本機能の主目的(見える化)であるため。

### 3.2 権限判定(アクセス権限マスタの拡張)

`backend/repositories/master_repo.py` の `アクセス権限マスタ` に列を1本追加する。

```sql
ALTER TABLE [アクセス権限マスタ] ADD COLUMN [スケジュール可否] INTEGER
```

既存の `ensure_audit_columns` と同じ「列が無ければ ALTER TABLE で足す」方式で
`ensure_access_permission_table` の末尾に追加する(既存DBの再作成は不要)。

判定規則:

| `編集可否` | `スケジュール可否` | 起動時の初期モード | 切替可能なモード |
|---|---|---|---|
| 行なし(未登録) | — | `edit` | `edit` / `view` |
| 編集可(1) | NULL または 0 | `edit` | `edit` / `view` |
| 編集可(1) | 1 | `edit` | `edit` / `view` / `schedule` |
| 閲覧のみ(0) | NULL または 0 | `view` | `view` |
| 閲覧のみ(0) | 1 | **`schedule`** | `view` / `schedule` |

- 「閲覧のみ ＋ スケジュール可」が工程管理端末の標準設定。起動しただけで
  スケジュールモードに入り、測定側は最初から触れない。
- 未登録行が既定で `edit` になる現行の互換ポリシーは変更しない
  (`スケジュール可否` は NULL=不可 なので、既存環境の挙動は一切変わらない)。
- 判定関数は既存 `has_edit_permission(c,login_id,pc_name)` の隣へ
  `permission_flags(c,login_id,pc_name) -> {'canEdit':bool,'canSchedule':bool}`
  を追加し、`has_edit_permission` はその薄いラッパとして残す(呼び出し元の変更不要)。

### 3.3 書込ガード(`backend/access_mode.py`)

現行の `_guard_write` は「モードが `view` かつ対象Blueprintかつ非GET → 403」。
これを次の表に置き換える。**Blueprint単位で許可モードを宣言する方式**にし、
新しいBlueprintを足したときに書き漏れると「どのモードでも通ってしまう」のでは
なく「どのモードでも通らない」側へ倒れるようにする(安全側の既定)。

```python
# Blueprint名 -> 非GETを許可するモードの集合
_WRITE_ALLOWED_MODES={
 'measurement':{'edit'},
 'masters':{'edit'},
 'schedule':{'schedule'},
}
```

```python
@app.before_request
def _guard_write():
 if request.method=='GET':return None
 bp=request.blueprint
 if bp is None:return None            # app直付け(モード切替API・shutdown等)は対象外
 allowed=_WRITE_ALLOWED_MODES.get(bp)
 if allowed is None:return None       # 未宣言のBlueprintは従来どおり素通し(§注記)
 if get_mode() in allowed:return None
 return jsonify(error=...),403
```

> **注記**: 未宣言Blueprintを素通しにするのは現行互換のため(`tables`/`quality`/
> `core` は読み取り専用Blueprintで非GETを持たない)。CLAUDE.md の
> 「新しい書込系APIを追加する場合、そのBlueprintが `_GUARDED_BLUEPRINTS` に
> 含まれるか確認すること」は、この表への追記に読み替える。実装時に
> CLAUDE.md 側の文言も更新する。

### 3.4 モード切替API

`GET /api/access-mode` の応答に `canSchedule` を追加:

```json
{"ok":true,"mode":"schedule","canEdit":false,"canSchedule":true,
 "loginId":"kato","pcName":"NLM-PLAN01"}
```

`POST /api/access-mode` の `mode` に `schedule` を追加。権限が無ければ 403。
権限はこれまでどおり呼び出しのたびにマスタを読み直す(再起動不要)。

### 3.5 フロント側の入口ガード(`static/js/access-mode.js`)

- `accessMode` に `canSchedule` を追加。`document.body` のクラスを
  `view-mode` / `schedule-mode` の2種で出し分ける。
  既存CSSの `body.view-mode` 由来の抑制(測定再開ボタン等)は
  `body.view-mode, body.schedule-mode` へセレクタを拡張する。
- ヘッダーのモードバッジはクリックで**巡回**ではなく、権限のあるモードを
  並べた小さなポップオーバーから選ばせる(3値になった時点で「クリックで
  トグル」は意味が取れなくなるため)。
- `openMeasurement` / `resumeRecordFromList` のラップは
  「`edit` 以外なら止める」に変更する(現行は `view` のときのみ止めている。
  条件を反転させないと `schedule` が素通りする)。**実装時の主要な事故ポイント**。

## 4. データの置き場所と共有方式

### 4.1 単一書き込み者モデル

作業予定は **スケジュールモード端末だけが書く**。他端末は読むだけ。
これは測定データバックアップの共有(`records_backup_export_path`)で既に
採用している考え方をそのまま踏襲する。

```
[工程管理端末: schedule]
  db/schedule.sqlite3  ← 唯一の書き込み先(ローカル)
        │  変更時 + 定期(既定300秒)に複製
        ▼
  共有フォルダ(Box等)/schedule.sqlite3
        │  読み取り専用で開く
        ▼
[設備の測定端末: edit] [参照端末: view]
```

- 書込は必ずローカルSQLiteへ行い、**共有先へは完成したものを複製するだけ**。
  SQLiteをネットワーク共有上で直接ロックしながら書く構成は採らない
  (SMB上のロックは不安定で、破損時の被害がスケジュール全体に及ぶため)。
- 複製は `backend/records_export.py` と同型の `backend/schedule_export.py`
  で行う。すなわち **書き込み時に変化フラグを立て、一定間隔で立っていたときだけ
  `sqlite3.Connection.backup()`(オンラインバックアップAPI)で複製する**。
  単純なファイルコピーは書き込み中に壊れたコピーを作りうるため使わない。
  複製の成否は予定の保存をブロックしない(失敗したら次回また試みる)。

### 4.2 読み取り先の決定規則

```
自端末に「スケジュール可」権限がある → db/schedule.sqlite3 (ローカル)
それ以外                             → schedule_share_path (未設定ならローカル)
```

計画者が自分の書いた直後の内容を、複製待ちのせいで古いまま見ることがない。

### 4.3 設定 (`config/local.json`)

| キー | 既定 | 意味 |
|---|---|---|
| `schedule_db_path` | `db/schedule.sqlite3` | ローカルの作業予定DB |
| `schedule_share_path` | なし | 共有先の複製パス。未設定なら共有しない(単独運用) |
| `schedule_export_interval_sec` | 300 | 共有先への複製チェック間隔 |

`backend/config.py` へ `SCHEDULE_EXPORT_INTERVAL_SEC_DEFAULT=300`、
`LOAD_FACTOR_CACHE_TTL_SEC=600` を追加(アプリ固有値は config.py へ集約する規約に従う)。

`backend/db_access.py` の `DBS` へは**追加しない**。`DBS` は
`/api/catalog` 経由でサイドバーの「一覧を見る/管理」へ自動的にナビ項目を
生やすため、ここへ足すと汎用グリッドに生データのテーブルが並んでしまう。
`SCHEDULE_DB` / `SCHEDULE_SHARE_PATH` をモジュール変数として別に持ち、
`connect()` は拡張子判定でそのまま使える。

## 5. データモデル

`db/schedule.sqlite3` に4テーブル。既存マスタの規約(全角テーブル名・
`INTEGER PRIMARY KEY AUTOINCREMENT`・`有効`による論理削除・監査列・
索引は別SQL)に合わせる。`Now()` は `db_access.connect()` がSQLiteへ
ユーザー定義関数として登録済みのため、そのまま使える。

データアクセス層は `backend/repositories/schedule_repo.py`(Flask非依存)。

### 5.1 作業予定

設備ごとの作業列。作業もメンテナンスも**同じ1本の列**に入れる
(順序の一貫性を型で保証でき、差し込みの表現が自然になる)。

```sql
CREATE TABLE [作業予定] (
  [予定ID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,            -- 正規化前の生表記。照合は normalize_equipment_name
  [表示順] INTEGER,         -- 同一設備内の順序。1始まりの連番(§5.1.1)
  [種別] TEXT,              -- '作業' | 'メンテナンス' | '休止'
  [ロット番号] TEXT,        -- 種別='作業' のみ
  [検査番号] TEXT,
  [鋳造番号] TEXT,
  [予定名称] TEXT,          -- メンテナンス名等。作業の場合は表示用の補助
  [明細JSON] TEXT,          -- 計画時点の仕掛行スナップショット(§5.1.2)
  [固定開始日時] TEXT,      -- ISO8601。指定時はこの時刻より前に開始しない
  [見積分] REAL,            -- 手動上書き見積(分)。NULLならモデル推定を使う
  [状態] TEXT,              -- '予定' | '着手' | '完了' | '取消'
  [実績測定ID] TEXT,        -- 突合できた測定データのid(§7.4)
  [備考] TEXT,
  [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
CREATE INDEX [IX_作業予定_設備順] ON [作業予定] ([設備名],[表示順]);
```

#### 5.1.1 順序の持ち方

`表示順` は**同一設備内で1から始まる連番**とし、並べ替えのたびに
その設備の全行を書き直す(`POST /api/schedule/plan/reorder` が
`[予定ID,...]` の配列を受け取り、その順に1..N を振り直す)。

他マスタは10刻みのスパース採番だが、ここでは採らない。理由:

- 1設備あたりの予定件数は数十件が上限で、全件UPDATEのコストが無視できる
- 「ドラッグで並べ替えた結果の配列を丸ごと保存する」という操作の形と
  1対1に対応し、挿入位置の再採番ロジックが不要になる
- スパース採番は再採番のタイミングが分散するぶん、順序の重複や欠番を
  生むバグが出やすい

#### 5.1.2 仕掛スナップショット(`明細JSON`)を持つ理由

仕掛(SIKALOTNOW)の行は**作業が終わると仕掛から消える**。
本アプリは既にこの前提で作られている(分割済み子ロットが仕掛に見つからない
場合の警告表示など)。予定がロット番号だけを持っていると、

- 完了した予定を後から見返したときに品種・寸法が表示できない
- 見積の内訳(どの係数が効いたか)を再現できない

ため、予定に追加した時点の仕掛行から `aliases`(`static/js/base.js`)で
拾える値をスナップショットして持つ。

```json
{"lotNo":"1234567","inspectionNo":"...","castingNo":"...",
 "purposeName":"缶材","mfgMaterial":"3004","mfgTemper":"H19",
 "mfgThickness":"0.285","mfgWidth":"1420","mfgLength":"...",
 "equipment":"SL-1","boxHorizontalCount":"6","boxVerticalCount":"1",
 "capturedAt":"2026-08-02T09:12:00+09:00"}
```

キー名は `aliases` のキーと同一にする。実績側の `basic{}` も
`Object.fromEntries(Object.keys(aliases).map(k=>[k,pick(row,k)]))` で
作られているため、**予定と実績が同じキー空間になる**(§6.2の要)。

### 5.2 稼働カレンダーマスタ

```sql
CREATE TABLE [稼働カレンダーマスタ] (
  [カレンダーID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,        -- 空文字は「全設備の既定」
  [区分] TEXT,          -- '曜日' | '特異日'
  [曜日] INTEGER,       -- 区分='曜日' のとき 0(日)〜6(土)
  [日付] TEXT,          -- 区分='特異日' のとき 'YYYY-MM-DD'
  [稼働] INTEGER,       -- 0=非稼働(休日)。1=稼働
  [開始時刻] TEXT,      -- 'HH:MM'
  [終了時刻] TEXT,      -- 'HH:MM'。開始>終了 は翌日跨ぎとみなす
  [表示順] INTEGER, [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
```

- **休憩は稼働帯を分割して表現する**。専用の休憩テーブルを作らない。
  例(常昼): `08:00-12:00` と `13:00-17:00` の2行 → 12:00-13:00 は自動的に非稼働。
  2交替・3交替・連続操業も、同じ曜日に複数行を置くだけで表現できる。
- 適用の優先順位: **特異日(日付一致) > 設備別の曜日 > 全設備既定の曜日**。
  該当行が1件も無い設備は「24時間稼働」とみなす(何も設定していない状態で
  予定が翌週に飛ぶより、素直に連続で積む方が驚きが少ない)。

### 5.3 メンテナンス定義マスタ

定型メンテナンスの雛形。計画者が毎回名称と時間を手入力しなくて済むようにする。

```sql
CREATE TABLE [メンテナンス定義マスタ] (
  [定義ID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,         -- 空文字は全設備共通
  [名称] TEXT,           -- 例: 'ナイフ交換' '定期点検' '刃物研磨'
  [標準所要分] REAL,
  [推奨周期] TEXT,       -- 表示用の目安。'毎週月曜' 等の自由記述(自動生成はしない)
  [色キー] TEXT,         -- タイムライン上の色分け。§9.3のトークン名
  [表示順] INTEGER, [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
```

`推奨周期` は**表示用の文字列に留め、自動生成の根拠にはしない**。
定期メンテの自動投入は「気づいたら勝手に予定が増えている」挙動になり、
単一書き込み者モデルと相性が悪い。投入は常に計画者の明示操作とする。

### 5.4 負荷率上書きマスタ

自動算出した係数を人が上書きするための表。行が無ければ自動算出値をそのまま使う
(表示マスタと同じ「行の存在＝上書き」ポリシー)。

```sql
CREATE TABLE [負荷率上書きマスタ] (
  [上書きID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,       -- 空文字は全設備共通
  [因子] TEXT,         -- 'purposeName' | 'mfgMaterial' | ... | 'BASE'
  [水準] TEXT,         -- 因子の値。因子='BASE' のときは空(基準時間T0の上書き)
  [係数] REAL,         -- 因子='BASE' のときは分単位の基準時間
  [理由] TEXT,
  [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
CREATE UNIQUE INDEX [UX_負荷率上書き] ON [負荷率上書きマスタ] ([設備名],[因子],[水準]);
```

## 6. 負荷率(換算係数)モデル

本機能の中核。「品種・材料ごとに重い/軽いがある」を、実績から**自動で**
数値化して見積へ反映する。

### 6.1 モデルの形: 対数線形(乗法)モデル

```
見積分(設備E, ロットL) = T0(E) × Π_j  f_j( 水準_j(L) )
```

- `T0(E)`: 設備Eの基準時間(分)。全因子が中立のときの1件あたり所要
- `f_j(v)`: 因子 j の水準 v の**負荷率(換算係数)**。1.0 が「平均並み」

この形を選ぶ理由:

1. **説明できる**。「この用途名は 1.32 倍」「この板厚帯は 0.88 倍」と現場の言葉で
   そのまま読める。ユーザーの要望文にある「負荷率(換算係数)」という語と一致する。
2. **未知の組み合わせに必ず答えが出る**。既存の `worktime-benchmark.js` は
   用途名・材質・調質・実測寸法・丈割数・条割数・設備の**完全一致**で過去実績を
   引くため、条件が1つでも違うと N=0 になる。計画は「まだ流したことのない
   組み合わせ」も並べるので、完全一致方式は計画用途には使えない。
   乗法モデルなら未知の水準は係数1.0(中立)で通せる。
3. **作業時間の分布に合う**。作業時間は下に0の壁があり右に裾を引く(対数正規に近い)。
   対数を取れば因子の効果が加法になり、平均ではなく**幾何平均**で扱える。

### 6.2 特徴量(因子)

予定側(仕掛スナップショット)と実績側(`basic{}`)で**同一のキー**が使えることが
前提。§5.1.2 のとおり両者とも `aliases` のキー空間で作られるため、
学習時と予測時で特徴量がずれない。

| 因子キー | 元の列 | 種類 | 備考 |
|---|---|---|---|
| `purposeName` | 用途名 | カテゴリ | 品種。要望の「品種ごと」の主軸 |
| `mfgMaterial` | 製造材質 | カテゴリ | 要望の「材料ごと」の主軸 |
| `mfgTemper` | 製造調質 | カテゴリ | |
| `mfgThickness` | 製造板厚 | 数値→帯 | ビン化(§6.3) |
| `mfgWidth` | 製造板幅 | 数値→帯 | ビン化 |
| `mfgLength` | 製造板丈 | 数値→帯 | ビン化。規模の代理変数 |
| `boxHorizontalCount` | BOX設計_横割数 | 数値→帯 | 条数。段取りに効く |
| `boxVerticalCount` | BOX設計_縦割数 | 数値→帯 | 丈割数 |
| `crewSize` | settings.crewSize | カテゴリ | 班人数。予定側は既定値(§6.7) |

**設備は因子にしない。設備ごとに別モデルを作る**。設備が違えばライン速度も
段取りも別物で、係数の掛け算では表現しきれないため。

**数値量をすべて帯(カテゴリ)に落とす**のが本設計の要点。板厚・板幅・板丈の
単位系(mm/m、コイル長かカット長か)がデータソースにより揺れうるのに対し、
帯に落とせば単位の解釈を一切必要とせず、非線形な効き方(薄物だけ極端に遅い等)も
そのまま吸収できる。

### 6.3 ビン境界の決め方

既定は**実績の分位点による自動ビン化**(四分位=4区間)。単位に依存せず、
どの工場・どの設備でも同じコードで機能する。

- 相異なる値が4種以下の因子(条数・丈割数など)は、値そのものを水準にする。
- ビン境界は**再計算のたびに確定させ、算出結果と一緒に保存・表示する**。
  境界が黙って動くと「先週の係数1.2は何の帯だったのか」が追えなくなるため、
  `/api/schedule/load-factors` の応答に必ず境界を含める。
- 固定境界を使いたい場合は `負荷率上書きマスタ` の因子キーに
  `BIN:mfgThickness` のような行を置いて上書きできる(v2で対応。v1は自動のみ)。

### 6.4 学習データ

対象: 共有の測定データバックアップ(§6.6)から読んだレコードのうち

- `status === '完了'`
- `workTime.startAt` と `workTime.endAt` が両方あり、差が正
- 設備(`settings.registeredEquipment`)が空でない

**外れ値の除去**: 対数所要時間 `y = ln(分)` について、中央値 `m` と
MAD(中央絶対偏差)を求め、`|y - m| > 3 × 1.4826 × MAD` の実績を除外する。

除去理由: 「作業開始を押したまま昼休みに入った」「終了を押し忘れて翌朝押した」
といった記録は必ず混ざる。平均や標準偏差ベースの除去はそうした極端値自身に
引きずられるため、中央値・MADで頑健に切る。**除外件数はAPIの応答に含めて
画面に出す**(黙って捨てない)。

### 6.5 推定手順

設備Eごとに、以下を実行する(`backend/load_factor.py`、Flask非依存)。

```
入力: 実績 {y_i = ln(所要分), 水準ベクトル v_i}  (i = 1..N)

1) 初期化   ln T0 = median(y_i)          … 幾何平均を中央値で頑健に初期化
             ln f_j(v) = 0  (全因子・全水準)

2) 反復(3巡)  各因子 j について:
     各水準 v で  r = mean( y_i − lnT0 − Σ_{k≠j} ln f_k(v_i) )   over {i : v_i,j = v}
     n = その水準の件数
     収縮:  ln f_j(v) ← r × n / (n + K)        K = 5 (既定)
     クリップ: ln f_j(v) を [ln 0.5, ln 2.0] に収める
   因子1巡ごとに ln T0 ← median( y_i − Σ_j ln f_j(v_i) ) で再センタリング

3) 残差の広がり  σ_log = 標準偏差( y_i − lnT0 − Σ_j ln f_j(v_i) )

出力: T0 = exp(lnT0), f_j(v) = exp(ln f_j(v)), σ_log, 各水準のN数
```

**収縮 (shrinkage)** `n/(n+K)` が実運用上いちばん重要な部品。
1件しかない用途名の実績が「たまたま3時間かかった日」だったとき、収縮が無いと
その用途名の係数が 2.0 に張り付き、以後その品種の予定がすべて倍の見積になる。
`n/(n+5)` により、n=1 なら効果は 1/6 しか採らず、n=45 で 90% 採る。
**件数が増えるほど自動的にモデルが自信を持つ**という素直な挙動になる。

クリップ 0.5〜2.0 は、収縮を抜けてなお極端な係数が出た場合の最終防波堤。

反復が3巡なのは、因子間の相関(例: ある用途名はほぼ特定の材質でしか流れない)を
数巡で概ね分離できるため。厳密な収束判定は費用に見合わない。

**設備の実績が少ないとき**: 有効実績が `MIN_SAMPLES=20` 件に満たない設備は、
自設備モデルを作らず**全設備プールで学習したモデル**を使い、`T0` だけを
その設備の実績中央値(または全体のT0)に置き換える。新設備・新端末でも
初日から見積が出る。この代替を使ったことは応答の `basis` フィールドで明示する。

### 6.6 実績の取得元

スケジュールモード端末は測定を行わないため、自端末の IndexedDB は空。
実績は**共有の測定データバックアップから読む**。これは閲覧モードが
既に使っている経路と同じ:

```
1st: RECORDS_BACKUP_EXPORT_PATH の records.sqlite3 (共有・Box等)
2nd: 未設定ならローカルの db/records.sqlite3
```

**集計はバックエンドで行う**。バックアップは1件が測定グリッド込みのJSONで
数十KBあり、数千件をフロントへ流して毎回パースするのは現実的でない。
`Web測定バックアップ` テーブルから必要な列だけ取り出し、payload JSON から
`basic` / `settings` / `workTime` のみを読んで学習する。

**キャッシュ**: 算出結果はプロセス内にキャッシュし、
`LOAD_FACTOR_CACHE_TTL_SEC`(既定600秒) または元ファイルの mtime 変化で無効化。
`POST /api/schedule/load-factors/recalc` で明示的に破棄もできる。

### 6.7 予測(1件の見積)

```
1. 予定に 見積分 が入っていれば → それを使う(手動上書きが最優先)
2. 種別='メンテナンス'/'休止' → 予定の見積分、無ければメンテナンス定義の標準所要分
3. 種別='作業':
     水準を 明細JSON から取り出し、数値因子は保存済みビン境界で帯へ変換
     係数 = 上書きマスタに行があればその値、無ければ自動算出値、
            水準が未知(実績に無い)なら 1.0
     見積分 = T0 × Π 係数
     予測区間 = [見積分 × exp(−1.96σ_log), 見積分 × exp(+1.96σ_log)]
```

`crewSize` は予定側に実測値が無いので、**その設備の実績の最頻値**を既定として
使い、予定ごとに計画者が変更できる。班人数を変えたときに見積がどう動くかが
その場で見えるのは計画作業として価値がある。

### 6.8 見積の内訳を必ず返す

`/api/schedule/estimate` は数値だけでなく内訳を返す。ブラックボックスの
時間を現場は信用しないため、画面に「なぜこの時間か」を出せる形にしておく。

```json
{"minutes":152.4,
 "low":98.1,"high":236.7,"sigmaLog":0.29,
 "basis":"equipment",
 "base":{"T0":118.0,"n":432},
 "factors":[
  {"key":"purposeName","level":"缶材","value":1.18,"n":96,"source":"auto"},
  {"key":"mfgMaterial","level":"3004","value":1.04,"n":210,"source":"auto"},
  {"key":"mfgThickness","level":"0.25〜0.31","value":0.93,"n":88,"source":"auto"},
  {"key":"boxHorizontalCount","level":"6","value":1.13,"n":51,"source":"override"},
  {"key":"mfgWidth","level":"1380〜1450","value":1.00,"n":0,"source":"unknown"}
 ]}
```

`source` は `auto`(自動算出) / `override`(手動上書き) / `unknown`(実績なし＝1.0)。
`unknown` が多い予定は見積の根拠が薄いことが一目で分かる。

### 6.9 モデルの精度を運用中に検証する

完了した予定について「見積 vs 実測」を突合し、画面に表示する(§9.4)。
指標は**対数誤差の中央値と分布**:

- 中央値バイアス `median(ln(実測/見積))` … 系統的に速い/遅いのずれ
- MAPE 相当 `median(|実測 − 見積| / 実測)` … 現場に説明しやすい形

これを見て `BASE` の上書き値を調整する、という運用ループが回るようにする。

## 7. 時間展開(ETA)

### 7.1 展開はバックエンドで行う

順序・見積・稼働カレンダーはすべてバックエンドにある。フロントで再実装すると
同じロジックが2箇所に生まれる(CLAUDE.md の「関数の定義は1箇所」に反する)。
`GET /api/schedule/plan` が**計算済みの予定開始/終了を返し**、フロントは
表示に徹する。`backend/schedule_calc.py`(Flask非依存)が担当。

### 7.2 アンカー(起点)の決定

```
先頭の有効な予定が '着手' 状態 (§7.4で実績突合により判定)
   → アンカー = その実開始時刻
      かつ 先頭の残り時間 = max(見積 − 既経過, MIN_REMAIN_MIN)   MIN_REMAIN_MIN = 5
それ以外
   → アンカー = 現在時刻。非稼働時間帯なら次の稼働帯の開始時刻へ繰り上げ
```

着手中の作業の残りを見積から経過を引いて出すことで、画面を開いた瞬間の
「今の作業はあと何分」が実態に追従する。`MIN_REMAIN_MIN` の下限は、見積を
超過した作業で残りが負になり後続が過去へ食い込むのを防ぐ。

### 7.3 展開アルゴリズム

```
cursor = アンカー
for entry in 有効な予定(表示順):
    if entry.状態 in ('完了','取消'): continue      # 列から外す(表示は別枠)
    if entry.固定開始日時 and 固定開始日時 > cursor:
        entry.待ち = 固定開始日時 − cursor          # 空き時間として明示
        cursor = 固定開始日時
    cursor = 次に稼働している時刻へ繰り上げ(cursor)
    entry.予定開始 = cursor
    remaining = entry.見積分
    while remaining > 0:
        slot   = cursor を含む(または直後の)稼働帯
        cursor = max(cursor, slot.開始)
        use    = min(slot.終了 − cursor, remaining)
        cursor += use ;  remaining −= use
        if remaining > 0: cursor = 次の稼働帯の開始      # 夜間・休日を跨ぐ
    entry.予定終了 = cursor
    entry.開始まで = 予定開始 − 現在時刻                  # 「◯時間後」表示の元
```

- 稼働帯の探索は最大 `MAX_HORIZON_DAYS=60` 日で打ち切り、超えた予定は
  `予定開始=null` + 「稼働カレンダー上、60日以内に収まりません」を返す
  (稼働カレンダーが全休で設定された場合の無限ループ防止)。
- `固定開始日時` を過ぎている(前の作業が押している)場合は**押し出す**。
  固定時刻のために前の作業を切ることはしない。ただし遅延量を
  `entry.遅延` として返し、画面で赤く出す。

### 7.4 進捗の反映は「実績突合」で行う(書き戻さない)

測定端末(編集モード)は共有先の読み取り専用コピーしか持たないため、
そこから予定DBへ書き戻すことはできない。代わりに**実績から状態を導出する**。

```
共有の測定データバックアップを ロット番号(+検査番号) で予定へ突合:
   完了レコードあり              → 状態 '完了' 相当として扱う
   startAt のみ (endAt なし)     → 状態 '着手' 相当として扱う
   実績なし                      → 予定のまま
```

- この判定は**表示のたびに動的に行い、DBへは書かない**。単一書き込み者
  モデルを崩さずに、どの端末でも同じ進捗が見える。
- 計画者が明示的に「完了として確定」した場合のみ `状態` 列へ書き込む
  (実績が上がらないまま飛ばした作業の消し込み用)。
- 突合したレコードの `id` を `実績測定ID` として応答に含め、
  画面からその帳票を開けるようにする(実績カレンダーの `openReportForRecord`
  と同じ導線を再利用)。

ロット番号だけでは分割済み子ロット等で重複しうるため、突合キーは
**ロット番号 + 検査番号**を第一候補、検査番号が空なら ロット番号 + 鋳造番号、
それも無ければ ロット番号のみ、の順に緩める。複数一致した場合は
「最も新しい更新日時」を採る。

## 9. 画面設計

### 9.1 情報アーキテクチャ(サイドバー)

現在のグループは「測定データ / 一覧を見る / 分析 / 管理」。
スケジュールは実績の分析ではなく**これからの計画**なので、既存グループへ
混ぜず新グループを作る。

```
測定データ
一覧を見る      仕掛（現在） / 品質データ
計画            ★ 作業スケジュール      ← 新設
分析            品質データ分析 / ダッシュボード / 実績カレンダー
管理            マスタ一覧 / マスタ管理
```

「作業スケジュール」は**全モードで表示**する(編集モードの測定端末から
見えることが目的のため)。モードによって編集操作の有無が変わるだけ。

### 9.2 ビューの排他制御

既存の `qa-mode` / `rp-mode` / `db-mode` / `cal-mode` と同じ方式で
`body.sc-mode` を追加し、`static/app.css` の該当行群
(`body.cal-mode #grid,...{display:none!important}` および
`qa-view-raw` との詳細度衝突を打ち消す行)へ `sc-mode` を並べる。
`window.exitScheduleView` を公開し、`selectDb` のラップと
`report-dashboard.js` / `calendar-view.js` の各 open 関数から相互に閉じる。

> 実装時の注意: 現在この相互排他は各ビューが「他のビューを個別に閉じる」
> 書き方になっており、ビューを1つ足すたびに N×N で追記が要る。
> スケジュール追加のタイミングで `closeAllMainViews(except)` を1本
> `base.js` に置き、各ビューはそれを呼ぶ形へ整理する(既存4ビューも移行)。

### 9.3 スケジュール画面のレイアウト


設計上の判断:

- **縦のタイムライン**を採る。横ガントは複数設備の比較には向くが、1設備の
  作業列を上から順に読む用途では縦の方が自然で、既存の一覧・カード群と
  同じ視覚語彙(`.rp-head` / `.db-card` 系)で組める。
- **非稼働帯を線として明示**する(「── 12:00 昼休み ──」)。時間が飛ぶ理由が
  見えないと、計算が間違っているように見える。
- **「◯時間後」は各カードに常時表示**する。これが要望の中心。
  60分未満は「◯分後」、24時間以上は「明日 9:20 (◯時間後)」の併記。
- **見積の不確かさを隠さない**。`±` と `実績なし ⚠` を出す。
  既存の `worktime-benchmark.js` が σ を出しているのと同じ思想。

### 9.4 並べ替え操作

`static/js/lot-split.js` の条割ドラッグ(単一ジェスチャー + ゴースト挿入位置表示)で
確立した操作語彙をそのまま使う。新しい操作を覚えさせない。

- ドラッグ&ドロップで並べ替え → 離した時点で `reorder` をPOST
- キーボード操作も用意する(`Alt+↑/↓` で選択中カードを上下移動)。
  キーボード動線の監査を一度通した経緯があるため、新規UIも同水準を保つ。
- 楽観更新はしない。POSTの応答(再展開済みの予定一覧)で描き直す。
  並べ替えると後続の全時刻が変わるので、サーバー計算結果で塗り替える方が
  ローカルで再計算するより安全かつ単純。

### 9.5 仕掛一覧からの投入導線

`static/js/list-view.js` の `renderGrid()` は既に `isWork`(SIKALOTNOW)のとき
「測定」列を出している。同じ場所へ、**スケジュールモードのときだけ**
「予定」列(＋ボタン)を追加する。

```js
const canPlan = window.accessMode?.mode === 'schedule';
// ヘッダ: isWork && canPlan のとき <th class="plan-action-head">予定</th>
// 行:     isWork && canPlan のとき <td><button class="plan-action-button">+ 予定</button></td>
```

- 編集モード・閲覧モードでは列自体が出ない(押せないボタンを見せない)。
- 複数行を選んでまとめて追加できるよう、行の複数選択(Shift/Ctrl)に対応する。
  現在 `S.selectedRow` は単一行のみのため、`S.selectedRows`(Set)へ拡張する。
  既存の単一選択ハイライト(`is-selected`)の見た目は変えない。

### 9.6 モード別の表示差分

| 要素 | edit | view | schedule |
|---|---|---|---|
| 「作業スケジュール」ナビ | 表示 | 表示 | 表示 |
| タイムライン | 読み取り専用 | 読み取り専用 | 編集可 |
| ドラッグ並べ替え・追加・削除 | 非表示 | 非表示 | 表示 |
| 仕掛一覧の「予定」列 | 非表示 | 非表示 | 表示 |
| 設備セレクタ | 自端末の使用設備で固定 | 全設備選択可 | 全設備選択可 |
| 負荷率の管理画面 | 参照のみ | 参照のみ | 上書き可 |

編集モードで設備セレクタを自端末の使用設備に固定するのは、測定端末で
他設備の予定を眺める用途が無く、誤読(他設備の予定を自分のと思う)の
リスクの方が大きいため。

### 9.7 測定画面との連携(読み取りのみ)

測定画面を開いたとき、そのロットが予定に含まれていれば基本情報タブに
1行だけ出す: 「予定 2番目 / 予定開始 11:44 / 見積 2時間32分」。
既に `openMeasurement` が仕掛行を持っているので、ロット番号で
`/api/schedule/plan` の結果を引くだけでよい。**書き込みは行わない**
(進捗は §7.4 の実績突合で自動的に反映される)。

> `openMeasurement` / `resumeStoredMeasure` はマスタ問い合わせ失敗で例外を
> 投げうるため、この表示処理を差し込むラップは `finally` に置く
> (CLAUDE.md の既知の落とし穴)。

### 9.8 負荷率・稼働カレンダー・メンテ定義の管理画面

`static/js/measurement-worklog.js` の `MASTER_DEFS` へタブを追加する形で
既存のマスタ管理モーダルに相乗りさせる(新しい管理画面を作らない)。

- `{key:'loadFactor', label:'負荷率', icon:'率', special:'load-factor'}`
  … 因子×水準の一覧(自動算出値・N数・上書き値)。`special` 扱いにするのは

  … これは素直な行編集なので汎用CRUDに載る。

### 10.3 特に事故りやすい点

1. **`access-mode.js` の入口ガード条件**。現行は `mode==='view'` のときだけ
   止めている。`schedule` を足した瞬間、条件を `mode!=='edit'` へ反転しないと
   計画端末から測定を開始できてしまう。サーバー側の403で最終的には止まるが、
   モーダルを開いて入力させた後に弾く最悪のUXになる。
2. **`body.view-mode` を前提にした既存CSS**。`schedule` でも同じ抑制が必要な
   ものはセレクタを拡張する。漏れると計画端末に「再開」「削除」が出る。
3. **`DBS` へ schedule を足さない**。足すとサイドバーに自動でナビが生え、
   生テーブルが汎用グリッドに出る。
4. **ロットの一意性**。ロット番号単独をキーにしない(分割済み子ロットで重複しうる)。
   照合は `normalizedFieldName` 系の考え方に合わせ、直接の文字列比較を避ける。
5. **稼働カレンダー未設定時の無限ループ**。全時間帯が非稼働の設定を作れて
   しまうため、`MAX_HORIZON_DAYS` の打ち切りは必須。

## 11. 実装フェーズ

各フェーズ末で「サーバー再起動 → Playwright検証 → 回帰確認 → `APP_VERSION`
更新 + CHANGELOG 追記 → コミット」を行う(既存の運用に合わせる)。

| # | フェーズ | 内容 | 単体で価値が出るか |
|---|---|---|---|
| 1 | モード基盤 | 権限マスタ拡張・3モード判定・ガード表・API・フロントのバッジ/入口ガード | ○(計画端末を安全に用意できる) |
| 2 | 予定データ層 | `schedule.sqlite3` の4テーブル・repo・CRUD API(展開なし) | △ |
| 3 | 稼働カレンダー + 展開 | `schedule_calc.py`・`/api/schedule/plan` の時刻展開 | ○(一律見積でも「何時間後」が出る) |
| 4 | スケジュール画面 | タイムライン・ドラッグ並べ替え・仕掛一覧からの投入 | ◎(ここで使い始められる) |
| 5 | 負荷率モデル | `load_factor.py`・算出API・見積の内訳表示 | ◎(要望の本丸) |
| 6 | メンテナンス | 定義マスタ・投入UI・固定開始時刻・非稼働帯表示 | ○ |
| 7 | 共有と進捗 | `schedule_export.py`・実績突合による自動進捗・測定画面への予定表示 | ◎(現場から見える) |
| 8 | 精度の検証 | 見積 vs 実測の指標・負荷率の手動上書きUI | ○(運用ループが回る) |

フェーズ3を「一律見積(全係数1.0)」で先に通し、フェーズ5でモデルを差し込む
順序にしてある。見積の精度を待たずにスケジュール機能自体を先に現場へ出せ、
かつ「モデルを入れたことで何がどう良くなったか」を前後比較で示せる。

## 12. 検証計画

サンドボックスに Access ドライバが無く仕掛/品質データ系APIは500を返すため、
既存の方針どおり `page.route` でモックして検証する。一方、
`schedule.sqlite3` は本アプリ自身が作るSQLiteなので、**予定のCRUD・展開・
負荷率算出はモック無しで実サーバー越しに検証できる**(マスタ系APIと同じ)。

| 対象 | 方法 |
|---|---|
| モード判定 | アクセス権限マスタへ3パターンを登録し、`/api/access-mode` の応答と初期モードを確認 |
| ガード | 各モードから `measurement`/`masters`/`schedule` へ非GETを投げ、403/200の組み合わせを網羅 |
| 入口ガード | schedule モードで `openMeasurement` を呼び、モーダルが開かないこと |
| 展開 | 稼働帯 8-12/13-17、見積90分の予定を11:30起点で置き、終了が13:30になること。夜間跨ぎ・休日跨ぎ・60日打ち切り |
| 固定開始 | 固定時刻より前の作業が押した場合に押し出され `overdueMinutes` が出ること |
| 負荷率 | 合成実績(既知の係数で生成した対数正規サンプル)を投入し、推定係数が真値へ収束すること。N=1の水準が収縮で1.0寄りに留まること。外れ値1件を混ぜても中央値/MAD除去で係数が動かないこと |
| 未知水準 | 実績に無い用途名で見積が出て `source:'unknown'` になること |
| 実績突合 | 完了実績を置いた状態で予定が '完了' 相当になり、DBの `状態` は書き換わっていないこと |
| 並べ替え | ドラッグ後に後続の時刻が再計算されること。`Alt+↑/↓` でも同じ結果 |
| 回帰 | `regression_check.js`(ナビ横断のコンソールエラー検出)を全フェーズで実行 |

負荷率の検証で**合成データを使う**のが要点。実データでは真の係数が分からず
「もっともらしい数字が出た」以上の検証ができない。既知の係数から実績を
生成して推定値と突き合わせれば、収縮・クリップ・外れ値除去が意図どおり
効いているかを数値で確認できる。

## 13. 未決事項

実装着手前に現場と確認したい点。いずれも設計の骨格は変えずに決められる。

1. **稼働パターン**。常昼か交替か、休憩の時刻、休日の扱い(工場カレンダーの
   有無)。§5.2 のテーブルはどれでも表現できるが、初期投入値が要る。
2. **メンテナンスの定型項目**と標準所要時間。§5.3 の初期データ。
3. **計画のホライズン**。何日先まで並べるか(画面の既定表示期間)。
   1日単位か、1週間まとめてか。
4. **班人数の扱い**。予定段階で人数まで決めるのか、時間だけ見えれば十分か。
   決めない場合は §6.7 の `crewSize` 因子を落とし、係数を1つ減らす。
5. **共有フォルダ**。`schedule_share_path` に使える場所(測定データバックアップと
   同じ Box 配下でよいか)。単独運用なら未設定のままでも動く。
