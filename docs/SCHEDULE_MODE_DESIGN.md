# スケジュールモード 詳細設計

作業スケジュール(作業順・所要時間・メンテナンス計画)を設備ごとに管理し、
「何時間後にどの作業を行うか」を可視化する機能の設計書。

対象読者はこのコードを実装・変更する人。全体構成は `docs/ARCHITECTURE.md`、
機能一覧は `README.md` を参照。

---

## 1. 目的と範囲

### 1.1 解きたい課題

現状、次に何を流すかは紙・口頭・個人の記憶で管理されており、

- 「今の作業はあと何分か」「次は何か」が作業者以外から見えない
- メンテナンス・段取り替えをどこに差し込めば無理がないか判断できない
- 所要時間の見積が「だいたい1本◯時間」の一律感覚で、品種・材料による
  重い/軽いの差が計画に反映されない

### 1.2 本機能で実現すること

1. **スケジュールモード**を起動時のモードとして追加する(編集可能/閲覧に次ぐ第3のモード)。
   閲覧モードの動作(測定データ・マスタへの書き込み禁止)に加え、作業予定の編集だけを許可する。
2. スケジュールモードの端末から、**仕掛一覧の行を選んで設備ごとの作業順に並べる**。
   設備停止(保全計画・段取り替え・待ち時間等、§5.3)も同じ列に差し込める。
3. **過去の作業実績から品種・材料ごとの負荷率(換算係数)を統計的に算出**し、
   予定1件ごとの所要時間を推定する。
4. 稼働カレンダー(就業時間帯・休日)を考慮して**予定開始/終了時刻を展開**し、
   「◯時間後」をタイムラインで表示する。編集モードの測定端末からも読み取り専用で見える。
5. **現場段取り機能**により、編集モードの測定端末からでも、まだ着手していない
   予定に限って順番を突発で入れ替えられる(追加・削除・見積変更は不可、§3.1.1)。

### 1.3 本機能の範囲外(今回やらないこと)

- 自動最適化(納期・段取り最小化による自動並べ替え)。順序は人が決める。
  負荷率はあくまで「人の判断材料としての時間の見える化」に使う。
- 設備をまたぐ負荷平準化・振り分け。予定は設備ごとに独立した1本の列とする。
- 予定の承認ワークフロー・履歴差分。排他制御(§4)による直列化を前提とし、
  監査列のみ持つ(誰がいつ書いたかは残すが、変更履歴の巻き戻しは持たない)。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 予定 / エントリ | 設備の作業列に並ぶ1件。種別は「作業」「設備停止」 |
| 作業列 (キュー) | ある設備の、順序付きの予定の並び |
| アンカー | 時間展開の起点時刻。通常は現在時刻、着手中の作業があればその実開始時刻 |
| 展開 (ETA展開) | 順序+所要見積+稼働カレンダーから予定開始/終了時刻を算出すること |
| 負荷率 / 換算係数 | ある因子水準(例: 用途名=「缶材」)が所要時間を平均の何倍にするかの係数 |
| 因子 / 水準 | 因子=用途名・製造材質など。水準=その因子の具体値 |
| 基準時間 T0 | ある設備の、全因子を中立(係数1.0)としたときの1件あたり所要時間 |
| 設備停止 | 保全計画・リール交換・刃交換・次工程待ち・材料待ち・人員不足・応援対応・突発停止など、作業以外で設備が動かない予定。設備停止マスタ(§5.3)で設備ごとに名称・標準時間を個別管理する |
| 現場段取り | スケジューラが立てた並びのうち、まだ着手していない予定に限って順番だけを入れ替えられる現場向けの権限。追加・削除・見積変更・設備停止の投入は含まない(§3.1.1) |

## 3. モード設計

### 3.1 3モードの定義

| モード | 内部値 | 測定データ・マスタへの書込 | 作業予定への書込 | 想定端末 |
|---|---|---|---|---|
| 編集可能モード | `edit` | 可 | 不可(読み取りのみ) | 設備の測定端末 |
| 閲覧モード | `view` | 不可 | 不可(読み取りのみ) | 参照専用端末 |
| **スケジュールモード** | `schedule` | **不可** | **可** | 工程管理・班長の端末 |

スケジュールモードは**閲覧モードの上位互換ではない**。測定データ・マスタへの
書き込みは閲覧モードと完全に同じく禁止で、作業予定という別ドメインの書き込み
だけが開く。これにより「計画担当の端末が誤って測定データを触る」経路を
最初から作らない。

作業予定の**読み取り**は3モードすべてで可能。編集モードの測定端末から
スケジュールが見えること自体が本機能の主目的(見える化)であるため。

### 3.1.1 現場段取り(モードに重ねる追加権限)

3モードとは別軸で、**現場段取り可否**という真偽値をアクセス権限マスタへ
追加する(§3.2)。「スケジューラが立てたスケジュール通りから突発でスケジュール
入れ替えできる現場段取り機能(順番入れ替えのみ可能)」という要望に対応する。

- モードを増やすのではなく、**書込1操作(並べ替え)だけを許可する権限**として
  設計する。追加・削除・見積の上書き・設備停止の投入・稼働カレンダー編集は
  含めない(含めるとスケジュールモードと同じになり、権限を分けた意味が無くなる)。
- 対象は `edit` モードの端末。§9.6のとおりedit端末は自端末の使用設備に固定
  されるため、権限を与えても理屈の上では「自分の設備の、まだ着手していない
  予定」しか触れないはずだが、これはUI側の制約に過ぎない。API側でも
  端末を設備へ縛るため、アクセス権限マスタにもう1列
  **現場段取り対象設備**(TEXT、1端末につき1設備)を追加し、並べ替えAPIが
  リクエストの設備名とこの値を照合する(§7.5)。
- `schedule` モードは元々すべての書込ができるため、この権限の有無を見ずに
  常に許可する。`view` モードは常に不許可(現場段取りは編集系権限の一種)。
- **設備停止(突発停止を含む)の新規投入はこの権限に含まれない**。現場で
  実際に機械が止まったときは、電話等で連絡を受けた計画担当(スケジュール
  モード)が設備停止エントリを追加する運用とする。現場段取りは「その状況を
  受けて残りの作業順を入れ替える」ところまでが役割。

### 3.2 権限判定(アクセス権限マスタの拡張)

`backend/repositories/master_repo.py` の `アクセス権限マスタ` に列を3本追加する。

```sql
ALTER TABLE [アクセス権限マスタ] ADD COLUMN [スケジュール可否] INTEGER
ALTER TABLE [アクセス権限マスタ] ADD COLUMN [現場段取り可否] INTEGER
ALTER TABLE [アクセス権限マスタ] ADD COLUMN [現場段取り対象設備] TEXT
```

既存の `ensure_audit_columns` と同じ「列が無ければ ALTER TABLE で足す」方式で
`ensure_access_permission_table` の末尾に追加する(既存DBの再作成は不要)。

初期モードの判定規則(**現場段取り可否は初期モードに影響しない**。§3.1.1のとおり
`edit` モードへ重ねる追加権限のため):

| `編集可否` | `スケジュール可否` | 起動時の初期モード | 切替可能なモード |
|---|---|---|---|
| 行なし(未登録) | — | `edit` | `edit` / `view` |
| 編集可(1) | NULL または 0 | `edit` | `edit` / `view` |
| 編集可(1) | 1 | `edit` | `edit` / `view` / `schedule` |
| 閲覧のみ(0) | NULL または 0 | `view` | `view` |
| 閲覧のみ(0) | 1 | **`schedule`** | `view` / `schedule` |

- 「閲覧のみ ＋ スケジュール可」が工程管理端末の標準設定。起動しただけで
  スケジュールモードに入り、測定側は最初から触れない。
- 「編集可 ＋ 現場段取り可(＋現場段取り対象設備にその設備名)」が現場の
  測定端末で突発の並べ替えも行いたい場合の設定。モードは `edit` のまま変わらない。
- 未登録行が既定で `edit` になる現行の互換ポリシーは変更しない
  (追加した3列はいずれもNULL=不可/未設定なので、既存環境の挙動は一切変わらない)。
- 判定関数は既存 `has_edit_permission(c,login_id,pc_name)` の隣へ
  `permission_flags(c,login_id,pc_name) ->
  {'canEdit':bool,'canSchedule':bool,'canFieldReorder':bool,'fieldReorderEquipment':str}`
  を追加し、`has_edit_permission` はその薄いラッパとして残す(呼び出し元の変更不要)。

### 3.3 書込ガード(`backend/access_mode.py`)

現行の `_guard_write` は「モードが `view` かつ対象Blueprintかつ非GET → 403」。
これを次の表に置き換える。**Blueprint単位で許可モードを宣言する方式**にし、
新しいBlueprintを足したときに書き漏れると「どのモードでも通ってしまう」のでは
なく「どのモードでも通らない」側へ倒れるようにする(安全側の既定)。

現場段取り(§3.1.1)は `schedule` Blueprint全体ではなく**並べ替えエンドポイント
1本だけ**を `edit` モードにも開ける必要があるため、Blueprint単位の表とは別に
エンドポイント単位の例外表を重ねる。

```python
# Blueprint名 -> 非GETを許可するモードの集合
_WRITE_ALLOWED_MODES={
 'measurement':{'edit'},
 'masters':{'edit'},
 'schedule':{'schedule'},
}
# 上の表より広く許可する例外(エンドポイント名 -> 追加で許可するモード)。
# 現場段取り: 並べ替えAPI(schedule.plan_reorder)だけをeditにも開ける。
# 新しい書込系エンドポイントをここへ追記する際は、権限の絞り込みを
# ハンドラ側(_field_reorder_permitted等)で必ず二重に行うこと。
_ENDPOINT_EXTRA_MODES={
 'schedule.plan_reorder':{'edit'},
}
```

```python
@app.before_request
def _guard_write():
 if request.method=='GET':return None
 bp=request.blueprint
 if bp is None:return None            # app直付け(モード切替API・shutdown等)は対象外
 allowed=_WRITE_ALLOWED_MODES.get(bp)
 if allowed is None:return None       # 未宣言のBlueprintは従来どおり素通し(§注記)
 mode=get_mode()
 if mode in allowed:return None
 extra=_ENDPOINT_EXTRA_MODES.get(request.endpoint)
 if extra and mode in extra:
  if mode=='edit' and not _field_reorder_permitted():
   return jsonify(error='この端末には現場段取り(並べ替え)の権限がありません。'),403
  return None                          # schedule.plan_reorder自身は
                                        # equipment一致チェックをハンドラ側で行う(§7.5)
 return jsonify(error=...),403
```

`_field_reorder_permitted()` は `_permitted()` と同じ形で、アクセス権限マスタの
`現場段取り可否` を照合する(マスタ未整備時は既定で不可。編集可否の既定=可と
非対称にする。「触れる範囲が広がる」側の既定を安全側に倒すため)。

> **注記**: 未宣言Blueprintを素通しにするのは現行互換のため(`tables`/`quality`/
> `core` は読み取り専用Blueprintで非GETを持たない)。CLAUDE.md の
> 「新しい書込系APIを追加する場合、そのBlueprintが `_GUARDED_BLUEPRINTS` に
> 含まれるか確認すること」は、この表(および現場段取りのような例外を追加する
> 場合は `_ENDPOINT_EXTRA_MODES` )への追記に読み替える。実装時にCLAUDE.md
> 側の文言も更新する。

### 3.4 モード切替API

`GET /api/access-mode` の応答に `canSchedule`・`canFieldReorder`・
`fieldReorderEquipment` を追加:

```json
{"ok":true,"mode":"schedule","canEdit":false,"canSchedule":true,
 "canFieldReorder":false,"fieldReorderEquipment":"",
 "loginId":"kato","pcName":"NLM-PLAN01"}
```

```json
{"ok":true,"mode":"edit","canEdit":true,"canSchedule":false,
 "canFieldReorder":true,"fieldReorderEquipment":"SL-1",
 "loginId":"ono","pcName":"NLM-SL1"}
```

`POST /api/access-mode` の `mode` に `schedule` を追加。権限が無ければ 403。
`現場段取り` はモードではないため `POST /api/access-mode` の対象にはならない
(常に `edit` モードのまま、並べ替えAPIの可否だけが変わる)。
権限はこれまでどおり呼び出しのたびにマスタを読み直す(再起動不要)。

### 3.5 フロント側の入口ガード(`static/js/access-mode.js`)

- `accessMode` に `canSchedule` を追加。`document.body` のクラスを
  `view-mode` / `schedule-mode` の2種で出し分ける。
  既存CSSの `body.view-mode` 由来の抑制(測定再開ボタン等)は
  `body.view-mode, body.schedule-mode` へセレクタを拡張する。
- ヘッダーのモードバッジはクリックで**巡回**ではなく、権限のあるモードを
  並べた小さなポップオーバーから選ばせる(3値になった時点で「クリックで
  トグル」は意味が取れなくなるため)。
- `openMeasurement` / `resumeRecordFromList` のラップは
  「`edit` 以外なら止める」に変更する(現行は `view` のときのみ止めている。
  条件を反転させないと `schedule` が素通りする)。**実装時の主要な事故ポイント**。
- `accessMode.canFieldReorder` が真の `edit` 端末では、モードバッジ自体は
  「編集モード」のままで変えず、代わりに「作業スケジュール」ナビの横へ
  小さな「並べ替え可」バッジを出す(新しいモードを増やしたと誤解させない
  ための表示上の工夫。実体は§3.1.1のとおりモードではなく権限)。

## 4. データの置き場所と排他制御

### 4.1 前提: 共有Box環境への複数端末書き込み

作業予定の実体(`schedule.sqlite3`)は**共有環境のBox上に1つだけ置く**。
書き込み手は主担当1名+副担当のスケジューラ1名を基本とし、開発者による
検証アクセスを含めて最大3端末程度が同時にアクセスしうる前提で設計する。

**なぜこれが単純にはいかないか**: SQLiteは「ネットワーク越しのファイル
ロックが信頼できない環境での複数プロセス書き込み」を明示的に非推奨として
いる(SQLite自身のFAQで案内されている既知の制約)。Boxのような同期型
クラウドストレージは、各端末がローカルにキャッシュしたコピーをバック
グラウンドで結果整合的に同期する仕組みで、真の意味でのファイルロックAPIや
アトミックな排他操作を提供しない。したがって、2端末が「ほぼ同時に」
`schedule.sqlite3`へ直接書き込むと、
- 同期エージェントが書き込み途中のファイルを中途半端にアップロードし
  破損したコピーになる
- 双方の変更のうち一方が気づかれずに消える(後から同期した側が勝つ)
- 最悪、Box側が競合を検知して「(競合コピー)」ファイルを分岐生成し、
  誰も気づかないまま予定が2系統に分かれる
という事故が起こりうる。これは実装の作り込みだけでは根本的に解消できない、
ストレージ選択そのものに起因する制約であるため、前提として正直に明記する。

### 4.2 設計方針: 「取得→適用→反映」の短命サイクル + 簡易ロック

複数端末の同時書き込みそのものを許すのではなく、**Box上のファイルへは
常に1端末だけが、短時間だけ、取得→適用→反映のサイクルで触れる**ように
限定する。既存の `records_export.py`(差分ありのときだけbackup()で複製する
方式)・`backend/watchdog.py`(ハートビートによる生存監視)と同じ考え方の
組み合わせで実現する。

```
どの書込系API呼び出しも、内部で以下のサイクルを踏む(スケジュールモードの
通常編集・現場段取りの並べ替えのどちらも同じサイクルを使う):

1. ロック取得を試みる(schedule.lock.json、§4.3)
   - 空き、または既存ロックが期限切れなら自分のトークンで確保
   - 埋まっていれば「編集中: ◯◯@△△(残りn秒)」を返して終了(423)
2. 確保できたら、Box上の schedule.sqlite3 を sqlite3.Connection.backup()で
   ローカルの一時ファイルへ取得する(records_export.pyと同じ技法。単純な
   ファイルコピーではなく整合性のとれたスナップショットを取る)
   - 取得直後に整合性を確認する(軽いSELECTが通るか等)。壊れていれば
     直前に取得できていた最後の正常ローカルキャッシュを使い、警告を出す
     (Box側の破損をローカルへ持ち込まない、§4.5)
3. ローカルの一時ファイルへ、この呼び出し分の変更(1回のadd/reorder/
   update/delete等)を適用する
4. 改訂番号(§4.4)を+1して、一時ファイルをBox上へ
   「一時名で書き込み→リネームで置き換え」の手順で反映する
   (直接上書きしない。リネームは多くのファイルシステムで準アトミックに
   扱われ、Box側が書き込み途中の中身を拾ってしまう窓を最小化する)
5. ロックを解放する(成功時・失敗時とも finally で必ず実行)
```

ロックは**呼び出し1回分だけを保持する短命ロック**とする(スケジュール
モードの編集セッション全体を長時間ロックし続ける方式は採らない)。理由:
- セッション全体を保持する方式は「閉じ忘れ」でロックが長時間残り、
  もう一方の担当者や現場段取りをブロックし続けるリスクがある
- 1回あたりの処理(取得・適用・反映)は数百KB程度の小さなSQLiteファイルに
  対する操作で、数秒以内に収まる見込みのため、呼び出しのたびに
  取得→反映しても体感上のコストは小さい
- 現場段取り(edit端末からの突発の並べ替え)とスケジュールモードの通常編集を
  **同じ1つの排他機構**で扱える(現場段取りだけ別ロジックを持たずに済む、§7.5)

### 4.3 ロックファイル(`schedule.lock.json`)

```json
{"token":"c3f1e2a0-...","holder_login":"kato","holder_pc":"NLM-PLAN01",
 "acquired_at":"2026-08-02T09:00:00+09:00","expires_at":"2026-08-02T09:00:30+09:00"}
```

- 有効期限は既定30秒(`schedule_lock_ttl_sec`)。期限切れのロックは次の
  取得試行時に無条件で上書きしてよい(異常終了・クラッシュからの回復。
  30秒という短さにより、自動失効を待つだけで実用上困らない。手動の
  「強制的に引き継ぐ」操作は用意しない=待てば必ず自然解消するため)。
- 取得直後に**再読込による簡易検証**を行う(自分のトークンのままかを
  既定1.5秒後(`schedule_lock_verify_delay_ms`)に確認する)。他端末と
  ほぼ同時に取得を試みた場合、双方が「自分が確保した」と誤認する余地が
  理論上残る(Boxが結果整合的である以上、完全なアトミック排他は原理的に
  作れない)。この残存リスクは§4.4の改訂番号チェックで最終的に検出・
  棄却する(ロックは一次防御、改訂番号は二次防御という二段構え)。
- ロック状態は `GET /api/schedule/lock-status` で全モードから参照でき、
  スケジュール画面のヘッダーに「編集中: ◯◯@△△」を表示する(§9.3)。

### 4.4 改訂番号による楽観的排他(ロックの保険)

`schedule.sqlite3` 内に1行だけの小さなメタ情報テーブルを持つ:

```sql
CREATE TABLE [スケジュールメタ] ([改訂番号] INTEGER, [最終更新者ID] TEXT, [最終更新日時] DATETIME);
```

§4.2の手順4で反映する直前、**取得時点(手順2)の改訂番号**を憶えておき、
書き戻す瞬間にBox上の現在の改訂番号と比較する。一致しなければ「自分が
読んだ後に別の変更が反映された」ということなので、**反映せずに中断し、
409で拒否する**(この呼び出し分の変更は失われるが、代わりに他人の変更を
静かに上書きすることは無い)。フロントは「別の端末の変更と競合しました。
最新の状態を読み直してからもう一度お試しください」と表示し、最新状態を
再取得したうえで、可能ならユーザーの入力内容を保持して再試行を促す。

ロック(§4.3)が「同時に触らせない」ための一次防御、改訂番号チェックが
「万一すり抜けても上書きしない」ための二次防御という二段構えにする。
ロック単体はBoxの結果整合性ゆえに完全ではないため、これを併用する。

### 4.5 破損時のフェイルセーフ

Box上の `schedule.sqlite3` が同期中の中途半端な状態や破損したコピーに
なっていた場合に備え、各端末は**最後に正常取得できたローカルキャッシュ**
を保持し続ける(§4.2手順2)。取得の整合性確認に失敗した場合は、
- 書込系操作はエラーとして中断する(壊れたベースへは絶対に書かない)
- 閲覧系(GET)は、警告付きでキャッシュの内容を表示する(何も見えない
  よりは、多少古くても最後に確認できた状態を見せる方が現場の実害が小さい)

### 4.6 開発者アクセスについての推奨

検証・デバッグ目的のアクセスは、可能な限り**本番のBox上ファイルを直接
触らず、ローカルの別ファイルへ向ける**ことを推奨する。`schedule_share_path`
は単なるファイルパスであり、Box配下である必要は無いため、検証時は
このキーをローカルの空ファイル(またはコピー)へ一時的に切り替えるだけで、
本番と全く同じコード経路を安全に試せる(`sikalotnow_path`等の検証時
上書きと同じ考え方、§4.7)。要望どおり3端末同時アクセスの構えは用意するが、
日常的な検証作業はここに含めず、実運用側(主担当+副スケジューラの2名)の
実際の競合可能性を下げておく。

### 4.7 設定 (`config/local.json`)

| キー | 既定 | 意味 |
|---|---|---|
| `schedule_share_path` | なし | `schedule.sqlite3`の実体パス(Box上の共有パス、または検証用のローカルパス)。**未設定ならスケジュール機能自体を無効化**する(仕掛/品質データの`sikalotnow_path`と同じく、拡張子で自動判定するパス指定方式) |
| `schedule_lock_ttl_sec` | 30 | ロックの有効期限。この秒数を過ぎたロックは次の取得試行で無条件に奪える |
| `schedule_lock_verify_delay_ms` | 1500 | ロック取得直後、再読込で確認するまでの待ち時間 |

`backend/config.py` へ `SCHEDULE_LOCK_TTL_SEC_DEFAULT=30`、
`SCHEDULE_LOCK_VERIFY_DELAY_MS_DEFAULT=1500`、`LOAD_FACTOR_CACHE_TTL_SEC=600`
を追加(アプリ固有値は config.py へ集約する規約に従う)。

`backend/db_access.py` の `DBS` へは**追加しない**(前段と同じ理由。
`/api/catalog`経由で汎用グリッドにナビが生えてしまうため)。
`SCHEDULE_SHARE_PATH`をモジュール変数として持ち、ローカルの一時取得先
(`SCHEDULE_CACHE_PATH`、`db/schedule_cache.sqlite3`固定、個別設定は無し)
は`connect()`の拡張子判定でそのまま使える。

## 5. データモデル

`db/schedule.sqlite3` に4テーブル。既存マスタの規約(全角テーブル名・
`INTEGER PRIMARY KEY AUTOINCREMENT`・`有効`による論理削除・監査列・
索引は別SQL)に合わせる。`Now()` は `db_access.connect()` がSQLiteへ
ユーザー定義関数として登録済みのため、そのまま使える。

データアクセス層は `backend/repositories/schedule_repo.py`(Flask非依存)。

### 5.1 作業予定

設備ごとの作業列。作業もメンテナンスも**同じ1本の列**に入れる
(順序の一貫性を型で保証でき、差し込みの表現が自然になる)。

```sql
CREATE TABLE [作業予定] (
  [予定ID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,            -- 正規化前の生表記。照合は normalize_equipment_name
  [表示順] INTEGER,         -- 同一設備内の順序。1始まりの連番(§5.1.1)
  [種別] TEXT,              -- '作業' | '設備停止'(旧設計の'メンテナンス'/'休止'を統合。
                            -- 内訳は設備停止マスタの[分類]列で持つ、§5.3)
  [ロット番号] TEXT,        -- 種別='作業' のみ
  [検査番号] TEXT,
  [鋳造番号] TEXT,
  [予定名称] TEXT,          -- 種別='設備停止': 追加時点の設備停止マスタ[名称]の
                            -- スナップショット(マスタ改名後も履歴の表示が変わらない
                            -- ようにする)。種別='作業'では表示用の補助(空でも可)
  [明細JSON] TEXT,          -- 種別='作業': 計画時点の仕掛行スナップショット(§5.1.2)
  [固定開始日時] TEXT,      -- ISO8601。指定時はこの時刻より前に開始しない
  [見積分] REAL,            -- 手動上書き見積(分)。NULLならモデル推定/設備停止マスタの
                            -- 標準所要分を使う
  [状態] TEXT,              -- '予定' | '着手' | '完了' | '取消'。'着手'/種別='作業'の
                            -- '完了'相当は原則§7.4の実績突合による動的判定で表示され、
                            -- この列へは書き戻さない。設備停止の完了確定など実績突合の
                            -- 効かないケースのみ、計画者の明示操作でこの列へ書く
  [実績測定ID] TEXT,        -- 突合できた測定データのid(§7.4)
  [備考] TEXT,
  [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
CREATE INDEX [IX_作業予定_設備順] ON [作業予定] ([設備名],[表示順]);
```

#### 5.1.1 順序の持ち方

`表示順` は**同一設備内で1から始まる連番**とし、並べ替えのたびに
その設備の全行を書き直す(`POST /api/schedule/plan/reorder` が
`[予定ID,...]` の配列を受け取り、その順に1..N を振り直す)。

他マスタは10刻みのスパース採番だが、ここでは採らない。理由:

- 1設備あたりの予定件数は数十件が上限で、全件UPDATEのコストが無視できる
- 「ドラッグで並べ替えた結果の配列を丸ごと保存する」という操作の形と
  1対1に対応し、挿入位置の再採番ロジックが不要になる
- スパース採番は再採番のタイミングが分散するぶん、順序の重複や欠番を
  生むバグが出やすい

#### 5.1.2 仕掛スナップショット(`明細JSON`)を持つ理由

仕掛(SIKALOTNOW)の行は**作業が終わると仕掛から消える**。
本アプリは既にこの前提で作られている(分割済み子ロットが仕掛に見つからない
場合の警告表示など)。予定がロット番号だけを持っていると、

- 完了した予定を後から見返したときに品種・寸法が表示できない
- 見積の内訳(どの係数が効いたか)を再現できない

ため、予定に追加した時点の仕掛行から `aliases`(`static/js/base.js`)で
拾える値をスナップショットして持つ。

```json
{"lotNo":"1234567","inspectionNo":"...","castingNo":"...",
 "purposeName":"缶材","mfgMaterial":"3004","mfgTemper":"H19",
 "mfgThickness":"0.285","mfgWidth":"1420","mfgLength":"...",
 "equipment":"SL-1","boxHorizontalCount":"6","boxVerticalCount":"1",
 "capturedAt":"2026-08-02T09:12:00+09:00"}
```

キー名は `aliases` のキーと同一にする。実績側の `basic{}` も
`Object.fromEntries(Object.keys(aliases).map(k=>[k,pick(row,k)]))` で
作られているため、**予定と実績が同じキー空間になる**(§6.2の要)。

### 5.2 稼働カレンダーマスタ

```sql
CREATE TABLE [稼働カレンダーマスタ] (
  [カレンダーID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,        -- 空文字は「全設備の既定」
  [区分] TEXT,          -- '曜日' | '特異日'
  [曜日] INTEGER,       -- 区分='曜日' のとき 0(日)〜6(土)
  [日付] TEXT,          -- 区分='特異日' のとき 'YYYY-MM-DD'
  [稼働] INTEGER,       -- 0=非稼働(休日)。1=稼働
  [開始時刻] TEXT,      -- 'HH:MM'
  [終了時刻] TEXT,      -- 'HH:MM'。開始>終了 は翌日跨ぎとみなす
  [表示順] INTEGER, [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
```

- **休憩は稼働帯を分割して表現する**。専用の休憩テーブルを作らない。
  例(常昼): `08:00-12:00` と `13:00-17:00` の2行 → 12:00-13:00 は自動的に非稼働。
  2交替・3交替・連続操業も、同じ曜日に複数行を置くだけで表現できる。
- 適用の優先順位: **特異日(日付一致) > 設備別の曜日 > 全設備既定の曜日**。
  該当行が1件も無い設備は「24時間稼働」とみなす(何も設定していない状態で
  予定が翌週に飛ぶより、素直に連続で積む方が驚きが少ない)。

### 5.3 設備停止マスタ

「作業以外で設備が動かない予定」の雛形。保全計画・リール交換・刃交換・
次工程待ち・材料待ち・人員不足・応援対応・突発停止など、要望に挙がった
名称をここへ登録しておき、予定へ投入するときに名称と標準時間を呼び出す。
計画者が毎回手入力しなくて済むようにするのが目的で、既存マスタ群と同じ
「行の存在＝選択肢」方式にする。

**時間は設備単位・停止内容単位で個別に持つ**(要望のとおり)。「刃交換」が
設備Aでは45分、設備Bでは30分、というように設備ごとに違う値を登録できる
必要があるため、`設備名` は必須項目とする(表示マスタ等にある「空文字=
全体共通」の省略記法はここでは使わない)。同じ名称でも設備が違えば別行として
個別に標準時間を持つ。

```sql
CREATE TABLE [設備停止マスタ] (
  [停止理由ID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,         -- 必須。正規化前の生表記、照合は normalize_equipment_name
  [分類] TEXT,           -- '保全' | '段取り' | '待ち' | '突発'(表示の色分け・
                         -- 将来の集計用。任意入力、未設定でも動作する)
  [名称] TEXT,           -- 例: '保全計画' 'リール交換' '刃交換' '次工程待ち'
                         -- '材料待ち' '人員不足' '応援対応' '突発停止'
  [標準所要分] REAL,     -- この設備・この停止理由での既定見積(分)。
                         -- 個別予定側の[見積分]で予定単位にも上書き可
  [色キー] TEXT,         -- タイムライン上の色分け。§9.3のトークン名
  [表示順] INTEGER, [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
CREATE UNIQUE INDEX [UX_設備停止マスタ_名称] ON [設備停止マスタ] ([設備名],[名称]);
```

`POST /api/schedule/stop-reason-master` は `設備名` が空なら400で拒否する
(他マスタの必須チェックと同じ方式。例: `ログインIDを入力してください。`)。

初期投入の目安(標準所要分の具体値・設備ごとの違いは現場に確認して個別に
入れる。§13の未決事項。ここでは分類の割り振り例のみ示す):

| 分類 | 名称の例 |
|---|---|
| 保全 | 保全計画 |
| 段取り | リール交換、刃交換 |
| 待ち | 次工程待ち、材料待ち、人員不足、応援対応 |
| 突発 | 突発停止 |

上表の8名称は**設備ごとに繰り返し登録する**(設備が5台あれば最大40行)。
ある設備に無い概念(例: その設備には「リール交換」が存在しない)は、
その設備の行を作らなければ選択肢から自然に外れる。

**「突発停止」は他の名称と性質が違う**点に注意する。保全計画・リール交換等は
計画者が事前に予定へ差し込む「これから起きるとわかっている停止」だが、
突発停止は現場で今まさに起きた・起きている停止を指す。本設計では
**設備停止エントリの新規投入は現場段取り権限に含めない**(§3.1.1)ため、
突発停止が起きた際は現場から連絡を受けた計画担当(スケジュールモード)が
`標準所要分` を仮の目安として投入し、実際に再開した時点で `見積分`
(または実績確定後の表示)を実測へ合わせて上書きする運用を想定する。
自動では起きない(計画者の明示操作)という原則は他の名称とも共通。

### 5.4 負荷率上書きマスタ

自動算出した係数を人が上書きするための表。行が無ければ自動算出値をそのまま使う
(表示マスタと同じ「行の存在＝上書き」ポリシー)。

```sql
CREATE TABLE [負荷率上書きマスタ] (
  [上書きID] INTEGER PRIMARY KEY AUTOINCREMENT,
  [設備名] TEXT,       -- 空文字は全設備共通
  [因子] TEXT,         -- 'purposeName' | 'mfgMaterial' | ... | 'BASE'
  [水準] TEXT,         -- 因子の値。因子='BASE' のときは空(基準時間T0の上書き)
  [係数] REAL,         -- 因子='BASE' のときは分単位の基準時間
  [理由] TEXT,
  [有効] INTEGER,
  [登録者ID] TEXT, [更新者ID] TEXT, [登録日時] DATETIME, [更新日時] DATETIME
);
CREATE UNIQUE INDEX [UX_負荷率上書き] ON [負荷率上書きマスタ] ([設備名],[因子],[水準]);
```

## 6. 負荷率(換算係数)モデル

本機能の中核。「品種・材料ごとに重い/軽いがある」を、実績から**自動で**
数値化して見積へ反映する。

### 6.1 モデルの形: 対数線形(乗法)モデル

```
見積分(設備E, ロットL) = T0(E) × Π_j  f_j( 水準_j(L) )
```

- `T0(E)`: 設備Eの基準時間(分)。全因子が中立のときの1件あたり所要
- `f_j(v)`: 因子 j の水準 v の**負荷率(換算係数)**。1.0 が「平均並み」

この形を選ぶ理由:

1. **説明できる**。「この用途名は 1.32 倍」「この板厚帯は 0.88 倍」と現場の言葉で
   そのまま読める。ユーザーの要望文にある「負荷率(換算係数)」という語と一致する。
2. **未知の組み合わせに必ず答えが出る**。既存の `worktime-benchmark.js` は
   用途名・材質・調質・実測寸法・丈割数・条割数・設備の**完全一致**で過去実績を
   引くため、条件が1つでも違うと N=0 になる。計画は「まだ流したことのない
   組み合わせ」も並べるので、完全一致方式は計画用途には使えない。
   乗法モデルなら未知の水準は係数1.0(中立)で通せる。
3. **作業時間の分布に合う**。作業時間は下に0の壁があり右に裾を引く(対数正規に近い)。
   対数を取れば因子の効果が加法になり、平均ではなく**幾何平均**で扱える。

### 6.2 特徴量(因子)

予定側(仕掛スナップショット)と実績側(`basic{}`)で**同一のキー**が使えることが
前提。§5.1.2 のとおり両者とも `aliases` のキー空間で作られるため、
学習時と予測時で特徴量がずれない。

| 因子キー | 元の列 | 種類 | 備考 |
|---|---|---|---|
| `purposeName` | 用途名 | カテゴリ | 品種。要望の「品種ごと」の主軸 |
| `mfgMaterial` | 製造材質 | カテゴリ | 要望の「材料ごと」の主軸 |
| `mfgTemper` | 製造調質 | カテゴリ | |
| `mfgThickness` | 製造板厚 | 数値→帯 | ビン化(§6.3) |
| `mfgWidth` | 製造板幅 | 数値→帯 | ビン化 |
| `mfgLength` | 製造板丈 | 数値→帯 | ビン化。規模の代理変数 |
| `boxHorizontalCount` | BOX設計_横割数 | 数値→帯 | 条数。段取りに効く |
| `boxVerticalCount` | BOX設計_縦割数 | 数値→帯 | 丈割数 |
| `crewSize` | settings.crewSize | カテゴリ | 班人数。予定側は既定値(§6.7) |

**設備は因子にしない。設備ごとに別モデルを作る**。設備が違えばライン速度も
段取りも別物で、係数の掛け算では表現しきれないため。

**数値量をすべて帯(カテゴリ)に落とす**のが本設計の要点。板厚・板幅・板丈の
単位系(mm/m、コイル長かカット長か)がデータソースにより揺れうるのに対し、
帯に落とせば単位の解釈を一切必要とせず、非線形な効き方(薄物だけ極端に遅い等)も
そのまま吸収できる。

### 6.3 ビン境界の決め方

既定は**実績の分位点による自動ビン化**(四分位=4区間)。単位に依存せず、
どの工場・どの設備でも同じコードで機能する。

- 相異なる値が4種以下の因子(条数・丈割数など)は、値そのものを水準にする。
- ビン境界は**再計算のたびに確定させ、算出結果と一緒に保存・表示する**。
  境界が黙って動くと「先週の係数1.2は何の帯だったのか」が追えなくなるため、
  `/api/schedule/load-factors` の応答に必ず境界を含める。
- 固定境界を使いたい場合は `負荷率上書きマスタ` の因子キーに
  `BIN:mfgThickness` のような行を置いて上書きできる(v2で対応。v1は自動のみ)。

### 6.4 学習データ

対象: 共有の測定データバックアップ(§6.6)から読んだレコードのうち

- `status === '完了'`
- `workTime.startAt` と `workTime.endAt` が両方あり、差が正
- 設備(`settings.registeredEquipment`)が空でない

**外れ値の除去**: 対数所要時間 `y = ln(分)` について、中央値 `m` と
MAD(中央絶対偏差)を求め、`|y - m| > 3 × 1.4826 × MAD` の実績を除外する。

除去理由: 「作業開始を押したまま昼休みに入った」「終了を押し忘れて翌朝押した」
といった記録は必ず混ざる。平均や標準偏差ベースの除去はそうした極端値自身に
引きずられるため、中央値・MADで頑健に切る。**除外件数はAPIの応答に含めて
画面に出す**(黙って捨てない)。

### 6.5 推定手順

設備Eごとに、以下を実行する(`backend/load_factor.py`、Flask非依存)。

```
入力: 実績 {y_i = ln(所要分), 水準ベクトル v_i}  (i = 1..N)

1) 初期化   ln T0 = median(y_i)          … 幾何平均を中央値で頑健に初期化
             ln f_j(v) = 0  (全因子・全水準)

2) 反復(3巡)  各因子 j について:
     各水準 v で  r = mean( y_i − lnT0 − Σ_{k≠j} ln f_k(v_i) )   over {i : v_i,j = v}
     n = その水準の件数
     収縮:  ln f_j(v) ← r × n / (n + K)        K = 5 (既定)
     クリップ: ln f_j(v) を [ln 0.5, ln 2.0] に収める
   因子1巡ごとに ln T0 ← median( y_i − Σ_j ln f_j(v_i) ) で再センタリング

3) 残差の広がり  σ_log = 標準偏差( y_i − lnT0 − Σ_j ln f_j(v_i) )

出力: T0 = exp(lnT0), f_j(v) = exp(ln f_j(v)), σ_log, 各水準のN数
```

**収縮 (shrinkage)** `n/(n+K)` が実運用上いちばん重要な部品。
1件しかない用途名の実績が「たまたま3時間かかった日」だったとき、収縮が無いと
その用途名の係数が 2.0 に張り付き、以後その品種の予定がすべて倍の見積になる。
`n/(n+5)` により、n=1 なら効果は 1/6 しか採らず、n=45 で 90% 採る。
**件数が増えるほど自動的にモデルが自信を持つ**という素直な挙動になる。

クリップ 0.5〜2.0 は、収縮を抜けてなお極端な係数が出た場合の最終防波堤。

反復が3巡なのは、因子間の相関(例: ある用途名はほぼ特定の材質でしか流れない)を
数巡で概ね分離できるため。厳密な収束判定は費用に見合わない。

**設備の実績が少ないとき**: 有効実績が `MIN_SAMPLES=20` 件に満たない設備は、
自設備モデルを作らず**全設備プールで学習したモデル**を使い、`T0` だけを
その設備の実績中央値(または全体のT0)に置き換える。新設備・新端末でも
初日から見積が出る。この代替を使ったことは応答の `basis` フィールドで明示する。

### 6.6 実績の取得元

スケジュールモード端末は測定を行わないため、自端末の IndexedDB は空。
実績は**共有の測定データバックアップから読む**。これは閲覧モードが
既に使っている経路と同じ:

```
1st: RECORDS_BACKUP_EXPORT_PATH の records.sqlite3 (共有・Box等)
2nd: 未設定ならローカルの db/records.sqlite3
```

**集計はバックエンドで行う**。バックアップは1件が測定グリッド込みのJSONで
数十KBあり、数千件をフロントへ流して毎回パースするのは現実的でない。
`Web測定バックアップ` テーブルから必要な列だけ取り出し、payload JSON から
`basic` / `settings` / `workTime` のみを読んで学習する。

**キャッシュ**: 算出結果はプロセス内にキャッシュし、
`LOAD_FACTOR_CACHE_TTL_SEC`(既定600秒) または元ファイルの mtime 変化で無効化。
`POST /api/schedule/load-factors/recalc` で明示的に破棄もできる。

### 6.7 予測(1件の見積)

```
1. 予定に 見積分 が入っていれば → それを使う(手動上書きが最優先)
2. 種別='設備停止' → 予定の見積分、無ければ 設備名+予定名称(=追加時点の
   設備停止マスタの名称)に一致する設備停止マスタ行の標準所要分。設備停止
   マスタは設備ごとに個別の時間を持つ(§5.3)ため、他設備の同名行とは
   照合しない。一致する行が無ければ0分(見積なしとして扱い、警告を出す)
3. 種別='作業':
     水準を 明細JSON から取り出し、数値因子は保存済みビン境界で帯へ変換
     係数 = 上書きマスタに行があればその値、無ければ自動算出値、
            水準が未知(実績に無い)なら 1.0
     見積分 = T0 × Π 係数
     予測区間 = [見積分 × exp(−1.96σ_log), 見積分 × exp(+1.96σ_log)]
```

`crewSize` は予定側に実測値が無いので、**その設備の実績の最頻値**を既定として
使い、予定ごとに計画者が変更できる。班人数を変えたときに見積がどう動くかが
その場で見えるのは計画作業として価値がある。

### 6.8 見積の内訳を必ず返す

`/api/schedule/estimate` は数値だけでなく内訳を返す。ブラックボックスの
時間を現場は信用しないため、画面に「なぜこの時間か」を出せる形にしておく。

```json
{"minutes":152.4,
 "low":98.1,"high":236.7,"sigmaLog":0.29,
 "basis":"equipment",
 "base":{"T0":118.0,"n":432},
 "factors":[
  {"key":"purposeName","level":"缶材","value":1.18,"n":96,"source":"auto"},
  {"key":"mfgMaterial","level":"3004","value":1.04,"n":210,"source":"auto"},
  {"key":"mfgThickness","level":"0.25〜0.31","value":0.93,"n":88,"source":"auto"},
  {"key":"boxHorizontalCount","level":"6","value":1.13,"n":51,"source":"override"},
  {"key":"mfgWidth","level":"1380〜1450","value":1.00,"n":0,"source":"unknown"}
 ]}
```

`source` は `auto`(自動算出) / `override`(手動上書き) / `unknown`(実績なし＝1.0)。
`unknown` が多い予定は見積の根拠が薄いことが一目で分かる。

### 6.9 モデルの精度を運用中に検証する

完了した予定について「見積 vs 実測」を突合し、画面に表示する(§9.4)。
指標は**対数誤差の中央値と分布**:

- 中央値バイアス `median(ln(実測/見積))` … 系統的に速い/遅いのずれ
- MAPE 相当 `median(|実測 − 見積| / 実測)` … 現場に説明しやすい形

これを見て `BASE` の上書き値を調整する、という運用ループが回るようにする。

## 7. 時間展開(ETA)

### 7.1 展開はバックエンドで行う

順序・見積・稼働カレンダーはすべてバックエンドにある。フロントで再実装すると
同じロジックが2箇所に生まれる(CLAUDE.md の「関数の定義は1箇所」に反する)。
`GET /api/schedule/plan` が**計算済みの予定開始/終了を返し**、フロントは
表示に徹する。`backend/schedule_calc.py`(Flask非依存)が担当。

### 7.2 アンカー(起点)の決定

```
先頭の有効な予定が '着手' 状態 (§7.4で実績突合により判定)
   → アンカー = その実開始時刻
      かつ 先頭の残り時間 = max(見積 − 既経過, MIN_REMAIN_MIN)   MIN_REMAIN_MIN = 5
それ以外
   → アンカー = 現在時刻。非稼働時間帯なら次の稼働帯の開始時刻へ繰り上げ
```

着手中の作業の残りを見積から経過を引いて出すことで、画面を開いた瞬間の
「今の作業はあと何分」が実態に追従する。`MIN_REMAIN_MIN` の下限は、見積を
超過した作業で残りが負になり後続が過去へ食い込むのを防ぐ。

### 7.3 展開アルゴリズム

```
cursor = アンカー
for entry in 有効な予定(表示順):
    if entry.状態 in ('完了','取消'): continue      # 列から外す(表示は別枠)
    if entry.固定開始日時 and 固定開始日時 > cursor:
        entry.待ち = 固定開始日時 − cursor          # 空き時間として明示
        cursor = 固定開始日時
    cursor = 次に稼働している時刻へ繰り上げ(cursor)
    entry.予定開始 = cursor
    remaining = entry.見積分
    while remaining > 0:
        slot   = cursor を含む(または直後の)稼働帯
        cursor = max(cursor, slot.開始)
        use    = min(slot.終了 − cursor, remaining)
        cursor += use ;  remaining −= use
        if remaining > 0: cursor = 次の稼働帯の開始      # 夜間・休日を跨ぐ
    entry.予定終了 = cursor
    entry.開始まで = 予定開始 − 現在時刻                  # 「◯時間後」表示の元
```

- 稼働帯の探索は最大 `MAX_HORIZON_DAYS=60` 日で打ち切り、超えた予定は
  `予定開始=null` + 「稼働カレンダー上、60日以内に収まりません」を返す
  (稼働カレンダーが全休で設定された場合の無限ループ防止)。
- `固定開始日時` を過ぎている(前の作業が押している)場合は**押し出す**。
  固定時刻のために前の作業を切ることはしない。ただし遅延量を
  `entry.遅延` として返し、画面で赤く出す。

### 7.4 進捗の反映は「実績突合」で行う(書き戻さない)

測定端末(編集モード)は共有先の読み取り専用コピーしか持たないため、
そこから予定DBへ書き戻すことはできない。代わりに**実績から状態を導出する**。

```
共有の測定データバックアップを ロット番号+鋳造番号+製造材質 で予定へ突合:
   完了レコードあり              → 状態 '完了' 相当として扱う
   startAt のみ (endAt なし)     → 状態 '着手' 相当として扱う
   実績なし                      → 予定のまま
```

- この判定は**表示のたびに動的に行い、DBへは書かない**。単一書き込み者
  モデルを崩さずに、どの端末でも同じ進捗が見える。
- 計画者が明示的に「完了として確定」した場合のみ `状態` 列へ書き込む
  (実績が上がらないまま飛ばした作業の消し込み用)。
- 突合したレコードの `id` を `実績測定ID` として応答に含め、
  画面からその帳票を開けるようにする(実績カレンダーの `openReportForRecord`
  と同じ導線を再利用)。

ロット番号だけでは分割済み子ロット等で重複しうるため、突合キーは
**ロット番号 + 鋳造番号 + 製造材質**の完全一致とする(3項目とも
`normalize_equipment_name`と同じ方式(NFKC正規化+前後空白除去)で比較し、
全角/半角ゆれを吸収する)。検査番号は未設定・不安定なことが多いため
突合キーから外す(以前の設計案にあった「検査番号優先、無ければ鋳造番号」
という段階的な緩和は行わない)。3項目のいずれかが欠けている場合はその
候補を突合対象にしない(緩い一致で誤って別ロットに実績を紐付けるより、
突合できずに「実績なし」のまま表示される方が安全なため)。複数一致した
場合は「最も新しい更新日時」を採る。

### 7.5 現場段取り(並べ替え)の制約

`POST /api/schedule/plan/reorder` は**専用の別エンドポイントを作らず**、
スケジュールモードの通常の並べ替えAPIをそのまま使う。現場段取りとの違いは
§3.3のモードゲート(呼び出せるか)だけで、並べ替えの業務ルール自体は
呼び出し元のモードによらず**常に同じ**にする。ルールを枝分かれさせると
「schedule権限なら本当は何でも並べ替えられてよいのか」を毎回考える必要が
生まれるため、単純化する。

```
入力: equipment, orderedIds(予定IDの配列)

0) §4.2の「ロック取得→schedule.sqliteを一時取得→適用→反映→解放」サイクルの
   「適用」の中身が以下の1〜6。ロックが取れなければ423を返す(§4.3)。
   現場段取りは「突発」用途のため、423を受けたら短い間隔(1秒・2秒・4秒)で
   最大3回まで自動再試行し、それでも取れなければ「他端末が編集中のため
   お待ちください(◯◯@△△)」を表示して終了する(スケジュールモードの
   長時間編集がedit端末からの突発操作を長々とブロックしないよう、
   §4.2のロックは呼び出し1回分だけの短命ロックにしてある)
1) equipment上の有効な予定を state 導出込みで取得(§7.4と同じ実績突合)
2) 対象 = 状態が実質的に '予定'(未着手)のものだけ
   (着手中・完了・取消は動かせない。将棋倒しの起点を勝手に動かさないため)
3) orderedIds の集合 == 対象の予定IDの集合 と厳密一致しなければ400
   (追加・削除・対象外の混入を拒否する。これが「並べ替えのみ」の実体的な保証)
4) 呼び出し元モードが 'edit' の場合、追加でアクセス権限マスタの
   現場段取り対象設備 が equipment と一致しなければ403
   (UIは自端末の設備に固定されているが、直接APIを叩かれた場合の
   保険としてサーバー側でも縛る)
5) 対象群を orderedIds の順で 表示順 を振り直す。対象外の予定(着手中の
   1件が先頭にあるのが通常)の位置は変えない
6) 更新後の展開結果(§7.3と同じ形)を返す。フロントはこれで描き直す
   (楽観更新はしない。並べ替えは後続の全時刻に波及するため)
7) §4.4の改訂番号チェックに失敗した場合(取得後に他端末が先に反映した)は
   409を返す。フロントは最新状態を再取得したうえで、選んだ並び順を
   保持できていれば自動的に1回だけ再試行する
```

> 現場段取りは「UIレベルの制約」と「APIレベルの制約」の2重で reorder-only を
> 保証する設計にしている。UIは追加・削除・見積編集のボタン自体を出さないが、
> それだけに頼ると開発者ツールから直接APIを叩かれたときに素通りしてしまう。
> 現場段取り可否を持つ端末が呼べるエンドポイントは`schedule.plan_reorder`
> 1本のみ(§3.3の`_ENDPOINT_EXTRA_MODES`)であるため、他の書込系エンドポイント
> (追加・削除・見積上書き・稼働カレンダー・マスタ編集)は edit モードのままでは
> 依然として403になる。ロック(§4.3)・改訂番号(§4.4)による排他は、
> スケジュールモードの書込・現場段取りの並べ替えの両方に等しく適用される
> (どちらも同じ`schedule.sqlite3`を取り合う以上、区別する理由が無いため)。

- `actual` は§7.4の実績突合で見つかった測定データから作る。着手中は
  `elapsedMinutes`(経過)、完了後は `minutes`(実測所要)と
  `varianceMinutes`(実測−見積)を返す。「実績などの時間表示」(順次作業表示・
  スケジュール一覧の両方)はこのフィールドをそのまま出す。
- `reorderable` は§7.5の対象判定結果(状態が実質的に'予定'かどうか)を
  そのままフロントへ渡し、ドラッグ可否の判定をサーバーとフロントで
  二重に持たないようにする。
- 完了済み(`state:"完了"`)の予定も、直近分は履歴として応答に含める
  (件数は`horizon`とは別に既定7日分。§7.3の「完了/取消は列から外す」は
  時間展開の計算対象から外す話であって、一覧表示からは外さない)。
- `warnings` は設定不備を黙って握り潰さないための枠。

### 8.2 `POST /api/schedule/plan/add`

```json
{"equipment":"SL-1","kind":"作業","position":"end",
 "lotNo":"1234567","inspectionNo":"...","castingNo":"...",
 "detail":{"purposeName":"缶材","mfgMaterial":"3004","...":"..."},
 "user_id":"kato"}
```

```json
{"equipment":"SL-1","kind":"設備停止","position":"end",
 "stopReasonId":12,"estimateMinutes":null,
 "user_id":"kato"}
```

- `detail` は**フロントが仕掛一覧の行から作って送る**。サーバー側で
  仕掛を引き直さない。仕掛は列表示マスタで列が落ちうる読み取り専用データで、
  追加時点の見え方をそのまま固定したい(再取得すると行が消えていて失敗する)。
- `equipment` は両 `kind` とも必須。空なら400(「どの設備の予定か」を
  常に一意に管理する、という要望に対応)。
- `kind:"設備停止"` は `stopReasonId`(設備停止マスタの主キー)を渡す。
  サーバー側でその行の `名称`・`標準所要分` を読み、`予定名称` へ
  スナップショットする(§5.1)。設備停止マスタは設備ごとに個別の行を持つため
  (§5.3)、その行の `設備名` がリクエストの `equipment` と一致しなければ
  400で拒否する(他設備の停止理由IDを誤って流用すると、意図と違う時間の
  設備停止が入ってしまうため)。`estimateMinutes` を渡せば標準所要分の
  代わりにその値を使う(突発停止など、その場で分かっている見込み時間を
  入れたい場合)。
- 重複追加(同一設備に同一ロットの未完了予定が既にある)は 409 で拒否し、
  画面側で「既に予定に入っています」を出す。この重複チェックは
  `kind:"作業"` のみに適用する(設備停止は同名を複数回積んでよい)。

### 9.1 情報アーキテクチャ(サイドバー)

現在のグループは「測定データ / 一覧を見る / 分析 / 管理」。

(`body.cal-mode #grid,...{display:none!important}` および

### 9.3 スケジュール画面のレイアウト(順次作業表示)

要望にある「順次作業表示とそのスケジュール一覧」は、このタイムライン
そのものを指す。1設備の作業列を上から順に読む縦のカード列とし、各カードに
予定(見積)と実績(わかっている範囲)を並べて出す。

```

│ [設備: SL-1 ▾]  起点 09:12(作業中)  稼働: 常昼 8-12,13-17  [再計算] │
├────────────────────────────┬─────────────────────────────┤
```

`🔒` は着手中(reorderable=false、動かせない)、`⠿` は未着手(reorderable=true、
ドラッグ可)を表すハンドル。現場段取り権限のみのedit端末では追加パネル・
見積の内訳パネルごと非表示にし、タイムラインとハンドルだけを出す(§9.4.1)。
ヘッダーの `[設備: SL-1 ▾]` は **schedule モードのみ**で、edit モードでは
`▾` を出さず `設備: SL-1(使用設備)` の固定表示になる(§9.6)。

設計上の判断:

- **縦のタイムライン**を採る。横ガントは複数設備の比較には向くが、1設備の
  作業列を上から順に読む用途では縦の方が自然で、既存の一覧・カード群と
  同じ視覚語彙(`.rp-head` / `.db-card` 系)で組める。
- **非稼働帯を線として明示**する(「── 12:00 昼休み ──」)。時間が飛ぶ理由が
  見えないと、計算が間違っているように見える。
- **「◯時間後」は各カードに常時表示**する。これが要望の中心。
  60分未満は「◯分後」、24時間以上は「明日 9:20 (◯時間後)」の併記。
- **見積の不確かさを隠さない**。`±` と `実績なし ⚠` を出す。
  既存の `worktime-benchmark.js` が σ を出しているのと同じ思想。
- **完了カードにも実績を残す**(カード0)。「見積とどれだけ差があったか」が
  その場で見えることが、§6.9の精度検証を画面上で日常的に感じさせる。
- **設備停止パネルは、選択中の設備に登録されている設備停止マスタの行だけを
  ボタン化**する(§5.3のとおり設備ごとに個別のため、他設備の行は出さない)。
  「突発停止」だけ既定で無効化(グレーアウト)し、ホバーで「発生時は計画
  担当へ連絡してください」と出す(§3.1.1のとおり投入は現場段取りの範囲外
  のため)。
- **ロック保有者はヘッダーに常時表示**する(`GET /api/schedule/lock-status`
  を数秒間隔でポーリング)。誰も保有していなければ何も出さず、保有者が
  いれば「編集中: 田中@NLM-PLAN02」を薄いバッジで出す(自分自身が保有中
  なら「編集中: 自分」)。書込系のボタンを無効化するほどではない
  (§4.2のロックは呼び出し1回分の短命ロックで、通常は一瞬で解放されるため、
  常時グレーアウトすると却って煩わしい)。423が返ってきたときだけ
  トースト通知で知らせる。

### 9.4 並べ替え操作

`static/js/lot-split.js` の条割ドラッグ(単一ジェスチャー + ゴースト挿入位置表示)で
確立した操作語彙をそのまま使う。新しい操作を覚えさせない。

- ドラッグ&ドロップで並べ替え → 離した時点で `reorder` をPOST
- キーボード操作も用意する(`Alt+↑/↓` で選択中カードを上下移動)。
  キーボード動線の監査を一度通した経緯があるため、新規UIも同水準を保つ。
- 楽観更新はしない。POSTの応答(再展開済みの予定一覧)で描き直す。
  並べ替えると後続の全時刻が変わるので、サーバー計算結果で塗り替える方が
  ローカルで再計算するより安全かつ単純。
- ドラッグ対象は `reorderable:true` の予定のみ(§7.5)。着手中・完了・
  固定開始日時が現在時刻より前の予定は掴めないようにする(掴んだ瞬間に
  ドロップを弾かれる方が、ドロップ後にエラー表示される体験より分かりやすい)。

### 9.4.1 現場段取り(edit端末での並べ替え専用表示)

`accessMode.canFieldReorder` が真の `edit` 端末は、§9.3のタイムラインから
**追加パネル・見積の内訳パネル**を除いた簡易版を表示する(設備セレクタは
§9.6のとおりeditモードでは元々出さない)。表示する操作はドラッグ並べ替えと
`Alt+↑/↓` のみ。

- 追加・削除・見積上書き・固定開始時刻・稼働カレンダー・マスタ管理への
  導線は一切出さない(§3.1.1の「順番入れ替えのみ」をUI側でも徹底する)。
- ヘッダーに「並べ替え可」バッジ(§3.5)を出し、通常の閲覧専用タイムライン
  との違いを示す。
- ドラッグの送信先は通常のスケジュール画面と同じ `POST /api/schedule/plan/reorder`
  (§7.5)。UIを分けても業務ロジック・エンドポイントは1本のままにする。

### 9.5 仕掛一覧からの投入導線

`static/js/list-view.js` の `renderGrid()` は既に `isWork`(SIKALOTNOW)のとき
「測定」列を出している。同じ場所へ、**スケジュールモードのときだけ**
「予定」列(＋ボタン)を追加する。

```js
const canPlan = window.accessMode?.mode === 'schedule';
// ヘッダ: isWork && canPlan のとき <th class="plan-action-head">予定</th>
// 行:     isWork && canPlan のとき <td><button class="plan-action-button">+ 予定</button></td>
```

- 編集モード・閲覧モードでは列自体が出ない(押せないボタンを見せない)。
- 複数行を選んでまとめて追加できるよう、行の複数選択(Shift/Ctrl)に対応する。
  現在 `S.selectedRow` は単一行のみのため、`S.selectedRows`(Set)へ拡張する。
  既存の単一選択ハイライト(`is-selected`)の見た目は変えない。

### 9.6 モード別の表示差分

| 要素 | edit | view | schedule |
|---|---|---|---|
| 「作業スケジュール」ナビ | 表示 | 表示 | 表示 |
| タイムライン | 読み取り専用(現場段取り可なら並べ替え可、§9.4.1) | 読み取り専用 | 編集可 |
| 未着手分のドラッグ並べ替え | 現場段取り可否に従う | 非表示 | 表示 |
| 追加・削除・見積上書き・稼働カレンダー | 非表示 | 非表示 | 表示 |
| 仕掛一覧の「予定」列 | 非表示 | 非表示 | 表示 |
| 設備セレクタ | 自端末の使用設備で固定表示(選択UIなし) | 全設備選択可(`▾`) | 全設備選択可(`▾`)、予定追加時は必須 |
| 負荷率の管理画面 | 参照のみ | 参照のみ | 上書き可 |

- **編集モード(測定作業中の端末)は、ナビの「作業スケジュール」を開くと
  `currentConfiguredEquipment()`(使用設備の登録値)のスケジュールが
  自動的に開く**。設備を選ぶ操作自体が無い(要望どおり「測定作業時は選択
  設備のスケジュールを開く」)。使用設備が未登録の端末は、仕掛一覧と同じ
  案内(`list-view.js`の`setup-first`と同型)で「まず使用設備を設定して
  ください」を表示し、スケジュール自体は開かない。
- **スケジュールモードは特定の設備に紐付かない**。ヘッダーの設備セレクタで
  どの設備のスケジュールでも切り替えて作成・編集できる(要望どおり
  「スケジューラとしてログインした場合はどの設備のスケジュールも作成可能」)。
- `POST /api/schedule/plan/add` は `equipment` が必須で、未選択のまま追加
  しようとするとボタン自体を無効化する(サーバー側の400は最終防衛、§8.2)。
  これにより「どの設備の予定として登録したか」が常に一意に決まる。
- 編集モードで設備セレクタを出さない(選ばせない)のは、測定端末で
  他設備の予定を眺める用途が無く、誤読(他設備の予定を自分のと思う)の
  リスクの方が大きいため。

### 9.7 測定画面との連携(読み取りのみ)

測定画面を開いたとき、そのロットが予定に含まれていれば基本情報タブに
1行だけ出す: 「予定 2番目 / 予定開始 11:44 / 見積 2時間32分」。
既に `openMeasurement` が仕掛行を持っているので、ロット番号で
`/api/schedule/plan` の結果を引くだけでよい。**書き込みは行わない**
(進捗は §7.4 の実績突合で自動的に反映される)。

> `openMeasurement` / `resumeStoredMeasure` はマスタ問い合わせ失敗で例外を
> 投げうるため、この表示処理を差し込むラップは `finally` に置く
> (CLAUDE.md の既知の落とし穴)。

### 9.8 負荷率・稼働カレンダー・設備停止の管理画面

`static/js/measurement-worklog.js` の `MASTER_DEFS` へタブを追加する形で
既存のマスタ管理モーダルに相乗りさせる(新しい管理画面を作らない)。

- `{key:'loadFactor', label:'負荷率', icon:'率', special:'load-factor'}`
  … 因子×水準の一覧(自動算出値・N数・上書き値)。`special` 扱いにするのは
  一覧が「自動算出＋上書き」の2層構造で、汎用CRUDのフォームに載らないため
  (列表示マスタ `columnDisplay` と同じ特別扱いのパターン)。
- `{key:'workCalendar', label:'稼働カレンダー', icon:'稼', special:'work-calendar'}`
- `{key:'stopReason', label:'設備停止', icon:'停', endpoint:'/api/schedule/stop-reason-master', hasDelete:true,
   fields:[{k:'equipment',label:'設備名',type:'select',required:true,key:true},
           {k:'category',label:'分類',type:'select',options:['保全','段取り','待ち','突発','']},
           {k:'name',label:'名称',required:true,key:true},{k:'minutes',label:'標準所要分',required:true}], ...}`
  … これは素直な行編集なので汎用CRUDに載る。`設備名`は必須項目(§5.3)。
  一覧は設備で絞り込めるようにする(全設備分がフラットに並ぶと見づらいため)。
  初期投入は設備ごとに§5.3の8名称を繰り返し登録する想定。

| `docs/ARCHITECTURE.md` / `README.md` / `CLAUDE.md` | 構成・ガード規約の更新 |

### 10.3 特に事故りやすい点

1. **`access-mode.js` の入口ガード条件**。現行は `mode==='view'` のときだけ
   止めている。`schedule` を足した瞬間、条件を `mode!=='edit'` へ反転しないと
   計画端末から測定を開始できてしまう。サーバー側の403で最終的には止まるが、
   モーダルを開いて入力させた後に弾く最悪のUXになる。
2. **`body.view-mode` を前提にした既存CSS**。`schedule` でも同じ抑制が必要な
   ものはセレクタを拡張する。漏れると計画端末に「再開」「削除」が出る。
3. **`DBS` へ schedule を足さない**。足すとサイドバーに自動でナビが生え、
   生テーブルが汎用グリッドに出る。
4. **ロットの一意性**。ロット番号単独をキーにしない(分割済み子ロットで重複しうる)。
   照合は `normalizedFieldName` 系の考え方に合わせ、直接の文字列比較を避ける。
5. **稼働カレンダー未設定時の無限ループ**。全時間帯が非稼働の設定を作れて
   しまうため、`MAX_HORIZON_DAYS` の打ち切りは必須。
6. **現場段取りの権限チェックを`before_request`だけに任せない**。
   `_ENDPOINT_EXTRA_MODES` はモード(edit)を通すだけで、「その設備の
   現場段取り対象設備と一致するか」はハンドラ内で別途必須(§7.5)。
   ここを漏らすと、権限のある端末が他設備の並びまで動かせてしまう。
7. **設備停止マスタの行は設備ごとに独立**(§5.3)。`stopReasonId`だけを
   頼りに追加すると、他設備からコピーしたIDで違う時間の停止が入る事故が
   起きうるため、`plan/add`は必ずリクエストの`equipment`とマスタ行の
   `設備名`が一致するか検証する(§8.2)。
8. **ロックの解放をfinallyから漏らさない**(§4.2手順5)。取得→適用→反映の
   途中で例外が起きてもロックだけは必ず解放しないと、次の呼び出し(他端末
   はもちろん自分自身の次の操作も)が最大`schedule_lock_ttl_sec`(既定30秒)
   待たされる。`openMeasurement`同様、finallyでの解放は既存の落とし穴
   パターンそのもの。
9. **改訂番号の比較を「取得時点」の値で行う**(§4.4)。反映直前ではなく
   §4.2手順2で取得した時点の改訂番号を保持しておき、手順4の反映直前に
   Box上の最新値と比較する。反映直前に読み直した値を使うと、自分の
   取得後・反映前に割り込んだ他人の変更を検出できず、排他が実質機能しない。
10. **Box上ファイルへの直接書込を絶対に行わない**(§4.1〜§4.2)。将来
    どこかのコードが「ついでにBox上のファイルへ直接UPDATEした方が早い」
    という近道を取ると、この設計全体の前提(常にローカルの一時取得先で
    加工してから反映)が崩れ、破損リスクが再発する。

## 11. 実装フェーズ

各フェーズ末で「サーバー再起動 → Playwright検証 → 回帰確認 → `APP_VERSION`
更新 + CHANGELOG 追記 → コミット」を行う(既存の運用に合わせる)。

| # | フェーズ | 内容 | 単体で価値が出るか |
|---|---|---|---|
| 1 | モード基盤 | 権限マスタ拡張(スケジュール可否・現場段取り可否・現場段取り対象設備)・3モード判定・ガード表・エンドポイント例外・API・フロントのバッジ/入口ガード | ○(計画端末・現場段取り端末を安全に用意できる) |
| 2 | 予定データ層+排他制御 | `schedule_repo.py`の4テーブル・`schedule_sync.py`(ロック・改訂番号・取得反映サイクル、§4)・CRUD API(展開なし) | △(基盤のみだが、ここで排他制御まで作り切る) |
| 3 | 稼働カレンダー + 展開 | `schedule_calc.py`・`/api/schedule/plan` の時刻展開・実績突合(§7.4) | ○(一律見積でも「何時間後」「実績」が出る) |
| 4 | スケジュール画面 | タイムライン(順次作業表示)・ドラッグ並べ替え・仕掛一覧からの投入・現場段取り簡易表示(§9.4.1)・ロック表示(§9.3) | ◎(ここで使い始められる) |
| 5 | 負荷率モデル | `load_factor.py`・算出API・見積の内訳表示 | ◎(要望の本丸) |
| 6 | 設備停止 | 設備停止マスタ・投入UI(8分類)・固定開始時刻・非稼働帯表示 | ○ |
| 7 | 進捗表示 | 実績突合による自動進捗・測定画面への予定表示 | ◎(現場から見える) |
| 8 | 精度の検証 | 見積 vs 実測の指標・負荷率の手動上書きUI | ○(運用ループが回る) |

フェーズ3を「一律見積(全係数1.0)」で先に通し、フェーズ5でモデルを差し込む
順序にしてある。見積の精度を待たずにスケジュール機能自体を先に現場へ出せ、
かつ「モデルを入れたことで何がどう良くなったか」を前後比較で示せる。
現場段取り(§3.1.1・§7.5)はフェーズ1で権限とAPI制約を作り切り、フェーズ4で
実際に使えるUIを載せる(権限だけ先にあってもUIが無ければ試せないため)。
**排他制御(§4)はフェーズ2で最初から組み込む**。後から差し込むと全ての
書込系ハンドラを書き直すことになるため、最初の書込系APIから
`schedule_sync.py`のサイクルに乗せておく。

## 12. 検証計画

サンドボックスに Access ドライバが無く仕掛/品質データ系APIは500を返すため、
既存の方針どおり `page.route` でモックして検証する。一方、
`schedule.sqlite3` は本アプリ自身が作るSQLiteなので、**予定のCRUD・展開・
負荷率算出はモック無しで実サーバー越しに検証できる**(マスタ系APIと同じ)。
排他制御(§4)はサンドボックス上で`schedule_share_path`をローカルの
一時フォルダへ向け、複数のPythonプロセス(またはPlaywrightの複数コンテキスト
から並行してAPIを叩く)で疑似的な同時アクセスを再現して検証する
(実際のBox同期挙動そのものは再現できないため、あくまでロック・改訂番号の
アプリ側ロジックの検証に限る)。

| 対象 | 方法 |
|---|---|
| モード判定 | アクセス権限マスタへ3パターンを登録し、`/api/access-mode` の応答と初期モードを確認 |
| ガード | 各モードから `measurement`/`masters`/`schedule` へ非GETを投げ、403/200の組み合わせを網羅 |
| 入口ガード | schedule モードで `openMeasurement` を呼び、モーダルが開かないこと |
| 展開 | 稼働帯 8-12/13-17、見積90分の予定を11:30起点で置き、終了が13:30になること。夜間跨ぎ・休日跨ぎ・60日打ち切り |
| 固定開始 | 固定時刻より前の作業が押した場合に押し出され `overdueMinutes` が出ること |
| 負荷率 | 合成実績(既知の係数で生成した対数正規サンプル)を投入し、推定係数が真値へ収束すること。N=1の水準が収縮で1.0寄りに留まること。外れ値1件を混ぜても中央値/MAD除去で係数が動かないこと |
| 未知水準 | 実績に無い用途名で見積が出て `source:'unknown'` になること |
| 実績突合 | 完了実績を置いた状態で予定が '完了' 相当になり、DBの `状態` は書き換わっていないこと。`actual.minutes`/`varianceMinutes` が応答に出ること |
| 並べ替え | ドラッグ後に後続の時刻が再計算されること。`Alt+↑/↓` でも同じ結果 |
| 現場段取り境界 | (a) `現場段取り可否=0` の edit 端末から `plan/reorder` を叩いて403 (b) `=1` の端末が自設備の未着手分だけ並べ替えられる (c) 着手中/完了を並べ替え対象に含めて400 (d) `現場段取り対象設備` と異なる設備名で403 (e) edit 端末から `plan/add`/`plan/delete`/`plan/update`/`calendar` を叩いて403(並べ替え以外は依然できないこと) |
| 設備停止 | 設備停止マスタの8名称を投入し、`kind:'設備停止'` の予定追加→見積が標準所要分どおりになること。突発停止ボタンがUI上グレーアウトしていること |
| 設備停止の設備別独立性 | 同名(例:'刃交換')を設備A=45分/設備B=30分で別々に登録し、それぞれの設備の予定追加で異なる見積になること。設備Aの`stopReasonId`を設備Bの`equipment`で追加しようとして400になること |
| 設備横断/自動オープン | scheduleモードの端末が設備セレクタで任意の設備へ切り替えて予定を作成できること。editモードの端末は設備セレクタを持たず、`currentConfiguredEquipment()`のスケジュールが自動的に開くこと。使用設備未登録のeditモードでは案内表示になりスケジュールが開かないこと |
| 実績突合キー | ロット番号+鋳造番号+製造材質が完全一致する実績のみ突合すること。鋳造番号または製造材質が片方でも欠けている実績・予定は突合されない(「実績なし」のまま)こと。検査番号だけが違っても突合されること(突合キーに含めていないため) |
| ロック取得/競合 | 1端末がロックを保持している間、別プロセスからの書込系呼び出しが423を返し、`lockedBy`に保持者情報が含まれること。TTL(既定30秒)経過後は無条件で取得できること。書込ハンドラ内で例外を起こしても`finally`でロックが解放され、次の取得がブロックされないこと |
| 改訂番号 | 取得後・反映前に別プロセスが先に反映した状況を再現し、後発側が409で拒否されること。かつ先発側の変更が上書きされず残っていること(データ消失が起きないことを直接確認する) |
| フェイルセーフ | `schedule_share_path`先のファイルを意図的に壊れた内容で置き換え、GETが警告付きで直前のローカルキャッシュを返すこと。書込系はエラーで中断し、壊れた内容をローカルキャッシュへ反映しないこと |
| 回帰 | `regression_check.js`(ナビ横断のコンソールエラー検出)を全フェーズで実行 |

負荷率の検証で**合成データを使う**のが要点。実データでは真の係数が分からず
「もっともらしい数字が出た」以上の検証ができない。既知の係数から実績を
生成して推定値と突き合わせれば、収縮・クリップ・外れ値除去が意図どおり
効いているかを数値で確認できる。

## 13. 未決事項

実装着手前に現場と確認したい点。いずれも設計の骨格は変えずに決められる。

1. **稼働パターン**。常昼か交替か、休憩の時刻、休日の扱い(工場カレンダーの
   有無)。§5.2 のテーブルはどれでも表現できるが、初期投入値が要る。
2. **設備停止マスタの標準所要分**。§5.3 で名称8種と分類の割り振り例、
   および設備ごとに個別の時間を持つ設計までは決まったが、設備×名称ごとの
   具体的な分数(「刃交換: 設備Aは45分、設備Bは30分」等)の実測値が要る。
   「突発停止」は実測に合わせて都度上書きする運用でよいか。
3. **計画のホライズン**。何日先まで並べるか(画面の既定表示期間)。
   1日単位か、1週間まとめてか。
4. **班人数の扱い**。予定段階で人数まで決めるのか、時間だけ見えれば十分か。
   決めない場合は §6.7 の `crewSize` 因子を落とし、係数を1つ減らす。
5. **共有フォルダの具体パス**。`schedule_share_path`に指定するBox上の実際の
   フォルダ(測定データバックアップと同じBox配下でよいか、専用フォルダを
   切るか)。データ本体をBoxへ置く方針自体は確定(§4)。
6. **現場段取り対象設備の登録運用**。アクセス権限マスタへの登録(§3.2)は
   管理画面からの手入力を想定しているが、測定端末側の「使用設備」設定
   (localStorage)と2重管理になる。運用上どちらを正として揃えるか
   (例: 使用設備を登録した際にマスタ側の値も一緒に更新する運用にする等)。
7. **ロックTTL・検証待ち時間の実測調整**(§4.3の`schedule_lock_ttl_sec`=30秒、
   `schedule_lock_verify_delay_ms`=1.5秒)。実際に使うBoxクライアント
   (Box Drive等)の同期の速さ次第で、値が短すぎて競合を見逃す/長すぎて
   待たされる、のどちらにも振れうる。運用開始後に実測して調整する前提の
   値であることを認識しておく。
