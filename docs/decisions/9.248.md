#### ③ 表示列が消える——**描くときに絞るのは正しい。保存するときに絞るのが不具合**

いちばん重い1件。実機で「一部表示されなかったり消えている」と出ていたのは、
**列レイアウトマスタの`order`が保存のたびに痩せていた**ため。

一覧は「横に見えている列しか本文を作らない」（§9.104）、スケジュール表は
「並びに載っている列だけを描く」、データ一覧は「一度も保存していないうちは
既定の15列」（§9.162）——**描くときに絞るのはどれも正しい**。壊れていたのは、
その**絞ったあとの一覧を、そのまま保存の`order`にも使っていた**3箇所:

| 場所 | 関数 | 何が落ちていたか |
|---|---|---|
| 仕掛一覧・品質データ | `list-view.js` `bindColumnHeaderTools`の`persist()` | `(v.order\|\|[]).filter(c=>all.includes(c))`——`all`はいま描いている列。畳んだ子ロットの列・結合が外れているときの品質列が丸ごと落ちる |
| 作業スケジュール表 | `schedule-view.js` `persistTimelineColumns()` | 描画用の`timelineColumnKeys()`をそのまま保存。モードや設定で出ていない列が落ちる |
| 列の設定パネル | `list-columns.js` の保存 | `draft.order`は候補に出ている列だけ |

`order`は**全置換**（§9.212 ②「並びだけは全体を送る」——部分的な並べ替えは
どちらが正か決まらない）なので、痩せた並びを1回送った時点で**落ちた列は
マスタから消える**。次に開くとその列は「知らない列」なので末尾へ回され、
幅・表示名・書式・読み替え・計算式も一緒に失われる。**列幅を少し引いただけで
起きる**（§9.110で番号・ボタンの列が右端へ飛んだのと同じ形の再発で、
今度はデータ列側）。

直し方は3箇所とも同じ——**保存済みの並びを土台にして、今ある列のうち
載っていないものだけを後ろへ足す**:

```js
const stored=(v.order||[]);
const kept=stored.filter((c,i)=>stored.indexOf(c)===i);   // 重複だけ落とす（§9.113）
await WL.columnLayout.patch(target,{order:[...kept,...all.filter(c=>!kept.includes(c))], ...});
```

スケジュール表は`timelineOrderForSave()`という**保存専用の並び**を別に持つ
（描画用の`timelineColumnKeys()`は絞ったまま——**絞る側を緩めない**。
緩めると隠した列が画面に出る）。列の設定パネルは`orderForSave()`が、
保存済みだが候補に出ていない列を**元の隣へ挿し直す**（末尾へ回すと、
次に開いたとき並びが変わって見える）。

**落ちるのは「今この瞬間、画面に出ていない列」だけ**なので、
**確かめるときは必ず列を隠した状態から保存すること**——全部出ている状態で
保存する網は、直す前でも通る（実際に既存の網7本が全部通っていた）。
固定は`tests/test_colkeep.js`。**古い実装を注ぎ込んで落ちることを確認済み。**

#### ④ 「表示中の列」「非表示中の列」の札——**出どころの札と掛け合わせる**

列の設定パネルの絞り込みは§9.105で「出どころ」（元データ／結合／計算・操作）
の3分類を持っていた。そこへ**2本目の軸**として状態（表示中／非表示中）を足す。

- **2つの軸はAND**（「結合の列のうち、いま出していないものだけ」が書ける）。
  1つの列に混ぜると「元データ」と「非表示中」が排他になり、掛け合わせられない。
- **件数は必ず文字で出す**（§3）。色や濃さだけで「今どちらで絞っているか」を
  伝えない。
- **同じ札をもう一度押すと外れる**（`stateFilter=''`）。外す場所を別に作らない。
- **開いたときは絞らない**（`stateFilter=''`）——覚えると、次に開いた人が
  「列が減った」と読む。
- **チェックを付け外ししたら札の件数を描き直す**（`renderOrigins()`）。
  忘れると「非表示中 3」と出ているのに一覧は2件、という食い違いになる。

区切りは`<i class="lc-chip-sep">`の縦線1本——**軸が2つあることを形で言う**
（同じ並びに8個の札が並ぶと、どれとどれが排他なのか読めない）。

#### ⑤ 選択肢の「よく使う順」——**並べる余地のある形だけ**

`操業データ項目マスタ`の`[選択肢の並び]`が`''`（登録順＝既定）か`よく使う順`。
回数は`操業データ選択肢マスタ`の`[使用回数]`列（「行が無ければ足す」で移行）。

- **効くのは新しい表示領域を開く形だけ**（`CHOICE_ORDER_WIDGETS`＝
  プルダウン／一覧／メニュー／パネル）。利用者の指示どおり、**余白に余裕が
  ある**形にしか意味が無い——セグメントやボタン群は並びが画面の形そのものなので、
  使うたびに札が動くと**筋肉記憶が毎回裏切られる**（探す時間が増える）。
- **並べる余地の無い形では、設定を残したまま登録順で出す**
  （`choice_order_usable()`）。設定を消すと、選ばせ方を戻したときに
  「前に選んだはずの設定が消えている」になる（§9.132・§9.227 ①と同じ作法）。
  盤では**押せなくして理由をその場に書く**（§4）。
- **並びの規則は`choice_list()`の1箇所**——`sorted(..., key=-used)`は
  **安定ソート**なので、回数が同じものは登録順のまま。回数で並べたあとに
  名前で並べ直したりしないこと（同点のときに順番が理由なく変わる）。
- **数えるのは実際に人が選んだときだけ**——`wireChoiceUsage()`は`document`へ
  委譲した`change`を1つ持ち、**`e.isTrusted`で人の操作に限る**。記録の復元や
  プリセットの当て込みは`.value`への代入＋合成イベントなので数えない
  （数えると、開き直すたびに前回の値の回数が増えて先頭へ固定される）。
- 口は`POST /api/operation-choice-master/used`で、**読み取り専用のPOST**
  （`_READ_ONLY_POST_ENDPOINTS`）。閲覧モードでも測定は開けるので、
  ここを書込扱いにすると閲覧の端末だけ回数が増えない。

#### ① 選ばせ方は24種。**束ねて出す**

「フローティングモーダル」「ポップオーバーメニュー」「スピナー」を、
利用者の言葉のまま3つ足すのではなく——**既にある形と役割が重なるものは
足さない**（§9.226 ①「種類を足すのは選ぶ状況が違うものだけ」）。

- **ポップオーバーメニュー＝`メニュー`**（§9.247 ①で追加済み）。足さない。
- **フローティングモーダル→`パネル`**。画面中央に浮く**マス目**の窓で、
  `一覧`（絞り込み欄つきの大きな窓）と`メニュー`（欄の真下に垂れる細い帯）の
  **あいだ**を埋める。選択肢を一度に見せたいが、絞り込みが要るほど多くはない、
  という状況が実際にある。
- **スピナー**は数値の欄の**右端に上下の矢印を重ねる**。`ステッパー`
  （−／欄／＋）と役割は同じだが、**欄の下に段を作らない**——狭いマスでは
  ステッパーが2段になって並びが崩れる。器は`margin-left:auto`で右へ寄せる
  （`align-self:flex-end`は効かない——`.opf-host`は常にflexとは限らない）。
  **欄に`width:100%;max-width:100%`を強いる**こと——中身なりの幅のままだと
  矢印だけが右端に居て欄から離れる。

そして**選び方そのものの作り直し**（利用者の指示の後半。ここが本題）:
24個を平らに並べると、目当ての形を**総当たりで探す**ことになる。
`WIDGET_GROUPS`（サーバーが持つ6つの束）で分類する:

| 束 | 何が同じか | 中身 |
|---|---|---|
| 開いて選ぶ | 押すと選ぶ面が開く。置き場所が狭くても選択肢を増やせる | プルダウン／メニュー／一覧／パネル |
| 並べて見せる | 選択肢が全部見えたまま選ぶ。数が少なく、迷わせたくないとき | ラジオ／セグメント／タブ／ボタン群／カード |
| 2択と順番 | 対になっているもの・順番に意味があるもの | トグル／入切／段階／切替 |
| 数を入れる | 打ち込む欄はそのまま。押して決める道具を添える | ステッパー／スピナー／スライダー／キーパッド／早見ボタン／メーター |
| 文字を書く | 自由記述の欄 | メモ／1行／定型文 |
| 自動で入る値 | 画面が値を入れる欄。選ぶ道具は要らず、見せ方だけを決める | 文字だけ／強調 |

**その型で選べない形は最初から出さない**（`opWidgetsFor()`）ので、数値の欄には
「並べて見せる」の束がそもそも現れない——**空の見出しを残さない**（§4）。

**語彙はサーバーだけが持つ**（`widget_group_of()`。§9.163の`LIMIT_SOURCES`と
同じ作法）——画面へ写すと、形を1つ足すたびに2箇所直すことになる。
**束が1つしか無いときは平らな格子へ落とす**（束が1つだけの見出しは、
情報を1つも足さずに1行を消費する）。**知らない綴りは「その他」へ**——
黙って捨てると、古い保存値を持つ端末でその欄だけ選ばせ方が空になる（§9.204）。
**いま選んでいるものは束の中で名乗る**（畳んだ束の中に居ると、
「選んだはずのものが見当たらない」になる・§2）。

#### ② 子ロットごとの統計——**入れた機能ではなく既定を疑う**

§9.247 ②で入れたものは全部動いていた（`[繰返]`列の移行も、
`rpRepeatLots()`も、`WL.reportStat.lots()`も）。それでも利用者からは
**何一つ変わって見えなかった**。理由は2つの既定が重なっていたこと:

1. `rpInitialHidden()`が**`測定値の統計`を常に隠していた**（§9.244で
   「今まで無かった塊なので現場の紙を勝手に増やさない」と決めた——
   **その判断自体は正しい**）
2. `[繰返]`の既定は`''`＝繰り返さない

つまり**「出す」を押して、さらに「子ロットごと」を選んで初めて見える**もので、
どちらも**設定画面の奥にある**。利用者は「対応をお願いします」と2度書いた。

直したのは**既定を場面で分けた**こと:

```js
function rpInitialHidden(){
 const solo=RP_MEAS_GROUPS.map(gr=>rpMeasSoloKey(gr.g));
 return rpHasSplitLots(rpLotForDefaults())?solo:solo.concat([RP_STAT_BLOCK]);
}
```

**異幅分割で子ロット番号が複数あるロットのときだけ既定で出す**。
そのときこそ子ロットごとのMIN/MAXが要る場面で、**分割の無いロットの紙は
1枚も増えない**（§9.244の判断を撤回しない）。判定は`rpStat()`の1箇所を通す
（別の数え方をすると、紙の中で条番号とロット№の対応が2通りになる・§9.244）。

**既定は「一度も配置を触っていない設備」にしか効かない。** 既に配置を保存して
ある設備では`hidden`に焼き付いているので、子ロットが複数あるロットを開いても
紙は増えない——そこで**先回りして画面で言う**（§2）: 帳票の帯に
`#rpSplitHint`＝**「子ロット◯件 統計を出す」**を出し、押すとその塊だけを
`hidden`から外す（§9.212 ②。他の塊の設定は触らない）。**紙に注意書きを
刷らない**——直す場所は画面なので、案内も画面に置く。

**確かめるときは紙になる節そのものを見ること**——`WL.reportStat.lots()`が
値を返すかだけを見る網は、**既定で隠したままの実装でも通る**（前回まさに
それで通っていた）。固定は`tests/test_rpprint.js`。

#### ⑥ 見せる範囲を「実施した設備」で絞る

実測すると、**データ一覧には設備の条件が1つも無かった**——`mergedRecords()`は
「端末内の全件＋共有DBの見出し全件」で、共有DBには全設備ぶんが入る（§9.91）。
設備Aの端末で開けば設備Bの測定がそのまま並ぶ。実績データには設備の選択欄が
あったが**既定が「すべての設備」**だった。作業スケジュール表は元から設備単位
（利用者の「これは既に対応済みと思いますが」のとおり）。

- **絞る鍵はこの端末の使用設備**（`AccessMeasurementConfiguredEquipment`）。
  記録側は`registeredEquipment`／`remoteEquipment`／`basic.equipment`の順で
  引き、**`normalize('NFKC')`してから比べる**（全角/半角のゆれ・§9.239 ⑥）。
- **設備の記録が無い古いデータは隠さない**（`!own||own===eq`）。
  隠すと、そのデータに設備を書き足す手立てが画面から消える（§9.15と同じ作法）。
- **黙って絞らない**（§3・§8）——`#recordScopeBtn`が**設備名**と
  **伏せている件数**を文字で名乗る。押すとすべての設備、もう一度押すと戻る
  （**片道にしない**）。覚えは`MeasurementRecordScopeV1`＝この端末。
- **使用設備が未登録の端末では絞らず、押せなくして理由を書く**（§4）。
  絞る材料が無いのに絞ると、その端末では一覧が常に空になる。
- 実績データは`loadPref()`の既定を使用設備にした。**覚えがあればそちらが勝つ**
  ——`hasOwnProperty(v,'equipment')`で見ること。真偽値で見ると、
  「すべての設備」を明示的に選んだ人の`''`が拾えず、開くたびに戻される。
  候補に無い設備は`syncHead()`が先頭へ足すので、実績が1件も無い設備を
  選んでいても黙って別の設備の実績が出ることは無い（§9.204と同じ罠）。

固定は`tests/test_eqscope.js`。**材料は自分で注ぎ込むこと**——検証用DBに
他設備の記録がある保証は無く、「無ければ素通り」の書き方だと直す前でも通る。
**古い実装を注ぎ込んで3件落ちることを確認済み。**

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **列の並びは「描くときに絞り、保存するときは絞らない」**（§9.248 ③、
  利用者の指摘「一覧表関係（仕掛一覧、品質データ、作業スケジュール表など）の
  表示列が一部表示されなかったり消えていることがあります」）: 一覧は横に
  見えている列しか本文を作らず（§9.104）、スケジュール表は並びに載っている
  列だけを描き、データ一覧は既定の15列だけ出す（§9.162）——**どれも描き方
  としては正しい**。壊れていたのは、**その絞ったあとの一覧をそのまま保存の
  `order`にも渡していた3箇所**（`bindColumnHeaderTools`の`persist()`／
  `persistTimelineColumns()`／列の設定パネル）。`order`は**全置換**
  （§9.212 ②）なので、痩せた並びを1回送った時点で落ちた列はマスタから消え、
  次に開くと「知らない列」として末尾へ回り、幅・表示名・書式・読み替え・
  計算式も一緒に失われる（§9.110・§9.113の再発。今度はデータ列側）。
  **列幅を少し引いただけで起きる。** 直し方は3箇所とも同じ——**保存済みの
  並びを土台に、今ある列のうち載っていないものだけを後ろへ足す**
  （スケジュール表は保存専用の`timelineOrderForSave()`を別に持ち、
  描画用の`timelineColumnKeys()`は絞ったまま。**絞る側を緩めないこと**
  ——緩めると隠した列が画面に出る）。列の設定パネルの`orderForSave()`は
  **元の隣へ挿し直す**（末尾へ回すと次に開いたとき並びが変わって見える）。
  **確かめるときは必ず列を隠した状態から保存すること**——全部出ている状態で
  保存する網は直す前でも通る（既存の網7本が全部通っていた）。
  固定は`tests/test_colkeep.js`。
- **列の絞り込みは「出どころ」と「表示中/非表示中」の2軸**（§9.248 ④、
  利用者の指示）: §9.105の3分類（元データ／結合／計算・操作）へ状態の軸を
  足す。**2つの軸はAND**——1つの列に混ぜると排他になり「結合の列のうち、
  いま出していないものだけ」が書けない。**件数は必ず文字で出す**（§3）、
  **同じ札をもう一度押すと外れる**（外す場所を別に作らない）、
  **開いたときは絞らない**（覚えると次に開いた人が「列が減った」と読む）、
  **チェックを付け外ししたら札の件数を描き直す**（忘れると「非表示中 3」と
  出ているのに一覧は2件になる）。軸の境目は縦線1本で**形で言う**。
  **札を1枚足したら`#lcOrigins`の中を数えている網を全部直す**——
  `test_lcpanel`・`test_reccols`・`test_sccontent`の3本が
  `.lc-origin-chip`を**全部**数えていたので、軸を1本足した時点で落ちた。
  数えるときは**軸ごとに`[data-origin]`／`[data-state]`で分ける**
  （混ぜると、次に軸が増えたときにまた3本まとめて落ちる）。
- **選択肢の「よく使う順」は並べる余地のある形だけ**（§9.248 ⑤、利用者の
  指示「プルダウンリストなど、新しい表示領域を作って表示するタイプのUIに
  ついては…使用回数の多いものほど上に来るようにすれば非常に使いやすくなる」）:
  `[選択肢の並び]`が`''`（登録順＝既定）か`よく使う順`で、回数は
  `操業データ選択肢マスタ`の`[使用回数]`。**効くのは`CHOICE_ORDER_WIDGETS`
  （プルダウン／一覧／メニュー／パネル）だけ**——セグメントやボタン群は
  並びが画面の形そのものなので、使うたびに札が動くと**筋肉記憶が毎回
  裏切られる**。**並べる余地の無い形では設定を残したまま登録順で出し**、
  盤では押せなくして理由を書く（§4・§9.132と同じ作法）。並びは
  `choice_list()`の1箇所で、**安定ソート**なので同点は登録順のまま
  （回数のあとに名前で並べ直さないこと）。**数えるのは人が選んだときだけ**
  ——`wireChoiceUsage()`は`document`へ委譲した`change`1つで、
  **`e.isTrusted`で絞る**（記録の復元・プリセットの当て込みは`.value`への
  代入なので数えない。数えると開き直すたびに前回の値が先頭へ固定される）。
  口は**読み取り専用のPOST**（`_READ_ONLY_POST_ENDPOINTS`）——書込扱いに
  すると閲覧モードの端末だけ回数が増えない。
- **選ばせ方は束ねて出す。語彙はサーバーが持つ**（§9.248 ①、利用者の指示
  「UIの選択自体もUIでもう少しグルーピングや階層を持たせて似たようなものを
  まとめわかりやすく選びやすく配置してほしい」）: 24個を平らに並べると
  目当ての形を総当たりで探すことになる。束は`WIDGET_GROUPS`／
  `widget_group_of()`の**サーバー1箇所**（§9.163の`LIMIT_SOURCES`と同じ
  作法。画面へ写すと形を1つ足すたびに2箇所直す）。分け方は6つで
  「開いて選ぶ（押すと選ぶ面が開く）／並べて見せる（全部見えたまま選ぶ）／
  2択と順番／数を入れる／文字を書く／自動で入る値」。**その型で選べない形は
  最初から出さない**ので、数値の欄に「並べて見せる」の束は現れない（§4）。
  **束が1つしか無いときは平らな格子へ落とす**（束が1つだけの見出しは情報を足さずに1行を消費する）。
  **知らない綴りは「その他」へ**（黙って捨てると古い保存値の端末でその欄
  だけ空になる・§9.204）。**いま選んでいるものは束の中で名乗る**（§2）。
  足したのは`パネル`（画面中央に浮くマス目。`一覧`の大きな窓と`メニュー`の
  細い帯の**あいだ**）と`スピナー`（数値の欄の右端に矢印を重ねる。
  `ステッパー`と役割は同じだが**欄の下に段を作らない**）——**器は
  `margin-left:auto`で寄せる**（`align-self:flex-end`は効かない。
  `.opf-host`は常にflexとは限らない）、**欄に`width:100%;max-width:100%`を
  強いる**（中身なりの幅だと矢印だけが右端に居て欄から離れる）。
- **同じ指摘が2度来たら、入れた機能ではなく既定を疑う**（§9.248 ②、利用者の
  指示は§9.247 ②と一字一句同じ）: 子ロットごとの統計は前回で全部動いていた
  （`[繰返]`の移行も`rpRepeatLots()`も）。それでも何も変わって見えなかったのは
  **既定が2つ重なっていた**ため——`rpInitialHidden()`が`測定値の統計`を常に
  隠し（§9.244「今まで無かった塊なので紙を勝手に増やさない」。判断自体は
  正しい）、`[繰返]`の既定も`''`。つまり設定画面の奥で2回選んで初めて見える。
  **既定を場面で分ける**——`rpHasSplitLots(rpLotForDefaults())`のときだけ
  出し、**分割の無いロットの紙は1枚も増やさない**（§9.244を撤回しない）。
  判定は`rpStat()`の1箇所（別の数え方をすると紙の中で条番号とロット№の
  対応が2通りになる）。**既定は「一度も配置を触っていない設備」にしか
  効かない**ので、保存済みの設備には**先回りして画面で言う**（§2）
  ——`#rpSplitHint`＝「子ロット◯件 統計を出す」を帳票の帯に出し、押すと
  その塊だけを`hidden`から外す（§9.212 ②。他の設定は触らない）。
  **紙に注意書きを刷らない**（直す場所は画面なので案内も画面に置く）。
  **確かめるときは紙になる節そのものを見ること**——`WL.reportStat.lots()`が
  値を返すかだけを見る網は**既定で隠したままの実装でも通る**（前回まさに
  それで通っていた）。固定は`tests/test_rpprint.js`。
- **見せる範囲は「実施した設備」で絞る。設備の無い記録は隠さない**
  （§9.248 ⑥、利用者の指示「データ一覧や実績データ…実施した設備ごとに
  見せる範囲を変えたい。設備設定を変えても他の設備の情報が表示されていたら
  混乱してしまいデータも混ざってしまうと問題になる」）: **データ一覧には
  設備の条件が1つも無かった**——`mergedRecords()`は端末内の全件＋共有DBの
  見出し全件で、共有DBには全設備ぶんが入る（§9.91）。実績データは選択欄が
  あったが**既定が「すべての設備」**だった。鍵はこの端末の使用設備で、
  記録側は`registeredEquipment`／`remoteEquipment`／`basic.equipment`の順に
  引き**`normalize('NFKC')`してから比べる**（全角/半角のゆれ・§9.239 ⑥）。
  **設備の記録が無い古いデータは隠さない**（`!own||own===eq`）——隠すと
  設備を書き足す手立てが画面から消える（§9.15と同じ作法）。
  **黙って絞らない**（§3・§8）——`#recordScopeBtn`が設備名と伏せている件数を
  文字で名乗り、押すとすべての設備・もう一度押すと戻る（**片道にしない**）。
  覚えは`MeasurementRecordScopeV1`＝この端末。**使用設備が未登録の端末では
  絞らず、押せなくして理由を書く**（§4。絞る材料が無いのに絞ると一覧が常に
  空になる）。実績データの既定も使用設備にしたが、**覚えがあればそちらが勝つ**
  ——`hasOwnProperty(v,'equipment')`で見ること（真偽値で見ると「すべての設備」を
  選んだ人の`''`が拾えず、開くたびに戻される）。固定は`tests/test_eqscope.js`
  ——**材料は自分で注ぎ込むこと**（他設備の記録がある保証は無く、「無ければ
  素通り」の書き方だと直す前でも通る）。
