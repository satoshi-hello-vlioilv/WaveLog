# §9.67 作業可否フラグを予定側の保存値で作る(判定の情報源を作り直す)

§9.51で入れた作業可否フラグは「スナップショットは古くなるから使わない。
毎回、現在の仕掛データを引いて判定する」という作りだった。この判断が
遅さとちらつきの原因だった。

**何が起きていたか**

- 仕掛一覧から投入したロットは、**投入したその行に残仕掛設備ｺｰｽが載って
  いる**。それを使えば往復ゼロで判定できるのに、仕掛を500件ずつ何ページも
  辿り直していた(実測10往復・3秒超)。フラグは辿り終わるまで「?」のまま。
- `invalidatePlanCache()`が`invalidateWorkable()`で索引を**丸ごと捨てて**
  いたため、予定を1件足すたびに全行が「?」へ戻り、しばらくしてまた変わる、
  というちらつきが出ていた。
- 取り直しの対象が「予定の全ロット」だったため、既に可と分かっている行まで
  毎回引き直していた。

**性質を使って整理する**

工程は前へしか進まない。投入時点で「可」(残仕掛設備ｺｰｽがこの設備で始まる)
だったロットは、その後この設備から出ていくことはあっても、「まだ来ていない」
状態へ戻ることはない。つまり:

- **可はそのまま信用してよい**(取り直さない)
- **不可・?は取り直す**(工程が進んで到着した可能性がある)

**作り直した形**

1. 予定投入時に残仕掛設備ｺｰｽをdetailへ保存する
   (`buildScheduleDetail`が元からalias名・生カラム名の両方で保存しており、
   単発追加・一括追加・ドラッグ投入のすべてが同じ関数を通る)。
2. `workableOf()`は**索引 → 保存値**の順で解決する。保存値があるので、
   仕掛一覧から投入した予定は往復ゼロで最初の描画から確定する。
3. 取り直しの対象は`lotsNeedingLookup()`＝**可になっていない行だけ**。
4. 取り直した値は索引へ**併合**する(作り直さない)。`invalidateWorkable()`も
   鮮度の印を落とすだけで、分かっている値は捨てない。
5. 対象が`WORKABLE_DIRECT_MAX`(8件)以下ならページ送りせず、ロット単位の
   絞り込みだけで済ませる(1件追加した直後に全件を辿り直さないため)。
6. 取り直した値は`rememberCourseOnEntries()`でその予定のdetailへ書き戻す
   (同一セッション内で引き直さずに済む)。共有DBへは書かない
   — 1件ごとに取得→適用→反映のサイクルが要るため。
7. 利用者が押した**「再計算」だけは可も含めて全件検証する**
   (`revalidateAll`)。普段は可を再確認しないが、利用者が明示的に最新を
   求めた操作では情報源そのものを取り直すのが筋。裏の2分見張りは
   可でない行だけを追いかける。

**実測**(仕掛2007件・予定446行)

| 場面 | 修正前 | 修正後 |
|---|---|---|
| 仕掛一覧から1件追加 | 索引を作り直し(最大10往復・3秒超)、その間「?」 | **往復0回**・最初の描画から「可」 |
| 続けて3件追加 | 追加のたびに全件走査 | **往復0回** |
| 既存行のフラグ | 追加のたび「?」へ戻る | 戻らない(可290→291) |
| 画面を開き直した直後 | 全行「?」から開始 | 保存済みの行は即確定・仕掛は未読(pages=0) |

保存値を持たない古い予定(検証用にAPIで直接作ったもの等)は従来どおり
裏の取り直しで確定する。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **新しいキャッシュは`WL.ttlCache()`を使う**（`base.js`）。期限切れの判定・件数の
  上限・取得中のPromise共有（同時呼び出しを1回にまとめ、失敗したPromiseは
  捨てて再試行できるようにする）を持つ。**既存のキャッシュは置き換えない**
  ——それぞれ無効化の条件が業務仕様と絡んでおり（例: §9.67の作業可否は
  「一度可になったら再取得しない」）、一括置換はその仕様を落とす。
