# §9.101 「ログ・診断」の診断の側（接続の1段ずつ）

**画面名の半分が空だった。** §9.99でログは読めるようにしたが、画面名は
「ログ・診断」なのに診断が無かった。`/api/db-diagnose`(§9.75)は前から
あるのに**画面からの参照は0件**で、現地の切り分けは今もURLの直打ち
だった。器はできているので、ここへ繋ぐ。

**何を見せるか。** DBを開くまでを1段ずつ試し、どこで止まったかを出す
(親フォルダの存在確認 → ファイルの存在確認 → stat → resolve → 1バイト
読む → URIの組み立て → 接続)。**読むだけで設定は変えない。**

**「走った」と「答えが是」は別物。** `Path.exists()`は例外を出さなければ
`ok=true`だが、値が`False`なら「無い」という答え。ここに✓を付けると
**見た人が成功と読む**(実装直後の画面が実際にそう見えた)。印を3つに分ける。

| 印 | 意味 |
|---|---|
| ✓ | 走って、答えも是 |
| − | 走ったが、答えが「無い」 |
| × | 例外で落ちた |

**最初に転んだ段階が原因**で、その先は道連れ。原因だけを強く出し、以降は
薄くする(全部を赤くすると、どれを見ればよいか分からなくなる)。見出しにも
`「〈段階名〉」で止まった`と最初の1つを名指しする。WinErrorがあれば添える
——現地では番号が決め手になる(§9.75の`WinError 59`が実例)。

**開くまで共有へ触らない。** 既定は畳んである。応答の遅い共有フォルダを
画面を開いただけで叩くと、ログを読みに来ただけの人を待たせる。

**対象の選択肢はサーバーが返す**(`/api/db-diagnose`の`targets`)。画面へ
決め打ちすると、データソースを増やしたときに画面だけ古いままになる
(§9.87と同じ轍)。

固定は`tests/test_logview.js`。畳んで始まること・開くと段階が出ること・
選択肢がサーバー由来であること・手元のDBは全段階を通ること、そして
**失敗の描き分け**(答えが「無い」に✓を付けない・例外は×・2件目以降は
薄い・WinErrorを添える)。描き分けは応答を差し替えて確かめる——検証用
フィクスチャでは仕掛DBも手元に実在して全段階通ってしまい、試せないため。
