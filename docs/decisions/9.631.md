# §9.631 測定実績の一覧を素直な横送りに・入れた操業データが空になる不具合・作業開始と終了を予定の実績で補う・ダッシュボードの作り直しを止める（利用者の指示）

索引: [決定記録](README.md)｜前: [§9.630](9.630.md)｜関係: [§9.630](9.630.md)・[§9.628](9.628.md)・[§9.611](9.611.md)・[§9.514](9.514.md)・[§9.94](9.94.md)・[§9.594](9.594.md)

## 経緯（利用者の言葉）

> １）「測定実績」リスト表示画面の不具合修正: 横スクロールしたときに固定される部分とスクロールする部分があり気持ち悪いので、変に固定せず素直な挙動にしてわかりやすい列表示にしてください。列も見切れが多くみられ、横スクロール操作後はさらにレイアウトが崩れてしまいます。
> ２）測定データの登録がなくても、作業開始時刻と作業終了時刻の欄は列に出せるようにしてください。現状、入力してあるはずの操業データや測定データで打ち込まれたなどがほとんど表示されておらず、すべてを対象にしたいです。ガントチャートの作成に必要な入力していれるべき作業開始時刻と作業終了時刻のデータ列も見当たりません。見つけていないだけであれば列の種類ごとわかりやすく表示する方法も検討してください。
> ３）ダッシュボード計算処理が非常に遅いです。データの取得元確認と処理の高速化も検討してください。
>
> （作業の途中で）高速化検討の際は、共有に触れる部分を特に注意し、スケジュール作成の不具合が発生しないように気を付けてください。

## ② 入れた操業データが一覧に出ない——不具合だった

- **物差し**（`test_aclayout`）: 操業データ項目マスタの自由項目ぜんぶ（見本の設備で27項目）に値を入れた記録を置き、一覧に**値つきで**出た項目の数。
  **直す前 0/27 → 直したあと 27/27**。
- 原因: 抜粋（`actuals._extract()`）は操業データを`settings`から分けて`item['opData']`へ置くのに、候補の道`settings.opData.<項目名>`は
  字のまま`item['settings']['opData']`を辿っていた。**記録に値があっても必ず空**で、画面はそれを「この期間に値の無い列」として表から外していた
  （利用者の画面の「この期間に値の無い列 48」のほとんどがこれ）。道の読み方は`_FLAT_BOXES`の1箇所（道の頭 → 抜粋の中の入れ物）にした。
- **前の網（§9.630 の`test_acinput`）が通した理由**: 「出ている」を見出しにあるか・畳んだ列の名前の一覧にあるかで数え、**値が出ているか**を数えていなかった。
  さらに網が置いた項目はマスタに無い名前で、マスタに無い項目だけが通る別の道（記録の`opData`を直に読む）を通っていた。
  今回の物差しは**置いた値（正解）を分母**にする（一覧自身の答えで分母を作ると、空で返る列は分母からも消える）。
- 同じ道をダッシュボードの測定データの写しも使うので、ダッシュボードでも操業データの列は空だった。さらにダッシュボードは候補の項目を`key`で読んでいて
  （候補は`path`しか持たない）、**候補の列が1本も入っていなかった**（芯の18列だけで数えていた）。両方を直した。

## ② 作業開始・作業終了を予定の実績で補う

- 前は記録の打刻（測定画面の「作業開始」「作業終了」）だけだった。作業スケジュールの「開始」「終了」（§9.611）・手で入れた時刻（§9.514）・
  取り込んだ時刻（§9.595）で作業していると、記録に時刻が無く、列は「値の無い列」として外されていた。
- いまはその記録が当たった予定の行（`actualRecordId`）の実績で、**記録に無いほうだけ**補う（`actuals._with_plan_times()`）。
  答えはダッシュボードのガントと同じ（作業予定の写し`sources.plan_rows()`の列「作業開始」「作業終了」「実績の出どころ」・鍵は新しい列「記録ID」）。
  出どころは列「時刻の出どころ」（測定画面／開始判定／手入力／実績データ（取り込み）…）。現場日・直も補った時刻で決める（期間で絞れる）。
- 作業開始・作業終了は**値が無い期間でも外さない**（`keep`）。
- **分からないこと・変えていないこと**: 予定の行に記録が当たり、その記録に打刻が無いとき、予定の計算（`schedule_calc`）は手で入れた時刻を使わない
  （`manual`は記録が当たっていないときだけ）。ガントにも出ない。スケジュールの答えを変えることになるので今回は触っていない（利用者の注意「スケジュール作成の不具合が発生しないように」）。

## ① 素直な横送り・見切れ

- **物差し**（`test_aclayout`、1728×1152 と 1536×864、左端・中ほど・右端で）: 留まる列・見出しの切れ・値の切れ・地と罫線の途切れ・見出しと値のずれ。

| | 直す前 | 直したあと |
| --- | --- | --- |
| 横に送ると留まる列 | 9 | 0 |
| 値が切れるセル | 22.2% | 0% |
| 送った後に地と罫線が途中で途切れる行 | 7（全部） | 0 |
| 見出しの字の切れ・列のずれ | 0・0px | 0・0px |

- 崩れの仕組み: 行（`.ac-row`）の箱が一覧の**見える幅**しかなく、列はその外へはみ出して描かれていた。横に送ると、留めたはずの列（§9.630 の「記録の基本」）は
  行の箱と一緒に流れて消え、縞・罫線・選んだ印は箱の右端で途切れた。いまは行の箱＝列の合計の幅（`width:max-content`）で、留める列は持たない。
- 列の幅は中身から数える（一覧と同じ`WL.list.estimateColumnWidth`の1箇所・描かずに数える・上位1割を外した長さ・上限320px）。前は`minmax(…,1fr)`で
  上限が下限の1.6倍だったので長い値が「…」で切れた。字幅の表は測定実績の器の書体で作る（引数`el`）。

## ③ ダッシュボードの作り直しを止める

- **物差し**（`test_dashperf`）: 既定のダッシュボード（7枚）を1回描くあいだに材料（測定データ・作業予定の写し）を作り直した回数と時間。

| | 直す前 | 直したあと |
| --- | --- | --- |
| 1回目 測定データ／作業予定 | 5回／2回 | 1回／1回 |
| 2回目（材料が同じ） | 5回／2回 | 0回／0回 |
| 合計（見本のデータ） | 約660ms／約470ms | 309ms／33ms |

- 原因: `_made_for()`は署名を比べる**前に**全部の記録・全部の予定から行を作っていた（署名が同じならファイルを書かないだけ）。画面は7枚を同時に問い合わせ、
  1分ごとに全部を引き直すので、パネルの数だけ同時に作っていた。作り直しの量は記録の件数×列の数（候補の列を入れたので1回は重くなる。3,000件×250列で値を引くのに約0.6秒）。
- いまは**材料の指紋**（`_inputs()`）が同じなら作らない。測定データ＝記録の読みの版（`db_access.backup_rows_version()`）＋master.sqlite3 の署名、
  作業予定＝それに手元の予定の写しの署名と「いまの分」。元ごとに作るのは同時に1本（錠）。指紋は作った後に取り直す（作る中で手元の写しが新しくなるため）。
- **共有に触れる回数は前より減った**: 指紋は手元のファイルだけを見る。共有の予定を写し直すか確かめる（`fetch_snapshot()`）のは作り直すとき＝1分に1回まで
  （前はパネル1枚の問い合わせごと）。書き込みの道（予定の作成・並べ替え・書込役）には触っていない。
- 網が読み口を差し替えたら`answer.forget()`で写しの控えも捨てる（データを入れ替えたとき捨てる口を1つにした）。

## 画面の作り（E の手順）

各回5案、1728×1152 と 1536×864 で左端・中ほど・右端へ送って撮り、自分で画像を確かめてから別のエージェントが採点した（採点表は §9.630 と同じ: 加点＝わかりやすさ25・
視覚化15・美しさ15・統一感10・使いやすさ20・正しさ／読みやすさ15、減点＝隠れる・切れる・重なる／同じ情報が2か所／押せそうで押せない／色だけ／大きな空き／1536 で崩れる／留まる列）。

| 回 | 案 | 最高 | 主な指摘 |
| --- | --- | --- | --- |
| 1 | 帯の名前を群の左端だけ／群の中でついて動く／種類の色／列の種類の札／札だけ | 70（札＋帯） | 送った先の左右の端で列が字の途中で切れる・「いまどこ」と「どう行く」が別の部品で情報が重なる・⇅ の位置が列で違う |
| 2 | 案内図（区画＝列の数）／帯＋直し／札だけ（塗り）／案内図（区画＝実寸）／札＋帯（名前だけ） | 77（案内図） | 区画が同じ幅に見える（**私の実装漏れ**）・実寸に比例させると「準備で決めた値」が潰れる・範囲の枠が名前に重なる |
| 3 | 区画＝名前の幅＋残りを実寸に比例・範囲は名前の下の別の帯（V11）／列数を title へ／値なし・伏せた列を区画で続ける／右上に「あと N列」／範囲の帯を上に | **85（V11・合格）** | 範囲の帯が細い・影が表の下まで伸びる |

- 共通で入れた直し: 横送りは列の左端で止める（`scroll-snap`。掴んで送るあいだは外す）・⇅ はどの列も名前の右・右に列が続くときは右端に影。
- 入れたあと（帯 6px・影は行のある高さだけ・数の列の ⇅ の余白）の前後の採点（同じ採点者・同じ採点表）: **前A（元のまま）50 → 後 86**、
  前B（サーバーだけ直し画面は元のまま＝列が多いとき利用者が見ていた崩れ）54。
- 残る指摘（直していない）: 右端の列が切れているのは影でしか言わない（淡い）・右端まで送り切ると左端は列の途中になる（`scroll-snap`の仕様）・
  時刻の無いセルは空（「—」にすると揃って見える）・範囲の帯の右端が「伏せている 72列」の手前で終わるので「ここで全部」と読める。

## 踏んだ誤り

- `sqlite_io.connect()`へ`str`を渡して一覧が読めなくなった（`Path`の約束）。網が理由を出すようにして見つけた。
- 帯の名前を群の中でついて動かす sticky が効かなかった: 帯のセルが`overflow:hidden`で、それが sticky の基準の箱になる。`overflow:clip`は箱を作らない。
- 2回目の案 v6 で、区画の幅を列の数に比例させる指定を入れ忘れ、全部の区画が同じ幅で採点された。
- 右端の札が見えなかった: 見出しの行（sticky・z-index 2）と同じ重なりの文脈にいた。
- 列の案内を押した後の網の待ちを「送り始めた（scrollLeft>0）」で書き、1536 で1回落ちた。押した物そのもの（区画が範囲に入った）を待つ形に直して2回とも通った。
  落ちた1回が「送った直後で範囲の印の塗り直しがまだだった」ためかは確かめていない（**分からない**）。
