# §9.47 起動ステップの可視化

「起動時の『接続を確認中』がかなり長い」という指摘の原因は、**その表示が
実際の進捗ではなかった**こと。待機画面(`loading.html`)はサーバーより先に
`file://`で開かれるためAPIを叩けず、段階表示を**経過秒数だけ**で切り替えて
いた(`sec<2`→実行環境、`sec<5`→準備中、それ以降は全部「接続を確認中」)。
共有の応答が遅いほど、この「何も言っていない表示」に留まり続ける。

`backend/boot_status.py`を新設し、起動処理が段階ごとにアプリ直下へ小さな
JSファイル(`boot_status.js`)を書き出すようにした。待機画面は0.5秒ごとに
`<script src>`で読み込む(`file://`同士なので`fetch`は使えない)。

| # | 段階 | 何を待っているか |
|---|---|---|
| 0 | 実行環境を確認 | ログ・作業ディレクトリの準備 |
| 1 | 起動中のアプリを確認 | ポート5029の二重起動チェック |
| 2 | 必要な部品を確認 | 依存パッケージ |
| 3 | データの置き場所を確認 | パス設定・**共有の応答**(ここが遅い) |
| 4 | アプリを読み込み | Flaskアプリのimport |
| 5 | Webサーバーを起動 | 待ち受け開始 |

- `report()`は書き込みに失敗しても**黙って続ける**(表示の都合で起動を止めない)。
- 段階は**後戻りさせない**(古いファイルを拾っても表示が巻き戻らない)。
- `detail`に「何を待っているか」を添え、経過秒数の隣に出す。
- `/api/ready.js`(サーバーが応答した時点)で`boot_status.clear()`。次回起動時に
  前回の内容が一瞬見えるのを防ぐ。`.gitignore`済み。

起動そのものの短縮としては、`warn_if_shared()`(実績DBがネットワーク共有上に
無いかの確認。`records.exists()`が共有パスだと待たされる)を**デーモンスレッドへ
逃がした**。警告を出すだけの処理で、サーバーの待ち受け開始を待たせる理由が
無い。
