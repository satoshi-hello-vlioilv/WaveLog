# §9.517 設備停止が入る位置の答えを1箇所に——選んだ位置でなく前に入れた位置へ入っていた（利用者から届いた不具合報告）

索引: [決定記録](README.md)

## 報告

「作業スケジュール一覧で、停止項目を選択して追加すると選択した位置に入らずページの先頭位置に項目が入ります。」
（利用者の指示「真偽を確かめて本当であれば修正をお願いします」）

## 真偽: 本当だった

「スケジュールだけ」の見え方で、行間を押して位置を選び、設備停止を追加した。**1件目は選んだ位置へ入るが、
2件目からは、選んだ位置にもボタンの字にも関係なく、1件目の位置へ入り続けた**。現場では、先に入れた位置は
たいてい一覧の上のほう（いまの作業の近く）なので、「先頭に入る」と見える。

### 何が起きていたか——入る位置の答えが3つあった

| 読む場所 | 読んでいた値 |
| --- | --- |
| 帯の追加ボタンの字（`stopWhereText()`） | `scState.insertBefore`（いま選んでいる位置） |
| 実際に入れる位置（`commitStopPick()`） | 手順の控え `stopPick.before` |
| 入る時刻の見積（`stopInsertIndex()`） | 手順の控え `stopPick.before` |

控えは`openStopPicker()`が作り、**「既に控えてあるなら奪わない」**（停止内容の選び直しで、落とした位置を
消さないための約束）。ところが「続けて入れる」が既定で入っているので手順（`stopPick`）は追加のあとも残り、
**窓を閉じても捨てなかった**。そのため次に停止内容を押すと、前回の控えがそのまま引き継がれた。
字は正しい位置を言うので、画面を見ても気づけない。

## 測った（評価関数・`tests/test_stoppos.js`）

道ごとに ①選んだ位置 ②追加ボタンの字 ③サーバーに入った位置 の3つがそろうかを見た（テスト設備A・予定40件）。

| 道 | 前 | 後 |
| --- | --- | --- |
| ① 位置を決めずにボタンで開く（いちばん後ろ） | ○ | ○ |
| ② 行間 L0005 の前 | ○ | ○ |
| ③ 同じ窓で続けてもう1件（同じ位置） | ○ | ○ |
| ④ スクロールして行間 L0030 の前 | **×（L0005 の前へ入る）** | ○ |
| ⑤ もう一度ボタンで開く（いちばん後ろ） | **×（L0005 の前へ入る）** | ○ |

## 決めたこと

- **入る位置の答えは`stopBefore()`の1箇所**。帯の字・入れる位置・入る時刻の見積の3つがここを読む。
  - 行間を押して**位置を固定している間**（`insertPinned`）… その位置。続けて何件入れても同じ位置で、窓を閉じると外れる（§9.179 のまま）。
  - ボタンを表へ**落とした**… 落とした位置（`stopPick.at`）。**1回使ったら忘れる**（`takeInsertBefore()`と同じ約束——
    続けて入れる次の1件が、思い出しもしない位置へ入らないように）。窓を閉じても捨てる。
  - どちらも無い … いちばん後ろ。
- 手順が控えるのは**落とした位置だけ**。行間で固定した位置はその場で読む（控えると、固定を外しても古い位置が残る——今回の原因そのもの）。
- 停止内容を選び直すとき（`at`を渡さない）は、落とした位置を引き継ぐ（§9.389 の約束はそのまま）。
- 落とした位置は`scState.insertBefore`へ置かず、手順へ直に渡す（固定していない値を共有の変数に残さない）。

## 固定する網
- `test_stoppos.js` … 上の7つの道で、選んだ位置・帯の字・入った位置がそろう。直す前のファイルに戻すと ④〜⑦ の4件で落ちる（6/10）。
