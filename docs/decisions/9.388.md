# §9.388 分割なしのコイルの幅・条数は「仕掛データ」から読む（利用者の不具合報告）

利用者の報告:

> ロットの分割対象ではないものも、**元幅に対して製品幅は小さく幅何条取り**と
> いったデータは持っていますが、それをガイダンスでは活用しきれていません。
> 子ロットに分割する方だけは（正しく動いている）、ロットを分割しないものに
> ついては幅情報が正しく活用されておらず**1条取り確定**になってしまっている
> ので、**測定メイン画面の時のように仕掛データから連携して**データを使い、
> 修正をお願いします。

## 1. なぜ1条になっていたか——写しには最初から入っていない

条数を読む先は合っていた（`boxHorizontalCount` ＝ `BOX設計_横割数`）。
壊れていたのは**どこから読むか**である。

ガイダンスが読むのは予定の写し（`detail`）で、その写しは
`buildScheduleDetail(row)` が**一覧の行**から作る:

```js
Object.keys(WL.base.aliases).forEach(k=>{
  const v=pick(row,k); if(v!==undefined&&v!==null&&v!=='')detail[k]=v});
```

`row` は**仕掛一覧が持っている行**なので、**列表示マスタで一覧に出していない
列は、そもそも `row` に無い**。`BOX設計_横割数` は表に出す列ではないから、
写しにも入らない。`n(...)` が `null` を返し、`Math.max(1, …||1)` が 1 になる
——**条数がいつも1**。分割ありの側は子ロットが `__childStrips` を自分で
持っているので、この影響を受けていなかった。利用者の見立てのとおりである。

## 2. 同じ問題は測定画面が先に解いていた

`lot-split.js` の `refreshSelfSourceFull()` に、そのままの説明が書いてある:

> 横割数(条数)・縦割数(丈割数)の初期値(BOX設計_横割数/BOX設計_縦割数)も
> **列表示設定で一覧側から欠落し得る**ため、完全な生データから改めて
> 反映し直す。

やっていることは1つ——`fetchChildLotRow(lotNo)` で**完全な生データを取り直す**。
利用者の「測定メイン画面の時のように」はこれを指している。

## 3. 直し方——口を1つにし、判定は純粋な関数へ

**取りに行く口は1つ**（§CLAUDE「1箇所が答える」）。`fetchChildLotRow` は
外へ出ていなかったので、`WL.split.lotRow` として名前空間へ出した。
別の口を作ると、2つの画面で「完全な行」の定義が割れる。

**読み取りは純粋な関数**（`bladeSeedLots` と同じ作法・網が合成した行で直に
呼べる）。`WL.scheduleView.bladeLotsFromSource(row, lotNo)` が
板厚・元コイル幅・製品幅・条数を返す:

| 読めたもの | 返すもの |
| --- | --- |
| 幅と条数 | `[{w:製品幅, n:条数}]` |
| 幅だけ | `[{w:製品幅, n:1}]`（**幅が分かっているのに出さない、はしない**） |
| 条数だけ | `[]`（幅が無ければ条を作らない・§9.231 0で埋めない） |
| 条数が1〜40の外 | 採らない（**測定画面の`defaultHorizontalCount`と同じ範囲**） |
| 行が無い | `null`（写しの値のまま進ませる） |

条数の範囲を測定画面と合わせたのは、**2つの画面で条数の考えが食い違わない**
ようにするため。

## 4. 当てない場面を2つ決めてある

- **条の設計が記録済み**のとき（§9.387。記録のほうが新しい決定なので、
  取り直した値で黙って上書きしない）
- **1本目が分割あり**のとき（幅を持っているのは子ロット。§9.387で
  `headSplit` を返すようにしてあるので、それで見分ける）

取りに行って失敗したときは**理由を残して**写しの値のまま進む
（§9.328 黙って捨てない）——読めないことより、止まるほうが困る。

## 5. 網（`test_bladeui` 109→116件）

欠陥注入で確認: 条数を読まないように戻すと
`[{"name":"S1","w":120,"n":1,"parent":"S1"}]` ——**報告された
「1条取り確定」そのもの**の形で赤になる。

**フィクスチャの仕掛データには `BOX設計_横割数` も `BOX実績_板幅` も無い**
（34列で、あるのは `BOX設計_設備名` と分割の切断巾だけ）。実データにはある
ので、これは**フィクスチャが薄いだけ**である。列を足すと仕掛一覧の列数が
変わって他の網へ波及するため、**判定を純粋な関数へ切り出して、合成した行で
見る**形にした（取りに行くところは呼ぶ側の仕事）。
