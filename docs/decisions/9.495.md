# §9.495 共有の元ファイルに一瞬届かなくても諦めない——理由を残し、待って取り直し、早めに取り直す（利用者の報告）

索引: [決定記録](README.md)

## 経緯

利用者の報告「仕掛情報の最新版が取れない不具合がありました。ログを添付するので調査解析と修正をお願いします」
（別の端末・VER2.381.0）。画面には「元データを取り込めませんでした 共有の元ファイルへ到達できないため、前の写しを
使い続けます（前の写しで表示しています）／元データ 9/25 12:45」。

## ログから読めたこと

- 12:44:24 に起動。最初の周回では SIK* の5つに「写しました」が出ず、12:45:25〜28 に5つとも写せている。
- 画面の「元データ 12:45」は**最後に写せた元ファイル自身の更新時刻**（`source_info().at`）。元は 12:45 に
  書き換わっていた——**元は別のアプリがこまめに書き直している**。
- 「到達できない」は`os.stat()`が失敗したときだけ出るが、**理由（OSの答え・どの元か）は`debug`でしか書いておらず**、
  ログにも画面にも残っていなかった。

**原因は断定できない**（理由が記録されていないため）。最も筋が通るのは「押した『再読込』の1回の`stat`が、元の
書き直しの最中（Windowsでファイルが一瞬『無い／アクセス拒否』になる）に当たった」。起動直後に共有へのつなぎが
まだ整っていなかった可能性も残る。どちらでも効く形で直した。

## 測った（`tests/test_dbmirror.py`）

| 物差し | 前 | 後 |
| --- | --- | --- |
| 届かなかった理由に OSの答えと元の名前 | 入らない | `（NOT_THERE.sqlite3: Errno 2 No such file or directory）` |
| 元が0.6秒だけ消えて戻る間の「再読込」 | 写せない（到達できない） | 写せる（1.0秒） |
| 届かなかった周回のあと次の周回まで | 60秒（通常） | 10秒 |

## 決めたこと

1. 共有の元を見るのは`_remote_stat()`の1箇所。取れなければ**0.3・0.7・1.5秒待って取り直す**（合計2.5秒まで）。
   写す（`refresh_one`）も確かめる（`check_one`）も同じ1本を通る。
2. 届かなかったときは`_unreachable()`の1箇所が**元の名前とOSの答え**を理由へ入れ、ログへ`warning`で残す
   （同じ理由が続くあいだは重ねない）。自動のときは「10秒後に自動でもう一度取りに行きます」と次に起きることも書く。
3. 届かなかった元が1つでもあれば、次の周回を**`next_wait_sec()`が早める**（10秒）。「再読込」（要求の中）で
   届かなかったときも`_retry_at`で背景の周回を早める。待つあいだに見るのは手元の値だけ（共有へ触らない）。

## あわせて直した（同じログにあった）

「待機画面: 起動画面を写せませんでした: `<lambda>() got an unexpected keyword argument 'quiet'`」。
`copy_waiting_page()`は写し終えたあと`say(..., quiet=True)`を呼ぶが、起動の裏の写し直しが渡す`say`は`quiet`を
受けず、**写せたのに例外になり、逆のこと（写せなかった）をログへ残していた**。`say`の約束は
`say(m, bad=False, quiet=False)`（§9.431）。`say=lambda`で渡す箇所を網で数える（直す前1件→0件）。
