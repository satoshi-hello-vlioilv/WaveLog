# §9.336 更新履歴を「利用者向け」と「開発ログ」に分ける（REVIEW 3-12）

## 何が問題だったか

現場の人が開く「更新履歴」に、`tests/test_scsnapread.py`・§番号・中のファイル名が
並んでいた。開発の記録はコミットメッセージと `docs/decisions/` が既に持って
いるのに、**同じものを現場の画面にも出していた**（§CLAUDE 8「同じ情報を2箇所に
出さない」）。実測 450版・1,521件。

## 決めたこと

**版ごとに `'dev': True` を宣言する。** 画面は既定でその版を伏せ、
「開発の記録も出す（N版）」で出せる（**消さない**——伏せるだけ・§4）。

- 付けるのは**構造の改善だけの版**（画面・サーバーの動きが1つも変わらない版）。
- **不具合を直した版には付けない。** 中身が内部の話でも、直ったこと自体は
  利用者に見える変更——VER2.206.0 は「作業スケジュールが開けない」、
  VER2.214.0 は「タブの中身が入れ替わる」を直した版で、どちらも
  「テストの名前が並んでいるから開発ログ」に見える。**中身の語彙で分けない。**
- 答えるのは `changelog_data.is_dev()` の1箇所（§9.163）。`/api/changelog` が
  `dev` と `devCount` を返し、**画面は `e.dev` を読むだけ**。
- **宣言が無ければ利用者向け。** 伏せる側へ倒すと、宣言を忘れた版が黙って
  現場から消える。

## 撤回した案

**「注記1件ずつを機械で分ける」はやめた。** `tests/`・§・パス・拡張子を
含む注記を開発ログとする案を実測すると 1,521件中131件（8%）が当たったが、
**1つの版の物語が割れる**——VER2.218.0 は4件のうち3件が当たり、残った
「画面・サーバーの動きは1つも変わりません」だけが現場に出る（何の話か
分からない）。版は1つのまとまりなので、分けるなら版の単位。

**「全部が開発ログの版を機械で見つける」もやめた。** 43版が当たるが、その中に
VER2.206.0（作業スケジュールが開けない不具合の修正）が入っていた。
**語彙は「誰に向けた話か」を語らない。**

## 版そのものは上げ続ける

「利用者に見える変更だけ版を上げる」という案は採らなかった。版は
「**どのコードが実際に動いているか**」を見分ける手掛かりでもあり
（§9.316 の起動の状況・画面のバッジ）、上げないと現場から「更新が届いたか」を
確かめられなくなる。**上げたうえで、更新履歴での見え方だけを分ける。**

## いま動いている版は伏せない

開発の記録の版であっても、**いま動いている版だけは必ず出す**。伏せると
「いま動いている版」の印が画面から消え、現場が唯一持っている手掛かりが
無くなる（実際に VER2.218.0 が dev だったため、最初の実装で印が消えた。
`test_changelogui` が拾った）。件数の文とボタンの数字も、その1版を引いた数で言う。

## 古い版には付けていない

VER2.200.x 以前の430版は宣言を付けていない（＝利用者向けのまま）。後から
judgment で分けると、**内部の話に見える本物の不具合修正を伏せてしまう**。
付いていない＝利用者向け、という安全側に倒してある。いま分かれているのは
16版（直近30版のうち利用者向けは14版）。

## 網

- `tests/test_changelog.py`（サーバー）——判定が1箇所にあること・宣言の無い版が
  利用者向けへ倒れること・**不具合修正の版に付いていないこと**（VER2.206.0 /
  VER2.214.0 を名指し）・構造の改善の版に付いていること・APIが `dev` と件数を
  返すこと・**画面のJSに判定を書き写していないこと**。
- `tests/test_changelogui.js`（画面）——**「ボタンが在る」だけを見ない**。
  伏せている版が実際に描かれていないこと・押すと出ること・もう一度押すと
  戻ること（片道にしない）・伏せている件数を文字で言うこと・
  **いま動いている版は伏せていても出ていること**。

**片方だけでは足りない**——サーバーが正しく分けても、画面が読まなければ
更新履歴は1件も変わらない。
