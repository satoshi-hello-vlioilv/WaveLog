# §9.571 本物の Python が終わるまで待つ——入口（別名の python.exe）だけを止めると program を掴んだまま残る

索引: [決定記録](README.md)｜前: [§9.570](9.570.md)｜関係: [§9.561](9.561.md)・[§9.568](9.568.md)・[§9.544](9.544.md)・[§9.546](9.546.md)

## 経緯

利用者の報告: 起動のたびに「版をそろえる: そろえられませんでした（入れ替えられません（program が使用中かもしれません）…
os error 32）。いまの版で起動します」。「つかんでいる exe による影響が出ないようにしてもらったはず」。

## 測った（前）

利用者の PC の`desktop.log`（窓の記録）:

- 入れ替えの失敗は**5回のうち5回**。どれも版の確かめから約6秒後（`TIMING`→`UPDATE そろえられませんでした`）。
- 窓が起こした Python は`…\AppData\Local\Microsoft\WindowsApps\python.exe`、報告に出る Python は
  `…\AppData\Local\Python\pythoncore-3.14-64\python.exe`。**別物**——前者は Python Install Manager（Store）の入口（別名）で、
  本物を子として起こす。
- 窓は入れ替えの前に「入力を閉じて5秒待ち（`STOP_WAIT`）、終わらなければ止める」。見ていたのは**入口だけ**。

CI の windows は python.org の Python を直に起こすので、入口を挟まない（この形は網に掛からなかった）。

§9.568 追補の「使用中なら3秒待つ」は窓の変更で、配られていなかった（CI の`publish`が支払いの上限で飛んだ）。
仮に配られていても、残った本物の Python は待っても終わらないことがあるので、それだけでは足りない。

## 決めたこと

- 本物の PID は起動の合図（`ready.pid`＝`os.getpid()`）が前から運んでいた。窓は**起こした PID と本物の PID の両方**を持つ
  （`Sidecar::pids()`）。違えば記録に「入口を通っている」と1行残す。
- 止めるとき（`Drop`）は**本物が終わるまで**待つ（入口が終わっても、本物が動いていれば待ち続ける）。5秒で終わらなければ
  入口も本物も止め、本物が消えたと見えるまで最大3秒待ってから戻る（その後で入れ替えが始まる）。
- PID を見る・止めるのは`proc.rs`の1か所（Windows は`OpenProcess`／`WaitForSingleObject`／`TerminateProcess`）。
- それでも入れ替えを断られたら、**誰が掴んでいるか**を Windows の Restart Manager に聞いて理由に添える
  （`program`の中のファイル 500件まで）。分からなければ「分からなかった」と書く（推して埋めない）。

## 網

- `cargo test`: 子の持ち手を使わず **PID だけで**「動いている」と見る・待つ・止められる（窓は本物の Python を PID でしか持たない）。
  無い PID は動いていない。最初は`sh`の`$!`で孫を作ったが、Windows の`sh`（Git Bash）の`$!`は Windows の PID ではなく
  CI の windows で落ちた。どの OS にもある`ping`／`sleep`を直に起こし、その PID を見る形に改めた。
- `clippy`（Linux と Windows の両方の的）。CI の windows の自己診断（4回の起動の道）。

## 分からないこと・確かめていないこと

- 入口が5秒以内に終わらなかった理由（本物の片付けが遅いのか、入口が子を待つ作りなのか）は確かめていない。どちらでも
  本物を待つので直る。
- 入口を挟んだ起動は CI では再現していない（python.org の Python しか無い）。利用者の PC で、記録に
  「PID 起こした …・本物の Python …」と「UPDATE … → …」が出るかで確かめる。
