# §9.182 開く前に用意し、見えないものは作らない（利用者の指示）

利用者の指摘は「スケジュールモードへの読み込みが少し遅いです。ローカルデータや
バックグラウンド処理を有効に活かして、ユーザーに読み込み待ちを意識させないように
工夫してデータの準備を行い、修正開始に間に合わない状況になった場合にのみWAITING
表示を出すように、速度と読み込み順改良して」。

実測（手元の検証環境。共有越しでは往復の数だけ伸びる）で分けて見ると、
遅さの出どころは3つだった。

| 出どころ | 直し方 |
|---|---|
| 表示設定→予定を**1本ずつ**待つ7段の直列 | 同時に始めて、描画の直前で待ち合わせる |
| 予定を描く前に**仕掛一覧の組み立て**が入る | 予定を描いて**1度描画させてから**一覧へ移る |
| 押してから**初めて**取り始める | 手が空いた時点・触れた時点で先に取っておく |

- **取得と描画を分ける**（`planFetch()`/`planApply()`）。1つの関数で両方やると、
  他の取得と同時に走らせる書き方ができない。
- **覆い（WAITING）は予定が出るまでだけ。** 以前は仕掛一覧を組み終わるまで
  出しており、予定はもう描けているのに待たされているように見えていた。
  覆い自身は350msの遅れを持つ（`withWaiting`）ので、間に合えば出ない。
- **1度描かせる**（`paintOnce()`。`requestAnimationFrame`2回）。awaitするだけでは
  描かれない——直後に重い処理が続くとブラウザは描画の隙を得られない。
- **畳んでいる仕掛一覧は中身を読まない。** 「スケジュールだけ」で見ているとき、
  一覧は幅0で画面に無いのに2000行×200列を組み立てており、**見えないものを作る
  ために見えているものの操作が止まって**いた（実測でメインスレッドの塞ぎが
  1458ms→501ms）。開いた時点（`toggleSplitListCollapsed`）で読む。
  **器（分割バー）は先に作る**——取っ手が無いと開く手立てが消える。
- **先読みは画面を触らない。** 取ったものは既存のキャッシュへ入れるだけ
  （先読みが画面を書き換えると、見ている画面が勝手に変わる）。
  手が空いてから（`requestIdleCallback`）と、**ボタン・俯瞰ボードの行に触れた
  時点**（hover/focus）の2つ。押すまでの200〜500msがそのまま準備に使える。
  重い`/api/schedule/overview`（設備ごとに予定を展開する）は**スケジュール
  モードのときだけ**——測定端末では自分の設備の予定だけを取る。
- **失敗は黙って捨てる。** 先読みが失敗しても、開いたときに普通に取り直す。

**固定するのは時間ではなく形**（時間で固定すると環境差で落ちる）。
`tests/test_scwarm.js`が「同時に取り始める」「畳んでいるあいだは組み立てない」
「開いた時点で読む」「2回目は待機表示を出さない」を見る。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **開く前に用意し、見えないものは作らない**（§9.182）: スケジュールの読み込みが
  遅い原因は3つで、①表示設定→予定を1本ずつ待つ7段の直列 ②予定を描く前に仕掛一覧の
  組み立てが入る ③押してから初めて取り始める、だった。**取得と描画を分ける**
  （`planFetch()`/`planApply()`——1つの関数で両方やると同時に走らせる書き方ができない）、
  **覆い(WAITING)は予定が出るまでだけ**、**`paintOnce()`で1度描かせてから**仕掛一覧へ
  移る（awaitするだけでは描かれない）。**畳んでいる仕掛一覧は中身を読まない**
  ——幅0で画面に無いのに2000行×200列を組み立てており、見えないものを作るために
  見えているものの操作が止まっていた（塞ぎ1458ms→501ms）。開いた時点で読む。
  **器（分割バー）は先に作る**（取っ手が無いと開く手立てが消える）。
  先読みは`requestIdleCallback`とhover/focusの2つで、**画面は触らずキャッシュへ
  入れるだけ**。重い`/api/schedule/overview`はscheduleモードだけ。失敗は黙って捨てる。
  固定は`tests/test_scwarm.js`（**時間ではなく形**を見る）。
