# §9.616 分割ロットの判定は並びの子ロットで／完了した測定データはどの PC・どのモードでも見え、開いても消えない（利用者の指示・2項目）

索引: [決定記録](README.md)｜前: [§9.615](9.615.md)｜関係: [§9.91](9.91.md)・[§9.149](9.149.md)・[§9.258](9.258.md)・[§9.268](9.268.md)・[§9.348](9.348.md)・[§9.582](9.582.md)・[§9.606](9.606.md)

## 経緯（利用者の言葉）

> １）幅ロット分割の測定時、子ロットの並び位置を変えたときに幅交差判定がうまくいかなくなってしまいました。判定の修正をお願いします。並び位置に連動して正しく判断判定するようにしてください。並びが変わったら並びを正として、入力済みデータも再判定するようにしてください。
> ２）測定完了済みのデータに関して、全PCで見られるようにしてください。自動的に同期されておらず、測定したそのPCでしか閲覧できないような状態になっているので修正をお願いします。

（「幅交差」は板幅の**公差**の判定と読んだ。）

## 1）分割ロットの判定

### 物差し（`tests/test_splitjudge.js`）

子ロット A（製造板幅 500・+0.2/-0）と B（480・+0.2/-0）に分かれる親ロット（1000・+1/-0）。条ごとに「並びの子ロットの基準で決まる答え」と
画面の答え（その条の公差・欄の NG の印と札）を突き合わせ、食い違った条を数える。

| 場面 | 直す前 | 直した後 |
| --- | --- | --- |
| J1 開いた直後（A,B） | 0 / 2 | 0 / 2 |
| J2 帯を掴んで並べ替えた直後（B,A）・打ってあった値を判定し直す | 0 / 2 | 0 / 2 |
| J3 並べ替えたあとに打ち直す／J4「1つ戻す」 | 0 / 2 | 0 / 2 |
| **J5 一時保存→開き直し→並べ替え** | **2 / 2**（公差が親の 1000〜1001 に化け、正しい値が両方 NG） | 0 / 2 |
| **J6 完了前の確認が数える公差外**（並び A,B／B,A） | **数え違い**（正 2条→1条／正 0条→2条） | 一致 |

### 原因

1. **開き直したあとの材料が公差を運んでいなかった。** 子ロットの候補はこの画面の中にしか控えが無く、一時保存した記録を開き直す・
   ページを読み直す・別の日に続ける、では確定済みの割当（`splitGroups`）から材料を作り直す（`rowsFromAppliedGroups()`）。そこだけ
   公差を`tolObj`という別の名前で持っており、`applySplit()`が読む`tolData`が空だった。**並べ替えた瞬間に全部の条の公差が消え**、
   次の提供者（親ロットの製造公差）が答えていた。開いた直後の並べ替えは候補の控えがあるので正しく、報告の「うまくいかなくなった」は
   この道（開き直した後）。
2. **完了前の確認だけが条の位置を0で固定していた**（`outOfToleranceOf()`）。欄の印は条ごとに引いていたが、③の公差外の件数と
   記録に残す「NG のまま完了」（`completedWithNg`）は全部の条を1条目の子ロットで数えていた——並べ替えて1条目が替わると件数が入れ替わる。

### 決めたこと

- 割当から作り直す材料は**候補と同じ形**（公差は`tolData`）で、**子ロットごとに1行**へ束ねる（並べ替えたあとの割当は A,B,A の
  ように同じ子ロットが2区間になる）。
- 欄の判定範囲は`WL.measureInput.toleranceRangeAt(key,j)`の1箇所。欄の印（`judgeInput`）・描くときの札（`toleranceInfoFor`）・
  完了前の確認（`outOfToleranceOf`）が同じ答えを読み、**条の位置を必ず渡す**。
- 「並びを正とする」は今までどおり: 並べ替えを離した時点で割当（`splitGroups`／`splitPositionGroup`）を作り直し、表を描き直して
  打ってある値を新しい子ロットで判定し直す（§9.149）。値はその条に残る（条の位置が正）。

## 2）完了した測定データを全 PC で

### 物差し

`tests/test_recshare.py`（サーバー）: 共有の置き場の設備フォルダに**別の PC の完了**を1件置き、各モードの一覧の口が返すかを数える。

| 口 | 直す前 | 直した後 |
| --- | --- | --- |
| S1 編集モードの一覧の見出し（summary） | 届く | 届く |
| **S2 閲覧・スケジュールモードの一覧（list-view）** | **0件**（`configured:false`） | 届く（中身つき） |
| S3 一覧が「他の PC の分も入っているか」を答える | 答えない | 置き場ありで true／未設定で false |

`tests/test_recshareui.js`（画面）: 共有に別の PC の完了（記録 ID はロットから決まる）を置き、この PC でふつうの操作をしたあと。

| 場面 | 直す前 | 直した後 |
| --- | --- | --- |
| **U1 この PC に同じ記録の古い「編集中」がある → 一覧の状態** | 「編集中」（完了の一覧に出ない） | 「完了」 |
| U2 古い「編集中」を残したまま同じロットを開く | 共有は完了のまま（ただし古い中身で再開） | 完了のまま |
| **U3 開くと完了済みと分かり、再編集するかを聞く** | 聞かない | 聞く（断れば何も書かない） |
| **U4 この PC に何も無いまま同じロットを開く** | **共有の完了が空の「編集中」に置き換わり、測定値が消える** | 完了のまま・聞く |

### 原因

1. **閲覧・スケジュールモードの一覧は「閲覧用の複製」1本だけを読んでいた**（`/api/measurement/backup/list-view`）。共有の置き場
   （§9.258・設備ごとのフォルダ）を決めると複製は役目を終えて止まるので、事務所などこのモードで見る PC には、新しい完了が届かない
   （§9.258 は「閲覧端末が設備ごとのファイルを直接読む」と書いていたが、コードはそうなっていなかった）。
2. **一覧が共有の新しい状態を写していなかった**（`mergedRecords()`）。手元に同じ記録の古い版があると、印と時刻だけ足して状態は
   手元のまま——別の PC で完了した記録が「編集中」の側に入り、完了の一覧に出なかった（コメントは「状態で見せる」と言っていた）。
3. **同じロットを開くと、同じ記録 ID の空の記録を作って共有へ送っていた**（`openMeasurementCore()`）。記録 ID はロットから決まる
   （`lotKey()`）のに、手元の未完了しか探していなかった。サーバーは同じ ID を他のファイルから消すので、**別の PC の完了がまるごと
   消える**（この PC で完了した記録も同じ）。「測定した PC でしか見られない」の形になる。

### 決めたこと

- 閲覧・スケジュールモードの一覧も**編集モードと同じ読み先**（`merged_backup_rows()`＝全設備の写し・この端末の分・閲覧用の複製）。
- 一覧に他の PC の分が入るかは`db_access.records_shared()`の1箇所（共有の置き場を決めたときだけ）。一覧の副題が言う
  （未設定なら「この端末で測ったぶんだけ」と、決める場所＝共通設定 > 置き場 >「測定データ（共有）」）——**未設定のときに
  「共有DBの測定データ」と名乗っていた**ので、他の PC の分が無いのを「同期されていない」と読むことになっていた。
- 一覧は共有が新しければ**状態も共有側**で見せる（一覧の中の写しだけ。開くときは取り込んでから・§9.91）。
- 測定を開くときは`latestRecordFor()`が手元（未完了→同じ ID）と共有の1件を比べ、新しいほうで開く（共有が新しければ取り込む）。
  **完了していれば一覧から開くときと同じく再編集するかを聞き**、断れば何も書かない。空の記録は、どこにも無いときだけ作る。

## あわせて直した網（main で元から赤だった2本）

関係する網を回したところ、今回触っていない所で2本が赤だった。**main のままのコードでも同じ形で赤**だったので、
前の変更（§9.612・§9.614）に網が追いついていなかったもの。製品は変えず、網の期待を製品の決まりに合わせた。

- `test_tablequery.py`（7件）: 一覧の行に添える鍵`__lotKey`（§9.612）を「列に無いキー」と数えていた。鍵は列ではない
  （`lot_identity.ROW_KEY`の1箇所が名前を持つ）ので、そこから引いて除く。
- `test_scale.js`（1件）: 列見出しの ▼（§9.614・1.25em＝18px）を1行の的の高さ規格で測っていた。ⓘ と同じ「字の横の印」なので、
  ⓘ と同じく理由つきで例外へ載せる。
- `test_qjoinui.js` は143本を続けて回したときだけ1回落ち（ページが閉じた）、単独・main・この7本の回し直しでは緑。
  **原因は分からない**（順番・状態への依存とまでは言えるが、どの本の何が残ったかは突き止めていない）。

## 分からないこと・利用者に確かめること

- **現場で「測定データ（共有）」の置き場が決まっているか**はコードからは分からない。未設定なら、各 PC は自分の records.sqlite3 に
  書いて自分の分しか読まない（§9.258 の「未設定なら今までどおり」）——この場合は今回の修正だけでは他の PC に届かず、置き場を
  決めて各 PC を再起動する必要がある。一覧の副題がどちらかを言うようにした。
- 実機の 2台（別のサーバー・共有フォルダ越し）では確かめていない。網は1つのサーバーの中で「別の PC が共有へ書いた」状態を作っている。
- 自動保存と完了の送信が前後して共有が「編集中」で上書きされうるか（送る順を比べていない）は追い切れていない（推測・未確認）。
