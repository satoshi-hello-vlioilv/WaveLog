# §9.447 左メニューの言葉——行き先は必ず説明を持つ／「実績」を3つ並べない

索引: [決定記録](README.md)

利用者の指示:

> 段1: 言葉と説明（推奨）

（点検の報告で挙げた4段のうち、**見た目を1pxも変えずにいちばん効く**段として
選ばれたもの。中身は「『実績』3つの呼び分け・群名と項目名の交差・説明の無い
3項目・機械語の説明・字の残骸」。）

---

## ① 測った（評価関数）

物差しは `tests/test_navwords.js` と同じ4つ。左メニューの**行き先11件**を
実際に描かせて読んだ（画面は利用者の常用環境に合わせた 1728×1030 CSS px）。

| 物差し | 直す前 | 直したあと |
| --- | --- | --- |
| **E1** 説明（`title`）の無い行き先 | **3/11（27%）** | **0/11（0%）** |
| **E3** 出どころが先に来る説明 | **3** | **0** |
| **A1c** 名前が中身を言っていない行き先 | **2** | **1**（マスタの`[表示名]`） |
| **W** ラベルが器からはみ出す | 0 | 0 |

E1 の3件は**データ一覧・作業スケジュール・マスタ管理**——**いちばん使う3つ**
だった。畳んだ左メニューの浮き出し（§9.265）は`title`を本文に使うので、
**畳んだ瞬間にこの3つだけ名前しか出ない**。

## ② 「実績」が3つ、3つの群に散っていた

| 群 | 名前 | 実体 |
| --- | --- | --- |
| 測定データ | **実績データ** | 共有DBに上がった測定記録を設備＋期間で読む（閲覧のみ） |
| 一覧を見る | **実績** | 元データ（前工程の実績。仕掛から消えたロットの行き先・§9.364） |
| 分析 | **実績カレンダー** | この端末の測定データを日ごとに集計 |

名前だけでは違いが読めない。「実績を見たい」人は**3つとも開いて確かめる**
ことになる（＝探させている・§CLAUDE 2）。

**直し方は「消す」ではなく「修飾語を付ける」。** `実績` という語は、この
現場では正しい言葉で、しかも元データ側の役割名（`PURPOSE_ACTUAL='実績'`）
でもある。取り上げずに、**誰の実績かを名前の頭で言い分ける**:

| 前 | 後 | 何が変わったか |
| --- | --- | --- |
| 実績データ | **測定実績** | 「データ」は中身を言わない語。取り去ると`実績`しか残らなかった |
| 実績カレンダー | **測定実績カレンダー** | 測定実績の「日ごとの見せ方」だと名前で読める |
| 実績（元データ） | 実績（そのまま） | **データソースマスタの`[表示名]`＝利用者のもの**。説明で「前工程の実績」と言い切る |
| データ一覧 | **測定データ一覧** | 何の一覧かを名前が言う（畳むと群名は消える） |
| 群「一覧を見る」 | 群「**元データ**」 | 動作名をやめ、**中身**で名乗る |

**残った曖昧さは書いておく**: `測定実績`（共有DBの記録）と
`測定実績カレンダー`（この端末の測定データ）は**読む先が違う**。名前は
同じ接頭語を持つので、**違いは説明のほうが言う**（両方の`title`に書いた）。

**群を「元データ」にしたのは軸を1つにするため。** 左メニューの分かれ目は
「**このアプリが記録したもの**（測定データ・測定実績・分析）」と「**外から
来る元データ**（仕掛・品質・実績）」。「一覧を見る」は動作名なので、
「データ一覧」という項目と**同じ『一覧』という語で交差**していた。
`元データ` はこのリポジトリが既に使っている語（§9.378・§9.286）。

## ③ 機械語の説明——出どころは「後」

直す前の元データの説明は、名前をもう一度書いて括弧を足しただけだった:

```
仕掛（現在）（キー: SIKALOTNOW / ファイル: sikalotnow_test.sqlite3）
```

**出どころを言うのは正しい**（§CLAUDE 6）。誤っていたのは**順番**で、
現場の人にファイル名は意味を持たない。用途を先に置き、出どころを2行目へ回す:

```
仕掛（現在）｜作業対象のロット一覧。測定を始める・作業予定へ入れるのはここから選びます
出どころ: sikalotnow_test.sqlite3（キー SIKALOTNOW）
```

**用途は役割（`purpose`）から引く**（`DB_NAV_WHAT` の1箇所）。`/api/catalog`
は以前から`purpose`を返している（§9.87）ので、**データソースを1行足せば
説明も付いてくる**——画面へ書き足す必要は無い。役割を増やしたときだけ
ここに1行足す（載っていない役割は`__other`に倒れるので黙っては壊れない）。

## ④ 撤回した案

- **`実績`という語を画面から追い出す。** 役割名がまさに`実績`なので、
  画面とマスタで語彙が食い違う。修飾語を足すほうが安い。
- **データソースマスタに`[説明]`列を足して1件ずつ書かせる。** 増えるのは
  **入力の手間**で、既に持っている`[役割]`から引けば1行も打たずに済む。
  自由文が要るとはっきりしたら、そのとき足す。
- **群「測定データ」の重複を嫌って項目名から`測定`を外す。** 畳むと群名は
  消える（§9.265）ので、**項目名は単独で読めること**のほうが勝つ。

## ⑤ 「語の重なり」は物差しにならなかった

最初に作った物差しは「群名と項目名が2字以上の語を共有する数」で、
**2 → 3 と悪化した**。`測定データ`群と`測定実績カレンダー`が`測定`を
共有したためだが、これは**わざと揃えた接頭語**であって欠陥ではない。
物差しが「意図して揃えた語」と「たまたまぶつかった語」を区別できていない。

**直したのは物差しのほう**（A1c＝曖昧語を取り去ると何も残らない名前の数）。
参考値として残してあるが、**この数の増減で良し悪しを言わない**。

## ⑥ 字の残骸

`templates/index.html` の「計画」群に、こんなコメントだけが残っていた:

> 刃組ガイダンス(§9.377)。…**行き先は左メニューにも置く**——予定を経由
> しないと辿り着けない画面は「探させる」ことになる(§CLAUDE 2)。

**ボタンは無い。** そして現行の規則（§9.379）は「入口は段取りの行だけ。
**左メニューには置かない**（文脈の無いまま開かせない）」。コメントが
**規則ともコードとも食い違っていた**ので消した。次のセッションが
「戻し忘れ」と読んで、規則に反するボタンを足す危険がある。

## ⑦ 固定した網

- `tests/test_navwords.js`（新規・7件）: 行き先が全部説明を持つ／説明は
  用途が先・出どころが後／元データの説明は「用途｜…」＋「出どころ: …」の
  2行／曖昧語を取り去ると何も残らない名前が無い（**マスタ由来は除く**）／
  ラベルがはみ出さない／`実績`で始まる行き先は1つまで。
- 欠陥注入で確かめた: `#openSchedule` の`title`を1つ外すと
  「行き先は全部が説明を持つ」が落ちる。

名前を写している場所（`registerView`の`header`・列設定の`eyebrow`・
在席の`PZ_VIEWS`）も一緒に直した。**画面名が4箇所に書き写されている**のは
それ自体が冗長だが、1本化は構造の変更なので**この段では触っていない**。
