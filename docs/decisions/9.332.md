# §9.332 紙まわりは `print-core.js` の1本（REVIEW 3-6）

### 何が問題だったか

紙を出す入口は4つある——作業予定表（`schedule-print.js`）・操業データ表
（`opsheet-print.js`）・測定帳票（`report-dashboard.js`）・異常位置判定書
（`defect-locator.js`）。**紙の性格はそれぞれ違ってよい**（多数のロットを1枚へ
詰める一覧／1ロット1枚の塊の配置／1件の判定書）。しかし

- 用紙の大きさと向きの表（A4/B4/A3 × 縦/横）
- 刷れる範囲（四辺8mmを引いた寸法）
- `@page`の中身と、その差し替え
- pxからmmへの換算（96dpi）
- **下限のある比例配分**（列幅を紙へ収める・§9.237 ⑤）
- 紙を`body`へ出して`window.print()`する段取りと後片付け

は**同じもの**で、それが写しで散っていた。だから§9.252では
「`opsheet-print.js`も同じ形へ揃えてある。**片方だけ直さないこと**」と
注意書きを足すしかなかった——**注意書きは仕組みではない。**

**実際に片方だけ古かった。** 下限つき比例配分の丸めは、作業予定表だけに
§9.295の直し（端数は**広い列から0.1mmずつ散らして**引く）が入っており、
操業データ表は**いちばん広い列から一度に引く**古い形のまま残っていた
——§9.295が「その列が必ず切れる」と名指しで禁じた形そのもの。

### どうしたか

`static/js/core/print-core.js`（207行）が `WL.paper` と `WL.printCore` を持つ。

```js
WL.paper.KINDS / ORIENTS          // 用紙の表はここ1つ
WL.paper.orients({orientFirst})   // 向きの並び（先頭＝その画面の既定）
WL.paper.sizes({orientFirst})     // 掛け合わせ（a4-portrait…）
WL.paper.sizeOf/usableMm/keyWith  // 引き当て・刷れる範囲・片方だけ選び直し
WL.paper.pageRule/applyPageStyle  // @page は実寸mmで（§9.252）
WL.paper.shareMm/trimRound        // 下限つき比例配分＋§9.295の丸め
WL.printCore.printOnPage({...})   // 紙を出す→刷る→afterprintで戻す
```

**画面ごとに違ってよいものは呼ぶ側が渡す。**

- **既定の向き**（`orientFirst`）——作業予定表はA4縦、操業データ表はA4横。
  どちらも「**並びの先頭が既定**」という約束を持っているので、共通核で順番を
  決め打ちにすると片方の既定が変わる（実際に一度変えてしまい、
  `test_opsheet`の「向きの札は横→縦の順」が落ちた）。
- **`<style>`のid**——同じ紙に2つの`@page`が並ぶとどちらが勝つか読めない
  （§9.243 ①で踏んだ）。画面ごとに1枚。
- **用紙を選べない紙**（判定書）は`paper`を渡さない＝`@page`に触らず
  CSSの既定のまま。

**測定帳票のiframe印刷（§9.244）は統合していない。** あれは「アプリの画面ごと
刷ると版面が変わる」ことへの答えで、刷り方そのものが違う。`@page`の作り方だけ
共通核へ寄せた——`size:A4 landscape`という**名前で頼む書き方**が残っていると、
用紙を1つ足したときにそこだけ既定のA4で刷られる（B4でまさに踏んだ）。

### 網（`tests/test_printcore.py`、`ALWAYS`）

写しが増えていないことを数える——用紙の実寸・`@page{size:`・`25.4/96`・
下限つき比例配分の本体は`print-core.js`だけ、`window.print()`は共通核と
**理由付きの一覧**（画面をそのまま刷る品質データ分析と、iframeが使えなかった
ときの落とし先）だけ。

**コメントと文字列は落としてから数える**（§9.328）——説明文に`@page`と
書いてあるだけで落ちる網は、直す気を削ぐだけで何も守らない。
**ただし`@page{size:`はテンプレート文字列の中にある**ので、そこだけは文字列を
残して数える——落とすと**共通核ですら1件も当たらず、写しが増えても通る**
（実際に一度そうなった）。正規表現リテラルを見分けることも同じ理由（§9.328）。

### 直った不具合

操業データ表の1行構成で、**表が紙より8px（約2.1mm）広かった**。
`shareMm`の端数が、下限（6mm）へ張り付いた列に吸われて引き切れずに残る
——刻みを0.1mmにすると起きる。§9.237の「列が多すぎて全部が下限でも入らない
ときは**下限のほうを下げる**（紙からはみ出させない、が最後まで優先）」を
丸めの側にも通した（ここでも広い列から1刻みずつ散らして引く）。

回した網: `test_printcore`・`test_scprint`・`test_opsheet`・`test_rpprint`・
`test_rpblocks`・`test_rpdefect`・`test_defectlink`（505/505 PASS）と
