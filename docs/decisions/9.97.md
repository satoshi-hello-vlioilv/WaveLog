# §9.97 起動のたびに1.4MBを読み直していた

**見つけ方。** 起動の内訳を測り直したとき、初回に**JSの各ファイルが
1.4〜2.3秒ずつ**かかっていた。資材は19本で1.0MB、CSSが0.4MB。
2回目も同じだけ運んでいたので、キャッシュの設定を見に行った。

**原因。** `app.py`の`after_request`が、**すべての応答へ無条件に**
`Cache-Control: no-store` を付けていた。画面(HTML)とAPIには正しい方針
だが、**JS/CSSまで巻き込んでいた**。

しかもこれには前段がある。`backend/routes/core.py`の`_css_bundle()`は
既に`public, max-age=31536000, immutable`を明示しており、

> URLに更新時刻(?t=)が入っているので、内容が変われば URL ごと変わる。
> **だから長期キャッシュしてよい。** 以前は no-cache で毎回取り直して
> おり、起動のたびに数百KBを読み直すうえ…

というコメントまで書いてあった。ところが`after_request`はビューの**後**に
走るので、その指定は上書きされ、**一度も効いていなかった**。
「直したつもりが効いていない」の典型で、しかも直した本人のコメントが
残っているぶん、次に読む人は効いていると信じる。

**直したこと。** `cache_policy`(旧`no_cache`)を、URLに版が入っている資材
だけ長期キャッシュへ回すようにした。

| 対象 | 方針 |
|---|---|
| `?t=` 付きの `/static/**` `/css/app.css` `/css/boot.css` | `public, max-age=31536000, immutable` |
| 画面(HTML)・`/api/**` | `no-store`（今までどおり。古い在庫を見せない） |
| `?t=` の無い資材 | `no-store`（どの版か分からないため） |
| ビューが自分で`no-store`を宣言した応答 | そのまま尊重 |

**ビューの「降りる」合図に`no-cache`を使わないこと。** Flaskの静的配信が
既定で`no-cache`を付けるため、それを合図にすると`/static/`が1本も長期
キャッシュにならない(最初にそう書いて、JSだけ効かず気づいた)。
資材が読めなかった回のCSSは`no-store`で降りる。

**版は全資材の最新更新時刻**(`core.home()`の`_newest_mtime`)なので、
どれか1つでも更新すれば`?t=`が変わり、全部が確実に取り直される。

**実測。** 同じブラウザで3回開く:

| | 一覧まで | 実際に運んだ資材 |
|---|---|---|
| 1回目 | 504ms | 21本 **1,435KB** |
| 2回目 | 278ms | **0本 0KB** |
| 3回目 | 487ms | **0本 0KB** |

固定は`tests/test_assetcache.py`(版付き資材は長期キャッシュ・画面とAPIは
毎回取り直し・版の無い資材は長期キャッシュしない・資材を触ると版が変わる)。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **資材(JS/CSS)は`?t=`付きなら長期キャッシュへ回す**（§9.97、
  `tests/test_assetcache.py`）: `app.py`の`cache_policy`が、画面(HTML)と
  APIへは`no-store`（古い在庫を見せない）、**版がURLに入っている資材だけ**
  `public, max-age=31536000, immutable`を返す。ここを「全部`no-store`」へ
  戻さないこと——起動のたびに1.4MBを読み直すことになり、しかも
  `core.py`が明示していた長期キャッシュ指定を`after_request`が黙って
  上書きする（**実際に一度も効いていなかった**）。ビューが「降りる」合図は
  `no-store`で書く——`no-cache`はFlaskの静的配信が既定で付けるため合図に
  使えない。版は全資材の最新更新時刻なので、1つ更新すれば全部が取り直される。
