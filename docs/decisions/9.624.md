# §9.624 帳票の紙は、描いたあとに字の幅が変わっても測り直す——器の下で行が切れたまま残るのを直す（利用者の報告）

索引: [決定記録](README.md)｜前: [§9.623](9.623.md)｜関係: [§9.622](9.622.md)・[§9.217](9.217.md)・[§9.221](9.221.md)

## 経緯（利用者の報告と2枚の画面）

> DELLのPCでLatitude3550の1920×1080でスケーリング100％で使っているときに帳票の画面を添付します。横幅の違いなのか収まりきらず2段に展開され押し出された行分を測定データ表示のブロックが吸収するため40条分の行が表示されるところ、この例では32条しか表示されない状態です。

同じロット（L8104R0・LS4）を、同じ 1920×1080・100% の Latitude 5340 で開いた画面と比べると、次のことが分かった。

| 塊 | 5340（正常） | 3550（報告） |
| --- | --- | --- |
| 寸法（オーダー／製造） | 「オーダー」「製造」の2行 | 「オーダー」が折り返し、「製造」の行が見えない |
| 運転条件 | 3段（3段目＝製品先端・製品後端・スプール種別） | 見出しが2行に折り返し、3段目が見えない |
| 測定データ | 40条 | 32条（33〜40条が見えない） |

3550 では字の幅が広く、折り返した分だけ中身が背高くなっている。ところが、どの塊も**器の下で切れている**。
- 縮められた形跡（`--rp-fit`）が無い。
- 塊の器が伸びた形跡も無い。

前回（§9.622）は、字の大きさが表示サイズで変わる道だけを直した。字の幅が変わることで割り付けが変わる道は確かめていなかった（§9.622 の最後に書いたとおり、見切れの元だったとは言い切れなかった）。

## 原因

紙は、描いた直後に1回だけ中身を測って器へ合わせる（`rpAfterPaint()` → `rpFitAll()`）。
- 中身なりの塊は、測った高さで行を割り当てる（`rpFitRows()`）。
- 場所と高さを決めた塊は、中身を縮める（`rpFitBlockBodies()`）。

そのあと字の幅が変わっても、測り直さない。器は `overflow:hidden` なので、広がった字が折り返した分は器の下で切れたまま残る。描いた最初から字が広ければ、測った時点で縮めるので切れない。だから「縮めもせずに切れている」3550 の画面は、測ったあとに字の幅が変わったことを示している。

3550 で何が字の幅を変えたのかは**分からない**。例えば、書体の用意が遅れて途中で差し替わる場合が考えられる。この環境（Linux）では、Windows の書体の振る舞いを再現できない。

## 直したこと

- 塊の中身の器（`.rp-block-fit`）の大きさを `ResizeObserver` で見張る（`rpWatchFit()`）。
  - 前の大きさと違ったときだけ、1フレームにまとめて測り直す。
  - 道は描いた直後と同じ（ふだんは `rpFitAll()`、組み換え中は `rpMarkOverflow()`）。
- 測り直しでも大きさは変わる（詰める・縮める）。それでも2回目で同じ答えに落ち着くので、回り続けない。
- 字の大きさ（計算値）は変えない。縮めるのは、器への合わせ込み（`--rp-fit`）だけ。

## 物差し（`tests/test_rprefit.js`・1920×1080）

帳票を開いて測り終えたあと、紙の字間を広げる（1.2em）。書体が後から差し替わって字の幅が変わるのと同じ形の変化として扱う。

| 項目 | 直す前 | 直した後 |
| --- | --- | --- |
| R2 中身なりの塊: 広げたあと器の下で切れる塊 | 3（寸法 113>74px・測定条件 167>101・母材実績 92>74） | 0 |
| R5 場所と高さを決めた塊（組み換えの中・16件）: 広げたあと切れる塊 | 3 | 0 |
| R3 字の大きさ（計算値） | 同じ | 同じ |

物差しの字間は、字の幅の変化を作るための仮の当て方で、3550 で起きた変化の量そのものではない。利用者の LS4 の配置そのものでは測れていない（検証用の設備に同じ配置が無い）。3550 で直ったかは、利用者の画面で確かめてもらう。
