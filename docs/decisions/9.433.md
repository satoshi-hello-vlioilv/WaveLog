# §9.433 模型は「何から組んだか」を名乗る／ショートカットの名前を残す／見え方の行き先

索引: [決定記録](README.md)

## ① 板のずれは「違う割付の物が混ざっていた」（③④の正体）

### 添付の図から読み取った数

絵を見ても「ずれている」以上のことは分からないので、**添付の画像から
画素で測った**（有効長の寸法線・切断の破線・材料の帯の左右端）。

| 測ったもの | 画素 | アーバー座標に直すと |
| --- | --- | --- |
| 有効長の寸法線 | x=106 → 1296 | 0 → 1600mm（0.7439 px/mm） |
| 切断の破線（5本） | 314.5 / 507.5 / 700.5 / 893.5 / 1087.5 | 280.4 / 540.2 / 800 / 1059.8 / 1319.6 |
| 材料の帯（4条） | 26–217 / 219–410 / 412–603 / 605–796 | −108.9 から 930.4 |

刃の位置は正しい（条幅 259.8mm ちょうどの間隔で、1本目は
`(1600 − 4×259.8)/2 = 280.4`）。**ずれているのは材料だけ**で、その量は
**−389.3mm ＝ 条幅の1.5本ぶん**、どの条でも同じだった。

### なぜ「混ざっている」と言えるか

材料の並び（`materialRun`）も刃の位置（`A.U`）も、**同じ `A`（`buildLayout()`
の答え）から出る**:

```
origin  = A.matStart + A.w.osTrim     ← 1条目の左端
A.U[i]  = origin + c_i ± dKnife/2     ← i 本目の刃
破線     = (U[i] + Lo[i]) / 2 = origin + c_i
```

`c_0 = 0` なので、**1条目の左端と1本目の破線は同じ座標**でなければならない。
測った値は 389.3mm 離れている——**同じ `A` からは出ない**。つまり、
**材料と刃が別々の割付から組まれた模型**が場面に残っていた。

さらに、ずれの量を逆算すると `matStart = −124.3`、これは
**`元板巾 = 1848.6`（＝ 259.8 × 7 + 耳15×2）のときの値**だった。7条の割付で
作った材料が、4条の割付で作った軸と一緒に描かれていた、ということ。

### 見張りが「図の種類」しか見ていなかった

§9.428 で `render()` に食い違いの見張りを入れたが、**見ていたのは図の種類
（`builtCut`）だけ**だった:

```js
if (D3.built && D3.builtCut !== D3.cut) { build(); return; }
```

模型は `ctx.res`（割付）から作るのに、**どの割付から組んだかは控えていない**。
だから「割付が入れ替わったのに組み直されていない模型」は素通りする。

組み直されない道は `build()` の入口にあった:

```js
function build() {
  if (!ctx || !ctx.res || !init()) return;   // ← 黙って戻る
```

割付がまだ無い・部品（three.js）がまだ無いときは**ただ戻っていた**ので、
**前の割付・前の図のまま組んである模型が「今の物」の顔をして残る**。
`D3.dirty` は立ったままだが、それを見ているのは `sync()`／`setMode()` だけで、
`render()`（掴んで回す毎フレーム・器の大きさの変化・台車の動き）は見ない。

### 直し方

**模型は「何から組んだか」を名乗る。描く前に食い違っていたら組み直す。**

1. `build()` は末尾で `D3.builtRes = res` を控える。`solve()` は呼ぶたびに
   新しい物を返すので、**同一性の比較がそのまま「同じ割付か」の答え**になる。
2. `build()` が組めなかったときは `D3.builtRes = null`——
   **「今の物ではない」と名乗る**（黙って戻らない）。
3. `render()` の見張りを**図の種類と割付の両方**にする。
4. 組み直せなかったときは **器を空にする**（`clearCanvas()`）。前の図の絵を
   残すと「断面図を押したのに立体図が出たまま」になる（④の症状）。
   絵は「いま何を見ているか」の答えなので、古い1枚を残してはいけない。

### 数で見張る（`view().matOff` ／ `view().stale`）

絵では「板が横へずれている」としか読めない。**網が名指しで見られるように
数で答える**（§9.418 の `pack` と同じ作法）:

| 鍵 | 何を答えるか | 正しいときの値 |
| --- | --- | --- |
| `matOff` | 1条目の左端 − 1本目の切断位置 | **0** |
| `stale` | 組んである模型がいまの割付の物か | **false** |

`test_bladeui.js` が、断面図へ切り替えた直後と、**条数を変えた直後**の
両方で見る。

### 断面図は必ずライン位置で見る

段取り（引き出し・軸端部・回す）は断面図では器ごと伏せてあるのに、
**台車の走行ぶん（`carX`）だけは立体図の操作の履歴を引きずって**いた。
カメラがそのぶんを足して見ているので絵は成り立つが、「いま何を見ているか」が
別の図での操作で変わることになる。断面図は**軸とその上の物だけ**を見る図
なので、台車はラインへ置く（`D3.carX = (D3.out && !D3.cut) ? -m.bcx : -M.ttX`）。

## ② ショートカットの名前は「押した瞬間だけの値」だった

`#pcScName` はどこにも保存されておらず、**「デスクトップに作る」を押した
その1回だけ**サーバーへ渡っていた。画面を組み直すと
`info.name || info.defaultName` で塗り直されるので、既定名に戻る。

直し方は**保存の道を2本目に作らない**こと——共通設定の欄はすべて
`data-pc-field` を名乗れば `savePathConfigMaint()` が集めて送るので、
そこへ載せるだけでよい:

- `パス設定マスタ`へ `shortcut_name` / `shortcut_icon` を足す
  （`PATH_CONFIG_LIVE_KEYS` と `_PATH_CONFIG_TEXT_FIELDS` の**両方**——
  片方だけだと「触っても何も起きず、開き直すと元に戻る」という
  §9.208 ⑨ でも踏んだ一番分かりにくい壊れ方になる）
- 欄へ `data-pc-field` を足し、**値は組み立てるときに入れる**
  （描いたあとから差し込むと、状態の問い合わせが戻るまで空欄になる）
- `status()` は名前を渡されなければ保存値を使う——既定名に倒れると、
  別の名前で作ったショートカットを「まだ作っていません」と言う
- **`create()` は渡された値をそのまま使う**。ここで保存値へ落とすと
  「アプリのマーク」を選んだのに前に指定した絵で作られる
  （空欄＝既定、を保存値が上書きしてしまう）
- 「アプリのマーク」を選んだら**指定の欄も空にする**。欄は保存の輪に
  載っているので、伏せたまま値が残ると既定を選んだのに前の絵が保存される

### 段の札の一言は「見えている欄」だけから作る

`mmTabSummaryText()` は `.mm-field` を無差別に拾っていたので、**作れない端末で
器ごと伏せてあるショートカットの名前**が段の札に出て、「この端末 EV4134」＝
端末の名前、と読めてしまった。伏せてある欄は数えない（§9.391「必須に数えるのは
いま出している面の欄だけ」と同じ考え）。見るのは `[hidden]` だけ
（`offsetParent` は使わない・§9.346）で、**段そのものの `hidden` は数えない**
——選ばれていない段は伏せてあるので、そこで止めないと全部空になる。

## ③ ローディングの見せ方は「在ったが、探せなかった」

実際に測ると、設定は**在って、効いていた**（「表示」バッジ → 3つめの節に
6種類）。足りなかったのは**行き先**:

- バッジの説明は「文字の大きさと時間の書き方を切り替えます」——
  **3つめだけ説明から漏れて**おり、畳んだ中に在ることを外から読む手がかりが
  1つも無かった。
- 設定を探しに来る場所は**共通設定**なのに、そこには何も書いていなかった。

**設定そのものは1箇所のまま**にする（§9.421「この端末の見え方の入口は1つ。
節を足す・入口は増やさない」）。増やすと同じ設定を直す場所が2つになり、
どちらが効くのか分からなくなる（§9.267 と同じ理由）。代わりに、

- バッジの説明に**節を全部書く**
- 共通設定の「この端末」に**「この端末の見え方」の行き先**を置く。
  作法は他の画面の「共通設定 > 置き場 で決める」と同じ（§9.267）——
  **いまの値**（文字／時間／読み込み）を字で出し、ボタンは
  **ヘッダーのバッジそのものを押す**（同じポップオーバーを2つ書かない）。

そのために `WL.uiSize` を足して、**3つとも同じ形**（`SIZES`/`STYLES` と
現在値）で読めるようにした。並べて出す側が3通りの読み方を書き分けずに済む。

変わったことは `wl:look-change` の1つの合図で知らせる（§9.285
「変わったら知らせる」と同じ作法）——選ぶ場所といまの値を出す場所が
分かれているので、知らせが無いと「選んだのに変わらない」に見える。

## ④ 直さなかったこと・分かっていないこと

- **④の「最初の1枚だけ断面にならない」は、この環境では再現できなかった。**
  初回の切り替え（three.js をまだ読んでいない状態）を Playwright で
  200枚ぶん追ったが、`ready` になった最初の1枚から `ortho`・`clips=1` で、
  断面でない枚は0枚だった。上の ①4（組み直せないときは器を空にする）は
  **症状（前の図の絵が残る）に効く**直し方で、根本の引き金を突き止めた
  わけではない。**分からないことは分からないと書く**（§9.426）。
- **③の引き金（どの操作で割付が入れ替わったまま組み直されないか）も
  特定できていない。** 場面を10通り試して（条数の変更・図の行き来・
  段取り向き・板の消し戻し・引き出し／戻す）、どれも `matOff` は0のまま
  だった。直したのは**混ざったものが描かれ得る構造**のほうで、
  混ざる引き金そのものではない。`matOff` / `stale` を網に載せたのは、
  次に起きたときに**絵ではなく数で**分かるようにするため。
