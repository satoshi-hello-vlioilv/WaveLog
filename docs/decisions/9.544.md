# §9.544 デスクトップ版への移行 P1——ポートを開かない窓口（`program/sidecar.py`）と、起動の背景処理を1箇所へ（利用者の指示）

索引: [決定記録](README.md)｜設計: [`docs/DESKTOP_MIGRATION_DESIGN.md`](../DESKTOP_MIGRATION_DESIGN.md)

## 利用者の言葉

最初の依頼: 「別リポジトリのDefect-Pitch-Analyzerで行ったように、大規模マイグレーションをしたいです。構成を変更して、
Flask/Pythonで補っていた部分を、Tauri/Rust/Pythonに変換し、ポートによる影響や得意な分野ごとに分けて対応させる
最適化を行いたいです。（中略）心配事としてはデータベースの共有管理面が現在の機能を維持して対応することが可能か
どうかという点です。この点についても問題がないか事前に確認をお願いします。」

事前確認（PR #130・設計書 §1〜§3）への答え:
「１．コピーしてから使うことにします。そうでない場合の懸念している問題をもう少し詳しく教えてください。
２．動きました。３．よいです。４．問題ありません。
他、最も重大な問題（端末内測定データがブラウザの置き場に依存している点）についてはどう対応できますか？
一時置き場にファイルを生成しますか？」

- 1 → exe は**端末の手元へ写してから起動**する（P5 の配り方。理由は設計書 §7）。
- 2 → Defect-Pitch-Analyzer の署名の無い exe は社内の PC で止められずに動いた（SmartScreen・AppLocker の懸念は解けた）。
- 3 → 移行のあいだはブラウザ版（Start.vbs）を残し、PC ごとに切り替える（**併存**）。
- 4 → P1 から始める（この節）。
- 端末内の測定データ → 設計書 §8（P3 の方針。一時置き場ではなく、端末の作業場所の「控え」へ常に写す）。

## 決めたこと

- **窓口を1本足す**: `program/sidecar.py`。窓（P2 の Rust）が子として起こし、**標準入出力の枠**（JSON 1行＋生の本文・
  Defect-Pitch-Analyzer と同じ形）で問い合わせる。**ポートを開かない**。アプリ本体（Flask）は WSGI のまま呼ぶので、
  画面・ルート・網はブラウザ版と同じものを使う。置き場の名前は`config.DESKTOP_SCHEME`（`http://wavelog.localhost/`）。
- **標準出力は枠だけ**: 何より先に fd 1 を標準エラーへ向け直す。print も、起動前の確認（`setup_check`）が起こす子プロセスの
  出力も枠に混ざらない（子は向け直した fd 1 を受け継ぐ）。
- **起動の背景処理は1箇所**: 写し（`db_mirror`）・共有スケジュールの見張り（`schedule_watch`）・書込役（`schedule_owner`）の
  開始を`backend/launcher/services.py`の`start()`へ移し、`server.py`（ポート版）と`sidecar.py`が同じ関数を呼ぶ。
  **窓口によって片方だけ動いていると、混在する端末どうしの共有の約束が崩れる**ため。
- **終わり方は1本のまま**: 標準入力が閉じたら`watchdog._exit()`を通る（`teardown()`＝書込役をやめる・編集セッションを
  手放す・在席を消す、を持ち時間3秒で）。`/api/shutdown`・終了ボタンと同じ道。
- **`watchdog.start()`（タブが0件で終わる見張り）はポート版だけ**。デスクトップ版の寿命は窓が持つ。
- **起動前の確認は同じ`setup_check.run()`**（刻印が合えば飛ばす）。していることは知らせの枠（`progress`）で窓へ流す。
- **知らせに枠の約束の版（`protocol`）を入れる**。exe は端末の手元へ写して使い、Python は共有のフォルダから読むので、
  更新が届くと版がずれうる。ずれたら窓（P2）が「開き直してください」と言う。

## 撤回した案

- **デスクトップ版でもタブの見張り（`watchdog.start()`）を回す**——寿命の持ち主が2人になる。WebView のハートビートが
  途切れただけで（読み込み中の失敗など）、窓が開いているのに Python が自分で終わる。窓を閉じれば入力が閉じるので
  推し量りは要らない。
- **背景処理の開始を`sidecar.py`へ書き写す**——片方だけ直すと、ブラウザ版とデスクトップ版で写し・書込役の振る舞いが
  ずれる（共有の約束を端末どうしで揃える前提が崩れる）。

## 測った（評価関数・設計書 §3）

| 物差し | 結果 |
| --- | --- |
| E1 共有の層（共有の基本部品を読むモジュール・構文木で集めて25本）が画面のポート・問い合わせの出どころを読む所 | 理由の無い当たり **0件**（理由つきの3件: 書込役の受け口の予備のURL・PC名の除外表2つ）。`test_portdep.py` 12/12 |
| E3 本物の子プロセスへパイプで送った答えと、同じアプリへ直接送った答え（状態・種類・本文の指紋・部品の Cache-Control） | **11/11 一致**（HTML 118KB・連結 CSS 1.4MB・更新履歴 1.5MB・404・日本語の 400・日本語の問い合わせ・約200KB の日本語の POST ほか）。40本同時 **40/40** |
| E4 入力を閉じてから終わるまで | **0.02秒**（持ち時間 3.0秒。ブラウザ版はタブを閉じてから約8秒） |
| E4 片付け | 在席が消える・書込役だった窓口が目印を手放す・`片付け : 書込役=やめた / 編集セッション=なし / 在席=消した` が記録される |

欠陥注入（1件ずつ入れて、その場で戻した）:

- 終わるときに片付けを通さない（`os._exit(0)`）→ **4件が落ちた**（在席・書込役の目印・終了理由・片付けの記録）。
  このとき書込役の目印と在席が共有の作業コピーに残った——**片付けないと他の端末が期限まで待たされる**ことを実際に見た
  （残った目印は手で消した）。
- fd 1 を向け直さない → **1件が落ちた**（子プロセスの出力 `child-noise` が枠の前に混ざった。print は`sys.stdout`の
  差し替えで逃げていたが、子プロセスは逃げない）。
- 共有の層の1本に`from .config import PORT`を足す → `test_portdep` が `backend/presence.py:618 PORT` と名指しして落ちた。

## 分からないこと

- 本物の WebView2（Windows）の中から問い合わせたときの振る舞い。P2 の自己診断で確かめる（ここで測ったのは窓口の Python 側）。
- 書込役の片付けは、**この窓口が書込役になれたときだけ**測れる。回帰のサーバーが書込役のとき（通しの中）は
  「測っていない」と書いて合否に数えない。
