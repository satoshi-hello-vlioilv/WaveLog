# §9.29 勤務形態の階層化(勤務体系 → 勤務区分)

現場の言い方は「日勤」「交替勤務(1,2,3直)」という**勤務体系**が先にあり、その中に
各直の時間帯がある、という2階層。当初のフラットな`勤務形態マスタ`
(名称+開始+終了の1テーブル)では、どの直がどの体系に属するのかを表現できず、
体系ごと切り替えることもできなかった。

| テーブル | 役割 | 主な列 |
|---|---|---|
| `勤務体系マスタ` | 親。日勤 / 交替勤務(1,2,3直) など | 勤務体系ID・名称・表示順・有効 |
| `勤務区分マスタ` | 子。1直 7:00-15:00 など | 勤務区分ID・勤務体系ID・名称・開始時刻・終了時刻・表示順・有効 |
| `勤務体系設備マスタ` | 適用設備(複数) | ID・勤務体系ID・設備名 |

- **適用設備は複数登録できる**。同じ勤務体系を複数の設備へ同時に割り当てたい
  (現場では同じ勤務シフトを複数ラインで共有する)ため、単一値だった
  `勤務体系マスタ.[適用設備]`列から子テーブルへ移した。方式は
  `オペレータ設備マスタ`(`operator_equipment_map`/`set_operator_equipment`)と同じ。
- **割当0件 = 全設備既定**。旧仕様の「空文字=全設備既定」をそのまま引き継ぐ。
  `shift_rows()`が「設備割当があればそれ、無ければ全設備既定」で解決する。
- 旧`[適用設備]`列の値は`_migrate_shift_pattern_equipment()`が一度だけ子テーブルへ
  移し、**移行後は列を空にする**(単一の情報源にするため。残しておくと
  テーブル生データ画面で古い値が正解のように見える)。移行後この列は読まない。
- **`shift_rows()`の戻り値のタプル形は旧フラット構造のまま**
  `(勤務ID,設備名,名称,開始時刻,終了時刻,表示順,有効)`にしてある。
  `schedule_calc.resolve_shift_label()`は形しか見ないので**あちらは無改修**。
- 旧データは`migrate_shift_patterns()`が一度だけ移行する。旧構造には
  「どの直が同じ体系か」の情報が無いため、**設備単位で1体系にまとめる以上の
  推測はしない**(移行後に画面上で分ければよい)。
- API: `GET/POST /api/schedule/shift-pattern-master`、
  `POST /api/schedule/shift-pattern-master/delete`。
  **親と子を1リクエストで保存**する(区分は全置換)。片方だけ保存された
  中途半端な状態を作らないため。

**入力負荷を下げる設計**(専用エディタ、`special:'shift-pattern'`):
- 時刻は`input[type=time]`。ピッカーでもキーボードでも入れられ、`8:15`のような
  表記ゆれ・全角数字が原理的に入らない。
- よくある勤務体系(日勤 / 交替勤務(1,2,3直) / 交替勤務(4,5直))は
  **テンプレートからワンクリック**で投入できる。
- 区分を追加すると**直前の区分の終了時刻が次の開始時刻の初期値**になる
  (連続する直の入力がほぼクリックだけで済む)。
- **24時間バー**で時間帯の埋まり方を色で示し、「24時間をすべてカバーしています」
  等の要約を出す。時刻の数字だけを見比べて抜け漏れを探さなくて済む。
- 終了≦開始の区分には自動で**「翌日」バッジ**が付く。

**権限**: 設定系マスタをmaster.sqlite3へ移した(§9.27)結果、これらは他のマスタと
同列になったため`_ENDPOINT_EXTRA_MODES`でeditモードにも書込を開いた
(マスタ管理画面はeditモードの画面)。このとき、`before_request`が
「editモードで例外的に許可された非GET」**すべて**に現場段取り権限
(`_field_reorder_permitted`)を要求していたため、無関係な設定マスタの保存まで
403になる不具合を踏んだ。判定対象を`_FIELD_REORDER_ENDPOINTS`
(=`schedule.plan_reorder`のみ)へ明示した。
