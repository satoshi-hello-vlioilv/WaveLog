# §9.638 予定へ入れた位置がずれる・一番下に入る・共有で書き戻される／さかのぼり「なし」で完了を出さない（利用者の指摘と指示・2項目）

索引: [決定記録](README.md)｜前: [§9.637](9.637.md)｜関係: [§9.179](9.179.md)（位置を指定して入れる）・[§9.514](9.514.md)（時間的に終わった設備停止）・[§9.605](9.605.md)（完了したロットの上の停止に時刻）・[§9.611](9.611.md)（完了→作業中→予定の並び）・[§9.613](9.613.md)（並べ替えが戻る）・[§9.366](9.366.md)（さかのぼり）・[§4](../SCHEDULE_MODE_DESIGN.md)（共有の書込サイクル）

## 経緯（利用者の言葉）

> スケジュールの完了分がさかのぼりの表示をなしにしても表示されてしまします。完了後のものはさかのぼりなしにした場合、
> 自動完了分は非表示にしてください。
> また、以前治してもらったはずのスケジュールにロットや設備停止など登録する際に位置が狙い通りに入らずズレたり一番下に
> 入る現象が発生しており直っていないようです。原因調査分析し修正をお願いいたします。

調べている途中の追加:

> D&Dで入れるので、一回入った位置が共有で書き戻しされる原因を疑ってほしいです。

## 測った（`tests/test_scinsertpos.js`・`tests/test_scwriteback.py`）

まず検証用のきれいな予定で、ロットと設備停止を先頭・真ん中・最後の前へ落とした。**6通りとも狙いどおりに入った**（落とした直後・サーバー・読み直した画面の3つで）。
現場で起きる条件を足して初めてずれが出たので、条件ごとに物差しを作った。

| 物差し | 前 | 後 |
|---|---|---|
| W1 共有が一時的に読めないときに書くと、ほかの PC が足した行が消えるか | **消えた**（古い手元の写しで共有を上書き） | 書かない（503・画面は数回送り直して理由を言う） |
| W2 反映の直前に共有の版の番号が読めないときに書くと、確かめないまま上書きするか | **上書きした** | 書かない |
| W3 状態欄が空の予定の行（前の版の行）を狙うと | **一番下** | その行の前 |
| W4 狙った行が書く前に始まっていたら | **一番下** | その次の予定の前 |
| S2/W6/W7 表示順で途中のロットを先に流した後、予定の先頭の前へ設備停止を入れると | **すぐ「完了」になって予定から消え、書込役の見回りがその時刻を共有へ書いて確定** | 予定のまま・入れた位置 |
| S3 時刻を固定した行の上端へ落とすと | **その行の後ろ**（1行ずれる） | その行の前 |
| H さかのぼり「なし」で時刻の分からない完了（自動で完了した行） | **出た** | 出ない |

## 原因と直し

1. **共有の書き戻し（利用者の指摘のとおり）**: `schedule_sync.with_write()`は、共有ファイルを取り直せないとき（同期中で
   開けない等）「最新性を確認できないまま書込を行います」と警告だけ残して**手元の古い写しへ書き、共有へ戻して**いた。
   反映の直前の版の番号の確かめも、読めなければ「処理は続行します」で進んでいた。どちらもほかの PC の変更（足した行・
   入れた位置）を消す。**確かめられなければ書かない**（`ScheduleUnavailableError`＝503）。画面の書込の列は503を数回
   送り直し、尽きたら理由を言って巻き戻す（§9.372）。錠は Box のような結果整合の共有では遅れて見えることがあり、一次防御
   として足りないので、二次防御を「警告だけ」にしない。
   - 現場で起きていたかは**ログで確かめられる**: 前の版では`スケジュールデータの最新性を確認できないまま書込を行います`・
     `反映前の改訂番号確認に失敗しました(処理は続行します)`が出ていたはず。この版からは`…書込をやめました`と出る。
2. **後から入れた停止が「終わった」と判定され、共有へ書き戻される**: 「後ろの作業が始まったら前の設備停止は終わった」
   （§9.514）と「完了したロットの上の停止に時刻を入れる」（§9.605）は**表示順の位置だけ**で判定していた。作業中・完了の
   ロットは画面では予定の上に並ぶ（§9.611）が、表示順では予定の行より後ろのことがある（次の1本は現場が自由に選ぶ・
   §9.339）。そのため画面で予定の先頭の前へ入れた停止が、表示順では「始まった作業の前」になり、入れた瞬間に完了
   ——§9.605 の時刻は書込役の見回り（`actual_keep.persist()`）が共有へ書いて確定させていた。
   **その作業が始まった後に入れた停止は数えない**（`_added_after()`）。境は`_work_mark()`＝作業の始まりと、その作業の行を
   予定へ入れた時刻の**遅いほう**。始まりだけで比べると、後から実績を入れる流れ（停止を先に入れ、作業の行が後から入り、
   開始を2時間前とさかのぼって登録する・網 test_sctimes）で、停止が「これから」に読まれて時刻の登録を促さなくなった
   （網 W8 で固定）。どちらかが分からなければ今までどおり。
3. **一番下へ落ちる道**: 位置を決める所（`plan_add`）だけが状態欄の「予定」の字を求め、画面・並べ替え・状態の判定は
   空の状態欄も「予定」と読んでいた。答えを`_insert_order_before()`の1箇所にし、空も予定と読む。狙った行が書く前に
   始まった・済んだときは、末尾ではなく**その次の未着手の予定の前**へ。
4. **固定した行の前へ入れられない**: 落とす先の境目を`reorderableEntry()`（掴んで動かせる行＝固定を除く）で数えていた
   ので、固定した行の上端は次の行の前になった。落とす相手は`insertTargetEntry()`（固定した行も含む）。
5. **さかのぼり「なし」**: 画面の`withinHistory()`は「時刻の分からない済んだ行は隠さない」（§9.366 の利用者の指示）を
   どの範囲にも当てていた。「済んだ行を出さない」だけは1件も出さない。範囲を決めたときは今までどおり出す。

## 網の前提を直したもの

§9.637 でフィクスチャの L0041〜L0046 をテスト設備Bのロットにしたため、「仕掛一覧のいちばん上の行をテスト設備Aへ入れる」
網が断られていた（前回の PR で回し損ねた）: `test_scinsert`・`test_scdndhold`・`test_wkfast`。使用設備のロットを選ぶ形に直した。

## 分からないこと

- 現場の共有（Box 等）で、錠のファイルが他の PC に見えるまでの遅れ。錠の確かめの待ち（既定 1.5 秒・ネットワークの置き場は
  別の既定）より遅いと、2台が同時に書けることがある。この版では二次防御（版の番号の確かめ）が抜けなくなったので、
  同時に書いた後の方は 409 で送り直しになり、変更は消えない。
