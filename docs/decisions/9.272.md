# §9.272 誰が繋いでいるかを見せ、切断できるようにする（権限区分・利用者の指示）

利用者の問いと指示は2つ。

> スケジュールモードは管理された環境での競合対策ができていると感じていますが、
> 通常の設定編集などのマスタのデータに絡む方の管理も同じように競合排除できますか？

> 誰がアクセス中か見える化し、接続中のユーザーを視覚化し、強制的に接続切断
> したりする機能を実装してください。ただしこの権限はアクセス権限マスタの
> 設定項目の上位権限として持っておきたいので…開発者、メンテナンス者、
> 一般ユーザーの3タイプを

#### 問いへの答え——マスタは「半分だけ」塞がっていた

| | 作業予定 | マスタ |
|---|---|---|
| ファイルが壊れる | 書込サイクル（§4） | 書込サイクル（§9.263）**あり** |
| 同時に書く | ロック＋改訂番号 | ロック＋改訂番号 **あり** |
| **誰が触っているか見える** | 在席チップ（§9.211 ②） | **無かった** |
| **同じものを2人が直す** | 設備ごとの編集セッション | **無かった**（後勝ち） |

§9.263 が塞いだのは**ファイルの壊れ方**で、それは**1リクエストぶんの直列化**。
2人が同じマスタを開いて別々に直せば、**後から保存したほうが黙って勝つ**。
ここで足すのは「**誰が居るか**」と「**出てもらう**」の2つ。

#### 権限区分——上位の軸として足す

`アクセス権限マスタ`の`[権限区分]`。既存の3つ（編集可否・スケジュール可否・
現場段取り可否）が「**何を触れるか**」なのに対し、こちらは「**アプリそのものを
どこまで管理できるか**」。**掛け合わせない**——閲覧モードの開発者でも切断はできる。

| 区分 | 接続状況を見る | 切断する | 開発者を切断 |
|---|---|---|---|
| 開発者 | ○ | ○ | ○ |
| メンテナンス者 | ○ | ○ | **×** |
| 一般ユーザー | ○ | × | × |

**答えるのは`master_repo.role_can()`の1箇所**（§9.163）。ルートにも画面にも
書き写さない——写すと「画面にはボタンが出るのにサーバーが断る」、逆に
「画面には出ないのに口は開いている」が作れる。画面へは`role_capabilities()`と
行ごとの`canDisconnect`で渡す。

**既定は一般ユーザー。** 登録の無い端末に管理の権限を配らない（触れる範囲が
広がる側の既定は安全側へ倒す、という既存の約束と同じ）。**編集可否の既定が
「可」なのは互換のためで、そちらへ揃えないこと。**

#### 在席——端末ごとに1ファイル

```
<共有>\presence\
├─ <端末キー>.json          … その端末だけが書く
└─ <端末キー>.revoke.json   … 切断の指示（管理する側が書き、対象が読む）
```

**1つのファイルを書くのはいつも1台**が構造として成り立つ（§9.258で測定データに
対してやったのと同じ理由）。全端末が1つのJSONを取り合う形にすると、**在席を
書くこと自体が共有への競合**になり、競合を減らすために作った仕組みが競合を増やす。

端末キーは`terminal_key()`。**使えない文字を潰すだけにしないこと**——
`a/b`と`a:b`が同じ鍵になり、**別の人の在席が1つのファイルに混ざる**
（§9.258の`records_dir_name`と同じ罠）。落としたときだけ短い識別子を足す。

**ハートビートに相乗りさせる**（15秒間隔・§9.98）。専用の周期を足すと、間隔・
失敗時の扱い・タブを閉じたときの後始末を2つ持つことになる。書くのは**裏の
スレッド**で、**共有が遅くてもハートビートを待たせない**——ハートビートは
アプリの生存そのものを支えている。書けなくても`ok`を返す。

置き場は`presence_dir()`が答える（共有マスタの隣 > 共有スケジュールの隣 >
手元）。**手元しか無い端末では「この端末しか出ません」と画面に書く**——
1件だけ並んでいるのを「他に誰も居ない」と読ませない（§9.107）。

#### 切断——書き込みだけを止める

別のPCのプロセスを外から殺すことはできないし、やるべきでもない（書きかけの
測定が消える）。**切断＝その端末の書き込みを止め、理由を画面に出す**こと。
読みは止めない。判定は`access_mode.revocation_now()`で、**リクエストのたびに
共有を読みに行かない**（5秒だけ覚える）。**読めなかったら止めない**（fail-open）。

**冷却時間つき**（既定5分）。すぐ繋ぎ直せるなら切断の意味が無く、恒久的に
締め出すと**間違えたときに直せない**。時間で自然に解ける。

**区分は在席ファイルではなくマスタから引く**（`_registered_role()`）。在席は
端末が自分で書くので、そこに「開発者」と書けば切断を免れる、という形にしない。

**断る理由を言い分ける**（§4）——権限が無い／相手が上位／もう居ない、で
打つ手がまったく違う。**権限が無いことは相手を探す前に言う**（後ろに置くと
「もう接続していません」という別の理由が返る）。

#### 固定

`tests/test_presence.py`（41件）と`tests/test_presenceui.js`（17件）。
画面の網は`/api/presence`を差し替えて、**行ごとに`canDisconnect`を変える**
——画面が自分の区分だけを見て決めていたら必ず食い違う。

6つの欠陥（メンテナンス者が開発者も切れる／既定を開発者にする／端末キーを
潰すだけにする／切断されても書ける／自己申告の区分を信じる／画面が自分で
判断する）でそれぞれ落ちることを確認済み。

**網が「間違った理由で」通っていたことに注意**——`backend/routes/presence.py`は
`from ..access_mode import current_permission_flags`で**名前を束縛している**ので、
`access_mode`側だけ差し替えても効かない。区分が一般ユーザーのまま、
別の理由の403で全部通っていた。**文言の一部が両方に出るとき、substringだけで
見分けないこと。**

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **権限区分（開発者／メンテナンス者／一般ユーザー）は「何を触れるか」と別の軸**
  （§9.272、利用者の指示「アクセス権限マスタに上位概念としてカテゴリ追加し」）:
  既存の編集可否・スケジュール可否・現場段取り可否が「**何を触れるか**」なのに対し、
  区分は「**アプリそのものをどこまで管理できるか**」。**掛け合わせない**
  （閲覧モードの開発者でも切断はできる。`_WRITE_ALLOWED_MODES['presence']`は
  3モードとも許してある）。**できることを答えるのは`master_repo.role_can()`の
  1箇所**——ルートにも画面にも書き写さない（写すと「画面にはボタンが出るのに
  サーバーが断る」が作れる）。画面へは`role_capabilities()`と行ごとの

- **在席は端末ごとに1ファイル。切断は「書き込みだけ」を止める**（§9.272、
  `backend/presence.py`）: `<共有>\presence\<端末キー>.json`で、**1つのファイルを
