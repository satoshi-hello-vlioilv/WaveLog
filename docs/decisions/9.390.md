# §9.390 設備停止の内訳をもう1階層（利用者の指示）

利用者の指示（原文）:

> **１）設備停止の内訳はもう1階層増やすことができるようにしてください。**

（7件のご指示のうちの1件目。2件目以降は別の記録。）

§9.389 で入れた3階層（分類 → 停止内容 → 内訳）に、**内訳の下をもう1段だけ**
足す。例に出ていた「刃組待ち > ゴムリング」は、実際には
「**ゴムリングの交換**」と「**ゴムリングの増し締め**」のように、
同じ内訳の中でさらに分かれる。

## 1. 深さは「2段まで」で止める

内訳の下にもう1段だけ置ける。**それ以上は作れない**
（`stop_sub_upsert()` が「内訳の階層は2段までです」で断る）。

底なしの木にしなかったのは、**予定へ入れる手順の段数が決められなくなる**から。
登録の画面は「① 内訳 → ② その内訳 → ③ 時間」と番号を振った段で出しており
（§CLAUDE 2「次にすることを常に1つだけ指す」）、深さが可変だと
「あと何段あるか」を人が数えることになる。2段と決めてあるので、
画面に出る段は**最大3つ**で固定できる。

登録する側から見ると、増えるのは**下を持つ内訳を選んだときだけ**。
下を持たない内訳を選べば段は2つのまま——**空の段は出さない**
（出すと「選び忘れた」と読まれる。§CLAUDE 4）。

## 2. 親は同じ表の1列。**親なしは`0`で、`NULL`にしない**

`[設備停止サブカテゴリマスタ]` に `[親サブカテゴリID]` を1列足した
（表を増やさない——2段しかないので、1段目と2段目で表を分ける理由がない）。

**ここが罠。** 親なしを `NULL` で持つと、自然キーの
`UNIQUE (停止理由ID, 親サブカテゴリID, 名称)` が**1件も重複を止められない**。
SQLite の UNIQUE INDEX は **NULL 同士を別物として扱う**ので、
同じ名前の1段目がいくつでも作れてしまう。だから親なしは `0`（`STOP_SUB_ROOT`）。

自然キーに**親まで入れる**のも必要だった。「刃組待ち > ゴムリング > 交換」と
「刃組待ち > フィンガー > 交換」は別物で、親を入れないと2つ目が作れない。
既にある索引は親を含まないので、`PRAGMA index_info` で**列の顔ぶれを見て**
張り替える（索引は導出物なので作り直してよい。行は1つも触らない）。
列そのものを足すのは `add_missing_columns()` の1箇所（§9.216）。

## 3. 並びは「親 → その子」。サーバーが並べて返す

`stop_sub_rows()` は `[親サブカテゴリID]=0` の行を先に置き、
**その直後にその子**を差し込んで返す。画面が木を組み直さずに、
上から順に描けば階層が出る。

**親を失った子**（親だけ消された行）も末尾へ落とさずに返す——
**見えないと消せない**からで、マスタ管理の一覧から片付けられなくなる。

## 4. 消すときは**子も一緒に**消す

`stop_sub_delete()` は `WHERE [サブカテゴリID]=? OR [親サブカテゴリID]=?` で
親と子をまとめて無効化する。親だけ消えると、上の「親を失った子」が
画面に残り、**どこにも属さない内訳**を選べてしまう。
消す前の確認では**巻き添えになる子の名前を並べる**（何が消えるか、押す前に言う）。

## 5. 数えるのは**1段目だけ**

マスタ管理の左ペイン（停止内容の一覧）の「内訳 N件」は**1段目の件数**。
右ペインの一覧に出る行数は親＋子の合計なので、合計で数えると
**同じ言葉が2箇所で違う数を言う**（§CLAUDE 8「同じ情報を2箇所に出さない」）。
2段目まで入れた数はマウスを乗せたときの `title` に出す。

`stop_sub_counts()`（設備停止の一覧の「内訳」列）も同じく1段目だけを数える。

## 6. 既定の分は「2段目 → 1段目 → 停止内容 → 無し」の4段

§9.389 で入れた3段の続き。`stop_default_minutes()` は
`while sid:` で親をたどるので、段が増えても**1箇所のまま**。
2段目に `[標準所要分]` が入っていればそれ、空なら1段目、
それも空なら停止内容の `[標準所要分]`、全部空なら「無し」。
**空欄を0にしない**（§9.389）。

## 7. 予定に書くのは `stopSub`（1段目）と `stopSub2`（2段目）

`[明細JSON]` に入る形は `stop_sub_detail(sub,parent)` の1箇所が決める。

| 選んだもの | `[明細JSON]` |
| --- | --- |
| 1段目（下を持たない） | `{stopSubId, stopSub}` |
| 2段目 | `{stopSubId, stopSub, stopSub2, stopSubTopId}` |

**1段目は `stopSub` のまま**なのが肝心。§9.389 で決めたとおり集計の軸は
`[予定名称]`（＝停止内容の名前）で、内訳は明細の中にある。ここで2段目を
`stopSub` に上書きすると、**今までの集計が黙って割れる**。
2段目は新しい鍵（`stopSub2`）を足す側で持つので、**既に入っている予定は
1文字も変わらない**。

サーバーへ渡すのは**いちばん下の内訳のID**1つ（`stopSubId`）。
親は `stop_sub_parent_of()` でサーバー側が引く——画面から2つ送ると、
食い違った組み合わせを受け取り得る。

行に出る札は `nonWorkSubText()` の1箇所が「**1段目 / 2段目**」と1枚で書く
（紙も同じ1本。§9.389）。

## 8. マスタ管理の画面: 「＋ 下へ」と「足す先」

2段目を作る道は、1段目の行にだけ出る `[＋ 下へ]` ボタン。押すと
一覧の上に「**「ゴムリング」の下へ** ［直下へ戻す］」と出て、
**次に足す行がどこへ入るか**を先に言う（§CLAUDE 2「推測させない」）。
2段目の行は名前を1段ぶん右へ寄せ、`└` を付ける。

**画面の見直しで直した2点**（実物をスクリーンショットで測って気づいた）:

- `[＋ 下へ]` が**器いっぱい（実測350px）に伸びていた**——4列目が `1fr`
  だったため。`justify-self:start` で**中身の長さで止める**（§CLAUDE 11）。
- 左ペインが「内訳5件」・設備停止の一覧が「3」と、**同じ言葉で違う数**を
  言っていた（上の §5）。

**欠陥注入で確かめた3件**（`test_stopsub.py`）:

1. 索引から `[親サブカテゴリID]` を外す → 親違いの同名で `IntegrityError`。
2. 深さの見張りを外す → 「段は2つまで」が落ちる。
3. 消すのを自分の行だけにする → 2件が赤（子が残る）。
