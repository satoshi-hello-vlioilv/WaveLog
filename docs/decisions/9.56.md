# §9.56 メンテナンス導線(マスタ管理)の棚卸し

§9.53・§9.54と同じやり方でマスタのCRUDを一通り叩いた。

**見つけた不具合(いずれも§9.29で適用設備を複数化したときの取りこぼし)**

- **設備を割り当てていない勤務体系が削除できない。** `shift_pattern_delete()`は
  無効化(UPDATE)のあとに設備割当のDELETEを足したが、返していた`cur.rowcount`が
  **後続のDELETEの件数**に上書きされていた。割当0件(=全設備共通、既定の状態)の
  体系では0が返り、呼び出し元が「対象が見つかりません」と判断していた。
  無効化直後に件数を確定させて返す。
- **更新者IDを省くと監査列が空になる。** 画面からは必ず送るが、直接APIを
  叩くと`[登録者ID]`/`[更新者ID]`が空文字で残る。`request_user_id()`が
  端末のログインIDへフォールバックするようにした(循環importを避けるため
  `access_mode`は遅延import)。

**確認して問題が無かったもの**: 同名の二重登録(既存を有効化して1件に保つ)・
論理削除からの同名再登録(復活する)・空文字/空白のみの名称(400で弾く)・
他設備の停止理由IDの流用(拒否)・適用設備の付け外し(消し残さない)。

**高速化**: §9.54のとおりマスタ管理は往復1〜3回/タブでいずれも
`master.sqlite3`(ローカル、1.9ms)。タブ切替のたびの`equipment-master`
再取得(1セッション10回)は、設備マスタで登録・削除した直後に他タブの
選択肢が古くならないための意図的な`force`で、据え置く。
