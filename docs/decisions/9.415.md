# §9.415 断面図の明るさ・模式図の角と字・差分の基準・起動の刻印（利用者の指示）

索引: [決定記録](README.md)

利用者の指示:

> １）刃組ガイダンスの断面図は切り替えた瞬間は断面図になっていません。
> 何度か切り替えて断面図にしても、暗すぎるか明るすぎるか反射の状況が
> 悪すぎて見にくいです。修正をお願いします。
>
> ２）刃組ガイダンスは差分がデフォルトでも出るようにデフォルトの刃組設定で
> 決定している状態にしてください。それを基に差分を出してください。
>
> ３）刃組ガイダンスの2Dのエッジ部分の丸角は無しにしてほしいです。また、やや
> 文字が大きすぎてバランスが悪い表示を見なおしてほしいです。
>
> ４）起動時、アップデート（一回起動した後の再起動や、update.bat起動した後など）
> した後でも「更新を反映中 — ふだんより長い／変わったもの: Pythonの場所
> （…\python.exe → …\pythonw.exe）」というメッセージが出ます。自然な
> メッセージへの修正と内部的に不一致が起こっていないか検証と修正をお願いします。

## ① 断面図は「明るさ」ではなく「光の配分と艶」の問題だった

**先に測った。** 描いた絵をそのまま数える評価関数を書き、切り替えた直後と
数回切り替えたあとの両方で撮った。

| | 直したまえ | 直したあと |
| --- | --- | --- |
| 部材の白飛び（輝度246以上） | **36.7%** | **0%** |
| 部材の平均輝度 ／ 地（`--bs-3d-bg`） | 241.1 ／ 241.3 | 187.4 ／ 241.3 |
| 地との差（ΔL） | **ほぼ0** | **53.9** |

**「切り替えた瞬間は断面図になっていない」は、状態の食い違いではなかった。**
`view()` は切り替えた直後も数回切り替えたあとも同じ（`cut:true`・`ortho:true`・
`clips:1`）で、器の大きさも6フレーム通して 1076×540 のまま動かない。
**絵が読めないので断面図に見えていなかった**——軸もスペーサーも板も真っ白で、
地との差が1も無かった（上の表）。原因は2つとも「断面図に固有」のもの:

1. **光が重なる。** 立体図の配分（地明かり.45／主光1.05／補助.38）は機械まわりを
   斜め上から立ち上げるためのもの。断面図の切り口は**カメラをまっすぐ向いた
   平らな面**で、そこへ手前光（.62・§9.413で足した）まで当たるので、
   4つが**同じ面に重なる**。
2. **艶が映り込む。** 立体図の部材は金属として磨いてある（`metalness` .6〜.8）。
   面が正対すると映り込みがそのまま返り、**材質の色ではなく光の色（白）**が出る
   ——鋼も板も耳も同じ白になる。

どちらか片方を直すだけでも白飛びは消える（欠陥注入で確かめた）が、
**両方直す**。狙いは「模式図と同じ読み方ができる」こと（§9.412）なので、
断面図は**地明かりを主役に平らに照らし、艶を落として材質の色を出す**。

| | 地明かり | 主光 | 補助 | 手前 | 艶（`metalness`） |
| --- | --- | --- | --- | --- | --- |
| 立体図 | 0.45 | 1.05 | 0.38 | 0 | 0.78（そのまま） |
| 断面図 | **0.78** | 0.22 | 0.10 | 0.26 | **0.10 以下** |

**分けるのは1箇所ずつ。** 光は `LIGHT` と `applyCut()`、艶は `matOf()`。
部材を作っているところ（`machine()`・`material()`）は今までどおり1つの綴りで
呼び、写しは名前（`…·cut`）で分ける——両方の図で同じ色・同じ名前のまま、
艶だけが変わる。

**板と耳屑は模式図と同じ色にした**（`--bs-fig-strip`／`--bs-fig-trim`）。
断面図の板は**いちばん薄い物**（見かけの厚みを8倍に誇張してなお数px）なので、
立体図の明るい鋼色のままだと地に溶ける（実測 231 対 241、差は10）。
2つの図で同じ物が同じ色になる（§CLAUDE 8）。

### 器の大きさは「窓」ではなく「器」を見張る

`resize` は窓の大きさしか見ていないので、**図を切り替えて器の幅・高さが
変わったときは呼ばれない**。描き終えたあとに器が動くと、前の大きさのまま
引き伸ばされた絵が残る。`ResizeObserver` で器そのものを見張る。
あわせて `setMode` は**図を離れるときも `applyCut()` を通す**——以前はそこで
戻っていたので、模式図へ移ったあとも切断面と断面図の光が場面に残ったまま
`D3.cut` だけ false になり、**断面図でも立体図でもない1枚**を描き得た。

## ② 差分の基準は「記録 → 標準構成 → 無し」の3段

記録が1件も無い台車では、台車の列が全部「—」になり
**「そのまま使える 0 ／ 棚から持ち出す 14」**と出ていた。
これは「部材を1つ残らず棚から持ち出す」という読みになるが、
**台車が空だとは分かっていない**ので事実ではない。

記録が無いときは、**いまの材料を既定の刃組設定（`刃組基準値マスタ`＋既定値）で
組んだ標準構成**を基準に置く。計算は**スケジュール一覧の見込みと同じ1本**
（`standardState()`＋`solve()`＋`snapshot()`・§9.408）から引く——2つ持つと
「一覧とガイダンスで数が違う」を作れる。

**出どころは字で書き分ける**（§CLAUDE 6）。列の見出しは「台車」ではなく
**「標準」**にし、窓の上で「組んだ事実ではありません」と断る——
取り違えると「もう組んである」と読める（§9.408 と同じ線引き）。
条の幅が1本も読めないときは標準構成も出さない（0で埋めない・§9.231）。

## ③ 模式図の「物」は直角、札は値より大きくしない

**角丸をやめる。** この図は実寸を目で比べるためのもので、角丸は縁を実際より
短く見せる——0.05mm刻みのスペーサーが並ぶ図で、**幅1.2pxの部材に rx=2**が
付いていた。直角にするのは、軸の帯・有効幅の青い印・部材・板／条／耳・刃、
そして区間の拡大図の同じもの。**角丸が残るのは文字の器だけ**——記号バッジ
（`bs-bdgr`）と設定の帯（`bs-chip-band`。名前を付けて網が名指しできるようにした）。

**字の順序が逆だった。** 図の情報は「①部材の並び（主役）→②読み取る値
（条番号・条幅・耳屑幅）→③文脈の目印（上軸・下軸・材料、DS／OS）」の順なのに、
③がいちばん大きかった。

| | 直したまえ | 直したあと |
| --- | --- | --- |
| DS／OS | 20.8px | **15.9px** |
| 行見出し（上軸・下軸・材料） | 18.4px | **15.9px** |
| 条の番号・記号バッジ | 15.9px | 15.9px（変えない） |
| 条幅 | 13.5px | 13.5px（変えない） |

網は**比べて見る**（`最大の字 ≦ 条番号の字 × 1.05`）。器の幅で倍率が動くので、
pxを直に書くと窓の大きさが変わっただけで落ちる。

## ④ `pythonw.exe` と `python.exe` を同じものとして数える

**update.bat の「次回からの起動が速くなります」が一度も守られていなかった。**

- `update.bat` は `python program\setup_app.py`（コンソールの **python.exe**）
- `Start.vbs` は `pythonw.exe`（黒い画面を出さない）

刻印（§9.225）は `sys.executable` をそのまま控えていたので、**この2つは
永久に食い違う**。update.bat を実行した次の起動は必ず完全な確認（30〜60秒）へ
落ち、待機画面に「変わったもの: Pythonの場所（…python.exe → …pythonw.exe）」と
出ていた。2つは同じフォルダーに並び、同じ `sys.prefix`・同じ `site-packages`・
同じバイトコードを見るので、**刻印が門にしているもの（部品の有無とバイトコード）に
差は出ない**。末尾の `w` だけを落としてそろえる（`python_mark()`）。

- **そろえるのは書くときと読むときの両方。** `current()` 側だけに書くと、
  **前の版が書いた刻印**が永久に食い違ったままになる。
- 綴りを切るのは**文字列のまま**やる。`pathlib` はいま動いているOSの綴りで
  読むので、Linuxで回す網が `C:\…\pythonw.exe` を1つの名前と読んでしまい、
  **本番だけ効いて網では確かめられない**作りになる。
- 刻印の形が変わったので `STAMP_VERSION` を 4 へ上げる（このあと1回だけ
  完全な確認が走る）。

### メッセージは「断片」ではなく1文にする

「変わったもの: 」＋名前、という組み立てだったので、
**「変わったもの: まだ確認していません」**のように文として成り立たない並びが
出ていた。理由は**それだけで読める1文**を返す（`ready.diff()`）:

| | 直したまえ | 直したあと |
| --- | --- | --- |
| 刻印が無い | 変わったもの: まだ確認していません | **この端末では初めての起動です** |
| 版が上がった | 変わったもの: アプリの版（2.313.0 → 2.314.0） | **アプリの版が上がりました（2.313.0 → 2.314.0）** |
| 形が変わった | 確認の仕組みの版（3 → 4）＋他が全部 | **起動前の確認の仕組みが新しくなりました**（これ1件だけ） |
| 長い置き場 | 絶対パス2本（実測124文字） | **…\pythoncore-3.14-64\python.exe**（末尾2つ） |

**版が上がっていないのに「更新を反映中」と言わない。** 初めての起動も
Pythonの入れ替えも同じ段（30〜60秒）を通るので、題を1つに決め打つと画面が
事実と食い違う。`boot_status` に `WORK_SETUP` を足し、待機画面は
**「更新を反映中」／「起動前の確認中」**を言い分ける。
**どちらかを決めるのはサーバー**（起動処理が刻印の鍵を見る）で、画面は答えを
字にするだけ——`ready.diff()` が鍵つきで返すので、画面が綴りを探さずに済む
（同じ言葉を2箇所が持たない・§CLAUDE 8）。
