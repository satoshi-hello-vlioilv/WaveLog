# §9.391 母材と丈毎を、入力内容の別々の項目にする（利用者の指示）

利用者の指示（原文）:

> **３）母材・丈毎の項目について、母材と丈毎を入力内容の項目が一緒になって
> いますが、ボタンを分けて1枚のカードに配置するように変更してください。**

確認して決めたこと（`AskUserQuestion`）:

| 迷い | 決めたこと |
| --- | --- |
| 母材と丈毎をどう分けるか | **2つに分ける**（入力内容の項目を2つにし、選んだ側のカードを1枚だけ出す） |

**これは §9.160 の決定を撤回する記録。** あちらは「母材」と「揃い/肉厚/長さ」を
1つの項目にまとめた（利用者の当時の指示「選択1つにまとめ、入力欄はわかりやすく
整理して」）。今回はその逆を指示された。**撤回の理由は下の §1 に書く。**

## 1. なぜ1つにまとめた形をやめるのか

§9.160でまとめた形は、**1つの面に2枚のカードを縦に積む**作りだった。
右の作業面は実測853pxで、そこへ母材（4列×3段）と丈の表（6列×N行）が
上下に入る。**どちらも面の半分しか使えない**ので、

- 丈が多いロットでは**丈の表が先に潰れる**（母材の高さは丈数に関係なく一定）。
- 進捗のチップも「母材8欄＋丈N本」の**合算**になり、
  **どちらが残っているのか数字から読めない**（§9.208 ②で入力数をその場で
  数えるようにしたのに、その数が2つの作業の和になっていた）。

項目を2つに分ければ、選んだ側が**面いっぱいの1枚**になる
（§CLAUDE 1「面積は頻度 × 重要度で配る」）。器（`.work-panel`）は1つのまま
**出るカードだけが入れ替わる**ので、割り付けの規則は1箇所で済む。

## 2. 名前と、保存済みレコードの寄せ方

| いま | 旧名（保存済みレコードにある） |
| --- | --- |
| `母材` | `母材/丈毎`（§9.208）、`母材・揃い/肉厚/長さ`（§9.160） |
| `丈毎` | `揃い/肉厚/長さ`（§9.160より前） |

寄せるのは `WL.measureItem.normalize()` の1箇所。**まとめていた頃の
`母材/丈毎` は「母材」へ寄せる**——先に入れる側なので、開いた人が
次にすることが変わらない。寄せないと `select.value` が空文字になり、
**どの項目でもない状態**で開く（`LEGACY`（板厚/板幅）と同じ扱い）。

`WL.measureItem` が答えるのは3つ:

- `isMother(type)` … 母材の面か
- `isPiece(type)` … 丈毎の面か
- `isMaterial(type)` … **どちらか**（＝測定器から受けない手入力の面）。
  入力欄の保護と案内の札だけがこれを使う。

## 3. 語彙は `WL.measureItem.ALL` の1箇所

入力内容の顔ぶれ（9項目）は `ALL` が持つ。**画面の `#measureType` とは別に
持つ**のが肝心で、マスタ管理の「開く条件」（操業データ項目の群を自動で開く
測定項目）は**画面に出ていない項目も選べる必要がある**——設備ごとに項目を
伏せられるようになると（次の段）、DOMを読む作りでは伏せた項目を条件に
できない。`tests/test_msteps.js` が語彙と画面の選択肢の一致を見る。

マスタに旧名で入っている「開く条件」も、読むときに `normalize()` へ通す
（寄せないと**当たらない群**ができ、畳んだまま開かない）。

## 4. 踏んだ罠: 器の無い鍵で測定表を描こうとして落ちた

`WL.measureItem.KEYS` は項目名 → 測定値の鍵。丈毎に `piece` を足したところ、
**`Cannot read properties of undefined (reading '1')` が2件**出た。

`renderMeasureGridVertical()` が

```js
const actualKey=key==='mother'?'width':key;
const values=m.measurements[actualKey][li];
```

と書いており、**`mother` だけを名指しで避けていた**。`m.measurements` は
`thickness`/`width`/`lateral`/… しか持たないので、`piece` を渡すと
`undefined[li]` で落ちる。

直し方は**名前を並べず、器の有無で見る**:

```js
const actualKey=(m.measurements&&m.measurements[key])?key:'width';
```

数直線の `numberlinePendingKind()` も同じ形（`key==='mother'||key==='flatness'`）
だったので、同じく器の有無で見るようにした。**手入力の面を足すたびに
名前の一覧を直して回る作りは、必ずどこか1箇所を忘れる**（§9.138 と同じ壊れ方）。

## 5. 見ているのは「いま出している面」だけ

`activeRequiredControls()` は、母材の面なら母材の欄、丈毎の面なら丈の欄だけを
必須に数える。§9.160では両方を一緒に見ていたが、それは**同じ面にあったから**。
面が分かれた今も両方を見ると、**画面に出ていない欄で赤が出る**。

全項目の取りこぼしは `measure-progress.js` の「完了前の確認」が別に見ている
（そちらは面を切り替えずに全部を集計する。これが本来の受け皿）。

## 6. 帳票の「丈別データ」は、面が分かれても今までどおり出す

一度 `rpShowProduct()` を `isMaterial` → `isPiece` にしたが、**戻した**
（§9.395）。**「最大」で刷る白紙の控え欄が出せなくなる**からで（§9.132／
§9.309。丈の表を空欄のまま刷って手で書く現場がある）、`isPiece` だけにすると
母材を選んだまま完了したロットで枠ごと消える。

`isMaterial` は母材・丈毎のどちらでも真なので、**§9.391より前とまったく
同じ顔ぶれ**になる——**触っていない現場の紙を勝手に変えない**ほうを採る。
（`tests/test_rpmaster.js` がこれを捕まえた: 丈を書いていない記録で
「丈別データ」が紙から消え、4件が赤になった。）

## 7. 固定した網（既存の網の書き換えを含む）

| 網 | 直したこと |
| --- | --- |
| `test_msteps.js` | 一覧は**9項目**／語彙と選択肢の一致／「母材」を選ぶと母材のカード1枚だけ・「丈毎」を選ぶと丈の表1枚だけ／丈を打つと**丈毎**の入力数だけが増える（母材は動かない）／幅の検査に丈毎の面を足す |
| `test_mcore.js` | 既定の項目名（`母材`） |
| `test_opmother.js` | 母材の進捗の**分母は母材の欄数ちょうど**（丈を足さない） |

**チップは埋まりきると「済」になる**ので、数だけで比べると丈1本のロットで
`0/1 → 済` が `NaN` になる（実際に落ちた）。判定は「済なら増えた」で書く。

`test_mcore` 41 ／ `test_opmother` 27 ／ 帳票・操業データ・見た目の22本 892）。
