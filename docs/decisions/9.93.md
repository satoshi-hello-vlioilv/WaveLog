# §9.93 一覧が出るまでの往復を減らす / 読み込みの拡張点をフックへ

**症状。** 「ブラウザを起動してからデータが読み込まれるまでが長い。
操作を受け付けるまで体感10秒くらい待たされる。」

**サーバーは0.16秒で待ち受けている。** 遅いのは画面側だった。要求の並びを
実測すると、**`/api/table`が始まるのは表示開始から631ms地点**で、その前に
往復が9本**直列で**並んでいた。

```
whoami → catalog → build → equipment-master → filter-presets → access-mode
  → tables → column-layout-master → display-rule-master → sort-presets
  → list-view-master → **ここでやっと /api/table**
```

サンドボックスでは1往復が4〜130msだが、**共有フォルダ越しの実機では
1往復が数百ms**になる。9本並べば、それだけで数秒を失う。

**直したこと。**

1. **見せ方の設定と一覧データを同時に取りに行く**(`fetchTableData`)。
   4つの設定(列レイアウト/表示ルール/並びプリセット/行間)はどれも一覧
   データに依存しない。束ねて並列に投げ、描く直前に揃っていればよい。
   どれが読めなくても既定の見せ方で一覧は出す(fail-open)。
2. **起動時のカタログと版数を同時に**投げる(`init()`)。下書き件数の更新は
   待たない(一覧の表示に要らない)。
3. **テーブル構成を端末に覚えておく**(`listTablesCacheV1`)。
   「カタログ→テーブル一覧→一覧データ」の3往復を毎回やり直していた。
   前回**実際に確認した**一覧なので推測ではない——データソースの
   `preferred`(設定値)は、そのDBに実在するとは限らない(品質データの既定が
   「仕掛」のまま、という実例がある。これで一度取り違えた)。
   覚えている一覧で先へ進み、**この起動で1回だけ**裏で取り直して
   食い違えば入れ替える。2回目以降の切替は往復ゼロ(§9.46の約束)。

結果: **一覧取得の開始 631ms → 342ms、直列の段数 9 → 3。**

**併せて`load()`の全置換をやめた。** `filters.js`が
`load=async function(){...}`で丸ごと差し替えており、元の定義をgrepで辿っても
最終的な実装に行き着かなかった。実際「list-view.js側だけ直して効いていない」
が**3回**起きている(品質データ結合・キャッシュ・読み込み時間の計測)。
→ **`WL.listHooks`**を新設し、拡張したい側は登録する。

| フック | いつ | 何をする |
|---|---|---|
| `onQuery(fn)` | 問い合わせを組み立てた後 | `URLSearchParams`へ条件を足す |
| `onAfter(fn)` | 一覧を描き終えた後 | 付随する表示を更新する |

本体は1箇所のままで、誰が何を足しているかが登録の行から分かる。1つの
フックが転んでも一覧は出す(fail-open、例外はコンソールへ)。
