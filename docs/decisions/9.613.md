# §9.613 作業スケジュールで運んだ行が、運んだ位置に留まり続ける——予定の並びで出す・書く前の読みを当てない（利用者の指摘）

索引: [決定記録](README.md)｜前: [§9.612](9.612.md)｜関係: [§9.11](9.11.md)・[§9.39](9.39.md)・[§9.185](9.185.md)・[§9.188](9.188.md)・[§9.192](9.192.md)・[§9.200](9.200.md)・[§9.201](9.201.md)・[§9.291](9.291.md)・[§9.611](9.611.md)

## 経緯（利用者の言葉）

> スケジュール機能のD&D位置がずれる不具合
> ドラッグした位置に入らず、一番上に入る、位置を調整しても戻る。戻らない時もあるし不安定。修正をお願いします。

## 物差し（直す前に測った）

本物のマウスで行を運び（Playwright の `mouse.down/move/up`・HTML5 のドラッグ）、**離したあと 100ms ごとに並びを控えて**
「狙った位置にいた割合（留まる割合）」と「最後に画面とサーバーが狙った並びか」を数えた。1回だけ見る網は「戻って、また来る」を見逃す。

| 場面 | 直す前 | 直した後 |
| --- | --- | --- |
| ふつう（見えている範囲で8通り） | 100%・8/8 | 100%・8/8 |
| 書込が遅い（1.8秒） | 100%・正しい | 100%・正しい |
| 書込の最中に描き直しが入る（測定画面を閉じた・見張りの読み直し） | **76%**（1.5秒戻る）・正しい | 100%・正しい |
| 書いたあとの読みが**書く前の並び**を返す（書込役への中継・Box の同期待ち） | **8%・戻ったまま** | 100%・正しい |
| 上の直後にもう1回運ぶ | **断られて戻る**（「ほかの端末が先に並べ替えました」） | 断られない |
| 仕掛一覧から落として差し込み、読みが古い | **入れた行が消える** | 100%・狙った行の前 |

固定する網は `tests/test_scdndhold.js`。直す前のコードへ戻すと 5件落ちる（欠陥注入で確かめた）。

## 原因（測って分かった2つ）

1. **時刻順に並べ直すので、並べ替えた直後の描き直しで行が戻る。** 表は予定の開始時刻で並べている（§9.39）。運んだ行は
   画面と`scState.entries`の並びは変わるが、**時刻はサーバーが展開し直して初めて新しくなる**。そのあいだに描き直しが
   1回でも入ると、前の時刻で並べ直して行が元の位置へ戻り、時刻が届くとまた動く——「戻る」「戻らない時もある」。
   描き直しは書込の最中にも起きる（測定画面を閉じた・共有の見張りの読み直し・楽観追加の差し替え）。
2. **書く前の並びを持った読みを当てていた。** 世代（§9.200）は「書込を積んだ時点より前に出した読み」しか捨てない。
   - 書込が**まだサーバーへ届く前**に出した読み（書込の列の 150ms の待ち・書込の往復中）は世代が同じで当たる。
   - **書込役へ頼んだ書込**（§9.192）のあと、この端末の写しは書込役が書いた共有に**まだ追いついていない**ことがある
     （写した直後30秒の休み・共有の見かけの控え・Box の同期待ち）。書込のあとの読み直し（§9.185）が書く前の並びを返す。
   古い並びが画面に出ると、それを土台に次を運ぶたびにサーバーが「掴む前の並びが違う」（§9.291 ③）で断り、また戻る。

「一番上に入る」は、フィクスチャ（40行・同じ設備）と上の場面では**再現できなかった**。端の自動の送り（§9.374）は
この画面の寸法では縁の帯（48px）に届かず、原因ではなかった（測った）。実機の並び・共有の条件で起きているかは**分からない**。

## 決めたこと

- **動かせる予定（固定していない・未着手・親の行）どうしは、時刻ではなく予定の並び（配列の順）で出す**（`keepPlanOrder()`）。
  時刻が新しければ2つは同じ並び（サーバーは予定の並びの順に時刻を置く・固定した行だけが時刻で割り込む）なので、ふだんは
  何も変わらない。固定した行・済んだ行・作業中の行が時刻で決めた席は残し、その席の間を配列の順で埋め直す
  （`commitDragOrder()`と同じ「席はそのまま・中身を差し替える」）。
- **書込の応答と予定の読みに共有の改訂番号（`revision`）を持たせる。** `with_write(..., with_revision=True)`が書いたあとの
  番号を返し、`_write_response()`が応答へ載せる（中継でも書込役の答えがそのまま届く）。`plan_list()`は読んだ写しの番号を返す。
- 画面は**自分の書込が返した番号より古い読みを当てない**（`planBehind()`）。0.6秒から間を広げて読み直し（合計およそ24秒）、
  待ち切れなければ当てて「共有への反映が遅れています」と字で言う（黙って古い並びに戻さない）。
- **書込が残っている間に出した読みは当てない**（`planFetch()`が`busy`の印を付ける）。捨てたら、書込の列の終わりで必ず
  1回読み直す（`takeReloadAfterQueue()`）。
- **掴んでいる最中に届いた読みは描かない**（表を組み直すと掴んだ行と運んだ途中の並びが消える）。動かさずに離したときだけ、
  離したあとに取り直す（動かしたなら書込のあとに取り直す）。
- 書込役へ頼んで書けたら、**書込役が答えた番号へ写しが届くまで、写した直後の休みと見かけの控えを当てにしない**
  （`schedule_sync.expect_revision()`・`_behind()`）。SMB の共有なら次の読みで追いつく。Box の同期待ちは上の画面の側が受け持つ。
- 網の顔ぶれの直し忘れ（§9.611 で「開始・終了」の口を中継に足したが`test_scowner`が6本のままだった）もここで直した。

## 撤回・採らなかった案

- 並べ替えた直後に画面で時刻を計算し直す: 稼働カレンダー・勤務・固定開始・枠を画面へ写すことになり、答えが2つになる。
- 書込のあとに必ず共有を丸ごと写し直す（`fetch_snapshot(force=True)`）: Box では写しても古いままで効かず、毎回の書込に
  数百 ms を足す。番号で「追いついたか」を見るほうが、どの共有でも同じ答えになる。
