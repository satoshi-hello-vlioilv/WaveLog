# §9.225 起動の高速化（確認を`setup.bat`へ切り出し、刻印で飛ばす）（利用者の指示）

> 起動の高速化を検討して下さい。起動に必要なライブラリ等のチェックを別の
> batファイルで受け持ち、繰り返し使用時には最小構成の起動ファイルで
> 起動したいです。

利用者の決定は3つ——**①刻印が食い違ったら自動で従来経路へ落ちる**、
**②常駐（待機モード）は今はやらない**、**③配置は基本共有・一部の端末は
任意でローカル**。③が設計をほぼ決める。

#### 実測（この環境。Windows・ウイルス対策あり・共有配置ではさらに開く）

| | |
|---|---|
| 素のPython起動 | 11ms |
| launcher系モジュール | 47ms |
| flaskの読み込み | 151ms |
| app本体（flask込み・44ファイル/19,130行） | 237ms |
| **バイトコードが無い状態のapp読み込み** | **1,168ms**（有ると211ms＝**5.5倍**）|
| flaskの有無だけを調べる（`find_spec`） | 83ms |

**アプリのコードは軽い**（backend全体で40ms）。効くのは
**バイトコードの有無**と、**毎回やっている確認**のほうだった。

#### 何を切り出したか

`setup.bat`→`setup_app.py`→**`backend/launcher/setup_check.py`**（実処理）。

  1. ローカル領域のフォルダを作る
  2. 必要な部品(flask)の確認と導入
  3. **バイトコードの事前コンパイル**（いちばん効く）
  4. 旧配置DBの取り込み
  5. 起動待機画面を手元へ写す
  6. 通ったら刻印を書く

**実処理は1箇所**。`setup.bat`と、起動時のフォールバックが同じここを通る
——2つ持つと「setup.batでは通るのに起動では失敗する」が作れる
（`start_app.py`が冒頭で「起動経路を1本に揃える」と書いているのと同じ理由）。
**起動用の別ファイルは作っていない**。利用者の求めた「最小構成の起動」は
既存の1本の入口の中で刻印が実現するので、入口を2つにする必要が無い。

#### 刻印（`backend/launcher/ready.py`）

**刻印は速さのための門であって、正しさの門ではない。** バイトコードが
古いかどうかは**Python自身が**`.pyc`の中の元ファイルの更新時刻と大きさで
判定する。だから刻印を見誤っても古いコードが動くことはなく、食い違ったら
**止めずに確認し直せばよい**（利用者の指示①）。止めると現場では
「起動しなくなった」としか見えない。

**刻印は端末ごと**（`%LOCALAPPDATA%\WaveLog\runtime\ready.json`）。
共有配置では、共有側へ書くと**1台で確認した結果を全台が信じる**ことになる
——Pythonの場所も版も端末ごとに違う。

**材料は軽いものだけ**にする——版・`requirements.txt`のstat・Pythonの
場所と版・置き場所。全44ファイルの更新時刻を見に行くと、**共有越しでは
確認そのものが起動より重くなる**。アプリの版は意味のある変更のたびに
上がる約束（CLAUDE.md）なので、これで足りる。

**食い違いは名前で言う**（「アプリの版（2.95.1 → 2.96.0）」）。
理由の分からない再確認は、遅いだけで利用者が打つ手を持てない（§4）。

**刻印があるのに部品が消えていたら、その場で確認し直して1回だけやり直す**
（`from backend.launcher import server`の`ImportError`を拾う）。刻印を
信じ切って落ちない。

#### 共有配置だから直したこと

**進捗ファイル（`boot_status.js`）を共有へ書かない。** 以前はアプリ本体の
隣へ、起動のたびに6回書いていた。共有配置では**全台が同じ1つを取り合う**
——2台が同時に起動すると相手の進捗が自分の待機画面に出る。
`loading.html`は`<script src="boot_status.js">`と**相対で**読むので、
**待機画面を手元へ写して開けば**それだけで置き場が切り替わる（画面側の
変更は要らない）。以前の版が共有へ残した1個は`setup_check`が片付ける。

**バイトコードも端末ごと**（`_pycache_bootstrap`が`sys.pycache_prefix`を
向けてある）。`compileall`は`importlib.util.cache_from_source()`を通るので
prefixに従う——**必ず`_pycache_bootstrap`が効いた状態で走らせること**。
素で走らせると元ファイルの隣（共有）へ書こうとする。

#### 体感の取りこぼし

待機画面のポーリングが**500ms固定**だった。起動が1秒を切ると、この
取りこぼしが体感の半分を占める。立ち上がりの5秒だけ120msにして、
そのあとは500msへ戻す（遅い端末で聞き続けても早くはならないし、共有の
応答待ちのときに問い合わせを増やしたくない）。

#### 結果

    更新直後（バイトコード無し・setup未実行）  1,181ms
    setup.bat のあとの1回目                      611ms
    2回目以降                                    227ms（3回測って同値）

**やらなかったこと**: 常駐（待機モード）は利用者の判断で見送り。
zipapp化も見送った——共有配置では効くが、現地で1ファイルだけ差し替える
運用ができなくなる。

固定は`tests/test_faststart.py`。**確かめるときは刻印を消した状態で
「起動できること」まで見ること**——「刻印が書かれる」だけを見る網は、
フォールバックが壊れていても通る。
