# §9.46 仕掛一覧・品質データの読み直しをやめる

§9.42でスケジュール画面に入れた「一度読んだら持っておく」を、**仕掛一覧と
品質データ**にも広げた。サイドバーで仕掛↔品質データを行き来するたびに
`/api/tables`と`/api/table`を取り直しており、本番では共有上のAccessを
その都度開き直すことになる。

**キャッシュの単位は「取得クエリそのもの」**。`db`/`table`/`page`/
`page_size`/`search`/`join_quality`を組み立てた`URLSearchParams`の文字列を
そのままキーにする(`tableCache`、TTL3分・最大40件)。条件が1つでも違えば
別の結果なので、キーが違えば必ず取りに行く。テーブル構成(`/api/tables`)は
運用中に変わらないため`tablesCache`で無期限に持つ。

**速いが嘘はつかない**ための3点セット:

| | |
|---|---|
| TTL 3分 | 仕掛は生きたデータ。無期限に持つと古い在庫を見せ続ける |
| 鮮度表示 | ヘッダーに「たった今の内容」「N分前の内容」(`#listFreshness`)。取り立てのときは消す |
| 再読込 | `#reload`は`invalidateTableCache()`→`load(true)`で必ずサーバーから取り直す |

**待機表示は「遅かったときだけ」出す**。`showWaiting()`直呼びをやめ、
`withWaiting()`の遅延表示(350ms)に委ねた。キャッシュ命中なら一度も出ない。
オーバーレイを出すこと自体が表示待ちの描画フレームを要求するため、
出して即消すと**速くなったのにかえって遅く見える**(実測: 切替~描画完了が
450ms→196ms、うちネットワーク往復は0回)。

`filters.js`は`load()`を丸ごと置き換えている(クエリにフィルタ条件と並べ替えを
足すため)。**片方だけ直して反映されない事故を防ぐ**ため、キャッシュ判定・
取得・鮮度更新・待機表示は`fetchTableData(key,force)`へ集約し、両方の
`load()`がこれを呼ぶ形にした。

サーバー側では`db_access.cols(c,t)`に60秒のキャッシュを入れた(列一覧は
1リクエスト中に何度も引かれるが、実行中にテーブル定義は変わらない)。

| | 改善前 | 改善後 |
|---|---|---|
| 仕掛↔品質データの往復 | 毎回 `/api/tables`+`/api/table` | **0回** |
| 切替~描画完了 | 450ms | 196ms |
