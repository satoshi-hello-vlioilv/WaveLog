# §9.180 誰が・どの端末で（登録者IDと端末名）（利用者の指示）

利用者の指示は「どのPC、どのIDから編集をされたデータなのか。スケジュールデータ→
スケジュールを組み込んだIDとPC名、測定データ→測定データを入力開始したIDとPC名を
データに追加する」。

IDだけでは足りない。同じ人が複数の端末を使うし、**端末ごとに役割が違う**
（測定する端末・計画を立てる端末）ので、「誰が」と「どこから」の両方が要る。

#### 端末名の出どころ

`socket.gethostname()`。**サーバーは各端末で動いている**（1台1プロセスが共有DBを
読み書きする作り）ので、これがそのまま操作した端末の名前になる。
`db_access.request_pc_name(x)`が`request_user_id(x)`と**対**で答える1箇所。

画面が明示的に送った値を優先するのは、**別のPCで作られたデータを引き継いで保存する
場合**に「作った端末」を上書きしないため。

#### 登録と更新を分けて持つ

| | 何 | 上書きするか |
|---|---|---|
| 登録者ID・登録端末名 | 予定へ入れた人／測定を始めた人と端末 | **しない** |
| 更新者ID・更新端末名 | 最後に動かした／保存した人と端末 | 毎回 |

**1つにまとめないこと。** 並べ替えただけの人が「入れた人」に見えると責任の所在が
変わる。測定は別のPCで続きを開ける（§9.91）ので、保存のたびに書き換えると
「誰が始めたか」が最後に保存した端末で塗り潰される。

#### 保存先

- **作業予定**: `[登録端末名]`／`[更新端末名]`を足す。**共有DBは既に現場で動いて
  いるので作り直さない**——「無ければ足す」で移行し、古い版のアプリが書いた行は
  NULLのまま読める（`ensure_plan_table`）。
- **Web測定バックアップ**: `[登録者ID]`／`[登録端末名]`／`[更新者ID]`／
  `[更新端末名]`／`[登録日時]`を同じやり方で足す。**1行を作り直す作り**なので、
  消す前に既存の登録側を控えてから入れ直す（そうしないと再保存で消える）。
- **測定レコード自身**にも`createdBy`/`createdPc`/`createdAt`を持たせる
  （`blankMeasure`）。**作った時点の名札を持って回る**のが正しく、別のPCで開いても
  始めた端末が残る。端末名が取れないことがあるので、そのときは空で保存し、
  サーバーが自分のホスト名で埋める。

#### 画面

- **スケジュール表**: 登録者・登録端末・更新者・更新端末の4列。**既定では出さない**
  （毎回見るものではないので場所を取らせない。§14「面積は頻度×重要度」）。
  一度も保存していないうちは既定の並び、という判定は`timelineHiddenSet()`が持つ
  （データ一覧の`recordInitialHidden()`・§9.162と同じ考え方）。
- **行の詳細（▾）には必ず出す。** 隠していても1クリックで辿れる。ラベル列は
  固定幅（§9.129）。端末名を持たない古い予定は、そのことを文で書く
  （空欄だけだと「読めていない」のか「記録が無い」のか分からない）。
- **データ一覧**: 入力開始者・入力開始端末・入力開始日時・最終更新者・最終更新端末を
  候補の列として足す（既定は非表示。§9.162のとおり新しい候補は自動で隠れる）。
  他のPCのぶんは**列の値から読む**——中身（ペイロード）は開くときに1件だけ取る
  決まりなので、列に無いと空欄になる。
- **セルの文字は1箇所が作る**（`SC_FIXED_TEXT`）。行の中身と設定パネルの見本が
  同じ表を見るので、片方だけ直した状態が作れない。

固定は`tests/test_audittrail.js`。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **「誰が・どの端末で」は登録と更新を分けて持つ**（§9.180）: IDだけでは同じ人が
  別のPCから触った場合を見分けられない（端末ごとに役割が違う）。端末名は
  `db_access.request_pc_name(x)`が答える**1箇所**で、`request_user_id(x)`と対。
  出どころは`socket.gethostname()`——**サーバーは各端末で動いている**ので、それが
  操作した端末になる。**登録側（予定へ入れた人／測定を始めた人と端末）は上書き
  しないこと**——並べ替えただけの人が「入れた人」に見えると責任の所在が変わり、
  測定は別のPCで続きを開ける（§9.91）ので保存のたびに書き換えると始めた端末が
  最後に保存した端末で塗り潰される。`Web測定バックアップ`は**1行を作り直す作り**
  なので、**消す前に既存の登録側を控えてから入れ直す**（控えないと再保存で消える）。
  列は`作業予定`＝`[登録端末名]`/`[更新端末名]`、バックアップ＝`[登録者ID]`ほか4列で、
  どちらも**「無ければ足す」で移行**する（共有DBは現場で動いているので作り直さない）。
  測定レコード自身も`createdBy`/`createdPc`/`createdAt`を持ち、**取れなければ空で
  保存してサーバーが埋める**。画面ではスケジュール表の4列・データ一覧の5列とも
  **既定で出さない**（`timelineHiddenSet()`が「保存済みの並びがあるか」で分ける。
  §9.162と同じ）が、**行の詳細には必ず出す**。セルの文字は`SC_FIXED_TEXT`の1箇所が
  作り、設定パネルの見本も同じ表を見る。固定は`tests/test_audittrail.js`。
