# §9.370 2段目（煙テスト）が「まっさらな取得」で落ちていた——原因は権限マスタの1行

**背景。** §9.369 で1段目（純粋な網）を緑にしたあと、2段目（煙テスト）だけが
`test_sccat.js` の1本で落ち続けていた。症状は

```
test_sccat.js              0 PASS / 0 FAIL    13s [FATAL]
      FATAL page.waitForSelector: Timeout 10000ms exceeded.   （.sc-board-row）
```

で、**単独で回しても必ず落ちる**（順番や置き土産ではない）。開発機では通る。

## 遠回りした2つの道（記録として残す）

**道①「マスタの表が無いのでは」。** まっさらな取得では `bootstrap()` が作るのは
`データソースマスタ`・`パス設定マスタ`・`クエリ結合マスタ`の3つだけで、残りは
**画面が最初に触ったときに作られる**。`reseed`（`make_fixture.fix_master()`）は
「表が在るときだけ」種を入れるので、**1件も入らないまま**その姿を
`snap_master` が「あるべき姿」として控えてしまう——という筋は**実際に本当だった**。
`warm_master()`（製品のGETを16本叩いて表を作らせる）で直り、
`設備マスタ` に `テスト設備A`〜`D` が入るようになった。**が、症状は変わらなかった。**

**道②「サーバーが未設定と答えているのでは」。** 手で立てたサーバーに
`/api/schedule/overview` を聞くと `configured:false` が返り、これが原因に見えた。
**この観測は無効だった**——答えていたのは、パス設定を書く前に起動して残っていた
**古いサーバー**で、自分が立てたほうは `Address already in use` で死んでいた。
**同じ港に2つ立てられない**ことを確かめずに読んだ数字を根拠にした。

**教訓。** 症状が変わらないのに「直したはず」を積み上げない。**測る前に、
その数字を誰が答えているのかを確かめる**（§9.200 と同じ形）。

## 本当の原因

網が走っているあいだにサーバーへ聞いたら、`/api/schedule/overview` は
`configured:true`・設備4件を**正しく**返していた。画面側を覗くと:

```
{"panelHidden":false,"hasBoard":true,"boardHidden":true,"boardHTML":"","rows":0,
 "api":{"configured":true,"n":4}}
```

`#scBoard` は**在るのに隠れている**。俯瞰ボードが出るのは
`scState.boardMode==='board'` のときだけで、それは
`scState.pickerEnabled=(am.mode!=='edit')` から決まる。つまり
**アプリが編集モードのままだった**。

```
POST /api/access-mode {"mode":"schedule"}  → 403 この端末はそのモードへ切り替える権限がありません
GET  /api/access-mode                      → {"mode":"edit","canSchedule":false,"role":"一般ユーザー"}
GET  /api/access-permission-master          → items=[]
```

`アクセス権限マスタ`が空のとき、既定は**「編集可・スケジュール不可」**である
（`master_repo._DEFAULT_PERMISSION_FLAGS`。触れる範囲が広がる側は安全側に倒す・
`docs/SCHEDULE_MODE_DESIGN.md` §3.2）。**この既定は正しい。**

**では開発機ではなぜ通っていたのか。** `db/master.sqlite3` に

```
(3,'root','vm',編集可否=1,有効=-1,スケジュール可否=1,現場段取り可否=1,
 現場段取り対象設備='テスト設備A',権限区分='開発者',登録者ID='envseed')
```

という行が**手で入れたまま**残っていたからである。`envseed` という登録者IDは
リポジトリのどこにも無い——**再現手順を持たない1行**に、スケジュール系の網が
まるごとぶら下がっていた。`tests/setperm.py` が `WHERE PC名='vm'` と
**開発機のPC名を直に書いていた**のも同じ根から出ている。

## 直したこと

**① 権限の1行はフィクスチャが持つ。** `make_fixture.fix_master()` に
`_fix_permission()` を足した。`データソースマスタ`・`設備マスタ`・`勤務体系`と
同じ「足りない行を戻す・冪等」の並びに置く。`restore_master` が1本ごとに
戻すので、権限を触った網の置き土産も次の本へは渡らない。

**② 誰の・どの端末かは推測しない。** 答えを持っているのは
`current_login_id()`／`current_pc_name()` の1箇所で、`make_fixture.py` は
**`backend` をimportしない**（§9.285 の追補。import するとマイグレーションが走り、
書込トランザクションを持ったままのフィクスチャを壊す）。そこで
**ランナーが `/api/access-mode` から取り、環境変数
`WAVELOG_FIXTURE_LOGIN`／`WAVELOG_FIXTURE_PC` で渡す**。`setperm.py` も
同じ口を読むようにし、**当たらなければ落とす**——以前は0行に当たっても黙って
成功したふりをしていた（「黙って何もしない後片付けは、無い後片付けより悪い」）。

**③ 製品のAPIでは入れられない。それでよい。** `POST /api/access-permission-master`
は §9.322 ①「自分の権限区分は自分では変更できません」で断る。**自己昇格を塞ぐ
門なので、これは正しい**。だからフィクスチャが「管理者が登録した1行」の代わりを
務める。**製品側は変えない。**

**④ 「入れた」ではなく「効いた」で確かめる。** ランナーは種を入れたあと、
**実際に `POST /api/access-mode {"mode":"schedule"}` を打って200を確かめる**。
403のまま進むと、スケジュール系の網が全部「編集モードの画面」を見ることになり、
落ちるのは10〜30秒待った先——原因がいちばん遠くなる形である。行の有無ではなく
**振る舞い**で見張る。

## この形が何度も出ている

「開発機にだけ在る物に、網がぶら下がっている」は §9.369 と同じ形である。
違いは、あちらが**ファイル**（`db/records.sqlite3`・`db/master.sqlite3`）で、
こちらが**1行**だったこと。**CIの1段目・2段目は、その差を見つけるためにある。**
新しい網が何かを当てにするときは、**その何かを誰が作るのかを書けるか**を先に問う。
書けないなら、それは開発機の置き土産である。
