# §9.578 失敗の報告の1通に「解析に要る事実」を全部入れる——書込の控え・失敗した問い合わせ・そのときのサーバーの記録・共有の状態・要約の1行（利用者の指示）

索引: [決定記録](README.md)｜前: [§9.577](9.577.md)｜関係: [§9.373](9.373.md)・[§9.510](9.510.md)・[§9.576](9.576.md)

## 経緯（利用者の指示）

> 問題が発生したときにしっかり分析できるようにユーザー報告用の仕組みもさらに高性能でわかりやすく改良してください。

§9.576 の報告（「指定のサブカテゴリが見つかりません」）は、1通だけでは原因に届かなかった。マスタを保存したことは
足あとに無く（足あとは作業スケジュールの画面が名乗る操作だけ）、送った内訳の番号も、同じ分にサーバーが書いた
「共有マスタへ書き出せませんでした」も、共有の置き場の状態も入っていなかった。コードを読んで推し量るしかなかった。

## 1. 物差しと前後（今回の報告と同じ形の失敗を作り、1通に入った事実を数える）

| 解析に要る事実 | 前 | 後 |
| --- | --- | --- |
| 版・端末・モード | ○ | ○ |
| 失敗の理由と HTTP | ○ | ○ |
| 失敗した問い合わせ（方法・宛先・時間） | × | ○ |
| 送った内容の要点（識別子） | × | ○ |
| 直前の書込（画面を問わず・マスタの保存も） | × | ○ |
| 同じ時間帯のサーバーの警告・エラー | × | ○ |
| 共有の置き場の状態（書き出せていない変更・錠・改訂） | × | ○ |
| 同じ失敗の回数 | × | ○ |
| 先頭の要約の1行 | × | ○ |
| 機械で読む1行 | ○ | ○ |
| 静かに見送った失敗 | ○ | ○ |
| **合計** | **4 / 11** | **11 / 11** |

自由記述の本文が1通へ漏れないこと（前後とも漏れ0）も同じ物差しで見た。1通の長さは 2,050字 → 9,523字
（網の環境はサーバーの警告が多い。トレースバックは最後の4行だけ・機械で読む行には入れない）。

## 2. 決めたこと

- **書込は全部、土台が控える**（`api()`の1箇所 → `WL.feedback.request()`・直近15件）。画面ごとの足あととは別の欄。
- 本文は**識別子だけ**（`gist()`: 鍵の名前が ID・番号・設備・種類…の短い値はそのまま、ほかの字は字数だけ）。
  入力値そのものは入れない（§9.373 ⑤のまま）。
- 失敗した問い合わせは Error に付けて（`err.req`）、記録に入れる。
- 失敗を記録したときに1回だけ、**そのときのサーバーの記録と共有の状態**を取りに行く
  （`/api/feedback/context?at=`・前10分〜後2分の警告とエラーを`problem_digest()`でまとめる）。
  コピーと「ログ・診断」の送る内容は、届くのを待ってから組む（上限3秒・届かなくても報告は出す）。
- 1通の並びは「要約の1行 → 失敗 → 失敗した問い合わせ → 直前の書込 → サーバーの記録 → 共有の状態 → 画面の状態 →
  足あと → 静かな失敗 → 機械で読む1行」。原因に近い物ほど上。
