# §9.385 押さえは「真下の条」に貼り付く／押せない物に指のカーソルを出さない

利用者の指摘は一言だった——**「フィンガーの図と板の図の間隙間があります」**。
そのほか、同じ場面で2度指摘の来ていた刃組表の字も一緒に直した。

## 1. 隙間の正体（§9.380 の直し方が誤りだった）

§9.380 で、利用者の指示「板に貼りついた形に表示。板との隙間を空けないで
ください」を受けて、押さえ（フィンガー）を板へ寄せた。そのとき当てた先は
**いちばん外へ寄った板の面**だった:

    const y0 = upper ? V.midY - V.matH - h : V.midY + V.matH;

これは**食い込みを避けただけで、貼り付いてはいなかった。**
条は千鳥（`matShift()` が ±1）で上下へ `matH/2` ずつ寄るので、
板1枚の箱は次のどちらかになる:

| 寄る向き | 上面 | 下面 |
| --- | --- | --- |
| 上へ寄った条 | `midY − matH` | `midY` |
| 下へ寄った条 | `midY` | `midY + matH` |

押さえを常に外側（`midY ∓ matH`）へ固定すると、**反対側へ寄った条に対して
板厚1枚ぶんの隙間**が残る。区間のおよそ半分がこれに当たる。
欠陥注入で実測すると **30枚中18枚が浮き、隙間はどれも 21px**
（＝そのときの `matH`）だった。

**直し方**: 当てる先は**その押さえの真下にある条の面**。1枚ごとに引く。

    const y0 = yOf(x + ww / 2);   // 真下の条の面。無ければ外へ逃がす

## 2. 板の場所を答えるのは1箇所（`matBands()`）

材料を描く側と押さえを当てる側が**別々に座標を出していた**ことが、
食い違いを生んだ元。§9.377 の「両方が使う小道具は1箇所へ置く」と同じ形に
畳んだ:

- `matBands(V, A, run)` … 条1枚ぶんの `{a, b, top, bot, cy, up}` を返す
- `bandAt(bands, x)` … その横位置に在る条を返す（無ければ `null`）
- `drawFigure()` が**先に1度だけ**呼び、`V.bands` に預ける
  （`drawMaterial` → `drawStack` の順なので、押さえを描くときには既に在る）

## 3. 網の前提も古くなっていた

「フィンガーは軸と板のあいだに置く」は、板**ぜんたいの外枠**
（全条の `min(top)`〜`max(bot)`）で見ていた。正しく貼り付けると、
**下へ寄った条を上から押さえる指は外枠の内側に入る**ので、
この判定は**正しい絵を「軸に被せている」と誤って落とす**。

判定を「軸と、**その押さえが当たっている条**のあいだ」に改め、
別に「**どの条にも食い込まない**」（横と縦の両方で重ならない）を足した。
外枠だけで見ていると、寄った条に対する隙間も食い込みも見逃す。

網: `test_bladeui` 97→99件。
- 「フィンガーは真下の板に貼り付く（隙間を空けない）」
- 「フィンガーはどの条にも食い込まない」

## 4. 押しても何も起きないのに、指のカーソルが残っていた

§9.378 で、記号の連動を**押す**から**マウスオーバー**へ変えた（利用者の
指示「マウスオーバーしている間だけに変更」）。配線は `pointerover` に
なっていたが、**CSS とコメントが押す形のまま**残っていた:

    .bs-bhit{cursor:pointer}
    .bs-g tr[data-badge]{cursor:pointer}

指のカーソルは「押せる」という**嘘**になる（§CLAUDE 4「できないことは、
できないと書く。押せるのに何も起きないボタンを残さない」）。両方消した。
反応していることは、重ねたときの明るさの変化（`brightness(1.25)`）と
表側の面の色が言う。

**作りを変えたら、その作りを説明していた見た目とコメントも一緒に動かす。**

## 5. 同じ指摘が2度来たら、上げ幅ではなく既定を疑う

刃組表の「区分」欄の条幅について、利用者から2度指摘が来ていた:

1. §9.378「刃組表のロット№の下の幅の表示が小さすぎて読みにくいです」
   → `--fs-sm`(12px) から `--fs-base-sm`(13px) へ1段上げた
2. §9.380「刃組表の区分の、板幅の文字サイズは少し大きくしてください」
   → そのまま据え置いていた

表の本文は `--tbl-fs` = `--fs`(14px) なので、**区分の欄だけが本文より
小さい**ままだった。区分の欄で読むのは**ロット番号と条幅の2つだけ**で、
どちらも読ませる値——付随情報ではない。

**上げ幅ではなく「そもそも縮めていたこと」が誤り**だった
（§9.248「同じ指摘が2度来たら、入れた機能ではなく既定を疑う」）。
ロット番号・条幅とも `--tbl-fs` にそろえた
（§CLAUDE「器と中身の文字サイズを食い違わせない」）。

## 6. 版番号の管理（利用者の確認依頼への回答）

「意味のある変更をコミットするたびに `APP_VERSION` を上げる」に対して、
**4つの製品コミットが版を上げずに積まれていた**:

| コミット | 内容 | 版 |
| --- | --- | --- |
| `d2ef63c` | 刃1・刃3 | 2.271.0 据え置き |
| `adb710e` | 刃2 | 2.271.0 据え置き |
| `5e6e2c5` | 刃4 | 2.272.0（上の3つをまとめて1版） |
| `dbaa6ca` | OS/DS移動 | 2.272.0 据え置き |
| `15f6e13` | 見た目6点 | 2.272.0 据え置き |
| `2eacc97`〜 | GUI盤以降 | 2.273.0〜（1コミット1版） |

**CHANGELOG の中身は欠けていない**（2.272.0 が刃1〜刃4、2.273.0 が
OS/DS移動・見た目6点・GUI盤を書いている）。欠けたのは**版の刻み**だけ。

これが効くのは §9.316（起動の状況）で、**版で「どのコードが動いているか」を
見分ける**ため——2.272.0 の端末が刃4までなのか見た目6点まで入っているのかが
区別できない。過去の版は振り直さない（配布済みの意味が変わる）。
文書だけのコミット（`c614c98`・`ab50a8a`）が据え置きなのは正しい。
