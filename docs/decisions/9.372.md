# §9.372 書込が失敗したら、必ず理由を言う——「黙って巻き戻す」をやめる（利用者の報告）

**利用者の報告（作業スケジュール一覧、3件）。**

> ①「組み込んだスケジュールを仕掛へ外してみましたが一度は外れたように
> 見えましたが時間が経つと**５秒程したら再度ロットが復活**しました」
> ②「ロットを**下方向へドラッグ**して入れ替えようとしましたが、移動できませんでした」
> ③「一旦ロットを外し**ドラッグで作業スケジュールの段取りに入れよう**としましたが
> 入りませんでした」

**3件は別々の不具合に見えるが、①と③は同じ1つの原因だった。**

## 探し方（遠回りも記録する）

**最初に疑ったのは「計画外実績」だった。** サーバーは「予定行が突合した実績」
だけを`matched_keys`から除き、残りを**計画外実績として合成し直す**（§9.33）ので、
測定データのあるロットは予定を外した瞬間に突合が外れ、同じロットが別の行として
戻るはずである。筋は通っていたが、利用者に確かめたところ
**「区分はついていません」**——作業中でも完了でもない、ただの予定だった。
**この筋は消えた。**

**次に手元で再現を試み、2件とも再現しなかった。**

| | 試したこと | 結果 |
| --- | --- | --- |
| ① | 予定に入れたロットを画面の「外す」で外し、25秒見張った | 戻らない（サーバー側の予定からも消えたまま） |
| ② | 1行目を実際にマウスで掴んで4行目の下へ運んだ | 動く。4秒後も保存されたまま |

**再現しないことが手掛かりだった**——手元では**書込が成功する**。現場で違うのは
そこだけである。そこで**書込を失敗させて**測ったら、一発で出た。

```
外した直後 消えている? true
★戻ってきた? true 2.9秒後
  利用者に出た知らせ: 「1件は仕掛一覧へ戻していません」だけ
```

## 本当の原因

`runWriteQueue`は、諦めたときこう書いていた:

```js
// onFailureを持つ操作は、そちらで利用者へ知らせる責任を持つ。
if(op.onFailure){ try{ e.__reported=true; op.onFailure(e) }catch(...){} }
...
const unreported=failures.filter(f=>!f.__reported);   // ← ここで消える
```

**`onFailure`があることを「知らせた」と数えていた。** ところが`onFailure`の中身は:

| 操作 | `onFailure`がしていたこと | 利用者へ |
| --- | --- | --- |
| 外す（`delete`） | 行を元の位置へ戻すだけ | **何も言わない** |
| 足す（`add`、6箇所） | 仮の行を捨てるだけ | **何も言わない** |
| 並べ替え（`reorder`） | 元の順へ戻して**トーストを出す** | 言う |

つまり**言っていたのは3つのうち1つだけ**で、残りは巻き戻すだけだった。
リトライは3回（`sleep 700` → `sleep 1400` ＋ 往復3回。共有ファイルへの書込は
実測1件約1.5秒・§9.45）なので、**ちょうど5秒前後で、理由も告げずに行が戻る**。
利用者の言葉「一度は外れたように見えたが5秒程したら復活」はこの通りの現象である。

**しかも出ていた1件が誤誘導だった。** `deleteEntry`は`noteRemovedLots()`を
**キューへ積んだ直後**に呼んでいたので、外せずに巻き戻った行について
「1件は仕掛一覧へ戻していません」（§9.368）と出る。外せていないのに
「外したが戻さなかった」としか読めない。

## 直したこと

**① 「知らせた」と数えるのは、実際に言ったときだけ。** `onFailure`の有無では
立てない。自分でトーストを出す操作（並べ替え）が`e.__reported=true`を立て、
**言わなかったぶんはキューの1箇所がまとめて言う**。まとめ経路（`batch`）も同じ
——片方だけ黙る、を作らない。

**② 見出しは「何ができなかったか」から始める。** 「一部の変更を反映できません
でした」では、外したのか足したのか並べ替えたのかが読めない。画面は既に巻き戻って
いるので、**この1行だけが手掛かり**になる。答えは`SC_OP_LABEL`の1箇所。

**見出しは組み立てず、完成した1文で持つ**——最初は`${label}できませんでした`で
作ったら「**予定から外すできませんでした**」と出た（実測）。語尾の活用を
テンプレートで吸収しようとすると、必ずどこかが不自然になる。

**③ 外せてから「仕掛一覧へ戻すか」を言う。** `noteRemovedLots()`を`onSuccess`へ移した。

**④ 動かせない行は、掴んだ時点で理由を言う**（②への手当て）。掴めてしまうのに
落としても戻るだけ、が「移動できませんでした」という報告になっていた——
止めている当人が黙っているので、利用者には壊れているようにしか見えない
（§CLAUDE 画面基準4「できないことは、できないと書く」）。判定は
`reorderableEntry()`と**同じ順**で見る（2つ持つと食い違う）。同じ理由は8秒間
繰り返さない（掴むたびに帯が積み上がる）。

## ②について、まだ分かっていないこと

**並べ替えの失敗は、以前から理由を出していた。** だから②が「何も出ずに動かない」
のだとすれば、原因は**書込の失敗ではなく、そもそも掴んだ行が並べ替えの対象に
なっていない**ことになる（`reorderableEntry()`が`null`を返す）。上の④はその
理由を画面に出すための手当てで、**②が直ったことの確認にはならない**。
利用者の画面で何が出るかを見てから、次を決める。

## この形は3度目

§9.362（黙って何もしない後片付け）・§9.328（エラーを捨てるときは理由を1行残す）
と同じ形である。違いは、あちらが**開発者にだけ見えない**もので、こちらが
**利用者にだけ見えない**ものだったこと。**「誰かが言うはず」で書いた責任の
受け渡しは、だいたい誰も言っていない。** 受け取る側が「言った」と記録する形に
しないと、渡したつもりのまま落ちる。
