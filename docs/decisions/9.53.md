# §9.53 導線ごとの棚卸し(往復回数の実測)

メイン作業導線とスケジューリング導線それぞれについて、操作ごとの
サーバー往復回数を数えて洗い直した(実時間ではなく**回数**で見る。
docs/ARCHITECTURE.md「共有ファイルを読む処理は回数が効く」)。

**(1) 分割・親ロット判定が行数に比例していた(メイン導線・最大の問題)**

一覧を1ページ描くたびに、子カード判定された行の**1行ごと**に
`findParentLotFor()`が走る(`checkParentLookupRows`)。中身は
テーブル名(`/api/tables`)→列名(`/api/table?page_size=1`)→
先頭5桁で親を探す(`/api/table?page_size=50`)の**3往復**で、行数ぶん線形に
増えていた(実測: 20行→60往復)。200行ページに子カードが80行あれば240往復、
共有越し(1回150ms)ならこれだけで30秒を超える。

- テーブル名・列名は**実行中に変わらない**ので保持する(列はテーブル名で引く。
  `resolveSikaTable()`は測定中だけ`S.measure.settings.sourceTable`を返すため、
  同じセッションでも引数が変わり得る)。
- 先頭5桁+設備が同じ検索は**まったく同じ問い合わせ**になるのでキーで束ねる
  (`searchByLotPrefix`)。同じ親を持つ子ロットが並ぶのが普通なので実データほど効く。
  進行中の呼び出しにも相乗りできるようPromiseのまま持つ。
- 生データのキャッシュなので、一覧の再読込(`invalidateTableCache`)で一緒に捨て、
  TTLも一覧と揃える(3分)。

| | 改善前 | 改善後 |
|---|---|---|
| 子カード20行の判定 | 60往復 | 3往復 |
| 同じ判定の2回目 | 60往復 | 0往復 |

**(2) 条割プレビューが子ロットの数だけ直列に問い合わせていた**

`fetchChildLotRow()`をロットごとに`await`で回していたため、10分割なら
10往復を直列で待つ(共有越しで1.5秒級)。子ロットは親と先頭5桁を共有するので、
(1)の`searchByLotPrefix`の結果から拾う。prefixの結果が上限(50件)に達していて
見つからなかったときだけ、取りこぼしの可能性があるので個別に引き直す。

**(3) 描き直し後も古い判定が走り続けていた**

分割判定・親ロット判定は描画後に非同期で追いつく作りで、ページ送り・検索・
並べ替えで描き直したあとも古い応答が返ってきて、既に取り除かれた行へ書き込み、
問い合わせも無駄に走り切っていた。`renderGrid()`で世代番号を進め、世代が
変わったら打ち切る。

**(4) 作業可否の索引が一括取得の上限で黙って欠けていた**

`loadWorkableIndex()`は仕掛を`page_size=5000`で一括取得する。仕掛がこれを
超えると、載らなかったロットは全部`?`になり**作業を開始できない**
(§9.51で`?`は開始不可としているため)。**こちらの都合で現場を止める**のが
最悪の失敗の仕方なので、`count`で打ち切りを検出し、載らなかった分は
**今のタイムラインに出ているロットに限って**個別に引き直す
(`fillMissingLots`、上限60件・並列3)。見つからなければ空文字を入れ、
`?`ではなく`不可`として確定させる。

**(5) 直さなかったもの(計測して見送った)**

スケジュール画面へ戻るたびに`schedule-column-master`・
`schedule-content-master`・`stop-reason-master`を読み直しているが、
実測で**各1.9ms**(master.sqlite3=ローカル)。キャッシュすると
マスタ管理で編集した内容が次に開いたときに反映されない不整合を作る側に
倒れるため、そのままにした。往復が重いのは`plan`/`overview`(各23ms)で、
こちらは§9.42で既にキャッシュ済み。
