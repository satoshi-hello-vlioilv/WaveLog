# §9.224 作業動線に沿った動作チェックで見つけた固まり（動作時間）

3つの立場（作業者・スケジューラ・メンテナンス者）で実際に操作しながら、
動作不良・意図しない挙動・動作時間を見た。**測ったのは「押してから
次に触れるようになるまで」**——APIの応答時間ではなく、画面が止まって
いた時間（`requestAnimationFrame`が飛んだ幅）で見る。

#### ① まとめて投入すると画面が40秒固まる

仕掛一覧から158件をまとめて投入すると、**押してから約40秒なにも
反応しなくなる**（実測。行は0.5秒で出るが、そのあと38秒間クリックも
スクロールも受け付けない）。「再計算する」も同じく32秒。

原因は`renderTimeline()`の最後で呼んでいる`refreshScheduledLotFilter()`
——投入済みのロットを仕掛一覧から消すために`renderGrid()`を呼ぶ（§9.15）。
予定を1本描くたびに呼ばれるので、158件の投入で**102回**走り、
仕掛一覧は実データで158行×214列あって1回約300ms、**合計31秒**だった
（CPUプロファイルで`makeColumnWindow`の`on()`＝`grid.clientWidth`を読む
強制レイアウトが69%）。

**描き直しは何度やっても同じ結果**なので、`requestAnimationFrame`で
**1フレームに1回へまとめる**。止めてはいけない（止めると§9.15が効かなく
なる）。列幅を掴んでいる最中に待たせるのは今までどおり（§9.211 ①）。

あわせて`fmtDateTime()`が`toLocaleString(…,{…})`を呼ぶたびに
`Intl.DateTimeFormat`を組み立てていた（200行の表を描き直すたびに数百回、
実測2.6秒）。**書式は1回だけ作って使い回す。**

    投入(158件)   40.2秒 → 5.9秒（止まり 38.4秒 → 3.8秒）
    再計算        32.5秒 → 8.0秒（止まり 31.9秒 → 3.5秒）
    仕掛一覧の描き直し 102回30.8秒 → 3回0.3秒

**「APIが速いから速い」と読まないこと**——このとき書込の往復は1.6秒で
返っており、遅かったのは全部ブラウザ側だった。**サーバーの時間だけを
見ていると気づけない。**

#### ② 立場ごとに見て、問題が無かったところ

- **作業者**: 起動0.9秒／一覧(200行)0.2秒／測定を開く0.4〜1.0秒／
  段の行き来0.6〜0.8秒／保存1.8秒／帳票1.1秒。転送は実機と同じく
  キー入力＋Tabで流し、**受信欄からフォーカスが外れないこと**を確認
  （§9.122）。測定器の文字列が今の項目に合わないときは帯が`[NG]`を
  出して値を入れない（板厚の欄にノギスの文字列を送った場合）。
- **スケジューラ**: 全体俯瞰0.6秒→設備を押して個別1.0秒／仕掛一覧1.3秒／
  印刷プレビュー(18枚)1.3秒。**紙の脚の「N / 18」は実測で切った枚数と
  一致**し、用紙から溢れた頁は無い。
- **メンテナンス者**: マスタ管理0.4秒、15タブすべて0.2秒以内。
  操業データ項目の設定窓は1560×940で画面内に収まり、保存は右上
  （縁から56px）、4段のタブはどれも器から溢れない、メモ欄は836×174（8行）。
  役割の付け替えは**マスタ→測定画面まで通し**で確認した——`operator`を
  別の項目へ与えると組み込みの欄（`#operator`）が測定画面から消え、
  役割を外すと戻る（§9.223 ①）。

#### ③ 見つけたが直していないこと

- 測定の受信の帯は`検知 N回`を大きく出し、受け付けたか（`[OK]`/`[NG]`）は
  そのあとに小さく出る。**受け付けなかった理由**（いまの項目はその測定器の
  書式ではない）までは書いていない。項目と測定器の対応をどう持つかを
  決めてからでないと、書ける文が「読めません」以上にならない。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **予定を描くたびに仕掛一覧を作り直さない**（§9.224 ①、
  `refreshScheduledLotFilter()`）: 投入済みのロットを仕掛一覧から消す
  （§9.15）ために`renderTimeline()`の最後で`renderGrid()`を呼ぶが、
  **予定1本ごとに呼ばれる**ので、158件をまとめて投入すると102回走り、
  仕掛一覧（実データ158行×214列・1回約300ms）で**31秒メインスレッドが
  止まる**（押してから40秒なにも反応しない。実測）。描き直しは何度やっても
  同じ結果なので`requestAnimationFrame`で**1フレームに1回へまとめる**。
  **止めないこと**——止めると§9.15が効かなくなる。列幅を掴んでいる最中に
  待たせるのは今までどおり（§9.211 ①）。**書式は作り直さない**のも同じ話で、
  `toLocaleString(…,{…})`は呼ぶたびに`Intl.DateTimeFormat`を組み立てるため、
  200行の表では数百回になる（実測2.6秒）。**遅さをAPIの応答時間で測らない
  こと**——このとき書込の往復は1.6秒で返っており、遅かったのは全部
  ブラウザ側だった。**押してから次に触れるようになるまで**（`requestAnimationFrame`が
  飛んだ幅）で測る。
