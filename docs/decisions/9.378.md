# §9.378 模式図の読みやすさ4点／書けない端末が403を並べる（利用者の報告・指摘）

## 1. 現場段取りだけの端末が403を並べる（利用者の不具合報告）

報告は **HTTP 403 が27件**、操作は `update`、端末は LS4、VER2.270.0。
控えには `現場段取りのみ:true` ／ `書ける:false` ／ `編集できる:true` とあった。

原因は `canSyncSource()` が `scState.editable` を見ていたこと。**現場段取りの
端末は「並べ替えだけ」できる**（`access_mode._FIELD_REORDER_ENDPOINTS` は
`schedule.plan_reorder` の1本だけを開けている）ので `editable` は真になるが、
`update` は開いていない。そこで元データの取り込みが**毎回サーバーに断られ**、
赤い知らせが件数ぶん並んだ。

**「見る」と「取り込む」を分けた**。差分の計算（`sourceDiffFor()`／
`checkWorkPresence()`）は読み取りしかしないので全端末で回し、写しを書き換える
`applySourceSync()` だけを `fullControl` に限る。

### 書けない端末にも変化は見せる（利用者の了承）

分けただけだと、書けない端末は**何も出ないまま入れたときの値を出し続ける**。
利用者へ「取り込みを試みないということは、最新を反映できないのか」と問われ、
**変化があること自体は見せる**ことにした。帯は取り込めない端末には常に出し、
窓は3通りを言い分ける（`decide` これから取り込む／`done` 取り込み済みの控え／
`cannot` この端末では取り込めない）。以前は真偽値1つで「取り込み済みか」しか
言えず、**取り込めない端末の説明が無かった**。

## 2. 模式図の4点（利用者の指摘）

| 指摘 | 直した内容 | 実測 |
| --- | --- | --- |
| 板がある側に番号を | 条の寄る向き（`up`）へ番号を出す | 直す前は**6条すべて**が板と逆側 |
| 条幅の字が小さい | `--fs-micro` → `--fs-sm` ＋ 太字 | 11px → 14px（本文と同じ） |
| 重ねている間だけ強調 | `click` → `pointerover`／`pointerleave` | 図と表のどちらに重ねても両方光る |
| 青い印がスペーサーと干渉 | 有効幅の**外**へ（`sx = x0 - cw`） | 直す前は**4枚すべて**が重なっていた |

3つ目は「押して選ぶ」形をやめた。選んだままにしたことを覚えておく必要があり、
解除も手で要る——**見比べるだけの操作には重い**。図でも表でも同じ印
（`[data-badge]`）で受けるので、どちらに重ねても両方光る。

## 3. 撤回した案: 「模式図の横幅が余っている」の診断（**私の誤り**）

利用者の「模式図の両側まだ余白に余裕がある」に対し、最初は
**`preserveAspectRatio` が左右に帯を作っている**と診断し、`grow` の下限を
1 → 0.62 へ下げる修正を用意した。**これは誤りで、実測で否定された。**

利用者の画面（2160×1440 ＠125% ＝ CSS 1728×1152）で測った値:

```
viewBox = [0, 0, 1000, 821]      中身の実寸 x = 10..1005
svg#bsStage 760x849  <  #bsFigRow 1112   （列は 168 | 760 | 168）
両脇の端部の表: 器 168px / 中身の自然幅 156px
```

中身は **viewBox の横いっぱい**（10..1005 / 0..1000）にあり、模式図はすでに
列の幅を使い切っていた。しかも描画は `preserveAspectRatio` で**必ず横幅に
律速される**（scale = min(760/1000, 849/vh) は vh ≤ 1117 のあいだ常に 0.76）
ので、**`grow` をどう動かしても描かれる幅は1pxも変わらない**。用意した
`growMin`／`textMin` は取り消した。

**網が先に教えてくれた。** 用意した修正を入れたまま「横幅を使い切る」網を
書いたところ、**欠陥（元の `Math.max(1, …)`）を戻しても緑のまま**だった。
一度も赤くならない網は網ではない（§9.200 の裏返し）ので、そこで初めて
診断を疑い、器の連なりを測って誤りに気づいた。

横へ広げる唯一の手は器の側なので、両脇の表を中身から測って 10.5rem → 10rem
へ詰めた。ただし戻るのは **16px（+2%）**で、利用者の言う「拡大」には遠い。
**根本は両脇の表そのもの**であることを報告し、判断を仰いだ（→ §9.379 で移した）。

## 4. バージョンが3コミット据え置きだった

`APP_VERSION` は 2.270.0 のまま**3コミット進んで**おり、そこには上の403の
直しが含まれていた。利用者の不具合報告には `VER2.270.0` と記録されていたので、
**直した後も 2.270.0 のまま**では、現場の端末が直しを持っているかを
VERバッジから見分けられない。2.271.0 へ上げた。
