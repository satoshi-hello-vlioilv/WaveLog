# §9.357 描き直しでスクロール位置を捨てない。紙は「画面で開いている子ロット」を出す

利用者からの改良2件。どちらも**使い方は変えず、今までできなかったことができる**ようにした。

## ① 予定へ足すたびに仕掛一覧が先頭へ戻っていた

利用者の指示:「仕掛一覧からデータをD&Dでスケジュール表に追加する際にスクロール位置が
戻されてしまうので、データ更新してもスクロール位置を復元して同じ位置にしてください。
**作業のしやすさがこの実装で格段に変わります。**」

原因: 1件足すたびに `refreshScheduledLotFilter()` が **`renderGrid()` だけ**を呼ぶ。
一覧のスクロールを控える `keepGridScroll()` は **`load()` の中にしか無かった**ので、
控える相手が居らず、行を並べ終えたあとの `applyPendingScroll()` が**戻す先を持たない**。
＝毎回先頭へ。続けて足すには「次の1件」を毎回探し直すことになる。

直し: **`renderGrid()` の入口で控える**。`load()` から来ても、スケジュール画面から
来ても、同じ1箇所を通る（§CLAUDE 8「同じことを2箇所に書かない」）。
戻すのは今までどおり並べ終えてから（§9.95。描いた直後は表がまだ短く、指定しても
ブラウザに切り詰められる）。

**タイムライン（`#scTimeline`）側は触っていない。** こちらも `innerHTML=''` で中身を
捨てるが、**同じ同期の流れで組み直す**のでブラウザは位置を切り詰めない——控えるのを
やめても位置が動かないことを注入で確かめた。**効果を確かめられないコードは入れない。**

## ② 画面で開いている子ロットが紙に出なかった

利用者の指摘:「作業スケジュールの印刷時に子ロット情報が展開状態でも、印刷一覧に
のってこないです。」

原因は**同じ判定が2箇所にあった**こと:

| 場所 | していたこと |
| --- | --- |
| `buildPages`（組み立て） | `opt.includeChildren ? allKids : []` |
| `pageHtml`（出力） | `opt.includeChildren && item.kids.length ? …` |

**決めた結果を出力側がもう一度確かめて握り潰す**形になっていた。`item.kids` に入れても、
出力が `includeChildren` を見るので出ない。

直し:
1. **画面で開いている親の子は、設定を入れなくても出す**（`view.childOpenIds()`）。
   紙は画面の見た目が正（§9.237）——同じ画面を見ているつもりで、刷ると中身が違うのが
   一番困る。
2. 設定（チェック）の意味を「**畳んでいる子ロットも載せる**」に変えた。入にすると
   畳んでいるぶんも含めて全部出す。
3. **出力側の二重判定を外した。** 載せるかどうかを決めるのは `buildPages` の1箇所。

## 網

- `test_scpick`: 予定を描き直しても仕掛一覧のスクロール位置が戻らない
  （注入で `keepGridScroll()` を外すと `200→0` で落ちる）
- `test_scprint`: 画面で開いている子ロットは、設定を入れなくても紙に出る
  （注入で開いている親を見ないようにすると落ちる）

どちらも**入れたあと注入で確かめた**——網が「守っているつもり」で守れていないことは
実際にある（§9.356）。最初にタイムライン側へ入れた網は、注入しても落ちなかったので
外した（守るものが無かった）。
