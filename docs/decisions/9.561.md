# §9.561 版の確かめと Python の起動を同時に進める（利用者の承認）

索引: [決定記録](README.md)｜前: [§9.560](9.560.md)｜関係: [§9.555](9.555.md)・[§9.559](9.559.md)・[§9.544](9.544.md)

## 経緯

利用者の問い:「Rustが得意な部分で置き換えられていない部分がもしあれば、さらに最適化も進めたいです。」
実測（Windows の CI・本物の WebView2、§9.559 の自己診断の記録）を示し、効き目のある所として「起動の順番」を挙げた。
利用者の承認:「起動の順番（共有の置き場で配る版を確かめる処理と、Python の起動を同時に進める）の改善は、進めてよい」

## 測った（前）

- 中身（Python）が準備できるまで: 立ち上げ直後の1回目 3.58秒／2回目から 0.71秒／入れた直後（起動前の確認つき）1.07秒
- 1回の問い合わせ: Python 4〜6ms／Rust の部品 4〜6ms（窓口の枠の重さは見えない）
- 連結した CSS を作る: 1回 約12ms（あとは控え）
- 起動の順番は**直列**だった: 版の確かめ（共有の`release.json`を読む・届かないと最大3秒で打ち切り）→ 終わってから Python を起こす。
  起動 ＝ 確かめ ＋ Python。

## 決めたこと

1. **確かめと Python の起動を同時に進める**（`main.rs`の`peek_in_background()`）。起動 ＝ 長いほう。
2. 更新を「読むだけ（`update::peek()`）」と「入れ替える（`update::apply()`）」に分けた。`check_and_apply()`は2つを続けて呼ぶ
   （初回のインストール・網が使う）。
3. 配る版と違うと分かったら、**Python を止めてから**入れ替え、起こし直す（`settle_update()`）。動いている Python のファイルを
   入れ替えない約束（§9.555）は変えない。持っている写し（`Arc`）を先に手放す——残すと Python が終わらない。
4. Python が起動できなかったときも、配る版と違えば入れ替えてから起こし直す（前と同じく、壊れた版は配る版で直る）。
5. 窓の記録（`desktop.log`）に`TIMING 版の確かめ Nms・中身の起動 Nms（同時に進めた）`を残す（実機の値を後から読める）。

## 見込み（前→後）

| 場面 | 前（直列） | 後（同時） |
| --- | --- | --- |
| 置き場に届かない日（確かめ 3秒で打ち切り・Python 0.71秒） | 約3.7秒 | 約3.0秒 |
| 立ち上げ直後（確かめ t・Python 3.58秒） | t ＋ 3.58秒 | max(t, 3.58秒) |
| 社内の共有に届く日 | t ＋ 0.71秒 | max(t, 0.71秒) |
| 配る版が新しい日（年に数回） | t ＋ そろえる ＋ Python | Python ＋ 止める ＋ そろえる ＋ Python（**1回ぶん遅くなる**） |

t（共有の`release.json`を読む時間）は**実機で測っていないので分からない**。窓の記録の TIMING が実機の値を残す。

## 撤回した案

- **画面を先に開き、確かめは裏で済ませて次の起動でそろえる**: 起動はいちばん速いが、「起動のときに配る版へそろう」（§9.555）が
  1回遅れる。配る版を決めた直後に開いた PC が古い版のまま一日動く。
- **業務の処理（SQLite・予定の計算）を Rust へ書き直す**: 問い合わせは 4〜6ms で、Python が待ちの原因になっていない
  （言語の住み分けそのものは別の記録で検討する）。

## 網

- Rust（`cargo test` 21）: `peek`／`apply`へ分けたあとも、そろえる・壊れた版は入れ替えない・途中で失敗したら戻す・届かなければ飛ばす。
- CI の自己診断を4回目へ: 配る版を新しくして（`make_share.py --bump`）写した PC で起動し、**起動のあいだに配る版へそろい**、
  起こし直した中身で自己診断が通ること・`TIMING`が記録に残ることを確かめる。

## 追補: CI の4回目が見つけた §9.559 の不具合（2.449.0）

**起きたこと**（Windows CI・4回目「update」）: 起動の記録が`UPDATE 確かめませんでした: 配る版が決まっていません`。
共有の置き場には配る版`2.448.0-ci`が在るのに、写した PC がそれを見ていなかった。

**仕組み**:
1. 共有の入口から入れた PC は、窓（`install::seed_config()`）が「入れた元の置き場」を`config/update.json`へ書く（既定でない置き場のとき）。
2. 起動した Python は、ハートビートの`remember()`で同じ控えを**共有の設定（パス設定マスタの`update_dir`）**で書き直す。
   共有の設定が空だと`{"update_dir": ""}`で上書きし、入れた元が消える。
3. 次の起動で窓は既定（`\\nlmsrvngy03…`）を見る。届かない UNC は OS が「無い」（WinError 53）と答えるので、
   `release_version()`は「`release.json`が無い＝決めていない」と取り違えた。

現場で踏む形: 配る版を決めた PC が**この PC だけの上書き（local.json）**で既定でない置き場を使い、共有の設定を空のままにしていると、
新しい PC は1回目だけ正しく、2回目から既定の置き場を見に行き二度と配る版へそろわない。

**直したこと**:
- 控えに**入れた元の印**（`"from": "install"`）を付ける（窓）。Python は共有の設定が空のあいだ、印のある控えを消さない
  （`app_update._origin_of()`の1箇所が読む）。共有の設定が決まれば、そちらで上書きする（共有の設定が勝つ）。
- 置き場の決める順を4段にした: この PC の local.json → 共有の設定 → **この PC を入れた元** → 既定。Python の`dir_choice()`も
  同じ答え（出どころ`install`）を返し、画面「アプリの更新」が「この PC を入れた元の置き場」と言う。窓の順は変えない
  （控え`update.json`が②③を持つ）。
- `release_version()`は「無い」を**置き場のフォルダが在るときだけ**「決めていない」と読む。フォルダごと見えなければ
  「置き場が見つかりません」と言う（取り違えた字が原因探しを遠回りさせた）。

**測った（前→後）**: `test_appupdate` 51/53 → 53/53（足した網: 入れた元を消さない・共有の設定が勝つ・窓が印を付ける）。
`cargo test` 21 → 22（置き場ごと無いのを「決めていない」と言わない）。CI の4回目が緑になるかは push で確かめる。
