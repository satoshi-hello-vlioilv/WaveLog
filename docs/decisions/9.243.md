# §9.243 帳票の印刷が用紙の8割に縮む・「記録した値の配置」をD&Dで組めるマスタ（利用者の指示）

利用者の報告と指示:

> VER2.116.0も確認しました。アプリ内の印刷プレビュー(帳票表示状態)と、実際の
> 印刷直前のWINDOWSのプレビューに違いが出ています。用紙内にしっかりレイアウト
> できているのがアプリ側の印刷プレビューです。…WINDOWSのプレビューは用紙を
> 最大活かせておらず、用紙に対して80％くらいの比率と共に表示内容のクオリティも
> 下がっているように見えます。帳票のアプリ内でのプレビュー表示に正確に合わせて
> その通りに印刷させてほしいです。

> （④「記録した値」のマスタ化について）これについて、画面で見えるように
> してほしいので、現在操業データ項目マスタで設定している内容を候補に出して
> 視覚的に配置して設定できるようなマスタを別で追加立ち上げして簡単にD&Dで
> 配置修正再設定、編集できるようにしてほしいです。

#### ① `@page`の余白の指定は2箇所にある

§9.242 ⑦で「刷るときもプレビューと同じ箱」にしたつもりだったが、**直したのは
CSS側だけ**だった。`@page`を書いているのは2箇所ある:

| 場所 | いつ効くか |
|---|---|
| `static/css/90-state.css` の `@media print{@page{...}}` | 常時（スタイルシートとして） |
| `report-dashboard.js` の `updatePageSizeStyle()` が `<head>` の末尾へ挿す `<style>` | 用紙の向きを切り替えるとき（＝帳票を開くたび） |

**後から読まれる`<head>`末尾のほうが勝つ**（§9.235 ②で作業予定表に入れた作法を
帳票にも使っており、そちらは「既定の`@page`より後に読ませて優先させる」ことが
目的だった）。JS側が`margin:5mm`のままだったため、

- 紙の箱（`.rp-page`）は `210mm × 297mm`
- 刷れる面（page area）は `200mm × 287mm`

という**箱のほうが紙より大きい**組み合わせになり、Chromiumの印刷パイプラインは
**2ページに割ってから**ダイアログの「用紙に合わせる」で1枚へ縮めていた。
実機の見え方が「用紙の80%くらい・文字のクオリティも下がる」だったのはこのため。

数は `RP_PAGE_MARGIN` の**1つ**が持ち、CSS側にも「この値と合わせること」と
書いてある。

**確かめ方**——`page.pdf({preferCSSPageSize:true})` の**枚数**を見る。
1枚に収まっていれば縮小は起きない。`@page`のルールが在ることだけを見る網では、
2つのうちどちらが勝つかを一度も通らない（実際に、わざと5mmへ戻して2ページに
なることまで確かめてある）。固定は `tests/test_rpprint.js`。

#### ② マスタ管理＞「記録した値の配置」

§9.242 ④で③確認の「記録した値」を操業データ項目マスタから作るようにしたが、
出す/出さないは**設定窓の①のチェック1つ**だった。項目を1つずつ開いて入切する
形では、**並べたときにどう見えるか**が分からない（操業データ項目の盤を
`special`にしたのと同じ理由・§9.216 ④）。

`special:'record-layout'` の専用画面を足した。

```
[候補に出す設備 ▼] [並びは設備によらず共通です] [群を追加][既定へ戻す][保存]
[案内]
┌────────────────┬──────────────────────────────────┐
│ 候補 3         │ ③確認のカード  51件・13群        │
│ （出していない）│ ┌ 誰が測るか 3 ┐ ┌ 製品 2 ┐   │
│  ・板厚測定器  │ │ オペレータ ✕ │ │ 内巻 ✕ │   │
│  ・スプール    │ │ 検査員   ✕ │ │ 後端 ✕ │   │
└────────────────┴──────────────────────────────────┘
```

- **盤は③確認のカードそのものの形**（群の塊＋その中の項目、2段組）。
  掴んで動かせば**並び**が決まり、**別の群へ落とせば見出しも変わる**。
  左の候補へ落とせばカードから外れる（**項目そのものは消えない**）。
- 書くのは `[記録表示]`／`[記録群]`／`[記録順]` の**3列だけ**。型・選択肢・
  上下限・意匠には触らない——**操業データ項目の盤と別の画面**にしてあるのは
  そのためで、1枚に混ぜると盤の1枚のカードが「何を記録するか」と「どう並べるか」
  の2つの並びを同時に表すことになる。
- 保存は `POST /api/operation-item-master/record-layout` の**まとめて1回**
  （1行ずつ送ると往復が増え、途中で切れると並びが半分だけ変わった状態が残る。
  `item_layout_save` と同じ理由）。
- **設備は候補を絞るためだけ**——`record_layout_save()` は行そのものを書くので
  並びは設備によらず共通。§CLAUDE 6のとおり、そのことを帯に書いてある。
- 保存したら `WL.opData.forget()`（捨てないとカードは古い並びのまま・§9.226 ①）。

##### 「既定へ戻す」は本当に空へ帰す

`[記録群]`と`[記録順]`は**空＝この項目の`[群]`／`[表示順]`に従う**。
`record_layout_save()` が `[記録順]` を必ず `(i+1)*10` で書き下ろす作りだと、
「既定へ戻す」を押しても**今日の`[表示順]`と同じ数を焼き付けるだけ**になり、
あとで表示順を変えてもカードが追随しない——**押しても戻らない設定**（§9.169で
「押しても保存されない設定」を作った罠と同じ形）。

行ごとの `follow` で分ける。掴んで動かした項目だけが `follow` を落とし、
触っていない項目は空のまま残る。盤は**点線／実線**と**件数の文**の両方で言う
（§3。色だけ・形だけでは伝えない）。

##### 見えている塊と保存される並びを食い違わせない

カードは `renderRecordedValues()` も盤も「出てきた順に束ねる」ので、同じ群が
ばらけて保存されていても**画面では1つの塊に見える**。平らな並び
（`rlBuildRows()` の戻り）のほうを束ねておかないと、**1塊に見えているのに
保存された `[記録順]` は2つに割れている**状態が作れる。束ねたことは画面に書く
（§9.219 ③と同じ作法）。

固定は `tests/test_reclayout.js`。**わざとばらけた並びを注ぎ込んで**確かめる
こと——検証用データが最初からまとまっていると、束ねる道を一度も通らない
（実際、フィクスチャには2箇所のばらけがあり、束ねる前は落ちた）。
