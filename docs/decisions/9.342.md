# §9.342 ダイアログは3つだけ。素の `alert()`／`confirm()`／`prompt()` を残さない

`docs/REVIEW_2026-09.md` 3-5・4-3 ⑪ の指摘:「自前モーダルとブラウザ既定の
`confirm`が混在（56件）。見た目も挙動（Esc・IME）も違う」。

## 何が起きていたか

**規約はあった。歯止めが無かった。** `base.js` の `confirmModal` は
51箇所で使われており、コメントには「ブラウザ標準の`confirm()`はアプリの
見た目に合わせられずタブ全体をブロックするため、こちらへ統一する」と
書いてある。それでも実測で**56件**残っていた。

| | 件数 |
| --- | --- |
| `confirm()` | 29 |
| `alert()` | 14 |
| `prompt()` | 13 |

さらに悪いことに、**「`prompt()`をやめる」と書いた自前の小窓が3つ**あった。

- `list-rules.js` の `askName`
- `filters.js` の `askGroupName`
- `master-opdata.js` の `promptModal`

そして **`master-opdata.js` は自前の `promptModal` を持ちながら、同じ
ファイルの5箇所で素の `prompt()` を呼んでいた。**

**やめる先が3つあると、やめていない呼び出しが残っていても誰も気づかない。**
「1箇所が答える」（§9.163）が守れていないと、規約は守れているように見える
だけで守れていない。

## 決めたこと

1. **窓は3つだけ。器は1つ**（`#appConfirmModal`）。
   - `confirmModal(opts)` … 確認。`true`／`false`
   - `alertModal(opts)` … お知らせ。ボタン1つ（「閉じる」）
   - `promptModal(opts)` … 1行入力。文字列、**やめたら `null`**
2. **自前の写しを作らない。** 3つの小窓は消し、`promptModal` へ寄せた。
3. **素の `alert()`／`confirm()`／`prompt()` は0件**にし、機械が見張る。

## 設計で気をつけたこと

**やめたときは `null`。** 素の `prompt()` と同じ形にした。「空で決定した」と
「やめた」を分けられることに意味がある——名前を聞く場面は `if(!v)return` で
どちらも弾けるが、**空でも通す欄**（在席の切断理由）は、分かれていないと
「やめた」が「理由なしで実行」に化ける。同じ形なので置き換えは1行で済む。

**Enterで決定する。** 素の `prompt()` はそうだった。**作法を落とさない**
——見た目を揃えるための入れ替えで、それまでできていた操作が減ると、
使う側にとっては改善ではなく劣化になる。

**「やめる」は毎回入れ直す。** お知らせは「やめる」を伏せるので、
`cancel.hidden=!!o.hideCancel` と**毎回代入する**。`if(hideCancel)hidden=true`
と書くと、**お知らせを1回出した次の確認から選択肢が片方消える**（A/Bで
確かめた。網が1件落ちる）。

**お知らせは待たない場所がある。** 4箇所（測定画面を開けない・手動入力の
注意・設計設備の不一致・予定日時が無い）は**同期の流れの中**にあり、
`await` すると関門そのものを非同期にしなければならない。お知らせは
「見せるだけ」で後続の処理は順序に依存しないので、待たずに出す。

**ついでに「守り」を外した。** `if(typeof confirmModal==='function')` で
囲われた確認が4つあり、うち2つは**偽なら確認せずに削除していた**
（作業予定の削除・勤務体系の削除）。`confirmModal` は `base.js` にあって
必ず定義されているので偽にはならないが、**取り消せない操作で緩む側へ
倒れる書き方**を残す理由が無い。

## 網

- **`tests/test_patchlint.py`**（純粋・サーバー不要）: 素の
  `alert()`／`confirm()`／`prompt()` を呼んでいないこと。文章の中の言及
  （中身が空の `prompt()` のような書き方）は数えない——**本物の呼び出しには
  必ず引数がある**。ブロックコメントの中も見ない。
- **`tests/test_modalkeep.js`**: 3つが揃っていること、お知らせはボタンが
  1つ、**お知らせの次の確認で「やめる」が戻っていること**、1行入力の焦点・
  Enter・空白落とし・`null`、そして**この間に素のダイアログが1度も出ない**
  こと（`page.on('dialog')`で拾う）。

**静的な網だけでは足りない。** lint は「呼んでいない」ことしか言えず、
**替わりの窓がちゃんと開いて答えを返すか**は動かさないと分からない。
そこが壊れていると「押しても何も起きない」になり、**素の `confirm()` の
ままより悪い。**

## テスト側にも波及した（ここがいちばん危なかった）

**5本のテストが素のダイアログを前提に書かれていた。**

| テスト | 何をしていたか |
| --- | --- |
| `test_colpreset` | `page.on('dialog',d=>d.accept(answer))` で名前を答えていた |
| `test_sctimecols` | 同上（計算列の名前） |
| `test_logview` | `window.confirm=()=>true` に差し替えていた |
| `test_qjoinui` | `page.once('dialog',d=>d.accept())` |
| `test_colscopeui` / `test_rlmaster` / `test_choicelinkui` | 一括の `d.accept()` に頼っていた |

素の窓が出なくなると、**この配線は何も受け取らないまま**、次の待ちで
時間切れになる。答え方も1箇所にまとめた（`tests/lib/wait.js` の
`answerPrompt` ／ `answerConfirm`）。

**ここで自分も踏んだ罠**: `answerPrompt` の中で窓が閉じるのを
`waitForSelector('#appConfirmModal[hidden]')` で待った。**既定の
`state` は `'visible'`** なので、伏せた要素はこの条件に永久に一致しない
——`state:'hidden'` を渡す。製品ではなく網の側が固まり、製品を疑って
探すことになった。

直した副産物として**遅かった網が速くなった**（`test_qjoinui` 42→12秒、
`test_logview` 35→7秒、`test_rlmaster` 25→5秒、`test_choicelinkui`
17→2秒）。**時間切れを待っていたぶん**で、通っていた頃から既に
無駄に待っていた。
