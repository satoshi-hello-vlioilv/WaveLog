# §9.640 予定へ入れても・読み直しても、作業スケジュールの表のスクロールの位置を動かさない（利用者の指示）

索引: [決定記録](README.md)｜前: [§9.639](9.639.md)｜関係: [§9.292](9.292.md)（一覧の下の余白）・[§9.179](9.179.md)（行間から入れる）・[§9.357](9.357.md)（一覧の描き直しで位置を控える）

## 経緯（利用者の言葉）

> 作業スケジュールのロット追加や設備停止の追加の際に問題なく指定の個所にスケジュールを組み込むことができるように
> なりましたが、反映されるたびにスクロールの位置が戻されるので使いづらいです。スクロールの位置を変えないように修正を
> お願いします。

## 測った（`tests/test_scscrollkeep.js`）

表を途中まで送り、見えている最初の行（目印）の、器の上端からの位置を控える。目印より下へ入れるので、目印が動く理由は無い（許す差 2px）。

| 物差し | 前 | 後 |
|---|---|---|
| K1・K2 見えている行の前へ設備停止・ロットを落とす（落とした直後・反映のあと） | 動かない | 動かない |
| K4 いちばん下まで送った表で落とす | 動かない | 動かない |
| **K5 行と行の境目を押して設備停止の窓 →「追加」**（人がいちばん使う道） | **58px → 654px（先頭まで戻る）** | 58px のまま |
| **K6 境目をダブルクリックして仕掛一覧の窓 → ロットをダブルクリック** | **44px → 654px（先頭まで戻る）** | 44px のまま（窓を閉じたあとも） |
| K3・K4 「再読込」を3回 | たまに先頭へ戻った（4回に1回ほど・43px→626px） | 動かない |

K1・K2 は網が落とす合図を直に送る道で、人の操作（マウスで境目を押す・仕掛一覧の窓を開く）を通らないため、直す前も動かなかった。
人と同じ道（K5・K6）で初めて再現した。

## 原因は2つ

1. **描き直しの途中で寸法を読む**: 表は描き直すたびに中身を空にして組み直す。組み直しの途中で末尾の余白（§9.292）を測り直す
   `fitTailSpace()`が寸法を読むと、ブラウザがそこで位置を切り詰めていた（境目から設備停止を入れた後の描き直しで 554px→0）。
   余白は測るために一度0へ戻すので、余白の所まで送っていた位置もそこで切り詰められる。
2. **予定の面を別の親へ移す**: 仕掛一覧の窓を開くと分割表示を畳み、予定の面（`#schedulePanel`）を別の親へ移し替える
   （`teardownSplitWrap()`・開くときは`ensureSplitWrap()`）。要素を移し替えると、ブラウザは中のスクロールを先頭へ戻す。

## 直し

- 位置の控えと戻しは`scrollMark()`／`scrollBack()`の1組。控えるのは**見えている最初の行と、その器の上端からの位置**——描き直しで
  上に行が増えても、見ていた行が同じ所に残る。その行が無くなっていたら位置の数のまま戻す。先頭に居るときは何もしない。
  楽観の仮の行（`tmp-`）は描き直しで本物に替わるので目印にしない。
- 使う所は3つ: `renderTimeline()`（空にする前に控え、組み終えたら戻す）・`ensureSplitWrap()`／`teardownSplitWrap()`（移す前後）。
- `fitTailSpace()`は測る前の位置を控え、測り終えたら戻す（窓の大きさが変わったときにも呼ばれるため）。

## 分からないこと

- 利用者の画面で、この2つ以外の道（共有の見張りの知らせからの読み直し等）でも戻っていたかは確かめていない。どれも
  `renderTimeline()`を通るので、同じ直しが効くはず。
