# §9.192 共有スケジュールへ書くのは1台だけ（持ち主とHTTP中継）（利用者の指示）

利用者の指示: 「1台を『持ち主』にしてHTTPで話す。……最初に入った人の1台を
持ち主にしてやる方法にしてほしいです。ただし懸念事項として、BOX環境に置いた
このアプリのファイル群を同じスタートファイルから、数人が起動して同時利用する
形です。おそらくブラウザ上のアドレスもみな `http://127.0.0.1:5029/` で同じに
なると思いますがその利用方法で実現可能でしょうか」。

**実現できる。ただし『ブラウザが持ち主へ直接つなぐ』のではない。**
各PCは今までどおり自分のFlask（`127.0.0.1:5029`）を開き、**画面もURLも
変わらない**。変えるのは**共有ファイルへ実際に書く役を1台に絞る**ことだけで、
持ち主以外のサーバーは「書き込みの依頼」だけを持ち主へHTTPで転送する。

```
  ブラウザ(PC-B) → 127.0.0.1:5029(PC-BのWaveLog) ─HTTP→ PC-A(持ち主) → 共有DB
                              （画面のURLは変わらない）
```

**なぜこの形か。**
 - **読みは中継しない。** 予定の一覧は「共有の予定＋**その端末の**実績・設備
   マスタ」の混成（`overview`）で、丸ごと中継すると測定端末の実績が消える。
   持ち主が落ちても読めなくなるのも困る（今は手元の写しで読める。§9.188）。
 - **書きだけ中継する。** 共有DBへ書くのは`_write_response()`→
   `schedule_sync.with_write()`の**1本**（§4.2）なので、差し込む場所も1箇所。
   中継するのは`plan/add|update|delete|reorder|batch`の5本だけで、
   **設定系マスタ（稼働カレンダー・設備停止・勤務形態・負荷率）は各端末の
   `master.sqlite3`**（§9.27）なので**中継してはいけない**。
 - **持ち主が居なくても止まらない。** 頼めなければ今までどおり自分で共有を
   掴んで書く（ロック＋改訂番号の砦はそのまま。§4.2）。自分で書いたことは
   応答の`relayFallback`と画面の帯で**黙らない**。

**持ち主の決め方**は、短命ロック（§4.1）・編集セッション（§9.11）と同じ作法。
共有フォルダへ目印（`schedule.owner.json`）を置き、**書く→1.5秒待つ→読み直して
自分か確かめる**。目印にはTTL（既定90秒）があり、期限の1/3ごとに更新する。
持ち主のPCを閉じれば、期限切れで**別のPCが自動で名乗り出る**。
**BOXの結果整合性では完全な排他にならない**ので、**二重に立ちうる前提**で
`with_write()`のロックと改訂番号は絶対に外さないこと（最後の砦）。

**素性は運ぶ。** 中継は「誰が・どの端末で・**どのモードで**」をヘッダで運ぶ。
運ばないと、ロックの保持者も編集セッションも監査列（§9.180）も全部
「持ち主PCの人」になる。モードを運ぶのは、設備単位の編集セッションを要求するのが
scheduleモードだけだから——持ち主はたいていeditモードなので、持ち主のモードで
判定すると**持ち主を経由した書き込みだけ排他が外れる**。

**二重に弾かない。** 中継された書き込みは、頼んだ端末が**自分のモードで既に
判定を通したあと**のものなので、持ち主側の書込ガードは素通しする
（`_relayed_write_ok()`。①自分が持ち主 ②合言葉が一致 ③受け口が通したパス、の
3つが揃うときだけ）。**中継されてきたものを中継し返さない**ことも要る
（目印が二重に見えると往復し続ける）。

**安全面。** LANへ開くのは持ち主だけ、しかも**専用の小さな受け口**（既定
`PORT+1`）で、本体のFlaskは`127.0.0.1`のまま。受け口が受けるのは目印ファイルの
合言葉（token）を持つ相手の、**決められた5つのパスへの書き込みだけ**。
合言葉は共有フォルダを読める端末しか知りようがない。`/api/shutdown`や
`/api/access-mode`はこの受け口に無いのでLANからは触れない
（`/api/shutdown`はBlueprint無し＝モードガードを通らないので、**本体を
0.0.0.0で開く案は採らなかった**）。**既定はoff**で、入れると決めた現場が
マスタ管理の1つのスイッチで入れる（`schedule_owner_enabled`）。

**残る制約**（現場へ入れる前に確かめること）:
 - PC間でTCPが通ること（同一セグメント／ファイアウォールの受信許可）。
   Windowsは初回起動時に受信の許可を聞く。**通らない環境では、頼めない端末が
   今までどおり自分で書くだけ**なので壊れはしないが、絞る効果も出ない。
 - 相手のURLはホスト名→IPの順で試す（複数NIC・VPNでは「自分から見える自分の
   IP」と「相手から届くIP」が違う）。ループバック宛てと同じく**プロキシを
   通さない**（`ProxyHandler({})`。§プロキシの罠）。
 - 持ち主が固まった（プロセスは生きているが応答しない）場合、TTLが切れるまで
   他の端末は待たずに**自分で書く**（タイムアウト12秒→自力へ）。

固定は`tests/test_scowner.py`（選出・引き継ぎ・受け口の合言葉とパス・素性の
持ち回り・二重弾き無し・往復しない・届かないときの自力書き）。

**ついでに1つ直した。** パス設定マスタの保存(POST)が、固定キーの側を
「送られてこなければ空文字」で**必ず書いて**いたため、一部だけを送る呼び出しが
残りの設定を黙って消していた——`{'user_id':...}`だけのPOSTで
`schedule_share_path`の行が消え、**以降その端末ではスケジュール機能が
「未設定」になる**。検証の通しで踏んで見つかった（単独で回すと通るので、
テストの落ち方からは原因が遠い。§9.121と同じ形）。§9.163でデータソースの
読み込み先だけ直していたのを、固定キーの側にも広げた。画面は全項目を送るので
「空欄で保存＝既定へ戻す」は今までどおり効く。固定は`tests/test_dscap.py`。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **共有スケジュールへ書くのは1台だけにできる**（§9.192、`backend/schedule_owner.py`）:
  **既定はoff。** onにすると、共有フォルダの目印（`schedule.owner.json`、TTL既定90秒）を
  「書く→1.5秒待つ→読み直す」で取った1台が持ち主になり、他の端末は**書き込みだけ**を
  持ち主の小さな受け口（既定`PORT+1`）へHTTPで頼む。**画面のURLは変わらない**
  （各PCは今までどおり自分の`127.0.0.1:5029`を開く）。**中継するのは
  `plan/add|update|delete|reorder|batch`の5本だけ**——読みは「共有の予定＋その端末の
  実績」の混成なので中継すると実績が消え、設定系マスタは各端末の`master.sqlite3`
  （§9.27）なので中継してはいけない。差し込み口は`_write_response()`の1箇所。
  **素性（ログインID・端末名・モード）をヘッダで運ぶこと**——運ばないとロックも
  編集セッションも監査列も全部「持ち主PCの人」になり、モードを運ばないと
  持ち主（たいていedit）経由の書き込みだけ**設備の排他が外れる**。中継された
  書き込みは持ち主側の書込ガードを素通しする（`_relayed_write_ok()`。依頼元で
  判定済み。①持ち主 ②合言葉 ③受け口が通したパス、の3つが揃うときだけ）。
  **中継されてきたものを中継し返さない**（目印が二重に見えると往復し続ける）。
  **頼めなければ今までどおり自分で書き**、そのことを応答（`relayFallback`）と
  画面（同期チップ）に出す。**`with_write()`のロックと改訂番号は最後の砦なので
  絶対に外さないこと**（二重に立ちうる前提）。本体のFlaskを`0.0.0.0`で開く案は
  採らない——`/api/shutdown`はBlueprint無しでモードガードを通らない。
  **既定は on**（§9.269、利用者の指示「常にそれを正にしてください」）——
  §9.192の「既定はoff」は撤回した。**切るスイッチは残すこと**（社内規程で
  listenポートを開けない現場がある。切っても各PCが自分で書く形に戻るだけ）。
  **受け口には読み待ちの上限を置く**（`_Handler.timeout`）——
  `ThreadingHTTPServer`は接続ごとにスレッドを作り、既定は無期限で、
  しかも**合言葉を確かめるのは本文を読んだ後**なので、繋いで黙る相手が
  並ぶと認証の前にスレッドが積み上がる。依頼側の12秒より短くする。
  **`handle_one_request`は上書きしないこと**——`BaseHTTPRequestHandler`が
  `socket.timeout`を自分で拾うので要らない（上書きを外しても網が通った＝
  動かして確かめられないコードだった）。
  **網は属性を見るだけで終わらせない**——実際に繋いで黙り、閉じられるまでの
  秒数とスレッド数が戻ることを見る。ただし**上限が無いときは繋ぎに行かない**
  （`None+6`で落ちると以降の網が1件も動かない。実際に落ちた）。
  固定は`tests/test_scowner.py`。
- **パス設定マスタ**（`db/master.sqlite3`、`backend/db_access.py`の
  `PATH_CONFIG_TABLE`）: 仕掛/品質データの読み込み先・共有パス・各種間隔設定
  （旧`config/local.json`）を保存する。キー1件=1行で、値の無い項目は行自体が
  無い＝既定値を使う（他マスタと同じ互換ポリシー）。CRUD APIは`backend/routes/
  path_config.py`の`/api/path-config-master`、UIはマスタ管理画面の「パス設定」タブ
  （`static/js/master/master-defs.js`のMASTER_DEFS、key:pathConfig）。
  本来なら`backend/repositories/master_repo.py`が持つべき層だが、
  `db_access.py`自身が起動時に接続先を1回だけ確定させる必要があり
  `master_repo.py`はdb_accessに依存する側のため、循環importを避けて
  `db_access.py`内に自己完結させてある。**保存(POST)は送られてきた項目だけを
  書く**——固定キーの側が「送られてこなければ空文字」で必ず書いていたため、
  一部だけを送る呼び出しが**残りの設定を黙って消していた**（`{'user_id':...}`
  だけのPOSTで`schedule_share_path`の行が消え、以降その端末ではスケジュール
  機能が「未設定」になる。§9.192で判明）。画面は全項目を送るので「空欄で
  保存＝既定へ戻す」は今までどおり効く。§9.163でデータソースの読み込み先だけ
  直していたのを、固定キーの側にも広げた形。`db_dir`/`master_db_path`/
  `records_db_path`（マスタDB自体の置き場所を決める3項目）だけは、値をマスタDBの
  中に保存すると読みに行く先が分からなくなる（鶏と卵）ため、引き続き
  `config/local.json`（唯一残るブートストラップ専用設定）でのみ上書きできる。
  `config/local.json`に残っていた他の値（旧`sikalotnow_path`等）は初回起動時に
  一度だけパス設定マスタへ自動移行される（`_migrate_legacy_path_config`。以後は
  移行済みの目印を残し、`config/local.json`の内容は二度と見ない。マスタ管理画面
  で空欄に戻して既定へ戻す操作が復活しないようにするため）。
