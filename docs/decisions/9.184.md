# §9.184 鍵付き・デフォルトのフィルタが外れない／場面ごとに分ける（利用者の指示）

利用者の報告: 「アプリを終了して再度立ち上げると、フィルタに設定して鍵も
かけたフィルタが検索枠から外れてしまいます。モード切替でも外れます。
仕掛一覧でも、スケジュールを作るときに開く仕掛一覧のフィルタと、単純に
一覧を見るから開く仕掛一覧のフィルタは別物扱いにしたい」。

**原因は「当てる相手が居なかった」こと。** 起動時の`loadMasterPresets()`は
DBもテーブルも決まる前に走るので、その一覧の登録フィルタは1件も入って
いない。それでも動いて見えたのは端末に残っていた控え（localStorage）を
読んでいたからで、控えが無い端末・別のPC・利用者IDが後から届いた場合は
そのまま空振りしていた（印は§9.172でマスタへ移してある）。

- **当てる前に取る。** `ensurePresetsFor(db,table)`が、開く一覧が決まった
  時点でその一覧ぶんを取りに行く（1度取ったら覚える）。`selectTable`は
  これを待ってから既定・鍵を当てるので、**1回目の問い合わせから効く**。
- **鍵の付け替えと既定の当て直しは`syncFilterContext()`の1箇所。** 以前は
  `selectTable`の中だけにあり、①起動直後 ②利用者IDが後から届く
  ③スケジュール画面との行き来（テーブルは変わらない）の3つで空振りした。
  **一覧を引く前には必ず`listHooks.onQuery`を通る**ので、そこで呼ぶ。
- **覚えの持ち主は利用者。** IDが空→本人へ切り替わる瞬間は、**入れ替える
  前の持ち主**へ書き戻す（`saveActiveFilterState(who)`）。
- **場面で分ける。** `presetMode()`はアクセスモードではなく
  `document.body.classList.contains('sc-mode')`で決める。列構成が変わるのは
  スケジュール画面の中の仕掛一覧（品質データを結合する）なので、判定も
  そこへ合わせる。これで「モードを変えても『一覧を見る』の条件は外れない」
  「スケジュール作成中の条件が普通の一覧に当たらない」が同時に成り立つ。
- **どの場面の設定かを画面に書く**（登録フィルタ一覧の見出し）。書かないと
  「登録したのに出てこない」と読まれる。

**真因はもう1つあった（追記）。** 利用者IDは`/api/whoami`から**起動のあとに
届く**（`base.js`が端末へ覚える）。一覧を開いた時点でIDが空だと、登録
フィルタを**空のIDで**読むことになり、その人の印（デフォルト・鍵）は1件も
載って来ない。そのまま「読んだ」ことにしていたため、IDが届いても二度と
読み直さず、既定・鍵が永久に当たらなかった。

 - **読んだ記録に利用者IDを含める**（`presetsLoadedFor`）。IDが変われば
   読み直す。
 - `syncFilterContext()`は、届いていなければ**その場で取りに行き、取れたら
   当て直す**（同期の中では待てないので、`then`で当て直して引き直す）。
 - 場面を分けた副作用として、**片方の場面にしか無い登録は「消えた」ように
   見える**（以前はスケジュールモードの端末では両方が同じ置き場だった）。
   登録一覧に「もう一方の場面に N件あります」と件数を出し、**印ごと写す**
   ボタンを同じ場所に置く（黙って両方へ出すと、列構成の違う条件が並ぶ。
   §9.80の理由は生きている）。

固定は`tests/test_filterkeep.js`（「IDが届いた時点で鍵付き条件が入る」を含む）。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **鍵付き・デフォルトのフィルタは「当てる前に取る」**（§9.184、
  `static/js/list/filters.js`）: 起動時の`loadMasterPresets()`はDBもテーブルも
  決まる前に走るので、その一覧の登録フィルタは1件も入っていない。それでも
  動いて見えたのは端末の控えを読んでいたからで、控えの無い端末・別のPC・
  利用者IDが後から届いた場合は空振りしていた（実機で「再起動すると外れる」）。
  `ensurePresetsFor(db,table)`で開く一覧が決まった時点で取り、
  **鍵の付け替えと既定の当て直しは`syncFilterContext()`の1箇所**（一覧を引く
  前に必ず通る`listHooks.onQuery`から呼ぶ）。**覚えの持ち主は利用者**なので、
  IDが空→本人へ切り替わる瞬間は**入れ替える前の持ち主**へ書き戻す。
  **場面（`body.sc-mode`）で置き場を分ける**——アクセスモードで分けると、
  スケジュールモードの端末では「一覧を見る」の仕掛一覧まで同じ置き場になり、
  モードが変わるとどちらも入れ替わる。**読んだ記録には利用者IDを含める**
  （`presetsLoadedFor`）——IDは`/api/whoami`から後から届くので、空のIDで
  読んだ結果を「読んだ」ことにすると、その人の印は永久に載って来ない
  （これが「再起動すると外れる」の真因だった）。届いていなければ
  `syncFilterContext()`がその場で取りに行き、取れたら当て直す。
  場面を分けた副作用で**片方にしか無い登録は「消えた」ように見える**ので、
  登録一覧に件数を出し、印ごと写すボタンを同じ場所へ置く。
  固定は`tests/test_filterkeep.js`。
