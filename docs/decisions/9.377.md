# §9.377 刃組ガイダンスを移植し、設備停止の行から呼べるようにする（利用者の指示）

利用者の言葉:

> 作業スケジュール一覧表の部分に設備停止を入れることができますが、その設備停止を
> 登録するマスタに刃組ガイダンス連携機能をリンクさせる紐づけ設定をできるように
> してください。まず、設備停止名とリンクさせるために設備停止マスタにカテゴリを
> 1つ増やし登録をできるようにします。
> 登録したものについての挙動として、作業スケジュール一覧表のところで、例えば
> 「刃組み」に刃組ガイダンス連携がセットされたとすると、そこをクリックすると
> 刃組ガイダンスに遷移することができるようにします。
> 刃組については必要なデータが元コイル幅、ロット毎の切断幅、板厚などです。
> 必要な追加すべきマスタは刃マスタ、スペーサーマスタ、ゴムリングマスタ、
> フィンガーマスタなど、添付のHTMLから計算ロジックも含めて参考に連携できるように
> 移植をお願いします。

添付は 1 枚の HTML（`刃組ガイダンス`・832KB）で、部材の在庫を `localStorage` に
持ち、元板巾とロットの切断幅から**刃組図・刃組表・所要・台車差分**を出す完結した
道具だった。ここではそれを WaveLog の**マスタ**と**画面の登録簿**へ載せ替え、
作業スケジュールの設備停止の行から呼べるようにした。

---

## 1. 何を移し、何を移さなかったか

移したもの（`static/js/bladeset/blade-core.js` ＋ `blade-view.js`）:

| 元 | 移した先 | 変えたこと |
| --- | --- | --- |
| 幾何（バリ方向→刃組方式／区間長／刃位置） | `blade-core.js` §4 | そのまま |
| 分解（手持ち寸法の動的計画法） | `blade-core.js` §5 | そのまま |
| 集約（刃組表の行・端部・所要・端数の累積） | `blade-core.js` §6 | そのまま |
| 刃組図（SVG） | `blade-view.js` | **色をトークンへ**（下記 5） |
| 刃組表・端部・所要・台車差分・刃の状態 | `blade-view.js` | そのまま |
| マスタ（`localStorage`） | `刃組*`の5マスタ（下記 2） | **共有のDBへ** |

**移さなかったのは立体図（three.js）**。同梱されていた three.js r149 は 608KB で、
アプリの JS 全部（60,000行）より大きい。立体図が言っていること——「DS 側から
部材を入れて OS 側へ詰める」「軸端部を外して台車を回す」——は模式図の向き切替
（`図面向き／段取り向き`）と端部カードが同じことを言っており、**同じ情報に
608KB を払う**判断ができなかった。**要るとなったら足せる**ように、計算
（`blade-core.js`）は画面を一切知らない形のまま置いてある。

## 2. マスタは5枚。**部材は設備ごと**

| マスタ | 1行が表すもの |
| --- | --- |
| `刃マスタ` | 刃（ナイフ）1種類＝径・刃厚・枚数・研磨の記録 |
| `スペーサーマスタ` | スペーサー（現場の別名はライナー）1寸法＝枚数 |
| `ゴムリングマスタ` | ゴムリング1本＝色（＝外径）×幅 |
| `フィンガーマスタ` | 板押さえ1種類＝幅・本数・適用板厚の上限 |
| `刃組基準値マスタ` | 1設備＝1行。アーバー有効長・判定の帯など |

ほかに `刃組履歴マスタ`（台車差分の材料。刃組を終えた記録）がある。

**設備停止マスタの `'*'`（すべての設備）は受け付けない。** 部材は設備ごとに実物が
違うので、1本が全設備の所要に混ざった瞬間に数が嘘になる——ロールマスタが
§9.239 ⑥で同じ理由で断っているのと同じ（`_check_equipment()`）。

### 呼び名を「スペーサー」にした

元の HTML は冒頭で「用語 ライナー（＝スペーサー）に統一」と書いて**ライナー**を
採っていた。利用者の指示は「スペーサーマスタ」なので**マスタ名はスペーサー**とし、
画面では「スペーサー（ライナー）」と併記する。現場はどちらでも呼ぶので、
**名前を1つに決めて、もう一方を消さない**。

## 3. ゴムリングの「同じ色は同じ外径」をどこで守るか

ゴムリングは**外周研磨で径が変わり、研磨は色の単位で行う**。つまり色と外径は
1対1で、**1本は（色, 幅）の2つで決まる**（在庫も色×幅）。

表は**1行＝（色, 幅）の平らな形**にした——マスタ管理の汎用の一覧にそのまま
載るのはこの形だけだからだ。そのぶん外径が行ごとにばらけうるので、
**揃えるのは `ring_upsert()` の1箇所**にする:

- **外径を渡さなければ、その色の今の外径を引き継ぐ**（同じ色の幅ちがいを足す
  ときに径を打ち直させない）
- **外径を渡したら、その色ぜんぶをその値へそろえる**（研磨したときの入力は1行）
- **そろえた件数は答えに載せる**（黙って他の行を書き換えない）

### 踏みかけた罠: 色名を外径から起こしていた

最初の実装は「色名が空なら外径から起こす」を**保存のたびに**通していた。
外径 322 の赤い輪の径を 318 へ直しただけで、行の色名が**茶へ書き換わった**
（周期は 1mm ごとに色が変わるため）。現場が「赤」と呼んでいる輪が画面から消える。

`ring_color_of()` の周期は**まだ名前の無い径を画面に出すときの言い換え**であって
保存の規則ではない——元の HTML も `ringByOd.get(od) || cycleColor(od)` と
**引けなかったときだけ**使っていた。いまは色名を必須にし、周期は
「登録の無い色の**色コード**を当てる」ときだけ使う。

## 4. 基準値は「既定はコード・上書きだけがDB」

`刃組基準値マスタ` に行が無い設備でも画面は開けること。`standard_for()` が
`STANDARD_DEFAULTS` に保存行を重ねて返すので、**何も登録していない設備でも
計算は成り立つ**。**既定値を黙ってDBへ書かない**——共有のマスタへ勝手に行を作ると、
他の端末からは「誰かが登録した」と読める。行を消せば既定へ戻るだけで、画面が
開けなくなることはない。

部材（刃・スペーサー・ゴムリング・フィンガー）は現物の在庫なので既定を持たない。
代わりに `seed_standard_parts()` が「図面の製作数どおりの1式」を**押したときだけ**
登録する（**既に1件でもあれば足さない**——押し間違いで在庫が倍にならないように）。

### 「できない」が保存できない欄になりかけた

基準値の `中抜き可` は選択欄で「できる／できない」を出す。`flags.OFF_WORDS` に
`できない` が載っていなかったので、`bool('できない')` が真になり**「できない」を
選んでも一度も保存できない欄**になっていた。語彙を1つ足して直した——この罠は
`flags.py` の冒頭が「画面が出しうる呼び名は全部ここに並べる」と書いているとおりで、
**5度目**である。

## 5. 保持層は「ゴムリング **または** フィンガー」

元のコードはフィンガー方式（板厚 < 切替値）で**保持層を持たなかった**——
軸はスペーサーだけで組み、ゴムリングは使わない、で終わっていた。利用者が
フィンガーマスタを挙げたので、**同じ層として数える**形に一般化した:

> スペーサーが軸方向の寸法を作り、その上に**保持層**が製品幅のぶんだけ載る。
> 保持層は軸方向の寸法には効かない。ゴムリング方式ではゴムリング、
> フィンガー方式ではフィンガーがその層になる。

こうすると分解（`zoneParts`）も集約（`aggregate`）も**1本のまま**で、
所要にフィンガーの本数と在庫が出る。押上げ・板ニップはリング径から決まる量なので、
フィンガー方式では「フィンガー方式」と書いて**判定そのものを出さない**
（0を出すと「適正か不適か」を答えたことになってしまう・§9.231）。

## 6. 連携機能——**行き先はマスタが持ち、行は持たない**

設備停止マスタへ `[連携機能]` を1列足した。空欄（なし）が今までどおりで、
`刃組ガイダンス` を選ぶとその停止の行から画面を開ける。

**行そのものには持たせない。** 停止の名前は予定を入れた時点の写しで、後から
マスタの設定を変えても写しは古いままになる（§5.1 で標準所要分をスナップショット
しないのと同じ理由）。予定の行は名前でマスタを引き直す。

**語彙（鍵と呼び名）はサーバーの `STOP_LINK_FEATURES` の1箇所**（§9.163）。
一覧は `linkKey` と `linkLabel` の両方を返すので、画面は綴りから呼び名を
組み立てない。行き先を増やすときに直すのはサーバーの1箇所と、画面の
**開き方の登録表**（`SC_LINK_TARGETS`）だけになる。

### 「クリックすると遷移」を、どのクリックにするか

利用者の言葉は「そこをクリックすると刃組ガイダンスに遷移」だが、設備停止の行の
クリックは**すでに2つ埋まっている**:

- 行いっぱいのクリック … その行を**選ぶ**（§9.363）
- ダブルクリック … **停止の内容を変える**（§9.220 2①）

どちらかを横取りすると、いま使えている操作が1つ消える。**題名のすぐ横に別の的**
（`刃組ガイダンス` と書いたチップ）を立てた——押すと何が起きるかが字で読め、
**連携の無い行には出さない**ので「押せるのに何も起きないボタン」も作らない
（§CLAUDE 4）。右クリックのメニューにも同じ項目を置く（入口を種別ごとに変えない）。

## 7. 持っていく文脈は「その行より後ろに並ぶ作業」

利用者の言う「元コイル幅・ロット毎の切断幅・板厚」は、予定の写し（`detail`）に
別名で入っている（`originalWidth`／`mfgWidth`＋`boxHorizontalCount`／`mfgThickness`）。
`bladeSeedFromEntry()` が**その停止の後ろに並ぶ作業**から集める:

- 次の**同じ連携の停止**まで（次の刃組までが1つの段取り）
- 元コイル幅に収まるところまで（条の合計が元幅を超えたら止める）
- 多くても9ロット（図で色を9種までしか見分けられない）

**読めない項目は渡さない**——0で埋めると、そこだけ嘘の値になる（§9.231）。
画面は「この予定から：刃組み（設備A）」と**出どころを出す**。

## 8. 画面まわりで直したこと

- **`bodyClass` は自分で外す。** `enterView()` は付けるだけなので、`exit` で
  `bs-mode` を外し忘れると、マスタ管理を開いても刃組ガイダンスが**上に居座る**
  （実際にそうなった。他の画面はどれも `exit` で外している）。
- **`min-height:0` の鎖を1段も抜かない**（§9.222）。器→行→図のどこかで抜けると、
  SVG の中身なりの高さが下の刃組表を画面の外へ押し出す。
- **余った縦は図へ渡す**（§CLAUDE 12）。刃組表は行数なりの高さで止め
  （`fit-content(45%)`）、残りを図が使う——ロット1本の構成では表は2行しかないのに
  画面の半分を取っていた。
- **図の上端の帯を戻した。** 元の HTML にあった「クリアランス／ラップ／大径・小径」の
  バッジは、図の上端に**必ず空く**帯ぶんの場所を使う。外すとそこがただの余白になる。
- **色はトークンから**（§CLAUDE 7）。SVG の `fill` は属性なので CSS を書けない。
  器が宣言した `--bs-fig-*` を `figPalette()` が1回だけ読み取って渡す
  （`measure-opdata.js` の `carryLook()` と同じ作法）。**ゴムリングの色だけは
  マスタの値**なので、ここには入れず `--bs-dot` で運ぶ。
- **マスタを書けるのは編集モードだけ。** 現場の端末（スケジュールモード）から
  この画面へ来たときは「初期セットを登録」を**出さずに理由を書く**。
  刃組を終えた記録（`刃組履歴マスタ`）だけはスケジュールモードにも開けてある
  ——押すのはラインに居る人だから。

## 9. 網

- `tests/test_bladeset.py`（1段目・サーバー不要）… 6枚の表／ゴムリングの
  「同じ色は同じ外径」／基準値の既定と上書き／初期セットが足し算にならないこと／
  連携機能の保存と「知らない鍵はなしへ倒れる」こと
- `tests/test_bladeui.js` … 左メニューから開く／**マスタが無ければそう言う**／
  初期セットのあと図・表・所要が同じ割付から出る／幅を変えると追従する／
  板厚を下げるとフィンガーへ替わる／設備停止の行にチップが出て押すと開く／
  **連携の無い行には出ない**／文脈が入っている

### 段を2つに割った（追補）

`masters/bladeset.py` は 25 ルートになり、**1段20ルート**の約束（§9.333・
`test_routesplit`）を破っていた。**固定（`PINNED`）に逃げずに割る**——境目は
「このラインはどういう機械か／いつ何を組んだか」（`bladeset.py`: 1画面ぶん・
初期セット・基準値・履歴＝9）と「何を何枚持っているか」（`bladeset_parts.py`:
刃・スペーサー・ゴムリング・フィンガー＝16）。Blueprint は `_base.py` の1つの
ままなので、**権限表の鍵は1つも変わらない**（それがこの分け方の値打ち）。

あわせて、既存の段に倣って書いた**関数の中の `import`**（21件）を先頭へ上げた。
`test_importlint`（§9.349）が「増やさない」を見張っており、新しいファイルの
上限は0。循環は無い（`master_repo` も `flags` も `bladeset_repo` を読まない）。

### 黙って捨てていた except を1つ直した（この版で見つけたもの）

`schedule_repo.plan_merge_detail()` の `except Exception:detail={}` は§9.375 で
入ったもので、`test_quietlint` が**この版の前から赤かった**。壊れた明細JSONを
空から組み直すのは正しいが、**壊れていたこと自体を残さない**と写しが消えた
理由が誰にも分からない。`quiet('予定の明細JSONを読めない（空から組み直す）')`
を添えた。

### 指紋から `sqlite_sequence` を外した（追補）

`tests/state_fp.py` は共有状態の行数を前後で比べて「汚した本」を名指しする
（§9.360）。`sqlite_sequence` は `AUTOINCREMENT` の**これまでに配った最大の番号**で、
行を消しても戻らない——つまり**テストには片付けようが無い**。新しいマスタを足した
本は必ず「+N を残した」と出るので、後片付けを足しても消えない指摘が毎回出る。
**うるさい報告は読まれない**ので、移行フラグ（同ファイルの `MARKER_TABLE`）と
同じ理由で数から外した。
