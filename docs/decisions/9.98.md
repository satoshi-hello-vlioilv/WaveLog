# §9.98 タブを閉じてもアプリが1分半残っていた

**見つけ方。** タブを閉じてからサーバーが終了するまでを測ったら**85秒**
あった。利用者から見れば「閉じたのに終わっていない」で、次に開いたときに
**古いプロセスが同じポートを掴んでいる**状態にもなる(起動ガードが
「別のアプリが応答した」と誤判定する経路)。

**原因は「0件」を1種類しか区別していなかったこと。** 監視
(`backend/watchdog.py`)が見ているのは「開いているタブが0件か」だけで、
**そうなった経緯**を持っていなかった。ところが0件には2つの意味がある。

| 経緯 | 意味 | 待つべき長さ |
|---|---|---|
| 閉じたと告げられた | 利用者がタブを閉じた。もう戻ってこない | 短くてよい |
| 気づいたら0件だった | 通知が届かなかった。閉じたのか一時的なのか分からない | 長く待つ |

後者に90秒(`EMPTY_GRACE_SEC`)待つのには理由がある——リロードや別ページへの
移動でも`pagehide`は発火し、一瞬0件になるためで、ここを短くすると
**読み直しただけでアプリが終了する**。問題は、**前者にも同じ90秒を
当てていた**こと。

さらに監視スレッドは10秒間隔で寝ているので、終了通知が届いても**まず
最大10秒気づかない**。85秒の内訳はこの2つ(通知に気づくまで＋90秒の猶予)。

**直したこと。** 3つ。

1. 最後の1件が`POST /api/heartbeat/close`で消えたことを`_closed_notice`
   として覚え、猶予を`CLOSED_GRACE_SEC`(8秒)へ切り替える。
2. 終了通知で監視を起こす(`_wake`。`threading.Event`)。**寝ている間は
   気づけない**ので、これが無いと「8秒の猶予」の前に最大10秒の寝落ちが
   挟まる(この段階で実測18秒だった)。
3. 閉じたと告げられた直後だけ、監視の間隔を1秒(`WATCHDOG_CLOSING_
   INTERVAL_SEC`)にする。

**リロードで落とさない仕掛けはそのまま。** 閉じた通知の直後に新しい
タブIDのハートビートが届いたら、`_closed_notice`を捨てて0件でもなくなる
——8秒は「読み直した画面が名乗るのを待てる長さ」として残してある。

**実測。**

| | 閉じてから終了まで |
|---|---|
| 修正前 | **85秒** |
| `_closed_notice`のみ | 18秒(監視が寝ている10秒が乗る) |
| `_wake`＋1秒間隔まで | **約8秒** |

リロードは12秒観察して終了しないことを確認済み。

固定は`tests/test_tabclose.py`。閉じたら終了する・**ただし即座ではない**
(猶予がある)・リロードでは終了しない・通知の無い0件は短い猶予では終了
しない・画面が`pagehide`と`unload`の両方で通知を送っている、の5点。
監視スレッドは`importlib.reload`でシナリオごとに作り直し、`_exit`を
差し替えて実際のプロセス終了は起こさない。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **「開いているタブが0件」は2つの意味を持つ**（§9.98、`backend/watchdog.py`）:
  **閉じたと告げられた**（`POST /api/heartbeat/close`で最後の1件が消えた＝
  `CLOSED_GRACE_SEC`8秒）と、**気づいたら0件だった**（通知が届かなかった＝
  `EMPTY_GRACE_SEC`90秒）。**この2つを1つに戻さないこと**——90秒へ揃えると
  タブを閉じてもアプリが1分半残り（実測85秒）、8秒へ揃えるとリロードや
  別ページへの移動で終了してしまう（`pagehide`は読み直しでも発火する）。
  終了通知は`_wake`(Event)で監視を**起こす**。**寝ている間は気づけない**ので、
  起こさないと8秒の猶予の前に最大10秒の寝落ちが挟まる（実測18秒）。
  ハートビート途絶だけを根拠にした終了(`HEARTBEAT_STALE_SEC`=丸1日)は
  異常系の保険で、短くしないこと（スリープ復帰・タブの間引きで誤終了する）。
  **タブが戻ったら「閉じたと告げられた」は下ろすこと**（§9.284、
  `if not empty: _closed_notice=False`）——旗が一度立つと二度と下りない作りだった
  ため、**リロードで立った旗のせいで、次に0件になったときの意味に関わらず
  8秒で終了**していた（＝上で禁じた「8秒へ揃える」が、旗の消し忘れという別の道で
  起きていた。実測: 重い一覧の読み直しでアプリが落ちる）。
  **開いていることは`templates/index.html`の先頭で名乗る**（§9.284）——
  `base.js`まで待つと、アプリのJS(1.4MB)を読み終えるまで名乗れず**その8秒を
  使い切る**。**IDは`index.html`が作って`base.js`へ渡す**（`window.__wlTabId`）
  ——2つ作ると閉じた通知が別のIDへ行き、今度は「開いたまま」の幽霊が残って
  終了しなくなる。**FATAL(`ERR_CONNECTION_REFUSED`)を見たら、まず
  `tests/server.log`の終了理由を読むこと**（理由は出ている。網を疑うと遠回り）。
  固定は`tests/test_tabclose.py`。
- **「0件になった時刻」はタブが名乗った時点で捨てる**（§9.302の追補、
  `backend/watchdog.py`）: `_empty_since`は**起動時にセットされ、監視が次に起きた
  ときにしか消えない**。そのため「起動 → 監視が一度も起きないうちに画面を開く →
  すぐリロード」をすると、閉じた通知で起こされた時点でまだ起動時の値が入っており、
  `now - _empty_since`が既に8秒を超えていて**その場で終了する**（実測: サーバー
  起動の7秒後に開いてリロードしたら1秒未満で落ちた）。§9.98で禁じた「リロードで
  終了してしまう」が、§9.284の旗の消し忘れとは**別の道**で起きていた形。
  `heartbeat()`が`_closed_notice=False`と一緒に`_empty_since=None`も置く。
  **判定は写しへ取ってから使うこと**——別スレッドが`None`を書きうるので、途中で
  読み直すと`now-None`で落ちる（終了の判定そのものが死ぬ）。
  **網は`settle()`を挟まないこと**——挟むと監視が一度起きて`_empty_since`が消え、
  この道を一度も通らないまま通る（`tests/test_tabclose.py`の2番がまさにそれ）。
