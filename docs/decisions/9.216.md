# §9.216 列設定の既知の不具合3件／準備の入力欄を操業データへ汎用化する（利用者の指示）

利用者の指示は5つ。ここでは①〜⑤を扱う（帳票のブロックは§9.217）。

  「１）既知の不具合3件について対応をお願いします。
   ２）マスタ管理 > 操業データ項目／操業データ選択肢
     ①既存のオペレータ、検査員、作業人数、内径、スプール、縦割数、横割数、
      板厚測定器、板幅測定器、巻出し方向、など、準備で入力させている情報の
      すべてを操業データとして、入力している項目を汎用化したい。一部の必須
      入力事項もマスタで設定可能とし、今あるデータ設定も汎用化、描画可能な
      エリア(縦2×横3のカード)内の中でレイアウトも含めてマスタ上で視覚的に
      調整D&Dで並び替え編集ができる汎用設定機能を実装したいです。設備ごとに
      この設定を持つことでどの設備でも同じアプリが使えるようになります。
     ②「条入力順」や「方向」については実は準備に無関係のものなので、測定の
      入力内容のカード内に移動し、折りたたむ。…条入力時に展開され共通項目に
      なります。
     ③UIが使いにくいのでより使いやすく修正をお願いします。特に「操業データ
      項目」と「操業データ選択肢」について、相互リンク、連携を強めてより
      登録の負荷を下げて汎用性を向上させてほしいです。
   ３）操業データのカード内の文字サイズがバラバラ」

---

#### ① 既知の3件（列の設定まわり）

いずれも**「触っていない設定が黙って変わる」**という同じ形の壊れ方で、
§9.212 ②で入口を安全側へ倒したあとに残っていた取りこぼし。

| | 症状 | 真因 | 直し方 |
|---|---|---|---|
| 1 | データ一覧で右クリック「この列を隠す」を**最初の操作**として押すと、既定で畳んでいた29列がまとめて出る | `recordHeadMenuSource()`が`hiddenOf`を答えないため、メニューが**保存値の`hidden`（＝空）**を土台に上書きしていた。データ一覧は「一度も保存していないうちは既定の15列」（§9.162）なので、保存値には隠す指定が入っていない | 口が`recordInitialHidden()`を答える（§9.197と同じ形） |
| 2 | 編集モードで見出しを1回動かすと、スケジュールモードで決めた並びから選択・予定の列が消える | `fullOrder()`が`listColumnKeys()`に無い列を**黙って捨てて**いた。顔ぶれは場面で変わる（`__select__`/`__plan__`はscheduleだけ、結合列は結合が当たったときだけ） | 覚えている並びは**そのまま残す**（描くときに`healedColumnOrder()`が今ある列へ当てはめ直す） |
| 3 | 列設定を一括取り込みしたあと、保存せずにパネルを閉じると、取り込みと無関係な**その一覧の設定が消えたように見える** | `forget()`は写しを捨てるが、`load()`は「写しがあれば取りに行かない」。捨てた直後に誰かが`get()`を呼ぶと**空の形が写しへ入り直す**。パネルは`useBody()`で下書きを当てて隠していたが、閉じた拍子に`discard()`で捨てられた | `forget()`のあと**いま開いている一覧ぶんを取り直し**、下書きは置かず保存済みからパネルを組み直す |

ついでに、右クリックの「隠している列」は**列の並び順**で出すようにした
——保存値の配列順のままだと、既定で29列畳んでいるデータ一覧では
「いま隠した列」が上限（10件）の外へ押し出されて戻せない。

**確かめるときは、その操作を「最初の操作」にすること。** ①の網は最初
`test_reccols.js`の中ほどへ置いたため、直前の節が幅を引いて`hidden`を
種まきしており、**不具合を注入しても通ってしまった**（実際に2回通した）。
`cleanup()`のあと**ページを開き直して**から確かめる。
固定は`tests/test_reccols.js`・`tests/test_collayout.js`・`tests/test_colio.js`。

#### ② 準備の入力欄も「操業データの1行」にする

**画面が持っている入力欄を、マスタが差配する形にした。** 作り直しては
いない——それぞれの欄は仕掛由来のプリセット（§9.204の内径）・条数の上限
（§9.210 ⑤）・171人ぶんを測った幅（§9.130）といった仕掛けを持っており、
マスタの定義から作り直すとそれを全部書き直すことになる。

`操業データ項目マスタ`へ列を5つ足した（**無ければ足す**で移行）。

| 列 | 何を決めるか |
|---|---|
| `[組み込みキー]` | 画面が持っている入力欄の名前（`operator`・`innerDiameter`…）。空なら自由項目 |
| `[置き場]` | `準備`（①のカード）／`入力内容`（②のカード） |
| `[列幅]` | カードの中の**6列グリッド**で何列ぶんか（1/2/3/6） |
| `[群折りたたみ]` | その群を畳んで出すか |
| `[表示条件]` | 畳んだ群を自動で開く測定項目（カンマ区切り） |

`measure-opdata.js`がこの並びから`order`と`grid-column: span N`を当てる。
**CSSから項目名が消えた**——以前は`[data-f="operator"]{grid-column:1;grid-row:2}`
のような行が14本並んでおり、設備を1つ足すたびに直すことになっていた。

- **DOMは動かさない**（§9.122／§9.125）。`.selectors`の直下のまま、`order`と
  `span`だけを当てる。自由項目もここが作るが、置き場は同じ`.selectors`直下で
  **組み込みと同じ`<label>`**にする（⑤の文字サイズがこれで揃う）。
- **群の見出しはJSが作る**。`index.html`から4枚の`.prep-head`と`#usualFold`を
  外し、`measure-steps.js`の`USUAL_IDS`（項目名の直書き）も廃止した。
  **同じ処理を2箇所に持たない。**
- **出さない組み込みの欄は名指しで返す**（`/api/operation-form`の`builtinOff`）
  ——画面はマスタに載っている欄しか差配しないので、伝えないと「マスタで
  外したつもりの欄が消えない」。
- **必須もマスタが決める**。`activeRequiredControls()`は
  `['operator','inspector']`の直書きをやめ、`WL.opData.requiredControls()`を
  見る。**答えが得られないときは元の2つへ倒す**——読めなかったことを
  「必須は無い」と同じに扱うと、完了前の確認が黙って緩くなる。
- **幅をそろえる単位を「カードの列」から「群の中の列」へ絞った**（§9.142の
  絞り込み）。カードが横3マスに広がって1トラック200pxになると、
  オペレータ（171人＝11em）と同じ列にいるだけで**1〜2桁の縦割数まで154px**に
  なる（実測。以前は器が124pxしか無く、トラックが上限を兼ねて偶然収まって
  いた）。自由項目の実測は`fitOpFields()`が群ごとに行う。

#### ③ 条入力順・方向は②の入力内容カードへ

準備に無関係（条を打つときの順番）なので`[置き場]=入力内容`にし、
`[表示条件]`に条を入力する測定項目（板幅・ラテラルボー・バリ・テレスコープ・
巻ずれ・フラットネス）を入れた。板厚は丈位置ごとに3点（OS/CL/DS）で条に
紐づかないので入っていない（§9.214）。

**畳むかどうかの既定は「条件があるかどうか」で決まる**——条件つきの群は
畳んで待ち、当たったら開く。条件の無い群（いつもと同じ設定）は開いておく
（§9.133）。どちらも押せば手で開閉でき、**触ったぶんだけ**端末に覚える
（読み方の好みなのでPCごとに違ってよい。§9.199の`childBadge`と同じ）。

#### ④ 項目と選択肢の相互リンク（マスタ管理）

行を1つずつ編集する一覧では、**並べたときにどう見えるか**が分からない。
「操業データ項目」を`special:'op-item'`の画面にし、測定画面のカードと
**同じ6列のグリッド**を出して掴んで動かす形にした。

- **群は「直前の見出し帯」で決まる**ので、1回の操作で並びと群の両方が
  決まる（別々に選ばせない）。帯をまたげば置き場（準備／入力内容）も変わる。
- 並び・群・列幅・置き場・必須・出す/出さないは
  `POST /api/operation-item-master/layout`で**まとめて1回**書く
  （1行ずつでは往復が増え、途中で切れると並びが半分だけ変わった状態が残る）。
- 右は選んだ1項目の設定で、**選択肢はその場で足せる**——項目を作る手を
  止めて別のタブへ行かせないのが、利用者の言う「登録の負荷」の正体。
- **組み込みの欄は型・上下限・選択肢を持たない**（画面が持っている入力欄
  なので、ここで決めても効かない）。欄ごと出さず、理由を文字で書く（§4）。
- 「操業データ選択肢」側には**どの項目が使っているか**を出す
  （`choice_usage()`）。使い道の見えない選択肢は消してよいのか判断できず、
  消すと項目側は`choiceMissing`で黙って空の欄になる。
- 群のふるまい（畳む・開く条件）は**群の全部の行へ同じ値**を書く。
  `form_for_equipment`は「1つでも畳むと言えば畳む」で読むので、1行だけ
  直すと消したはずの条件が残る。

#### ⑤ 文字サイズをそろえる

利用者の指摘「操業データのカード内の文字サイズがバラバラ」。原因は
**器が違った**こと——自由項目は`.op-*`という独自の器を別のカードへ置いて
おり、名前・値・注記がそれぞれ別のサイズを宣言していた。②で自由項目も
準備と同じ`<label>`＝同じカードに置いたので、①のCSSがそのまま当たる。
`.opf-*`に残るのは**組み込みには無いもの**（単位・必須の印・直した理由）
だけ。§9.127の「規格を守らせる仕組みの中に入れる」と同じ考え方。

固定は`tests/test_opdata.py`・`tests/test_msteps.js`・`tests/test_opui.js`。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **後から足した列を「無ければ足す」のは`db_access.add_missing_columns()`の1箇所**
  （§9.315、利用者の報告「起動時に *読み込みに失敗しました: 操業データ項目マスタの
  読込に失敗しました: duplicate column name: 丸め方* と出る。リロードして再度
  読み込みをさせると正しく読み込めるようになる」）: 現場ではマスタを作り直さず
  「無ければ足す」で移行する（§9.216 ②）が、その処理は**17箇所に散っていて**
  どれも「`PRAGMA table_info`で読む → 無い列だけ`ALTER TABLE ADD COLUMN`」だった
  ——**読んでから足すまでのあいだに、別のリクエストが同じ列を足せる。**
  `flask_app.run(threaded=True)`（§9.98で外さないと決めてある）なので、画面を
  開いた瞬間に走る何本かの問い合わせが素直に重なる。2本とも「無い」と見て2本とも
  足しに行き、後の1本が`duplicate column name`で落ちる（実測: 同時に2本
  `ensure_item_table()`を呼ぶと再現する）。
  **その版へ上げた最初の1回にしか起きない**（次からは列が在るのでALTERを通らない）
  ので、**リロードすると直る**——原因に辿り着きにくいのはこのため。
  **「足そうとしたら既に在った」は失敗ではない**（他の誰かが今足した、という
  だけ）。それ以外の失敗（権限・読み取り専用・ディスク）は**握り潰さない**
  ——列が無いまま先へ進むと、別の場所で「そんな列は無い」と落ちて原因が遠くなる。
  **戻り値は「自分が足した列」**なので、`_add_missing_column()`のような
  「初めて作ったときだけ真」の一度きりの移行の合図（§9.288 ②）もそのまま書ける。
  **新しいマスタを足すときも必ずここを通すこと**——`tests/test_ddllint.py`が
  「素の`ADD COLUMN`が窓口の外に無い」ことを機械で数える（目で数えない）。
  **網はスレッドの重なりに頼らないこと**——速いマシンではすれ違って通ってしまう。
  `cols()`が「無い」と答える状況を作れば、ALTERは**必ず**duplicateで落ちる。
  固定は`tests/test_ddllint.py`（欠陥を戻すと3件落ちることを確認済み）。
