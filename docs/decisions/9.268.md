# §9.268 測定データの閲覧も手元の写しから／local.json の意味を言い直す（利用者の指摘）

> 「書き込みについてはある程度制約を設けて制御している設計ですが、スケジュールや
> 測定データを閲覧するときは、ローカルにコピーしてから見る設計になっている
> でしょうか。閲覧は複数人が同時にアクセスするため、直接閲覧はデータ書き込み
> 更新を阻害する要因になるはずです。」

#### ① 指摘は当たっていた

共有のデータは4つあり、**3つは手元の写しから読んでいたが、測定データだけが
共有を直接開いていた。**

| データ | 直す前の閲覧 | 仕組み |
|---|---|---|
| 作業予定 | 手元の写し | `fetch_snapshot()`（§9.188） |
| 仕掛・品質 | 手元の写し | `db_mirror`（§9.89） |
| マスタ | 手元の写し | `master_share`（§9.263） |
| **測定データ** | **共有を直接** | — |

SQLiteの読み手は読んでいるあいだSHAREDロックを持つので、閲覧端末が増えるほど
測定端末の書込（EXCLUSIVEが要る）が待たされる。SMB越しのロックは元々当てに
ならないので、なおさら重なりを減らすほうがよい。

**写しにすると効く理由は2つ。** ①`Connection.backup(pages=256, sleep=0.05)`は
**塊ごとにロックを手放す**ので、書き手が割り込める（素の`SELECT`は読み切るまで
持ち続ける）②共有を開くのが「間隔ごとに1回」になり、リクエストのたびでは
なくなる。

#### ② 作りは`db_mirror`をそのまま使う

新しい仕組みを作らない。`db_mirror.records_targets()`が
`<share>/<設備>/records.sqlite3` を写す対象として並べ、
`db_access.records_read_paths()`が読む先を答える。

**分けるのは「読む先」と「書く先」。**

    records_paths_all()   … 実物（**書く・消す**ときはこちら）
    records_read_paths()  … 写し（**読む**ときはこちら。無ければ実物＝fail-open）

**自分が書いたファイルは写さない。** 写しは間隔ぶん古いので、自分の書込が
自分に見えなくなる。`note_records_written()`がこのプロセスの書込先を覚え、
そこだけ実物を読む（1ファイル1書き手なので競合しない）。判定は1箇所。

**キャッシュが切れたら背景スレッドを起こす**（`db_mirror.wake()`）——
このリクエストは待たせず、次の読みで新しい写しが読める。

#### ③ 網が捕まえたこと

**「読む先を答える関数」だけを見る網は素通りする。** 読む側がその答えを
使っていなくても通るため（実際に素通りした）。写しと実物の中身を**わざと
食い違わせて**、どちらが出るかで見分ける。

    共有にだけ行を足す → まだ見えない（＝写しを読んでいる）
    写し直す           → 見える（＝取りこぼしではなく、写しが古いだけ）

#### ④ local.json の意味を言い直す（同じ指摘の中で）

> 「私の頭の中では `"db_dir": "%LOCALAPPDATA%\\WaveLog"` ←ローカルの自由に使う
> コピー領域、`"records_db_path": "\\\\...\\Records"` ←測定データの置き場の大元、
> みたいな感じで考えていました」

**3つの別のものが1つに見えていた。** 説明のほうが悪い。

| 実際 | 何か | 設定 |
|---|---|---|
| `db_dir` | この端末が持つ**2つのDBファイル**を置くフォルダ | local.json |
| 作り直せるファイルの置き場 | 写し・作業コピー・バイトコード | **設定は無い**（`work_dir()`が決める） |
| `records_share_dir` | みんなで使う測定データの**大元** | パス設定マスタ（画面） |

`records_db_path`は**この端末の`records.sqlite3` 1ファイル**（ファイル名まで）で、
共有の大元ではない。呼び名を「records.sqlite3 だけ別の場所へ」に変え、
「ファイル名まで指定します」「共有の置き場はこれではありません」を欄に書いた。

**環境変数を展開するようにした。** `%LOCALAPPDATA%\\WaveLog`は
`Path()`にそのまま渡ると**相対パス扱いの文字列**で、`%LOCALAPPDATA%`という
名前のフォルダをアプリの隣に作りに行っていた（利用者が書いたそのものが
動かない状態だった）。**書いたまま保存し、使うときに展開する**——展開して
保存すると端末ごとに違う文字列になり、同じ`local.json`を全端末へ配れなく
なる（変数で書きたい理由がまさにそれ）。**`%VAR%`も`$VAR`も両方見る**
——`os.path.expandvars`はプラットフォーム任せなので、それだけに頼ると
**検証がLinuxで走るこの構成では`%VAR%`の道を一度も通らない**
（§9.108・`is_network_path`と同じ理由）。**未定義の変数は残す**（消すと
フォルダ名の一部が抜けたパスに化けて、身に覚えのない場所へ書きに行く）。

固定は`tests/test_recmirror.py`（17件）と`tests/test_storage.py`。

#### ⑤ 置き場の一覧はマスタDBを1回しか開かない（追補）

`_saved_of()`が**行ごとに**パス設定マスタを開いており、
`/api/storage-layout`1回で**11回**開いて11回statしていた（9行＋`items()`の
明示2回）。手元に置いている端末では実害が出ないが、マスタを共有へ移すと
そのぶん往復が増える。`_path_config_once()`が`items()`の1回ぶんだけ写しを
持つ（**スレッドごと**——Flaskは`threaded=True`なので、モジュール変数に
置くと別のリクエストの写しを読みうる）。

あわせて**`connect()`の前の`exists()`を外した**。読みたいのはファイル
そのもので、確認は別のファイルアクセスになる——共有越しでは「開けるのに
statだけ失敗する」ことがあり、確認のつもりの1行が唯一の失敗原因になる
（CLAUDE.mdの既存の約束。書いた時点で破っていた）。

**網はソースの字を見ないこと。** 最初「`_read_path_config`の本体に
`.exists()`が無い」を字で見る形で書いたが、切り出す位置を1つ間違えて
（`split('def ')[1]`は**次の関数の本体**）**欠陥を注いでも通った**。
`pathlib.Path.exists`を見張って**実際に呼ばれるか**で見る。
読む回数も同じで、`_read_path_config`の呼ばれた回数と行数を並べて出す
（行の数だけ増えていないことが見たいこと）。

#### ⑥ `requirements.txt` に使っていない `pyodbc` が残っていた（追補）

利用者の質問「Flaskだけでなく、waitressもつかったほうがよいですか？」を
調べる過程で見つかった。**Access接続は廃止済みで、コードのどこも
import していない**のに、`requirements.txt` に残っていた。

`REQUIRED_PACKAGES`は`('flask',)`だけなので普段は誰も気づかない。しかし
**flaskが入っていない端末では`pip install -r requirements.txt`が走る**
（`setup_check.ensure_packages`）ので、そこに残っていると使っていない
pyodbcまで入れに行く——まさに「依存を増やさない」で避けたかった失敗の芽。

`tests/test_noaccess.py`は`REQUIRED_PACKAGES`しか見ておらず、
**`requirements.txt`そのものを見ていなかった**のが素通りの理由。
「pyodbcが無いこと」と「flaskだけであること」の2つを足した
（後者があると、依存を足したときに**網を書き直すところまでが1組**になる）。

**waitressは入れない。** 1台1プロセスで相手は同じPCのブラウザ1つ、
`host='127.0.0.1'`でループバックのみ、同時要求はブラウザの接続上限
（同一オリジンで6本程度）で頭打ちなので、`threaded=True`で足りる。
LANへ開く唯一の口（§9.192の受け口、既定OFF）はFlaskですらなく
stdlibの`ThreadingHTTPServer`で、合言葉つきの5経路だけを受ける。
唯一の実質的な差は「werkzeugは要求ごとに無制限にスレッドを作る／waitressは
固定プール＋キュー」だが、同時要求が頭打ちなので効かない。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **共有のデータは「読むのは写し・書くのは実物」で揃える**（§9.268、利用者の
  指摘「閲覧は複数人が同時にアクセスするため、直接閲覧はデータ書き込み更新を
  阻害する要因になるはず」）: 作業予定（`fetch_snapshot`）・仕掛/品質
  （`db_mirror`）・マスタ（§9.263）は写しから読んでいたが、**測定データだけが
  共有を直接開いていた**。SQLiteの読み手は読んでいるあいだSHAREDロックを持つ
  ので、閲覧端末が増えるほど測定端末の書込が待たされる。仕組みは増やさず
  `db_mirror`へ載せる（`records_targets()`）。**読む先と書く先を分けること**
  ——`records_paths_all()`＝実物（書く・消す）／`records_read_paths()`＝写し
  （読む。無ければ実物＝fail-open）。**自分が書いたファイルは写さない**
  （`note_records_written()`が覚える。写しは間隔ぶん古いので自分の書込が
  自分に見えなくなる）。**キャッシュが切れたら`db_mirror.wake()`**（この
  リクエストは待たせない）。**「読む先を答える関数」だけを見る網は素通りする**
  ——読む側がその答えを使っていなくても通る（実際に素通りした）。写しと実物の
  中身を**わざと食い違わせて**どちらが出るかで見分ける。
  固定は`tests/test_recmirror.py`。
  **一覧を作るのにマスタDBを行ごとに開かないこと**（§9.268 ⑤）——
  `storage_layout._saved_of()`が行ごとに開いており、1回の
  `/api/storage-layout`で**11回**開いていた。`_path_config_once()`が
  1回ぶんの写しを持つ（**スレッドごと**。`threaded=True`なので
  モジュール変数だと別のリクエストの写しを読みうる）。
  **網はソースの字を見ないこと**——「本体に`.exists()`が無い」を字で
  見る形で書いたら、切り出す位置を1つ間違えて欠陥を注いでも通った。
  `pathlib.Path.exists`を見張って**実際に呼ばれるか**で見る。
- **`config/local.json`のパスは環境変数を展開する。保存は書いたまま**
  （§9.268 ④、利用者の指摘）: `%LOCALAPPDATA%\WaveLog`は`Path()`にそのまま
  渡ると**相対パス扱いの文字列**で、`%LOCALAPPDATA%`という名前のフォルダを
  アプリの隣に作りに行っていた。窓口は`paths.expand_path()`で、
  **`%VAR%`も`$VAR`も`~`も見る**——`os.path.expandvars`はプラットフォーム
  任せなので、それだけに頼ると**検証がLinuxで走るこの構成では`%VAR%`の道を
  一度も通らない**（§9.108・`is_network_path`と同じ理由）。
  **展開して保存しないこと**——端末ごとに違う文字列になり、同じ
  `local.json`を全端末へ配れなくなる（変数で書きたい理由がそれ）。
  **未定義の変数は残す**（消すとフォルダ名の一部が抜けたパスに化けて、
  身に覚えのない場所へ書きに行く）。保存の入口では**展開してから**絶対パスかを
  見て、**理由を言い分ける**（相対／変数が空、で打つ手が違う）。
  **`db_dir`・`records_db_path`の意味を取り違えさせないこと**——`db_dir`は
  **この端末の2つのDBファイルを置くフォルダ**であって作業用のコピー置き場では
  なく（写しの置き場は`work_dir()`が決める・設定は無い）、`records_db_path`は
  **この端末の`records.sqlite3` 1ファイル**であって共有の大元ではない
  （そちらは`records_share_dir`）。実際にこの3つが1つに見えていた。
  **展開は`_planned_of()`と`prepare_path()`も通すこと**（§9.271）——通して
  いなかったので、変数で書いた端末では「これから効く値」に`%LOCALAPPDATA%`が
  生で出て（どこへ置かれるか画面から読めない）、**「無いので作る」が
  「絶対パスで指定してください」と断っていた**（書いてあるのに否定する文言で、
  §9.267の「設定さえ書いてあれば作る」が一度も効かない）。
- **`requirements.txt`は`flask`だけ。増やしたら網も書き直す**（§9.268 ⑥）:
  `REQUIRED_PACKAGES`は`('flask',)`だけなので普段は誰も気づかないが、
  **flaskが入っていない端末では`pip install -r requirements.txt`が走る**
  （`setup_check.ensure_packages`）——余分な行があると、使っていない部品まで
  入れに行く。Access接続を廃止したのに`pyodbc`が残っており、実際にこの状態
  だった（コードのどこも import していない）。
  **Webサーバーを`waitress`等へ替える必要も無い**——1台1プロセスで相手は同じ
  PCのブラウザ1つ、`host='127.0.0.1'`でループバックのみ、同時要求はブラウザの
  接続上限で頭打ち。`flask_app.run(threaded=True)`で足りる（LANへ開く唯一の口
  ・§9.192の受け口はFlaskではなく stdlib の`ThreadingHTTPServer`）。
  固定は`tests/test_noaccess.py`（`pyodbc`を戻す・別の依存を足す、の両方で落ちる）。
