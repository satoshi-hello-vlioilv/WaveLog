# §9.523 品質一覧へ戻ると表が伏せたまま／権限を読めず黙ってスケジュール不可に倒れる／表示ルールに「または」とかっこ（利用者の報告と指示）

索引: [決定記録](README.md)

## 利用者の言葉

「VER2.409.0で作業スケジュール一覧から、品質一覧を開くと一覧が表示されない不具合が発生しました。」

「VER2.409.0で開発者権限なのに、スケジュールモードへの切り替えができなくなりました。修正をお願いします。」
（添えられた画面: モードの面に「編集モード」「閲覧モード」の2つだけ）

## 1. 品質一覧へ戻ると表が伏せたまま

### 測った（評価関数）

物差しは「一覧を開いた後に **表（`#grid`）と絞り込みの帯が見えているか**」。行の数では見ない——
伏せた表にも行は在る（実測 91行在るのに見えない）。道を3つ回した。

| 道 | 直す前 | 直した後 |
| --- | --- | --- |
| 起動 → 品質データ | 見える | 見える |
| 起動（仕掛）→ 作業スケジュール → 品質データ | 見える | 見える |
| **品質データ → 作業スケジュール → 品質データ** | **見えない**（`body`は`qa-mode`だけ） | 見える（`qa-mode qa-view-raw`） |

VER2.408.0（このPRの前）でも同じく見えない——**このPRで入った不具合ではない**。いつから在るかは
分からない（取れる履歴の最も古い版 VER2.279.0 の時点で同じ作りだった）。

### 原因

「品質データを出していたか」を**2箇所**が持っていた。

- 画面の印 `qa-mode`／`qa-view-raw`——一覧を離れるとき一覧の`exit`（`list-view.js`）が外す
- `quality-analysis.js`の控え `prevQa`——「品質から品質へ」なら元データへ戻さない、のための控え

一覧の`exit`は印だけを外し、控えは知らないまま真で残る。戻ってきた`sync()`は「前も品質だった」と
読んで`setView('raw')`を飛ばし、`qa-view-raw`の無い＝**表も帯も伏せた**一覧が出た。

### 決めたこと

- 控えをやめ、**「品質を出していたか」は画面の印（`qa-mode`）そのものから読む**。答えを1つに
  しておけば、どの道で離れても入り直しは同じ扱い（元データから）になる。
- 網は`test_flows.js`（画面をまたいだときの壊れ方を見る網）に**来た道を戻る1節**を足す。
  直す前のファイルで 81/82（この1件だけ落ちる）、直した後 82/82。

## 2. 開発者なのにスケジュールモードを選べない

### 測った（評価関数）

モードの面に「スケジュール」が並ぶのは`/api/access-mode`が`canSchedule:true`を返したときだけで、
その答えは**この端末に効くアクセス権限マスタの1行**の`[スケジュール可否]`。フィクスチャ
（開発者・スケジュール可）では VER2.409.0 でも3つ並び、自分の行を**変えずに保存しても**
`可`のまま（保存の本文は`"canSchedule":"可"`）——保存の道は壊れていない。

残る道は**権限を読めずに既定へ倒れる**こと。既定は「編集可・スケジュール不可・一般ユーザー」で、
画面は添えられた絵とちょうど同じになる。物差しは「後の版で足した列が1つ欠けたマスタを、
**読み取り専用の接続で**読んで、正しい権限が返るか」（欠けなし・6列それぞれ欠け・全部欠けの8通り）。

| | 直す前 | 直した後 |
| --- | --- | --- |
| 正しく読めた | **1/8**（欠けなしだけ） | **8/8** |
| 欠けたときの答え | 例外「attempt to write a readonly database」→ 黙って既定 | 無い列だけが既定、他は行のとおり |

### 原因

権限は読み取り専用の接続で引く（`access_mode._permission_flags()`）が、
`access_permission_master_rows()`は**読むたびに列を足しにいっていた**（`ensure_access_permission_table`）。
後の版で足した列（例: §9.512 の`[表示列編集]`）が1つでも無いマスタでは`ALTER`が読み取り専用で投げ、
`_permission_flags()`は理由を捨てて既定へ倒れる。

列が足されるのは書ける接続で読んだとき（マスタ管理 > アクセス権限を開いたとき）だけ。
**マスタを共有に置いていると、読むのは手元の写し**（§9.263）で、写しは共有から取り直すたびに
戻るので、誰かがこの表へ保存するまで直らない。

**利用者の端末で本当にこれが起きているかは分からない**（端末のマスタを見ていない）。確かめたのは
「この形なら添えられた画面になる」ことと「このとき直す前は必ず倒れる」ことまで。

### 決めたこと

- **読むのに書込を要らないこと**。列を足せるなら足し、足せなければ理由を1行残して
  **無い列は空（`NULL`）として読む**。空の読み方は既定と同じ（列が無い＝まだ誰も決めていない）。
  読む列の並びは`_PERMISSION_READ_COLUMNS`の1箇所（呼び出し側の添字そのもの）。
- **倒れた理由を持って返す**。`_permission_flags()`は理由をログへ残し、`/api/access-mode`が
  `permissionError`で運ぶ（読めていれば空）。画面にどう出すかは**見た目が変わるので未実施**
  （利用者に確かめてから）。
- 網は`test_roleperm.py`の⑪（節8「列が足りない古いマスタでも読める」は書ける接続・列のそろった
  マスタしか見ておらず素通りしていた）。直す前のファイルで⑪の1件目が落ち、直した後 55/55。

## 3. 表示ルールの行の中に「または」とかっこ

### 利用者の言葉

「表示列の読み替えルールについて、AND条件しか同じ条件の中に追加で組み込めないので、OR条件も追加で組み込めるようにしてほしいです。」

「かっこも入れられるようにしたい。使いやすいUIで実装をお願い」

### 以前の決め事を改めた

`list-rules.js`の頭には「**行=OR、行の中=AND**と決めてある。『ORもANDも1画面で』は組み合わせが
爆発して、作った本人にも読めなくなる」とあった。ORのたびに同じ表示の行を2つ書かせることになり、
利用者には「できない」と映っていた。読めなくなる心配は**見た目で抑える**ことにした:

- 「または」から新しい組。組は**「かつ」を先にまとめる**（式の and/or・Excelと同じ強さ）。組の頭に
  区切りの線を引く——どこまでが1つの組かを並びが言う。
- かっこは**条件の代わりに置く組**（`{kind:'group',conditions:[…]}`）。左の太い線が括弧で、中の
  1つ目の接続詞が「（」、足元が「）」——「かつ（ … または … ）」と式のように読める。
- かっこは**2段まで**（`GROUP_DEPTH`／`RULE_GROUP_DEPTH`）。それより深い組は保存のとき中身を
  1つ上へ平らに並べる（捨てない）。

### 測った（評価関数）

| | 前 | 後 |
| --- | --- | --- |
| 「または」12場面: 画面の判定／式への変換／サーバーの判定 | 5/12・5/12・5/12 | 12/12・12/12・12/12 |
| 「または」の保存の往復 | 消える（全部「かつ」へ） | 残る |
| かっこ12場面（2段の入れ子を含む）: 画面の判定／式への変換／サーバーの判定 | 7/12・7/12・8/12 | 12/12・12/12・12/12 |
| かっこの中が見る列（列を引く・行の値を作る） | 0/3 | 3/3 |
| かっこの保存の往復 | 0/3 | 3/3 |
| 窓の接続詞の列（「または」の字＋余白＋矢印） | 56px（字が切れる・実測 必要65px） | 72px |

### 決めたこと

- 区切り方と組の中へ降りる道は**1箇所ずつ**: 画面は`WL.displayRules`の`groupsOf()`／`condsTrue()`／
  `leavesOf()`、サーバーは`sort_order`の`rule_groups()`／`rule_conds_true()`／`rule_leaves()`。
  判定・式への変換・見る列・並べ替えが同じ答えを使う。
- 保存（`normalize_rule_conditions`）は印と組を残す。**壊れて落ちた組の頭は次の条件が継ぐ**——
  落としたせいで組が「かつ」でつながると、当たる行が黙って変わる。空のかっこは保存しない。
- 窓の手当て: 組の頭（または）を消すと次が頭を継ぐ／かっこの最後の1つを消すとかっこごと消える／
  「かっこを外す」で中身を1段上へ（前とのつなぎ方は中の1つ目が継ぐ）。
- 網: `test_colrule.js`と`test_displayrule.py`。直す前のファイルではどちらも落ちる。
