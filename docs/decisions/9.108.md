# §9.108 置き換えがWindowsで拒まれる（開いているファイルは上書きできない）

実機からの報告: **「ローカルにコピーしてsqlite3の仕掛関連ファイルを使用する
ことが多いと思いますが、ローカルにコピーを失敗したりするような挙動も確認
できています。問題が通信回線の不安定部分だけであれば特に問題はありませんが、
通常ベースで起こる場合は改善をお願いします。」**

ログに出ていたのは次の2件。

```
WARNING スケジュール編集セッションの解放に失敗しました: [WinError 5]
  アクセスが拒否されました。:
  '\\Nlmfangyshrd\...\schedule.sessions.<uuid>.tmp'
    -> '\\Nlmfangyshrd\...\schedule.sessions.json'
WARNING SIKALOT の写しを置き換えられませんでした: [WinError 5]
  アクセスが拒否されました。:
  'C:\boxdrive\Box\...\db\cache\SIKALOT.sqlite3.tmp'
    -> 'C:\boxdrive\Box\...\db\cache\SIKALOT.sqlite3'
```

#### 回線ではない

**答えは「通常ベースで起こる」。** どちらも同じ1つの規則で説明が付く。

POSIXの`rename(2)`は、**置き換え先を誰が開いていても成功する**。開いたままの
ファイルはinodeとして生き残り、名前だけが差し替わる。ところが
Windowsの`MoveFileEx(..., MOVEFILE_REPLACE_EXISTING)`は、置き換え先に
`FILE_SHARE_DELETE`無しで開かれたハンドルが1つでもあると
`ERROR_ACCESS_DENIED`(WinError 5)で失敗する。そして**SQLiteはWindowsで
`FILE_SHARE_READ|FILE_SHARE_WRITE`しか指定しない**(`FILE_SHARE_DELETE`は
付けない)。つまり——

> **こちらが写しを1件読んでいる間、その写しは置き換えられない。**

同じことが共有上のJSONにも起きる。`schedule.sessions.json`は全PCが
数十秒ごとに読み書きするので、置き換えようとした瞬間に**別のPCが読んで
いる**確率は普通に高い。回線が健全でも起きる。

**Linuxでは絶対に再現しない。** テストは全部Linuxで走っているので、
この種の不具合は実機のログでしか見えない。

#### 3つの対処を重ねる

**(1) 待てば直る失敗は、待つ。** `backend/atomic_io.py`が
`replace()`/`unlink()`を持ち、WinError 5/32/33/1224 と POSIXの
`EBUSY`/`ETXTBSY`だけを「一時的」とみなして0.05秒から倍々で粘る(既定5秒)。
**恒久的な失敗は再試行しない**——`EACCES`(POSIXの本物の権限エラー)や
WinError 87を粘ると、間違いに気づくのが遅れるだけになる。予算を使い切ったら
**最後の例外をそのまま送出する**(握り潰すと呼び出し側が「置き換えたつもり」で
進む)。ラベルごとに再試行・失敗の回数を数え、`GET /api/db-mirror`の
`replaceStats`で見える——**「たまに」なのか「毎回」なのかは数字でしか
分からない**ためで、回線の揺らぎなら再試行で吸収されて`failed`は増えず、
構造的な問題なら`failed`が積み上がる。

**(2) 写しは上書きしない。** 再試行は「掴まれている時間が短い」ときにしか
効かない。写しの置き換えは**そもそも上書きをやめる**のが正しい:
`db/cache/<キー>.sqlite3`という決まった名前ではなく
`<キー>.g<世代>.sqlite3`という**毎回新しい名前**へ書き、台帳
(`_mirror.json`)の`file`が今読むべき世代を指す。読み手は開いた世代を最後まで
読み切れ、書き手は誰も開いていない名前へ書くので、両者がぶつからない。
古い世代は**消せたときに消す**(消せないのは誰かが読んでいるときだけなので、
次の周回で片付く)。旧い形の台帳と決まった名前の写しは**そのまま読める**
——読めないと、版を上げた瞬間に全データソースを共有越しに写し直すことになる。

**(3) 置き場がクラウド同期フォルダなら、そう言う。** 実機の写しの置き場は
`C:\boxdrive\Box\...\WaveLog_v1\db\cache`、つまり**アプリごとBox Driveの中**に
置かれていた。Box Driveは同期のあいだファイルを掴むため、掴む時間が
桁違いに長い(数秒〜数分)。世代名にしたので致命傷ではなくなったが、
**写しが毎回クラウドへ上がる**という無駄は残る。起動時に名前で見分けて
警告し、`config/local.json`の`db_dir`を実ローカル(例:`C:\WaveLog\db`)へ
移すよう案内する。見分けは名前だけなので確証ではない——だから止めずに、
「置き換えに失敗したときの心当たり」として添えるに留める。

#### どこに効くか

| 置き換え | 何とぶつかるか | 対処 |
|----|----|----|
| `db/cache/<キー>.sqlite3` | 自分の読み取り / Box同期 | 世代名(上書きしない)＋再試行 |
| `schedule.sessions.json` | 他PCの読み取り | 再試行 |
| `schedule.lock.json`の削除 | 他PCの読み取り | 再試行(消せなければTTL任せ) |
| 共有`schedule.sqlite3`(push) | 他PCの読み取り | 再試行 |
| ローカル作業コピー(fetch) | 自分の読み取り | 再試行 |
| RNEの公開先 | 別アプリ | 既存の保留(pending)＋再試行 |

固定は`tests/test_atomicio.py`(何を一時的とみなすか・恒久的な失敗は
1回で諦めること・予算切れでも握り潰さないこと)と`tests/test_dbmirror.py`
(**`os.replace`/`os.unlink`を差し替えてWindowsの規則を持ち込み**、
開いている写しがあっても写し直せること・読み手が前の内容を読み続けられる
こと・掴まれている世代は残し手を離したら片付くこと・旧い形からの引き継ぎ)。
**「前提」の確認を先に入れてある**——決まった名前への上書きが本当に
拒まれることを見ておかないと、真似が効いていないまま両方PASSして
何も確かめられない(§9.102)。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **終わる前に片付ける。片付けは`watchdog.teardown()`の1箇所**（§9.301 ②、利用者の
  指示「そういう意味で安全なアプリの終了ボタンも欲しいです」）: これまで
  `/api/shutdown`は0.3秒後に`os._exit`するだけで、**共有の目印を残したまま落ちて
  いた**——書込役の目印（既定90秒）・編集セッション（同）・在席が期限まで残り、
  他の端末はそのあいだ「書込役は生きている」と信じて**書き込みのたびに届かない
  相手を待つ**（§9.301 ①の待ち時間の元）。いまは`_exit()`が片付けを通すので、
  **タブを閉じても`stop.bat`でも終了ボタンでも同じ道**（3つ持つとどれか1つだけ
  片付け忘れる）。**終了そのものは止めない**——片付けは別スレッドで走らせて
  3秒で見切る（共有が不調で閉じられなくなるほうが困る・§9.108）。
  **`teardown()`を直に呼ぶ網では足りない**——`_exit()`が通していなくても通る
  （§9.290と同じ形）。`os._exit`を差し替えて**落ちる道が本当に片付けを通るか**
  を見る。画面のボタンは左メニューの**足元**（§CLAUDE 5。`.nav-item`にしてあるので
  畳んだときのアイコン化と浮き出し・§9.265がそのまま効く）で、押す前に
  **何が起きるかを1行ずつ並べる**（§6。事実は`/api/app/quit-check`が答え、
  **未保存の測定だけは画面が添える**——端末のブラウザの中にあるので画面しか
  知らない・§9.202）。**終わったら「接続が切れました」を出さない**（§3。自分で
  終了したのに事故のように見せない）。**切断されている端末でも自分は閉じられる**
  （§9.272は共有への書き込みを止める仕組みで、閉じられないほうが困る）。
  固定は`tests/test_scowner.py`・`tests/test_appquit.js`——**網の中で本当に終了
  させないこと**（`/api/app/quit`を差し替える。落とすと以降の全部が道連れになる）。
- **Windowsは開いているファイルを置き換えられない**（§9.108、
  `backend/atomic_io.py`）: POSIXの`rename(2)`は置き換え先を誰が開いていても
  成功するが、Windowsの`MoveFileEx`は`FILE_SHARE_DELETE`無しのハンドルが1つ
  でもあると**WinError 5**で失敗する。SQLiteはその指定をしないので、
  **こちらが写しを1件読んでいる間その写しは置き換えられない**。
  **Linuxでは絶対に再現しない**ので、テストが通っても安心しないこと
  （実機のログでしか見えない。実際に写しの更新が毎分失敗していた）。
  新しく`os.replace`／`unlink`を書くときは`atomic_io.replace()`/`.unlink()`を
  通す——待てば直るもの（WinError 5/32/33/1224・`EBUSY`）だけを粘り、
  **恒久的な失敗（`EACCES`等）は1回で諦める**（粘ると間違いに気づくのが
  遅れるだけ）。予算切れでも**例外は握り潰さない**。
  **ただし再試行は「掴む時間が短い」ときにしか効かない。** 写しのように
  自分が読んでいる先は、**そもそも上書きしない**のが正しい
  （`db_mirror`は`<キー>.g<世代>.sqlite3`という毎回新しい名前へ書き、台帳の
  `file`が今の世代を指す。古い世代は消せたときに消す）。**決まった名前へ
  上書きする実装に戻さないこと。** 置き場がクラウド同期フォルダ
  （Box/OneDrive等）だと掴む時間が桁違いに長いので、`cloud_sync_hint()`が
  見分けて起動時に警告する。固定は`tests/test_atomicio.py`・
  `tests/test_dbmirror.py`（`os.replace`/`os.unlink`を差し替えてWindowsの
  規則を持ち込む。**「前提」の確認を先に置くこと**——真似が効いていないと
  両方PASSして何も確かめられない）。
