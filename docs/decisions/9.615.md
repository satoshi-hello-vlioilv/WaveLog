# §9.615 版の ZIP を置くと「ZIP ファイルが届いていません」で断られる——本文はバイト列で送る（利用者の指摘）

索引: [決定記録](README.md)｜前: [§9.614](9.614.md)｜関係: [§9.546](9.546.md)・[§9.555](9.555.md)・[§9.556](9.556.md)・[§9.610](9.610.md)

## 経緯（利用者の言葉）

> 失敗するのですが何か違うのでしょうか？

2.506.0 を配るため、GitHub の main の ZIP（`WaveLog-main.zip`）を「アプリの更新」の「ZIP から版を置く」で選んだところ、
窓に「版を置けませんでした／ZIP ファイルが届いていません。」と出て置けなかった（デスクトップ版の窓・画像で確かめた）。

## 原因（分かったことと、分からないこと）

- 断ったのはサーバーの`app_update_publish()`（`backend/routes/core.py`）。**本文が0バイト**のときの答え。
- 画面は選んだファイル（`File`）をそのまま`fetch`の本文にしていた（§9.555 から）。デスクトップ版の窓は画面の問い合わせを
  `wavelog:`の受け口（Tauri／wry の`register_asynchronous_uri_scheme_protocol`）で受け、wry は WebView2 が渡す
  `Request.Content()`のストリームを読む（`wry-0.57.0/src/webview2/mod.rs`）。
- **最初の見立て「File／Blob を本文にすると WebView2 が空で渡す」は、そのままでは誤りだった。** CI の自己診断（本物の WebView2・
  5通りの起こし方）で 16MB を送ると、バイト列・**メモリ上の Blob・メモリ上の File** のどれも 16,777,216 バイト全部届いた。
- 利用者の窓で0バイトになったのは、**ファイルを選ぶ窓で選んだ、ディスクのファイルを指す File**。これは自己診断の中では作れない
  （ファイルを選ぶ窓は人が操作する）。ディスクを指す本文だけが渡らない、と考えると辻褄は合うが、**確かめてはいない（分からない）**。
- 前の版（2.496.0〜2.504.0）がどの道で置けたのかも**分からない**（ブラウザで開いた開発の入口から置いたのか、WebView2 の
  ランタイムの更新で振る舞いが変わったのか、記録が無い）。

## 決めたこと

1. **画面は本文をバイト列で送る**（`await file.arrayBuffer()`・`master-update.js`の`publish()`）。読むのは選んだ ZIP 1つ（十数MB）。
   バイト列はメモリ上の中身なので、ディスクを指す本文の扱いに左右されない。
2. **自己診断で本物の WebView2 の届き方を測る**（`desktop/src/selftest.js`の 6b）。窓に受け口`POST /__desktop/echo`
   （届いたバイト数と頭の4バイトを返すだけ）を足し、16MB を「バイト列」で送って欠けずに届くことを確かめる。
   メモリ上の`Blob`・`File`で何バイト届くかも結果に添える（CI の`selftest.json`に残る）。

## 物差し

| 物差し | 直す前 | 直した後 |
| --- | --- | --- |
| 利用者の窓で ZIP を置くと届くバイト数 | 0（「届いていません」） | 利用者の窓で確かめる（まだ） |
| 本物の WebView2 で 16MB のバイト列が届く（CI・5通り） | 測っていない | 16,777,216／16,777,216（5通りとも） |
| 同・メモリ上の Blob／File | 測っていない | どちらも 16,777,216（見立ての反証） |
