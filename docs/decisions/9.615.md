# §9.615 版の ZIP を置くと「ZIP ファイルが届いていません」で断られる——本文はバイト列で送る（利用者の指摘）

索引: [決定記録](README.md)｜前: [§9.614](9.614.md)｜関係: [§9.546](9.546.md)・[§9.555](9.555.md)・[§9.556](9.556.md)・[§9.610](9.610.md)

## 経緯（利用者の言葉）

> 失敗するのですが何か違うのでしょうか？

2.506.0 を配るため、GitHub の main の ZIP（`WaveLog-main.zip`）を「アプリの更新」の「ZIP から版を置く」で選んだところ、
窓に「版を置けませんでした／ZIP ファイルが届いていません。」と出て置けなかった（デスクトップ版の窓・画像で確かめた）。

## 原因

- 断ったのはサーバーの`app_update_publish()`（`backend/routes/core.py`）。**本文が0バイト**のときの答え。
- 画面は選んだファイル（`File`）をそのまま`fetch`の本文にしていた（§9.555 から）。デスクトップ版の窓は画面の問い合わせを
  `wavelog:`の受け口（Tauri／wry の`register_asynchronous_uri_scheme_protocol`）で受け、wry は WebView2 が渡す
  `Request.Content()`のストリームを読む（`wry-0.57.0/src/webview2/mod.rs`）。**ファイル（`File`／`Blob`）を本文にすると、
  そのストリームが空で渡る**——窓も Python も空の本文しか受け取れない。
- 文字列の本文（JSON）はこれまでも届いていた（自己診断の「約 460KB の日本語の本文が往復する」）。バイナリの本文を送るのは
  画面の中でここ1箇所だけで、自己診断は測っていなかった。
- 前の版（2.496.0〜2.504.0）がどの道で置けたのかは**分からない**（ブラウザで開いた開発の入口から置いたのか、WebView2 の
  ランタイムの更新で振る舞いが変わったのか、記録が無い）。

## 決めたこと

1. **画面は本文をバイト列で送る**（`await file.arrayBuffer()`・`master-update.js`の`publish()`）。読むのは選んだ ZIP 1つ（十数MB）。
2. **自己診断で本物の WebView2 の届き方を測る**（`desktop/src/selftest.js`の 6b）。窓に受け口`POST /__desktop/echo`
   （届いたバイト数と頭の4バイトを返すだけ）を足し、版の ZIP と同じ 16MB を「バイト列」で送って欠けずに届くことを確かめる。
   同じ中身を`Blob`・`File`で送ったときに何バイト届くかも結果に添える（CI の`selftest.json`に残る）。

## 物差し

| 物差し | 直す前 | 直した後 |
| --- | --- | --- |
| 窓で ZIP を置くと届くバイト数 | 0（利用者の画面で「届いていません」） | CI の自己診断で確かめる（16MB のバイト列） |
| バイナリの本文を測る自己診断 | 0件 | 1件（バイト列・Blob・File の届いた数を並べる） |
