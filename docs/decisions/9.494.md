# §9.494 網のアクセスモードは土台が始めの値へ戻す——`test_sctimecols`が`test_scpick`の後で落ちていた（利用者の指示）

索引: [決定記録](README.md)

## 経緯

利用者の指示「test_sctimecolsの原因を調べて直して」。§9.493 の作業中に見つかり、原因が分からないまま残していた赤。

## 測った

`test_sctimecols`の中に一時の計測を入れて、落ちる組み合わせ（`test_scpick`の直後）と単独とで比べた。

| | 予定の応答 | 測定データの一覧 | 前提の記録の保存 |
| --- | --- | --- | --- |
| `test_scpick`の直後 | 40件・全部「作業/予定」（完了の行なし） | 0件 | **HTTP 403**「現在のモードでは、この操作は実行できません」 |
| 単独 | 41件（`actual:stc-done`＝計画外の完了あり） | 1件 | HTTP 200 |

## 原因

1. `test_scpick`は後片付けでアクセスモードを`schedule`にしたまま終わる。「テスト側でモードを切り替える」群は
   モードが次の網へ持ち越される。
2. `test_sctimecols`は**モードを`edit`にする前に**前提の完了記録を保存し、**応答を見ていなかった**。
   `schedule`モードでは測定データの書込が403で弾かれるので、記録が1件も無いまま進み、ずっと後の
   「当たる行と当たらない行の両方がある」で落ちた。
3. ランナーの単独の回し直しで「1回目は落ち2回目は通る」のは、1回目の途中で`edit`へ切り替わるから。

前回の見立て（`test_scpick`が取った編集セッションを返していない）は**外れ**だった（返しても同じに落ちた）。
写しから読んでいる（§9.268）という見立ても外れ——保存の口は`records_path_for(create=True)`で書いた先を覚えている。

## 決めたこと

1. **アクセスモードは土台（`harness.js`の`run()`）が始めの値へ戻す**。`mode`を渡した網も、網の中で自分で
   切り替えた網も同じ。網ごとに片付けを書き写さない（§9.491 の`SIDE_EFFECT_TABLES`と同じ考え）。
2. 土台の後片付け（実績の削除）は**`edit`で**行う。`schedule`のままだと削除も403で黙って弾かれていた。
3. **網の中で切り替えたまま終えた網は`MODE-LEAK:`の1行で名指し**する（`mode`を渡した網は土台が切り替えて
   土台が戻すので名指ししない）。
4. `test_sctimecols`はモードを**先に**決めてから保存し、保存できたことを`rec`で確かめる
   （前提が作れなければ、その場で「前提」として落ちる）。

## 直したあと

- `test_scpick`→`test_sctimecols`: **63/65 → 66/66**（前提の確認1件を足した）。
- 「テスト側でモードを切り替える」群44本: 1263/1263。切り替えたまま終えていた網は**7本**
  （`test_audittrail`・`test_lotcopy`・`test_sccat`・`test_scinsert`・`test_scpick`・`test_startwork`・`test_wipgone`）。
  どれも土台が戻すので、次の網には持ち越さない。
- 土台を使っていない網は`test_formula.js`の1本だけで、モードに触らない。
