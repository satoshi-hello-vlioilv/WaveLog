# §9.351 実績を置く網は自分で消す。一時保存は開始を打刻しないと「作業中」にならない

3-18（§9.350）の網を回したとき、`test_theme` の3件（実績のある行に削除ボタンが出る）が
落ちた。CSSを戻しても落ちる。調べると**網が置き土産で緑になっていた**。

## 何が起きていたか

- `test_scsync`（開始→一時保存→スケジュールで「作業中」）は、**単独では落ち、
  `test_startwork` の直後に回すと通る**。`test_startwork` が `sw-running`（開始時刻
  つきの編集中）・`sw-old`・`sw-done` を `records.sqlite3` に置いたまま終わり、
  後続の網はそれを「作業中」「完了」と数えていた。判定は
  `/作業中/.test(自分の行)||作業中の行数>0` なので、他人の行で通る。
- `test_theme` の5節も同じで、「実績のある行」を前の網の残りに頼っていた。
- 製品は**勝手に開始・終了へ書き込まない**（作業時間カードの方針・2026-08-26）。
  一時保存だけでは `workTime.startAt` が空で、サーバーの `derive_state()` は
  `startAt` の無い実績を「着手」にしない。**網のほうが製品の方針と食い違って
  いた**——「開始」ボタンで測定画面を開くだけでは「作業中」にならず、
  打刻して初めて移る（`startWorkFromEntry` の注釈にもそう書いてある）。
- 後始末の `reliableDelete(S.measure.id)` は、スケジュールへ戻った時点で
  `S.measure` が空なので**一度も効いていなかった**。一時保存が毎回1行残る。

最後に緑だった通し（同日 04:08）でも順番のおかげで通っていただけで、
**この日のどの変更も原因ではない**（CSS・JS・テストの変換、いずれも戻して同じ）。

## 決めたこと

1. **実績を置く網は自分で消す**（`test_startwork` の `sw-*`、`test_sccat`／`test_screport` の
   `rec-*` を末尾で `/api/measurement/backup/delete` へ）。他の網が拾えるものを残さない。
2. **「作業中」を見る網は開始を打刻してから保存する**（`#stampWorkStart` を押し、
   `workTime.startAt` が入ったことを1件として記録する）。製品の方針のとおりの手順。
3. **後始末は控えたIDで消す**。`S.measure.id` は保存前に控え、最後に API で消す。
4. 3本とも**単独で**緑（`test_scsync` 6/6・`test_theme` 42/42・`test_startwork` 17/17）、
   終わったあと `records.sqlite3` に行が残らない。

## 見つけたが触っていないもの

- スケジュールの「開始」から開いた測定の記録IDは `|L0001|K0001|C001` と
  **設備の段が空**（仕掛一覧から開くと `テスト設備A|L0001|K0001|C001`）。同じ
  ロットの記録が入口によって2本になり得る。製品の挙動なので、ここでは
  記録だけにとどめる（直すなら記録IDの組み立てを1箇所へ）。

## 罠

- **緑の網を疑う根拠は「順番を変えても緑か」**。落ちた網より、**その前に
  回った網が何を残すか**を先に見る（§9.121・§9.284 と同じ形。今回は
  `records.sqlite3` で、`reseed` も `resetcontent` も触らない置き場）。
- 「直したのに落ちる」を製品側の退行と読んで bisect に時間を使った。
  bisect の前に**単独で回して落ちるか**を見れば、置き土産だと10分で分かった。
