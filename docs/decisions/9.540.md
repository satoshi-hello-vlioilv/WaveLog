# §9.540 スペーサーの在庫の見通し——札に乗せると図が浮き、押すと表と入れ替わる（利用者の選択 E-11＋E-14）

索引: [決定記録](README.md)

## 利用者の言葉と選んだ経緯

マスタの視覚化の候補 E「在庫の棒」を4回で詰めた。

1. E-1〜E-5（下限を主役にした棒）→「そもそも下限という管理項目が不要」→ 下限を外した（§9.539）。
2. E-6〜E-10（下限なし）から **E-7 作れる端数の地図・E-8 並べた長さと分布・E-9 台車に載っている／棚にある** を選び、
   「E-7とE-8とE-9の組み合わせ複合案で見やすく、階層化UI調整も含めて再提案」。
3. E-11〜E-14（帯がタブを兼ねる／2ペイン／畳む／札＋ポップオーバー）→ **「E-11とE-14の複合でお願いします。」**
   →（作業中に）**「クリックでE-11、マウスオーバーでE-14タイプでお願いします。」**

案の画像はスクラッチの `mockE2.js`／`mockE3.js`（製品のコードではない）。

## 決めたこと

- **階層は3段**: 札（いつも見る3つの数）→ 乗せると浮く図（ちょっと確かめる・表は動かない）→ 押すと全幅（じっくり見る・札がタブを兼ねる）。
  いま開いている札には浮く図を出さない（同じ図を2か所に出さない）。浮く面は `WL.popMenu` の1つ（`.wl-menu.bk-peek`・読ませる面なので role=dialog）。
- **台車の載り方は `carriageLoad()` の1箇所**（`blade-core.js`）。稼働中＝直前の記録（外せない）、組み替える台車に載っている＝その台車の
  （直前を除く）いちばん新しい記録（そのまま使える）。刃組ガイダンスの `stockPlan()` も同じ関数を読むように切り出した（振る舞いは変えていない）。
  1部材の内訳の式も `stockSplit()` の1つ（4か所の書き写しを1つに）。
- **作れる端数は刃組ガイダンスと同じ積み**（`buildFiller`→`fillWith`、在庫を超える寸法は外して組み直す）で、50mm台の区間を
  在庫が尽きるまで何か所作れるか（40で頭打ち）。マスの濃さ＝数、赤＝作れないだけ（区切りの数を持たない——下限の言い換えにしない）。
- 見通しは**いまの表の値で毎回計算**する（約60ms）——保有を直すとその場で札と図が変わる（§CLAUDE 15）。
- 刃組の記録が無い設備では「保有をぜんぶ使えるとみなしている」と字で言う（出どころ）。

## 誤り（モックとの違い）

モック（E-9・E-11〜E-14）では「棚にある＝保有−A台車−B台車」と数えていた。刃組ガイダンスの決まりでは、組み替える台車に載っている部材は
**そのまま使える**（使えないのは稼働中の台車だけ）。モックの数え方だと .025 などの端数が「0か所」に見えていたが、正しくは「1か所」。
実装はガイダンスの決まり（`carriageLoad()`）にそろえ、表は「稼働中／組み替える台車／棚」の3色で分けた。

## 分からないこと

- 端数の地図の数は「同じ端数の区間を続けて作る」と数えたもの。実際の刃組では区間ごとに端数が違い、寸法を取り合うので、
  1回の刃組でその数だけ作れるとは限らない（上限の目安）。
- 区間の長さを50mm台に決めて数えている。整数の寸法が少ない設備では、長さによって答えが変わるかもしれない。
