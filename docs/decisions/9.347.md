# §9.347 固定待ちは「増えない」を機械で固め、1本ずつ条件待ちへ。骨組みは1本

`docs/REVIEW_2026-09.md` §6.3 3-15（第2回の最優先）。実測: `waitForTimeout`
**967箇所・792秒＝通し39分の34%**、ハーネスの写し（起動・rec・pageerror・
close）**159本**、`tests/lib/wait.js` を使う本は13本だけ。

## 決めたこと（4段）

1. **上限を先に固める**（`tests/test_waitlint.py`・純粋）。本ごとの件数・
   合計ms・ハーネスの写しを `tests/fixtures/wait_baseline.json` へ固定し、
   **下げる方向だけ**動かせる（`test_eslint` の baseline と同じ作法）。
   わざと待つ行は `固定待ち:` と理由を書けば数えない（`test_scsave` の
   4000ms＝遅らせた応答を待つ時間そのものが検証の材料）。
   注いだ固定待ちを数える自己検査つき。
2. **待ちの道具を3つ足す**（`wait.js`。§9.102 で `test_fit` を 70→35秒に
   したときの形そのもので、あちらに閉じていた）:
   `paint`（rAF×2＝レイアウトの確定）／`track→idle`（取得が0のまま静か。
   **page を作った直後に張る**）／`changed`（押す前に控えた字と違う字になるまで）。
3. **骨組みを1本に**（`tests/lib/harness.js`）: 起動・rec・pageerror・
   **素のダイアログの記録**（§9.342 の横断の約束はここで1つ判定を足す）・
   `mode` の戻し・落ちても閉じる `finally`・集計と終了コード。
4. **1本ずつ置き換える。** 置き換えた本は**置き換え前後の全PASS行（測った
   値ごと）を突き合わせ**、**本物の不具合を注いで落ちる**ことを見る。

## 固定待ちが守っていたものは、数種類しか無い

| 守っていたもの | 置き換え |
| --- | --- |
| その画面ぶんの取得（一覧・ダッシュボードのビュー・再読込・設備の変更） | `idle()`（重い集計は cap 15〜20秒） |
| 起動直後／予定の描画 | `W.booted`／`W.settleFlags` |
| 同期の描き直し（段・倍率・窓の幅・パネルの開閉・右クリック） | `paint()` |
| `evaluate` が `await` し終えている処理（`reloadRowStyles`・`columnLayout.save`） | `paint()` |
| 紙の組み直し（`renderPreview` が figure を丸ごと入れ替える） | 押す前の紙を控え、**別のノードになる**まで |
| サーバー書込 | `W.poll`（答えが出るまで取り直す） |
| debounce（検索 300ms・列幅の保存 300ms・式の検査 350ms） | `idle(600)`／`changed` |

## 踏んだ罠

- **守っていたものを取り違えると、速くなった網が嘘をつく。** 式を打った
  あとの700msを `paint` にしたら「まだ式が入っていません」のまま読んで
  2件落ちた。製品側は 350ms の debounce で盤を組み直しており、待つべきは
  「札の字が変わる」だった。**固定待ちを消す前に、製品側で何が起きるかを
  読むこと**（§9.102「待っている対象を名指しできれば、時間は要らない」）。
- **`--no-sandbox`・`newContext`・`addInitScript` の違いは骨組みで吸収する**
  （`init`・`viewport`）。網ごとの差を残すと写しが減らない。

## 追補: 測ってから直す（`WAVELOG_WAIT_TRACE`）

`test_screorder` を置き換えたら **14→26秒と遅くなった**。当てずっぽうを
やめて `wait.js` に計測の口を足した（`WAVELOG_WAIT_TRACE=1` で各待ちの
所要と、`idle` が上限に当たったとき**何が取得中のままか**を出す）。

```
[wait] idle が上限に当たった。取得中のまま: POST /api/schedule/plan/update (21429ms)
```

**`idle` は正しかった。** スケジュールモードの単独実行では
`/api/schedule/plan/update` が21秒以上返らず、元の網は3秒の固定待ちで
**見切って先へ進んでいた**だけ。判定はどちらでも同じ9/10（残る1件は
「作業中の行がある」前提の順序依存。§9.325 ② と同じ形で、通しでは前の網の
記録を拾って緑になる）。ここは**元と同じ上限で見切る**（`idle(400,3000)`）。

**分かっていないこと**: なぜ update が返らないか（編集セッションを持たない
端末の書込がロックの再試行で待たされている疑い）。3-15 の範囲ではないので
記録だけ残す。

## 残り

122本・871箇所。上限は固まっているので増えない。**箇所が少なく秒数の
大きい本から**（`wait_report.py` の上位）。1本ずつ、同一性と注入で。
