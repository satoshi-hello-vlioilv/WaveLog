# §9.198 読み込みを速くする／親ロットのバッジ／まとめの現場歴・太陽暦／行の見せ方／操作の整理／基準時刻の5分刻み／表示範囲の起点（利用者の指示）

利用者の指示は7件。①読み込みが遅い（自前サーバーやクエリ結合の影響か、
マージ済みの1ファイルをローカルに置く手はあるか） ②親ロットの「・子ロット3」が
場所を取りすぎるので、ロット番号のお尻に「親」バッジを付けてそこをボタンに
③まとめの日付が現場歴か太陽暦か分からない・どちらでも選べるように
④設備停止の行の配色やアイコン（絵文字以外も）を変えられるように
⑤メニューが増えたので分かりやすく ⑥再計算の基準時刻を5分刻みに
⑦表示範囲が「現在から過去」なのか書いていない。

**① 読み込みが遅い理由は4つあり、いちばん効いていたのは「クエリ結合が
写しではなく共有を直接読んでいた」こと。**

- **クエリ結合が`DBS`を直に見ていた**（`backend/query_join.py`）。`DBS`が
  持っているのは設定に書いてある元のパス＝**共有フォルダそのもの**で、
  読み取り専用のデータソースは`db_mirror`が手元へ写している（`cfg()`が
  その写しを指す）。直に見ていたため、一覧を開くたび・予定を読むたびに
  **共有越しで相手の表を走査**していた（しかも写しを作った理由である
  「書込中の共有を読むと壊れる」も一緒に戻ってきていた）。`source_cfg()`
  ——`cfg()`を通す1箇所——を置いて、左右とも写しから読む。
  **`DBS[...]['path']`を新しく書かないこと。**
- **相手の行を`SELECT *`で読んでいた**。実データは1表200列を超えるのに、
  使うのは突合キーと足す列だけ。読む前に`_added_names()`で「要る列」を
  決めてから`SELECT`する。
- **実績の索引を毎回作り直していた**（`schedule_calc.build_actual_index`）。
  材料の`merged_backup_rows()`は中身が変わらないかぎり**同じリスト**を
  返すので、その同一性で覚える。ここを作り直すと予定を1回読むたびに
  **測定データ全件のJSONを解き直す**ことになり、**記録が増えるほど遅く
  なる**という一番たちの悪い形で出る。
- **見積を予定1本ごとに引き直していた**。設備マスタの標準時間と換算係数の
  上書きは設備が同じなら同じ値なのに、1本あたり「表の一覧→列の一覧→
  設備マスタ全走査→上書きマスタ全走査」を回していた（200本で800回）。
  1回の展開で使い回す控え(`memo`)を渡す。検証用フィクスチャで
  **1回あたり13.8ms→3.1ms**。

**「自前サーバー（持ち主）」は読み込みには関係しない**——中継するのは
`plan/add|update|delete|reorder|batch`の**書き込み5本だけ**で、既定はoff
（§9.192）。ただし状態表示が10秒ごとに`myUrls`の名前解決をしていたので、
**offのときは名前解決へ行かない**ようにした（使っていない機能のために
DNSの調子で待たされていた）。

**「マージ済みの1ファイルを置く」案は採らない。** 写し（`db_mirror`）を
読むようになった時点で、結合は**手元のファイルを1回走査するだけ**になる。
これ以上まとめると、①抽出時に結合をやり直す仕組みが要る ②結合の定義を
変えたとき抽出まで戻らないと反映されない ③同じ値の出どころが2つになる、
の3つを抱え込む。**どこが遅いのかは画面で見えるようにした**ので、
実データで測ってから決められる。

**読み込みの内訳を画面に出す**。`GET /api/schedule/plan`が
`timings`（共有の取り込み／予定の読み出し／実績の突合／時刻の展開／件数）を
返し、画面は**遅かったときだけ**「読み込み◯秒」と出す（速いときに毎回
ミリ秒を並べても読まれない）。内訳と**いちばん重い工程に応じた打つ手**は
読込時点のチップのツールチップに入れてある。結合の往復は予定を描いた
あとに走るので**合計には足さない**（体感には乗らない）が、内訳には出す。

**② 親ロットは「番号 → 親バッジ」の順**。以前は「▸子ロット3」を番号の
**手前**に置いていたため、①番号より先に修飾語を読まされ ②そのぶん番号が
右へずれ ③6文字ぶんの幅を毎行占めていた。読む順は「どのロットか → それは
親か」なので、番号を先に出して**お尻に「親」のバッジ**を付ける。
件数はバッジの中に小さく残す（消すと何件畳んであるか開くまで分からない）。
開閉は色だけで伝えず、`▾`/`▸`と`aria-expanded`を必ず添える。

**③ まとめの日付は現場歴・太陽暦の両方**。名前に**どちらでまとめているかを
書く**（「日付ごと（現場歴）」「日付ごと（太陽暦）」）——同じ「8/18」でも
入る行が違うので、推測させてはいけない。まとまりの見出しにも小さく
`現場歴`/`太陽暦`を出す（設定は画面の上にあるが、行を追っている目は下に
ある）。**既定は現場歴のまま**。**紙も画面のまとめ方に従う**
（`WL.scheduleView.groupBasis()`）——画面が暦でまとめているのに紙が現場歴で
切ると、日ごとに配る紙の件数が画面と合わない（§9.115と同じ理由）。

**④ 行の見せ方（配色・アイコン）は`行表示マスタ`の1行**。
**全設備共通で持つ**——区分の色は設備をまたいで意味を持つ言語で、同じ
「設備停止」が設備ごとに別の色だと色が何も語らなくなる（設備停止分類マスタが
全設備共通なのと同じ理由）。区分キーは1つの名前空間
（`cat:<区分>`／`stopcat:<分類名>`）で、**効く順は「分類の指定 → 区分の指定
→ 既定」**。判定は`rowStyleOf()`の1箇所。
**色は8色から選ばせ、16進は選ばせない**（自由に選べると、淡すぎて読めない
色や画面ごとに違う赤が必ず増える）。8色には意味を割り当ててある
（灰=目立たせない／青緑=基準／青=情報・待ち／緑=完了・良／橙=注意／
赤=停止・異常／紫=臨時）。**色だけで伝えない**ので区分名の文字は必ず出し、
行の地は`color-mix`で更に淡くする（面が濃いと文字が読めない）。
**アイコンは絵文字だけではない**——外部のアイコンフォントは取りに行けない
（社内で閉じて動くアプリ）ので、**同じ見え方の線画アイコンを同梱**する
（`SC_ICON_SVG`、24×24・線幅2・`currentColor`）。値は`svg:<名前>`で、
それ以外はそのまま文字として出す。**「なし」は`[アイコン表示]=0`**で、
アイコンの選択と出す/出さないを1つの操作にまとめてある。
**既定へ戻す＝行を消す**（空文字を保存すると「空という設定」になり、
既定を変えても追随しない。§9.99と同じ約束）。
編集はスケジュール画面の「🎨 行の見せ方」から**その場で当ててその場で保存**
（マスタ管理にタブは作らない——`cat:stop`のようなキーを手で打たせる画面は、
実物を見ながら選ぶこの画面より必ず分かりにくい）。
**設備停止の一覧はモードによらず読む**——分類ごとの色を当てるのに
「この停止はどの分類か」が要る。モードで読み分けると、同じ予定が端末に
よって違う色になる。

**⑤ 操作は「見る → 足す → 出す」の4つの塊にする**。11個のボタンが1列に
並んでいたため、目的のものを探すのに毎回全部を読む必要があった。
`表示`（まとめ・さかのぼり・表示列・行の色・配置）／`追加`（ポップアップ・
設備停止・コメント）／状態（読込時点・共有・現場段取り）／`印刷`・`再計算`。
**どれも畳んで隠さない**——奥へ入れると押すまでに1手増える。塊の中身が
1つも出ていないときは**見出しごと消す**（「表示」とだけ書かれた空の枠が
残ると壊れて見える）。

**⑥ 予定の起点は5分刻みへ切り上げる**（`ANCHOR_ROUND_MIN`）。現在時刻を
そのまま起点にすると「10:23開始・11:47終了」が延々と続く。**切り上げ**
なのは、切り下げると既に過ぎた時刻から始まる予定になるため。
**着手中の作業があるときは丸めない**——そちらは実績の開始時刻＝記録された
事実で、見栄えのために動かしてよい値ではない。丸めた先が稼働帯から出る
ときも丸めない（勤務終わり際に起点だけ翌日へ飛ぶのを避ける）。
**丸めたことは書く**（「再計算」のツールチップに、丸める前の現在時刻と
刻みを出す）——黙って5分ずれた時刻を出すと「時計と合っていない」と読まれる。

**⑦ 表示範囲は「いまから過去◯時間」と言い切り、起点の日時を横に出す**。
時間数だけでは、いま何時なのかを頭の中で引き算しないと分からない。
名前も「表示範囲」から**「さかのぼり」**へ変えた（未来の予定は範囲に関わらず
全部出るので、「表示範囲」だと先の予定まで消えると読まれる。そのことも
ツールチップに書く）。起点の日時は**10秒ごとの巡回で書き直す**
——止まった時刻を出しておくと、そのうち嘘になる。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **読み取り専用のデータソースは`cfg()`で開き、開く前に存在を確かめない**
  （§9.317、利用者の報告「測定画面を開けません: [WinError 5] アクセスが拒否
  されました。: `\\srv\Read\…\SIKADEF.sqlite3`」「書き込み権限がないところに
  ある品質ファイルを読んでいるので開き方に問題があるのでしょうか？…競合を避ける
  ため、そもそもローカル一次領域にコピーしてから読んでいるはずです」）: **欠陥は
  2つ重なっていた。**
  ① **`DBS`から直に引いていた**（`/api/measurement/context`・
  `/api/quality/analysis`）——`DBS`が持つのは設定に書いてある元のパス＝**共有
  そのもの**で、写しへ差し替えるのは`cfg()`（§9.198。同じことを3度目に踏んだ）。
  一覧（`/api/table`）は`cfg()`を通るので、**同じ端末でも一覧は出るのに測定画面
  だけ開けない**という分かりにくい形で出る。
  ② **開く前に`Path.exists()`を置いていた**——「無い」と読み替えるのは
  ENOENT/ENOTDIR/EBADF/ELOOP と WinError 21/123/1921 だけで、**WinError 5
  （アクセスが拒否されました）はそのまま送出する**。読み取り専用の共有では
  ファイルは読めるのに属性の問い合わせだけが5で断られることがあり、
  **確認のつもりの1行が唯一の失敗原因**になる（§9.108と同じ形）。
  **まず開き、失敗したときだけ`connect()`が理由を切り分ける。**
  **参照データが読めなくても測定は始められること**（利用者の指示「いずれにしても
  編集モードでの測定作業に影響がないようにしてほしい」）——以前は品質が読めない
  だけで例外が`loadMeasurementContext()`まで伝わり、`openMeasurementCore()`の
  続き＝**記録の初回保存（`reliablePut`）と共有への登録**が丸ごと走らなかった。
  サーバーは0件で返して理由を`diagnostics.quality_error`へ残し、画面は
  **投げずに`null`を返す**。
  **黙って続けないこと**（§3・§CLAUDE 6）——品質情報の札は「異常なし」ではなく
  **「読めません」**にし、理由と「測定は続けられます」を文字で出す（読めていない
  だけなのに「異常なし」と出すのは画面が嘘をつくこと）。**エラー文は
  `#qualityInfo`へ書かない**——`collect()`がその中身をそのまま記録へ入れるので、
  品質情報として保存され**帳票にも刷られる**。控えは`S.measureContextError`
  （記録ではなく画面の状態）。
  見張りは`tests/test_srcread.py`——**`DBS`を`'MASTER'`以外で引いている箇所を
  機械で数える**（許可は理由付きの一覧。目で数えない・§9.96）。
  **網は写しと実物の中身をわざと食い違わせること**（§9.268）——「読む先を答える
  関数」だけを見る網は、呼ぶ側がその答えを使っていなくても通る。画面側は
  `tests/test_ctxfail.js`で、**「測定画面が開く」で終わらせない**（覆いは取得の
  前に出るので、投げる実装でも開いて見える）——**記録が実際に作られるか**まで見る。
- **読み取り専用のデータソースは`cfg()`で開く。`DBS[...]['path']`を直に使わない**
  （§9.198、`backend/query_join.py`）: `DBS`が持つのは設定に書いてある元のパス＝
  **共有フォルダそのもの**で、`db_mirror`が写した手元のファイルを指すのは`cfg()`。
  クエリ結合が`DBS`を直に見ていたため、**一覧を開くたび・予定を読むたびに共有越しで
  相手の表を走査**していた（写しを作った理由の「書込中の共有を読むと壊れる」も
  一緒に戻ってきていた）。窓口は`query_join.source_cfg()`の1箇所。相手の行は
  **`SELECT *`にしないこと**——1表200列を超えるのに使うのはキーと足す列だけなので、
  読む前に`_added_names()`で要る列を決める。
- **同じ材料なら作り直さない**（§9.198）: `build_actual_index()`は
  `merged_backup_rows()`が**中身が変わらないかぎり同じリストを返す**ことを使って
  覚える（`rows is 前回`で判定）。ここを毎回作り直すと予定を1回読むたびに
  **測定データ全件のJSONを解き直す**ことになり、**記録が増えるほど遅くなる**。
  見積(`resolve_estimate`/`estimate_work`)も、設備が同じあいだ変わらない値
  （設備の標準時間・換算係数の上書き・設備停止の標準所要分）を1回の展開で
  使い回す控え(`memo`)へ入れる——以前は予定1本ごとに引き直しており、200本の
  設備で800回の問い合わせになっていた。**戻り値を書き換えないこと**（写しを
  配っているので、書き換えると次の呼び出しへ持ち越される）。
- **遅いときは「どこが遅いか」を画面に出す**（§9.198）: `GET /api/schedule/plan`が
  `timings`（共有の取り込み／予定の読み出し／実績の突合／時刻の展開／件数）を返し、
  画面は**遅かったときだけ**読込時点のチップへ「読み込み◯秒」と出す（速いときに
  毎回ミリ秒を並べても読まれない）。内訳と**いちばん重い工程に応じた打つ手**は
  ツールチップに入れる。結合の往復は描画のあとに走るので**合計には足さない**。
- **行の見せ方（配色・アイコン）は`行表示マスタ`**（§9.198、対象は全設備共通）:
  区分キーは`cat:<区分>`／`stopcat:<分類名>`の1つの名前空間で、**効く順は
  「分類の指定 → 区分の指定 → 既定」**（判定は`rowStyleOf()`の1箇所）。
  **設備ごとに分けないこと**——区分の色は設備をまたいで意味を持つ言語で、同じ
  「設備停止」が設備ごとに別の色だと色が何も語らなくなる（設備停止分類マスタが
  全設備共通なのと同じ理由）。**色は8色から選ばせ、16進を選ばせない**（自由に
  選べると淡すぎて読めない色や画面ごとに違う赤が増える）。**色だけで伝えない**
  ので区分名の文字は必ず出し、行の地は`color-mix`で更に淡くする。
  **アイコンは同梱の線画(`SC_ICON_SVG`、値は`svg:<名前>`)も選べる**——外部の
  アイコンフォントは取りに行けない（社内で閉じて動く）。**既定へ戻す＝行を消す**
  （空文字を保存すると「空という設定」になり、既定を変えても追随しない）。
  設備停止の一覧は**モードによらず読む**（分類ごとの色を当てるのに要る。モードで
  読み分けると同じ予定が端末によって違う色になる）。固定は`tests/test_scrowstyle.js`。
- **予定の起点は5分刻みへ切り上げる**（§9.198、`ANCHOR_ROUND_MIN`）:
  **切り上げ**なのは、切り下げると既に過ぎた時刻から始まる予定になるため。
  **着手中の作業があるときは丸めない**（実績の開始時刻＝記録された事実で、
  見栄えのために動かしてよい値ではない）。丸めた先が稼働帯から出るときも
  丸めない。**丸めたことは画面に書く**（黙って5分ずれた時刻を出すと
  「時計と合っていない」と読まれる）。
- **「表示範囲」は「さかのぼり」と言い、起点の日時を出す**（§9.198）:
  時間数だけでは、いま何時なのかを頭の中で引き算しないと分からない。
  **未来の予定は範囲に関わらず全部出る**ことも書く。起点は**10秒ごとの巡回で
  書き直す**（止まった時刻を出しておくと、そのうち嘘になる）。
  まとめ方の日付も**現場歴か太陽暦かを名前に書く**——同じ「8/18」でも入る行が
  違う。**紙も画面のまとめ方に従う**（`WL.scheduleView.groupBasis()`）。
