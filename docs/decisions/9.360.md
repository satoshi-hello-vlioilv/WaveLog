# §9.360 通しの赤を「対症療法」で潰すのをやめる——状態は丸ごと戻し、汚した本を名指しする

利用者の指示:「**毎回フルスイートで何件か赤が出て、修正したつもりになって、
実際は直っていないか解釈の違いみたいなことを繰り返しており、フルスイートの
時間もコストも無駄になってしまうので、今回テストの実施の仕方、単独で検出する
方法の検討など、さらなる最適化を徹底的に実施し、今回類似の問題は完全に
潰してください。**」

## 何が起きていたか

通しのたびに**顔ぶれの違う数本**が赤になり、単独では緑。直すたびに別の本が
赤くなる。§9.121・§9.284・§9.356 はどれもこの症状への手当てだったが、
**どれも対症療法**だった——「戻す行」を1つずつ足していただけで、
**戻し漏れが増える速さに追いつけない**。

| 層 | それまで | 何が起きるか |
| --- | --- | --- |
| 共有状態 | `reseed`(=`fix_master`)が**知っている行しか戻さない** | 片付け損ねた1本が以降ぜんぶを巻き添えにする |
| 犯人特定 | できない。**落ちた本**しか分からない | 汚した本ではなく**被害者**を直す |
| 不安定の見分け | 単独で1回だけ回す | 「単独では緑」＝順番依存と**決めつけて**しまう |
| 待ちの失敗 | `waitFor…().catch(()=>{})` で**黙って進む** | 「古い値で比べて不一致」という**別の顔**で落ちる |

## 決めたこと（4つ）

### ① マスタDBは1本ごとに**丸ごと**戻す
開始時に `reseed`＋`resetcontent` を通した直後の `db/master.sqlite3`（360KB）を
1枚控え、**テストのたびにファイルごと差し替える**。知っている行かどうかに
関係なく白紙へ帰るので、**戻し漏れが原理的に無くなる**。
`journal_mode=delete`（WAL無し）なので差し替えで安全。テストの合間は通信が
無いので、開いた接続の下で入れ替わることもない。

### ② 共有状態を残した本を**その場で名指しする**
テストの前後で「表ごとの行数」の指紋を取り、違えば
`-- 共有状態を残したまま終わった本 --` に**本の名前と差分**を出す。
①が実害を消すので落ちはしないが、**後片付けを忘れた本はここでしか分からない**。

### ③ 落ちた本は単独で**2回**回す
1回で緑だと「順番のせい」と読んでしまうが、**単独でも落ちたり落ちなかったり
する本**がある（実測: `test_opunit` は単独で3回に1回落ちていた）。3つに分ける:
**単独でも必ず落ちる（本物）／単独でも落ちたり落ちなかったり（不安定）／
単独では緑（順番・状態への依存）**。

### ④ 待ちは timeout しても**黙らない**
共有の `until()` が `.catch(()=>{})` で握りつぶしていた——**全員が使う道具が
黙っていた**のが読みにくさの元。`WAIT-TIMEOUT: <何を待っていたか> が Nms で
成立しませんでした` を出し、ランナーが落ちた本の要約に添える。
生の `waitFor…().catch(()=>{})` は**禁止しない**（「出ないことを確かめる待ち」は
正しい）が、`test_waitlint` の控えで**89箇所に固定**し、増えたら落とす。

## 踏んだ罠（どれも「入れたのに働かない」形）

- **`trap ... EXIT` をもう1つ書くと前のものを上書きする。** 一時ファイルの
  後始末を別の `trap` で書いたら、**パス設定を戻す・ロックを外すが動かなく
  なった**。同じ `trap` へ畳み込むこと。
- **相対パスで書いた指紋は1件も読めない。** ランナーは `tests/` から動くので
  `db/master.sqlite3` は存在せず、**比較が常に一致＝検出0件**になる。
  置き場は `__file__` から決める。
- **「文字列があるか」を見る網は網ではない。** `restore_master` をコメントに
  しただけの注入を素通りした。**行そのもの**（`^\s*restore_master\s*$`）を見る。
- **スナップショットは「開始時のDB」でしかない。** 手で汚したまま通しを
  始めると、その汚れごと控えてしまう。②があるので以後は溜まらない。

## 確かめ方（注入）

仕組みが**働いていること**は注入で見た。①②は次の3行の本を `tests/` に置き、
ランナーの一覧へ一時的に足して回す（**置きっぱなしにしないこと**——回すたびに
汚すのが仕事なので、確かめたら消す）:

```python
import pathlib, sqlite3
con = sqlite3.connect(pathlib.Path(__file__).resolve().parent.parent/'db'/'master.sqlite3')
con.execute('CREATE TABLE IF NOT EXISTS 注入用置き土産(id INTEGER PRIMARY KEY)')
con.execute('INSERT INTO 注入用置き土産 DEFAULT VALUES'); con.commit(); print('PASS: 置き土産')
```

`-- 共有状態を残したまま終わった本 --` にその名前が出ること、次の本の前に
その表が消えていることを確かめた。③は `test_opunit` を3回回して1回落ちることで、
④は `restore_master` をコメント化する注入と、`waitFor…().catch(()=>{})` を1つ
足す注入で確かめた（どちらも網が落ちた）。

## 見つかった製品側の挙動（未修正・要判断）

`test_opunit` が単独で3回に1回落ちていた原因を辿ると、**操業データ項目の設定窓で
単位の置き場を選んだ約1秒後に、選択が保存値へ戻る**ことが分かった。
`master-opdata.js` の `loadOpItemMaint()` が末尾で `renderOpModal()` を呼ぶため、
**マスタの再読み込みが遅れて届くと編集中の選択を捨てる**（§9.331 の
「いつの分の応答か」が、この窓には効いていない）。
利用者から見れば「設定を変えたのに、少し後に黙って元へ戻る」。
**画面の振る舞いなので直していない。** 網の側は「戻ったら押し直し、戻らなく
なったところで測る」で決定的にした（3回とも緑）。
