# §9.267 置き場を1枚で見せて、その場で直す（利用者の指示）

> 「特にlocal.jsonの扱いがわからないので、優先順位も含めて今回のデータの
> 取り扱いに絡むパス設定を一元管理したい。マスタの置き場、スケジュールの
> 置き場、測定データの置き場、バックアップの置き場などを含めた全ての設定を
> 共通設定に視覚的に表現した上でそのままその表示とリンクして設定を簡単に
> わかりやすく出来るように参照ボタンやドラッグ&ドロップなど、使い勝手の
> 良い機能も使って設定画面から再構成、重複する部分の設定マスタの統合を行い
> 初期設定も含めて使いやすく美しいUIで実装をお願いします。」
> 「設定さえ書いてあればフォルダやファイルが存在しない場合には強制的に
> フォルダやファイルを作成して、ユーザーの操作を妨げないようにしたいです。
> 但し作成する前にユーザーに確認する方式にして欲しいです。」

#### ① 何が困りごとだったか

置き場の設定は**2つの保存先**に分かれている。

| 保存先 | 何が入るか | 直す場所（直す前） |
|---|---|---|
| `config/local.json` | `db_dir` / `master_db_path` / `records_db_path` / `master_share_mode` | **画面に無い**（テキストエディタ） |
| パス設定マスタ | 作業予定・測定データ（共有）・閲覧用の複製・RNE資材・参照データ | 共通設定／測定データの保存／データ接続 の3画面 |

利用者から見ると**同じ「置き場の設定」なのに直す場所が4通り**あり、しかも
`local.json`の側は画面に一切出ていなかった（「local.jsonの扱いがわからない」）。
さらに`local.json`には**優先順位**があるのに、それを言う場所も無かった。

#### ② 直し方

**判定は`backend/storage_layout.py`の1箇所**（§9.163）。`layout()`が
「いまどこか・これからどこか・どの設定から決まったか・優先順位・種類・
在るか」を1つの答えで返し、画面はそれを並べて直す口を添えるだけ。
§9.260でここに置いた`_share_layout()`は**同じ問いの2つ目の答え**になるので
廃止した（`config/local.json`の側が入っていなかった）。

**`config/local.json`は画面から直せる。** 鶏と卵なのは**読む側**の話
（起動時にマスタDBの場所を知るために外のファイルが要る）であって、
書く側を塞ぐ理由は無い。守りは3つ——①受け付ける鍵を4つに限る
②絶対パスだけ ③書く前に`local.json.bak`へ控える。

**保存のボタンは1つ**（利用者の指示「一元管理したい」）だが、保存の口は
2つある。**片方だけ失敗したことは必ず言う**（§4）——まとめて「保存しました」
と返すと、効いていない側に気づけない。

#### ③ 「これから効く値」を出す

置き場はどれも起動時に1回だけ読むので、保存しただけの値はまだ効いていない。
**利用者が直すのも作るのも「保存した値」のほう**——再起動しないと置き場を
作れないのでは、それこそ操作を妨げる。だから1行は3つを持つ:

    path    … これから効く値（保存値から解決したもの）＝直す・作る対象
    active  … いま効いている値
    pending … その2つが食い違っている＝再起動待ち

**綴りの解釈は本体と同じ1箇所を通す**（`resolve_schedule_share`）——作業予定は
フォルダを書いてもよいので、ここで自前に組み立てると画面と実物が食い違う。

**一言も「これから効く値」で書くこと。** 保存した直後は in-process の値が
まだ空なので、そちらで書くと「まだ設定されていません」と出て、**いま入力した
値を否定する**（実際にそう出た）。

#### ④ 「無ければ作る。ただし作る前に確認する」

`POST /api/storage-layout/prepare` は**既定が下見**（§9.193）。返すのは
「これから作るフォルダの連鎖」と「作るファイル」で、`apply:true` を送るまで
1つも作らない。画面は作るものを**1つずつ並べて**確認する（§4・§6。
「作ります」だけでは、どこに何ができるのか確かめようがない）。

**作ったあと、実際に書けるかまで確かめる**——作れても書けない共有があり、
そこで止まると「作ったのに動かない」になる。

**空のSQLiteはヘッダまで書かせること。** SQLiteは中身を書くまでファイルへ
1バイトも書かないので、`PRAGMA user_version`（読むだけ）では**0バイトの
ファイル**が残る——それは`touch()`と同じで、コピーに失敗した残骸と見分けが
付かない。書き込みを伴う`PRAGMA user_version=0`でヘッダだけ書かせる。
**この誤りは網が捕まえた**（「開けたこと」で終わらせる網は素通りしていた——
`sqlite3.connect()`は遅延なので0バイトでも例外を出さない）。

#### ⑤ 入口は1つ（§9.207）

保存は `#masterMaintForm` の `[data-pc-field]` を**全部**集めるので、
同じ鍵の欄が2つあると**DOM順で後の側が勝つ**＝どちらが効くのか分からなく
なる。実際に `rne_assets_dir` が置き場の行とRNE抽出の節の両方に出ていた
（網が捕まえた）。欄を持たない置き場は**直す場所へ連れて行く**。

そのぶん、**よそに欄を残さない**:

- 測定データの保存 → `records_share_dir` と `records_backup_export_path` の
  欄を外し、「いまどこか」を書いて共通設定へ連れて行く。§9.202では複製先を
  あちらに置くと決めていたが、**置き場が画面に散っていること自体が困りごと**
  だったので撤回した（利用者の指示に「バックアップの置き場」が明記されている）。
- 共通設定の`schedule_share_path`の素の欄 → 置き場の行に統合。

#### ⑥ ローカルのパスは推奨されないのか（利用者の疑問）

> 「ローカルのパスは基本的にユーザー個別のアプリデータ置き場を設定していた
> のでそのままそこを利用したいのですが推奨されないのでしょうか。」

**推奨される。** `paths.py` が警告しているのは `db_dir` が**共有・クラウド
同期フォルダの上**にある場合だけで、`%LOCALAPPDATA%` のような端末ごとの
場所はむしろ理想的——`work_dir()` は `db_dir` をそのまま使い、逃がす処理が
一切走らない（`work_dir_reason()` が空になる）。画面にもそう出る。

#### ⑦ 網

`tests/test_storage.py`（サーバー側）と `tests/test_storageui.js`（画面）。
§9.260の`tests/test_pcshare.js`は**同じ画面を同じ目的で見ている**ので
統合して廃止した（§9.249 ④）。**欠陥注入で確かめた7件**——保存値のかわりに
効いている値を返す／下見で作ってしまう／`local.json`を丸ごと置換する／
0バイトのファイルで済ませる／測定データの保存に欄を戻す／欄に効いている値を
入れる／確認せずに作る、のどれでも落ちる。
