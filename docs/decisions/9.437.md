## ① 「初回だけ断面にならない」——§9.433 ④ で「分からない」と書いた件の決着

### 再現できた

§9.433 では**再現できず**、「分からないことは分からないと書く」として残した。
今回は利用者の言葉から**「初回」の条件を2つに割って**組み立てたら一発で出た:

1. three.js を**まだ読んでいない**（刃組ガイダンスを開いた直後）
2. 立体図を**一度も押していない**（模型が1度も組まれていない）

§9.433 のときに試していた手順は**立体図を見てから断面図へ移る**もので、
②が成り立っていなかった。網（`test_bladeui.js`）も同じ順で通しているので、
**この道は1度も通っていなかった**。

### 値はすべて正しいのに、絵だけが立体図だった

押した直後に `view()` を読むと、**どれも正しい**:

```
{builds:1, builtCut:true, cut:true, ortho:true, clips:1, matMag:11.6, ends:4, stale:false}
```

場面の中身（215行の木）も、描画器の状態（`clippingPlanes` 1枚・材質14・
プログラム1本・描画12回・三角19,352）も、**1回目と2回目で1つも違わなかった**。
違うのは**絵だけ**——1回目は軸が「縦にぼかしの入った丸い殻」、2回目は
「平らな一様の灰色＋青い印＋板」。

### 正体は「切り口の面」の置き場所

断面図は**切っただけでは中が空洞に見える**ので、切り口に薄い板（`capRects()`）を
置いている（§9.412）。その置き場所は:

```js
const z = D3.keep * (CAP_T / 2 + 0.05);
```

`D3.keep`（どちら側を残すか）を書いているのは **`applyCut()`**。
そして `applyCut()` が呼ばれるのは **`build()` の終わりのほう**——
`machine()`・`material()`（＝`capRects()` を呼ぶ側）は**その前**に走る。

つまり**初回の組み立てだけ、1つ前の `D3.keep` で切り口を置いていた**。
初期値は `-1`、いまの向き（DS左＝`flip:true`）の答えは `+1` なので、
切り口の面は `z = −0.65`、すなわち**切り落とされる側**へ置かれる。
クリッピングは効いているのに切り口の板が無いので、**中身の無い殻＝
立体図と同じ絵**になる。2回目は控えが正しくなっているので直る——
利用者の「もう一度押すと解消しますが初回だけです」と完全に一致する。

### 同じ罠がもう1つ在った（段取り向きの裏返し）

`spinTo()` は断面図のとき `applyCut(); render();` だけで**組み直さない**。
切り口の面は**組む時に置き場所が決まる**ので、裏返すとクリップ面だけが
反対側へ行き、切り口は元の側に残る——**裏返した瞬間に同じ絵**になる。

### 直し方: 控えではなく、引く

「どちら側を残すか」は**向きから決まる**ので、控えずに要るたびに引く:

```js
const keepSide = () => (D3.flip ? 1 : -1);
```

`capRects()` も `applyCut()` も同じ1箇所から引くので、**呼ぶ順に依らない**。
あわせて、**何の向きで組んだか**も控える（§9.428・§9.433 と同じ作法）:

```js
D3.builtKeep = keepSide();                      // build() の終わり
if (D3.built && (D3.builtCut !== D3.cut || D3.builtRes !== ctx.res
                 || (D3.cut && D3.builtKeep !== keepSide()))) build();   // render() の見張り
```

これで裏返しも `render()` が組み直す。網が見るのは `view().capSide`
（組んである切り口が今の向きの物か）の1つの真偽。

| 測ったもの | 前 | 後 |
| --- | --- | --- |
| 初めて断面図を押したとき `capSide` | **false**（切り口が反対側） | **true** |
| そのときの絵 | 丸い殻（立体図と同じ） | 平らな切り口 |
| 2回目 | true | true |

## ② OS・DS の札が上の帯へ食い込んでいた

**実測 25×5px**（`bs-t3-ds` × `bs-len3`）。原因は2つ重なっていた。

**（1）帯の高さを決め打ちしていた。** `place()` は `TOP = 42` / `BOT = 44` の
固定値で札の置ける範囲を決めていた。ところが断面図の左上の帯は**2行**
（画面左DS…／有効長…）で**実測56px**——決め打ちより14px高い。
固定の数に足して追いかけると、行が増えるたびにまた重なる（§9.250）。
**帯の場所は測って決める**（`hudBox()`）ようにし、**横も見る**
（帯の下でも、帯より右に居る札は下げなくてよい）。

**（2）帯より先に札を置いていた。** `tags()` は `place(put,w,h); sides(at);`
の順で、**帯の中身を書く `sides()` のほうが後**だった。図を切り替えた
最初の1枚では帯がまだ空（`offsetWidth` 0）なので、`place()` は「帯は無い」と
読んで札を上へ置く——そのあと帯が出て重なる。帯の中身は札の位置に依らないので、
**先に書いてから置く**。

あわせて、**OS と DS は対**（両端の呼び名）なので、片方だけ帯を避けて下がると
段違いに見える。`place()` が同じ高さへそろえる（`q.pair`）。

| 測ったもの | 前 | 後 |
| --- | --- | --- |
| 札どうしの重なり（断面図・実測） | **25×5px** | **0** |
| OS と DS の高さの差 | 11px | **0** |

## ③ 拡大図の引き出し線

### 「つながっていないように見える」の正体は、1行の札の 12px

線の始点は「段の縁」（`near`）で、段の高さ `rowH` は**2行ぶん**
（値＋名前＝`VFS + NFS + 5`）で決め打ちだった。ところが
**部材の札は値だけの1行**（名前は左の余白が言っている・§9.430）。
軸心より下の段では `near = top + rowH` なので、**字の下端と線の始点のあいだに
`NFS + 2 ≒ 12px` の空白**が開く——線が宙から始まって見える。

いま何行書くかは `q.plain` が決めるので、**その高さから縁を出す**。

### 「対象の中心位置から伸ばす」（§9.418 を撤回）

§9.418 では「引き出し線は**対象の縁から**引く（宙に浮かせない）」と決めていたが、
拡大図では**隣り合う細い部材のどちらの縁か**が読めない。利用者の指示どおり
**中心まで引き、終端に点を打つ**——線の先が物の**中**で終わるので、どの部材の
ことかを絵だけで言い切れる。§9.418 のこの行は拡大図については撤回する
（断面図の引き出しは縁のまま）。

### 「各段によって少し色を変える」

軸の地（`--muted`・輝度.19）の上に3段ぶん引くので、**段ごとに色みだけを変える**
（明度は3段とも高いまま・地との比 8:1 前後）。**線と字は同じ色**にして、
「同じ色＝同じ組」を辿る手がかりにする。色はトークンで持つ（§9.350）:

| 段 | トークン | 値 |
| --- | --- | --- |
| 1段目 | `--bs-fig-lead0` ＝ `--card-bg` | `#f8fbfc` |
| 2段目 | `--bs-fig-lead1` ＝ `--look-amber-pale` | `#fdf3e2` |
| 3段目 | `--bs-fig-lead2` ＝ `--rs-blue-bg` | `#e9f1fa` |

### 「線も細いので」（太くしすぎない）

`stroke-width` 1 → **1.3**、`opacity` .85 → **.95**。
**これ以上太くしない**——1mm 台の部材（隙間は 0.01mm 台）の幅より線のほうが
太くなると、線が部材を隠す（利用者の「太いとそれは別の問題になる」）。

| 測ったもの | 前 | 後 |
| --- | --- | --- |
| 線の始点と字の縁の距離（1行の札） | 12px（コードから） | **0〜2.7px**（実測） |
| 線の太さ | 1.0 | 1.3 |
| 段の色 | 1色（白） | 3色 |
| 終端 | 部材の縁 | 部材の中心＋点 |

## ④ 拡大図の窓は掴んで動かせる

押した区間の**真下**へ出すのは変えない（どこを開いたのかを目で辿れる・§9.413）。
そのうえで、隠れてしまった物を見たいときに**利用者が自分でどかせる**ようにする。

- 掴むのは**見出しの帯だけ**。図そのものを掴めると、図の中の的を押す道をふさぐ。
- はみ出す側は**器の縁で止める**（画面の外へ持って行かれると戻せない）。
- `setPointerCapture` は掴めないと投げる（§9.413）ので、**理由を1行残して続ける**
  ——掴めなくても動かすこと自体はできる。
- 押せるのに何も起きない的を作らないため、**カーソルの形（`move`）と説明の字
  （`title`）の両方**で言う（§CLAUDE 4）。
- 別の区間を押したときは**また真下へ出す**（`hit` が渡るのはそのときだけ）。
  同じ区間を描き直すときは動かさない（窓が飛ぶと探し直しになる）。

実測: 見出しを (−120, −60) 動かすと、窓もちょうど (−120, −60) 動く。

## ⑤ 網を書くときに踏んだ2つ（どちらも「素通りする網」だった）

**（1）控えを見ても、置き場所は分からない。** 最初は `capSide` を
`D3.builtKeep === keepSide()`（＝**どちら向きで組んだと言っているか**）で
出していた。欠陥を入れ戻して（`keepSide()` → `D3.keep`）確かめたら
**282件そのままPASS**——控えは正しいまま、置き場所だけが違うのだから当然だった。
**実際に置いた z を控える**（`D3.capZ`）ようにして測り直したら、
`capZ:-0.65 / keep:1` で落ちた。
**網は「そう言っているか」ではなく「どこへ置いたか」を見る。**

**（2）当たらない寸法で重なりを測っても、何も確かめていない。**
札が帯に当たるかどうかは**器の高さ**で決まる（札は立体の点を写した位置に出る）。
網の器は 1104×849 で、札の上端140・帯の下端66——**もともと180px も離れている**。
そこで重なり0を見ても意味が無く、欠陥（`place()`→`sides()` の順に戻す）を
入れても素通りした。**器を 1104×597 まで縮めて前提を作り**、
さらに「札が帯のすぐ下で止まっている」（＝止める側が実際に効いた）ことまで
見るようにして、ようやく落ちた（575px²）。
**「物が無い」を確かめたことにしない**（§9.369）。

網は `tests/test_bladeui.js`（283件。§9.437 ぶんは11件）。
