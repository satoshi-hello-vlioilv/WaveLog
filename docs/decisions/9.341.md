# §9.341 時間の書き方は1箇所が答える（既定は「分」・切り替えは「表示」の1枚）

利用者の指摘（`docs/REVIEW_2026-09.md` 4-4 ⑰）: 稼働状況の「見込」「最大の
遅れ」「経過」が `150分` と出ている。利用者の判断: **「分」で統一。表示の
切り替え機能を付けることで回避。**

## 何が起きていたか

REVIEW には「書いた側の意図は `2時間30分` で、`fmtMin` が死んでいた」と
書いたが、**これは不正確だった**。死んでいたのではなく、**同じ「所要時間」を
書く関数が7つ・表記が5種類あった**（実測）。

| 書き方 | 表記 | 置き場 |
| --- | --- | --- |
| `fmtMin` | `150分` | `report-dashboard.js` |
| `fmtMin`（別物） | `2時間30分` | `measure-worklog.js` |
| `fmtMinutes` | `2時間30分` | `schedule-view.js` |
| `fmtCompact` | `2:30` | `schedule-view.js` |
| `fmtHour` | `2.5時間` | `report-dashboard.js` |
| `formatDuration` | `2時間 30分`（**空白入り**） | `base.js` |
| `fmtLfMinutes` | `2時間30分` | `master-data.js` |
| `scheduleMinutesLabel` | `2時間30分` | `measure-view.js` |

稼働状況は `150分`、作業スケジュールは `2時間30分`、その実績列だけ `2:30`、
測定の作業時間カードは `2時間 30分`。**同じ数字が画面をまたぐと別の顔に
なる**ので、読む側は毎回どの単位で読むのかを確かめ直すことになる
（画面基準6「単位を画面に出す」）。

**名前で探したら3つ取りこぼした。** 最初は `fmtMin` `fmtMinutes` `fmtCompact`
`fmtHour` の4つだと思っていた。`formatDuration` `fmtLfMinutes`
`scheduleMinutesLabel` は名前が違うので grep に掛からず、**機械の網を書いた
ときに初めて出てきた**。同じことをする物を数えるときは、名前ではなく
**やっていること（時と分を組み立てる式）で探すこと。**

## 決めたこと

1. **答えるのは `WL.duration` の1箇所**（§9.163）。`text()` は通常表記、
   `compact()` は密な列用。
2. **既定は「分」**（利用者の指示）。作業時間は分まで見る（§9.242 ①）
   現場の数え方に合わせる。
3. **書き方は選べる**（`min` ／ `hm`）。選んだ書き方はこの端末に覚える。
4. **単位を落とした裸の数字は作らない。** 以前の `fmtCompact` は密な列で
   `2:30` と書いていたが、見出しは「実績」としか言っておらず、時分なのか
   分秒なのかは値の側にしか手掛かりが無い。「分」の書き方では密な列でも
   `150分` と書く（4文字で `2:30` と同じ幅に収まる）。
5. **所要時間と、時点・間隔は別の軸。** 「30分ごと」（同期の間隔）と
   「30分後」（到達点）と「30分かかる」（所要時間）は違うことを言っている。
   `WL.duration` が答えるのは3つ目だけで、`fmtRelative`（〜後）・
   `clEvery`（〜ごと）・`agoText`（〜前）はそれぞれの軸のまま残す。
   ただし `fmtRelative` の1日未満のぶんは `WL.duration` に合わせる
   （`150分後` ／ `2時間30分後`）——1日を超えるぶんだけは自分で持つ
   （`4320分後` は読めない）。

## 切り替えをどこに置いたか

**ヘッダーの「A 中」バッジを「表示」の1枚にまとめ、中を2つの節にした**
（文字の大きさ／時間の書き方）。**入口を2つに増やさない**（§9.207）。

- 文字の大きさも時間の書き方も「この端末の見え方」という**同じ性格の設定**。
- ヘッダーの一等地は有限で、常設の物を1つ増やすたびに主役の一覧が狭くなる。
- **バッジの字は入っている物の名前にする。** `A 中` のままだと、時間の
  書き方がそこにあると誰も思わない（画面基準: 探させない）。いまどれかは
  開いた先の `is-current` が言う。
- **札には見本をそのまま出す**（`150分` ／ `2時間30分`）。「分」「時間と分」
  という名前だけでは、選ぶ前にはどう出るか分からない（§9.200）。
- `.global-actions` の中でも**このバッジだけは伏せない**（`90-state.css` は
  `.hd-search` ／ `.hd-field` ／ `#reload` だけを伏せる）。作業スケジュール
  こそ時間の書き方がいちばん効く画面なので、そこで開けないと意味が無い。

これは 4-2 ⑧（ヘッダー右上の常設設定を畳む）の第一歩でもある。

## 変えたら、いま出ている数字も書き直す

`wl:duration-style` を投げ、作業スケジュール（盤・一覧）・稼働状況・測定の
作業時間カードが受けて描き直す。**「次に描くときから効く」にしない**
——直らない画面が必ず残り、**選んだのに変わらないのは、設定が壊れているのと
見分けが付かない。**

## 網（2本で役割が違う）

- **`tests/test_patchlint.py`**（純粋・サーバー不要）: 「時と分を自前で
  組み立てている場所」が `WL.duration` の実装以外に無いこと。
  **これが3つの取りこぼしを見つけた。** 除外は3件（`durationText`・
  `fmtRelative`・`clEvery`）で、それぞれ理由を書いてある。
- **`tests/test_uisize.js`**: バッジの中身（2つの節・見本・いまどれか）、
  出力（`150分` ／ `2時間30分` ／ `2:30` ／ `-` ／ 負の値）、覚えること、
  そして**稼働状況を実際に開いて描かれた字が変わること**。

**関数の出力だけを見て終わりにしない**（§9.229 ⑥）。関数が正しくても、
画面がその答えを使っていなければ 4-4 ⑰ は直っていない。実際、稼働状況が
`WL.duration` を迂回して自前で `分` を書く欠陥を入れると、
**`test_patchlint` は 6/6 PASS のまま**（`時間` を組み立てていないので
lint には掛からない）で、**落ちるのは `test_uisize` の描画の2件だけ**だった。
静的な網と描画の網は、どちらか片方では足りない。

A/Bで確かめた欠陥は2つ:

| 入れた欠陥 | 落ちる網 |
| --- | --- |
| 稼働状況が `WL.duration` を迂回して自前で書く | `test_uisize` 2件 |
| 書き直しの合図（`wl:duration-style`）を止める | `test_uisize` 1件 |
