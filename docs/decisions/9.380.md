# §9.380 刃組ガイダンス: 入口・刃選択の盤・模式図の見た目（利用者の指示）

## 1. OS/DS入替を刃組図の見出しへ

効く先はその図の左右（DS／OSの字と部材の並び）なので、手順バーの尻尾に置くと
「何に効くボタンか」を探すことになる（§CLAUDE 14）。

**移したことで手順の窓の下に入った。** 窓（`.bs-pop`）は図の見出しへ垂れ下がる
ので、開いたままだと札に手が届かない——立体図の札が先に踏んでいた罠と同じで、
網も同じ作法（Escapeで閉じてから押す）にした。自分の網でこれを踏み、
`page.click` が30秒で落ちて気づいた。

## 2. 模式図と刃組表の見た目6点

| 指摘 | 直した内容 |
| --- | --- |
| バッジを短く小さく | 3つだけ（クリアランス／ラップ／板押さえ）・16→13px |
| フィンガーは四角・隙間なし | 角丸を外し、板に密着 |
| 「耳」は耳屑のそばへ | 耳屑と同じ高さで、板の外側の縁へ |
| 上軸・下軸が図と被る | 青い印のぶんまで避ける・19→15px |
| 刃組表の条幅 | 12→13px |
| 条ごとの寸法 | 番号のすぐ外側へ。読めない大きさなら出さない |

### 踏んだ罠: 「隙間ゼロ」を板の中心線に合わせた

②で `gap = 0` にしたとき、当てる先を**板の中心線**（`midY ± matH/2`）にした。
条は千鳥で `matH/2` ずつ上下へ寄るので、寄った条に食い込んだ。
当てる先は**いちばん外へ寄った板の面**（`midY ± matH`）が正しい。
既存の網（「フィンガーは板の両側に出る」）が赤で教えてくれた。

## 3. 刃選択マスタの条件をGUIで組む盤

直感的にするために置いたものは3つ:

1. 決まりは**文として読める**（「板厚 ≧ 1.6 → 専用の刃 A を使う」）。表の升目に
   散らすと、どこまでが1つの決まりなのかを目で囲み直すことになる。
2. **試し欄**に値を入れると、どの決まりが当たるかがその場で出る
   ——書いた本人が確かめられることが要件（§9.117 と同じ考え）。
3. 試し欄に値があるときは**条件1つずつに○×**。落ちた決まりは「どの条件で
   落ちたか」が見えるので、直す場所を探さずに済む。

実測（盤で確かめた）:

| 板厚 | 答え | 条件の印 |
| --- | --- | --- |
| 1.8 | 「厚板は専用」に当たる → 専用の刃 A | ○× |
| 0.4 | 「薄板は専用」に当たる → 専用の刃 B | ×○ |
| 1.0 | どの決まりにも当たらない → 一般の刃 | ×× |

判定は書いていない。`blade-core.js` の `pickGroup()`／`condHits()` をそのまま
呼ぶ——盤とガイダンスで判定が食い違うと、「盤では当たるのに現場では当たらない」
という最も分かりにくい形で壊れる。

### 踏んだ罠: 触るたびに窓を作り直していた

値を `change` だけで受け、変更のたびに `renderList()` で窓ごと描き直していたので
**打ちかけの字が消えた**——条件の値と刃の組が空のまま保存されかけ、ブラウザも
`The node to be removed is no longer a child of this node. Perhaps it was moved
in a 'blur' event handler?` を出していた。いまは `input` で打つそばからモデルへ
写し、**描き直すのは編集していないカードだけ**。窓を作り直すのは条件を足す・消す
のように形が変わるときに限る（§9.361・§9.227 と同じ約束）。

**`test_loadorder` を広げた。** `special:` の登録を master の5本だけでなく
**読み込まれる全部**から拾う（専用画面を領域フォルダへ置けるように）。ただし
「盤より後に読まれること」まで見る——先に読まれると名乗れないまま素通りするので、
緩める方向の変更にならないようにした。
