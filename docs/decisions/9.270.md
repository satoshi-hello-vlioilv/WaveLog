# §9.270 `with connect(...)` は閉じない——共有マスタが Windows で使えなかった（利用者の報告）

実機の報告は「マスタのデータを指定した先から読んでくれない。列の編集など
記録ができない」。ログは3件で、**上2件は同じ1つの原因**だった。

```
できませんでした: 共有のマスタを更新できませんでした:
  [WinError 32] 別のプロセスが使用中です:
  'C:\...\WaveLog\master.local.pull.<hex>.tmp' -> 'C:\...\WaveLog\master.local.sqlite3'
共有マスタを取り込めませんでした（写しで続けます）: [WinError 32] ...（同じ）
データソースマスタに役割「仕掛」の行がありません。
```

#### 何が起きていたか

`with connect(...) as c:` は**接続を閉じない**。`sqlite3.Connection.__exit__`
がするのは**コミットかロールバックだけ**で、close ではない。しかも
`sqlite3.Connection` は参照の輪を作るので、`with` を抜けても
**GCが回るまでハンドルが開いたまま**残る（実測）。

```python
def probe():
    with sqlite3.connect(path) as c:
        c.cursor().execute('PRAGMA integrity_check').fetchone()
probe()                    # 関数から戻った直後 … fd が 1本 残っている
gc.collect()               # gc.collect() の後  … 0本
```

`master_share._pull()` はこう書かれていた。

```python
if not _verify(tmp):       # ← ここで tmp を開き、閉じずに戻る
    raise ...
atomic_io.replace(tmp, mirror, label='master.mirror')
```

POSIX の `rename(2)` は**置き換え先も置き換え元も、誰が開いていても成功する**。
だから Linux では何も起きず、網も全部通っていた。**Windows は違う**——
開いているファイルは置き換えも削除もできない（§9.108）。しかも
**掴んでいるのは自分自身**なので、`atomic_io.replace()` が5秒粘っても
その間に手放す者がいない。**毎回・確実に失敗する。**

`_read_revision()` と `_bump_revision()` も同じ形だった。後者は写しへ
**書き込みの**接続を開いたまま残すので、1回保存した端末は**次の保存から
ずっと**取り込みに失敗する。

3件目（役割「仕掛」の行がありません）は別件で、**共有に置いた
`master.sqlite3` が新品だった**ため。中身が空なので当然そう出る（→下記の移行手順）。

#### なぜ `master_share` だけだったか

同じことをする `db_mirror._verify()` と `schedule_sync._verify_integrity()`は、
最初から `finally: c.close()` で書かれていた。§9.108 を踏んだ直後に書かれた
モジュールだからで、**あとから書いた `master_share` だけが `with` を使った**。
`with` は「閉じる」ように見えるので、レビューでも網でも気づけない。

#### 直し方（2つ。片方だけでは足りない）

**① 置き換える側のモジュールは接続を必ず閉じる。** `_opened()`（`@contextmanager`）
を通す。`master_share` の全接続をこれに載せた。

**② 写しは名前を差し替えず、中身を書き換える。** ①だけでは足りない——
写し（`master.local.sqlite3`）は**アプリが開いて読んでいるファイル**で、
その開き方は約100箇所ぜんぶ `with connect(...)`＝閉じない形である。1つでも
GCされずに残っていれば、Windows では置き換えが失敗する。**72箇所を
書き換えない**という §9.263 の前提を守るなら、**置き換えられないことを
前提に書く**しかない。

`_copy_db()` は SQLite のバックアップAPIで**中身を上書きする**。SQLiteの層で
書くので、**開いているだけ（＝トランザクションを持たない）の接続は何の
邪魔にもならない**。読み手はロックで待つだけで、中途半端な中身も見えず、
途中で落ちればジャーナルが巻き戻す。共有側（`_push`）は今までどおり
名前の差し替えでよい（書きかけを他端末に拾わせないため。`schedule_sync._push`
と同じ作法で、こちら側の読み書きは①で必ず閉じている）。

#### ついでに塞いだ穴

`_pull()` は `if not src.exists():` を「共有にまだ無い（初回）」と読んでいた。
**共有越しでは stat だけ失敗することがある**（§9.108・§9.262）ので、
一瞬の応答不良で「初回」と読み、**手元の写しを正として次の保存で全員の
マスタを上書きしかねなかった**。`path_exists_safe()` の3値で受け、
**None（確かめられなかった）は断る**。

#### 固定

`tests/test_mastershare.py` の8節。**Linuxでは `rename` が通ってしまうので、
「動いたか」を見る網では絶対に捕まらない。**

- `/proc/self/fd` で**開いているハンドルを実際に数える**（取り込み後・
  書込サイクル後とも0であること）。前提として「数えられること」を先に確かめる
- 写しの **inode が変わらない**こと（＝名前を差し替えていない）
- `path_exists_safe` が None を返す状況を作り、**取り込みを断る／書込サイクルに
  入らない／ロックを残さない**こと
- 置き換える側の3モジュールに `with connect(...)` が無いことを**構文木で**見る
  （綴りで見ると説明文の中の `with connect(...)` まで拾い、直したのに落ちたままになる）

4つの欠陥（`_verify`を戻す／`_read_revision`を戻す／写しを`os.replace`で
置き換える／`src.exists()`で見る）でそれぞれ落ちることを確認済み。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **`with connect(...) as c:` は接続を閉じない**（§9.270）: `sqlite3.Connection`
  の`__exit__`がするのは**コミットかロールバックだけ**で、closeではない。
  しかも参照の輪を作るので、`with`を抜けても**ハンドルはGCが回るまで開いた
  まま**残る（実測。`gc.collect()`で消える）。POSIXの`rename(2)`は開いている
  ファイルも置き換えられるので**Linuxでは何も起きず**、Windowsだけが
  `WinError 32`で落ちる（§9.108）。しかも**掴んでいるのが自分自身**なので
  `atomic_io.replace()`が5秒粘っても手放す者がおらず、**毎回・確実に失敗する**
  ——実機で、マスタを共有に置いた端末が起動時の取り込みも保存も一切できない
  状態になっていた。**ファイルを置き換える／削除する側のモジュールでは
  `with connect(...)`を書かないこと**（`master_share._opened()`のように
  `finally: c.close()`を持つ`@contextmanager`を通す。`db_mirror`と
  `schedule_sync`は最初からそう書かれており、だから実機で動いていた）。
  **さらに、自分が読んでいるファイルは名前を差し替えない**——写し
  （`master.local.sqlite3`）はアプリの約100箇所が`with connect(...)`で開くので、
  1つでも残っていれば置き換えは失敗する。SQLiteのバックアップAPIで**中身を
  上書きする**（`_copy_db()`。SQLiteの層で書くので、開いているだけ＝
  トランザクションを持たない接続は邪魔にならない）。
  **網は「動いたか」で見ないこと**——Linuxでは壊れた実装でも通る。
  `/proc/self/fd`で**開いているハンドルを数え**、写しの**inodeが変わらない**
  ことを見る（`tests/test_mastershare.py`8節。綴りで`with connect(`を探す網は
  説明文まで拾うので**構文木で見る**）。
