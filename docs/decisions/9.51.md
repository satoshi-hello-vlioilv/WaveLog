# §9.51 作業可否フラグ(まだ来ていないロットを開始させない)

予定に並んでいても、そのロットが**まだこの設備まで流れて来ていない**ことが
ある(前工程が終わっていない)。計画は先に立てるので当然起こる状態だが、
オペレータからは予定行の見た目で区別できず、着手できないロットの測定画面を
開いてしまう余地があった。

現場の判断基準をそのままフラグにする:

> **仕掛データの「残仕掛設備ｺｰｽ」が使用設備の文字列で始まっていれば作業可能**

- タイムラインに**必須列**「作業」を追加する(列表示マスタ §9.18 の選択対象に
  しない。作業できるかどうかは表示の好みではなく、開始の可否そのものだから)。
  `可`(緑) / `不可`(赤) / `?`(黄・判定不能) / `—`(設備停止など作業以外)。
- **`可`の予定にしか「開始」ボタンを出さない**。加えて`startWorkFromEntry()`
  側でも状態を再確認する(行のダブルクリック等、ボタン以外の経路があるため)。
  着手済みの「再開」は対象外(既に始めた作業を止める理由が無い)。
- `不可`の行は薄く表示する。並べ替え・削除はできる(計画の操作は妨げない)。

**判定は必ず「現在の仕掛データ」で行う。** 予定投入時のスナップショット
(`明細JSON`)は投入時点の値で固まっており、工程が進んでも変わらない。
これで判定すると「まだ来ていないロットを作業可能と表示し続ける」ことになり、
フラグの意味が無くなる。`loadWorkableIndex()`が`/api/table?db=SIKALOTNOW`
から「ロット番号 → 残仕掛設備ｺｰｽ」を作り直す(TTL3分、§9.46のキャッシュと
同じ考え方。`invalidatePlanCache()`で一緒に捨てる)。

- **`include_hidden=1`を必ず付ける**。列表示マスタで残仕掛設備ｺｰｽが
  非表示にされていても判定には要る(CLAUDE.md「内部計算用の問い合わせには
  `include_hidden=1`」)。
- 列名の解決は`aliases`(`static/js/core/base.js`)で行う。サーバー側で
  SIKALOTNOWのエイリアス解決を再実装しない、という§5.1の規約に合わせる。
- **仕掛が読めない/該当ロットが無いときは`可`にしない**(`?`にする)。
  確認できないものを既定で通すと、フラグを付けた意味が失われる。

**判定材料の取得で操作を止めない。** 仕掛一覧の取得は共有越しだと時間が
かかることがあり、待つとその間ずっと予定が出ない。`loadPlan()`のあとに
`refreshWorkableInBackground()`を**awaitせず**呼び、可否は取れ次第そのセルだけ
差し替える(初回は`?`で出て、数百ms〜数秒後に確定する)。実測: 仕掛の取得に
6秒かかる状況でも予定は638msで表示される。

反映は`applyWorkableFlags()`が**既存の行を書き換える**。`renderTimeline()`を
呼ぶと行が総入れ替えになり、ドラッグ中・詳細を開いている最中・スクロール位置が
すべて飛ぶ。可否セル・薄表示・開始ボタンの有無だけを差し替える
(行要素には`__scEntry`で自分のエントリを持たせてある)。

**可でない行は裏で追いかける。** まだ来ていないロットは工程が進めば`可`に
変わる。利用者に「再読込」を押させずに追いつくよう、**可でない予定が
残っている間だけ**2分間隔で取り直す(`scheduleWorkableWatch()`)。全部`可`に
なったら見張る理由が無いので止め、画面を出るときも`stopWorkableWatch()`で
止める(無駄な問い合わせを残さない)。

外から更新したいときは`window.refreshScheduleWorkable(force)`。
なぜその可否なのかを切り分ける用に`window.scheduleWorkableState()`
(索引の件数・取得時刻・見張り中か)を公開してある。

## 守ること（`CLAUDE.md` から移した規則の本文）

CLAUDE.md には見出しの1行だけを残してある。ここが本文。

- **開始ボタンを作る場所は2つある。文字とHTMLは1箇所**（§9.302の追補、利用者の
  報告「作業スケジュールを表示したときに、開始ボタンが2種類ある」）: 作業可否
  （§9.51）は仕掛データを読まないと分からず共有越しでは時間がかかるので、
  **待たずに先に予定を描く**（`refreshWorkableInBackground`）。そのため
  「表を描くとき」（`renderEntryRow`）と「あとから可になってボタンを足すとき」
  （`applyWorkableFlags`）の**両方が必ず使われる**のに、文字が`開始`と`▶ 開始`で
  食い違っていた——**仕掛データが最初の描画に間に合ったかどうかだけで見た目が
  変わり**、しかも`applyWorkableFlags`は「無ければ作る」だけなので一度描かれた行は
  そのまま固定される（押したときの動きは同じなので、合図が嘘をついている・§3）。
  いまは`SC_START_BTN`（文字と説明）・`canStartEntry()`（押せるか）・
  `startBtnHtml()`（HTML）の3つが1箇所で、**DOMで足す側も`insertAdjacentHTML`で
  同じHTMLを通す**（クラス名を2箇所に書くと、CSSを直したときに片方だけ当たらない）。
  **網は「足す道」を自分で通すこと**（`tests/test_workable.js`）——最初の描画で
  出た状態だけを見る網は、足す側が何を書いていても通る。
