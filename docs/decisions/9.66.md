# §9.66 列名キャッシュが別DBのものを返していた(表示のずれ)

品質データの一覧で、ロット№欄に日時が出て、実際のロット番号は2つ隣の
列に入る、という**列と中身のずれ**が報告された。原因は§9.46で入れた
`cols()`のキャッシュのキー。

`cols()`は「列名を`SELECT *`と同じ並びで返す」関数で、`/api/table`は
`dict(zip(cols, 行タプル))`で行を組み立てる。つまり**列名リストが違うDBの
ものだと、値が別の列名へ紐づく**。列数が違えば`zip`が末尾を黙って捨てる。

キャッシュは「接続先ごとに分ける」つもりで、接続オブジェクトへ目印
(`_wavelog_source`)を付けて引いていた。ところが
**`sqlite3.Connection`も`pyodbc.Connection`もC実装で属性を追加できない**
(`AttributeError`)。目印付けは`try/except`で握りつぶしていたため常に失敗し、
キーは用意していたフォールバック`id(type(c))`＝**同じエンジンなら全DB共通の
定数**へ落ちていた。結果、キーは実質テーブル名だけになり、
**同じ名前のテーブルを持つ別のDBを60秒以内に続けて開くと、先に開いた方の
列名が返る**。仕掛→品質の順に開けば品質データが仕掛の列名で描かれる。

接続オブジェクトから接続先を推測するのは諦め、**呼び出し側から明示的に
渡す**形にした。`cols(c,t,source=...)`で`source`が与えられたときだけ
キャッシュし、無ければキャッシュしない(速度より正しさを優先)。共有越しの
往復が効く経路(`/api/table`・品質結合・品質分析・測定コンテキスト)では
`cf['path']`等を渡すので、§9.46で得た往復削減はそのまま維持される。

**波及していた範囲**(いずれも`cols()`の結果を前提に組み立てるため、
列名を取り違えると静かに壊れる):

| 経路 | 壊れ方 |
|---|---|
| `/api/table`の行組み立て | 値が別の列名へ紐づく・末尾の列が落ちる |
| 検索(`search`)のWHERE | 存在しない列を参照して500、または別の列を検索 |
| 絞込(`filters`) | `col in columns`の検証に落ちて条件が無視される |
| 並替(`sort`) | `sort_col in cs`に落ちて並替が無視される |
| 品質結合(`join_quality`) | キー列を見つけられず結合しない/別の列を足す |
| 品質分析(`/api/quality`) | 集計に使う列の自動選択が別DBの列名になる |
| 測定コンテキスト | 品質情報のロット列解決が狂う |

同種の再発を防ぐため、`dict(zip(列名, 行))`を行う箇所(4か所)はすべて
`source`付きの`cols()`から列名を得ている。
