# WaveLog 基盤再編 計画書

「汎用Webアプリ作成 基盤仕様書」をWaveLogへ適用するための評価と実装計画。
アーキテクチャの現状は `ARCHITECTURE.md`、開発規約は `../CLAUDE.md` を参照。

---

## 1. 前提の確定

### 1.1 監視レベル = レベル1（通常の操作アプリ）

仕様書「3. 監視レベルの選び方」に照らすと、WaveLogは**レベル1**に該当する。

- 入力・検索・公差判定・帳票作成が主機能で、バックグラウンド処理を持たない
- 自動実行・スケジュール実行が無い
- 作業中の測定データはブラウザのIndexedDBに保存されるため、
  **サーバープロセスが落ちても作業内容は失われない**

したがってレベル2/3の機能（処理状態API・実行キュー・常駐運転・通知領域）は
**実装しない**。仕様書も「新規アプリは、必要以上にレベルを上げないことが重要」と
明記している。

### 1.2 配布形態は未定・混在

現時点で「端末ごとにフォルダをコピー」か「共有フォルダから各端末が起動」かが
確定していない。よって**どちらでも破綻しない設計**を採る（詳細は 4.1）。

## 2. 現状の問題

### 2.1 【最優先】起動レース × ウォッチドッグ自決の複合バグ

`start_app.bat` はブラウザを開いてからサーバーを起動している。

```
15: start "" "http://127.0.0.1:5029/?build=v29"   ← ブラウザが先
17: python app.py                                  ← サーバーは後
```

結果として次の経路で「アプリが起動しない」状態に陥る。

1. ブラウザが先に開く → サーバー未起動のため**接続エラー画面**
2. 数秒後にサーバーが起動する
3. 利用者がリロードに気づかず放置する
4. **90秒後、ウォッチドッグ（v1.42で追加）がサーバーを自動終了**
5. 利用者がリロード → また接続エラー → 「起動しない」

**実測で確認済み**: ブラウザを一度も繋がずに起動すると、きっかり90秒で
`[watchdog] 開いているタブが90秒以上存在しないため終了します` を出力して
プロセスが終了する。

ウォッチドッグ自体は正しく動作しており、原因は「起動完了を確認せずに
ブラウザを開く」起動順序（仕様書2.3の未実装）にある。

### 2.2 その他の潜在的不具合

| # | 内容 | 影響 |
|---|---|---|
| B1 | 長時間放置（PCスリープ等）で1時間経つとタブが失効し、その90秒後にサーバー終了。画面には何も表示されない | 復帰時に無言で操作不能 |
| B2 | ブラウザを強制終了すると`pagehide`が飛ばず、最大1時間プロセスが残る | 設計上の許容範囲（記録のみ） |
| B3 | ログが一切残らない。コンソール出力のみで、ウィンドウを閉じると消える | 障害調査が不可能 |
| B4 | 接続断が利用者に見えない。API呼び出し時のみエラーが出る | 原因不明の操作不能 |
| B5 | 多重起動の防止が無い。2回起動するとポート競合でtraceback | 利用者が混乱 |
| B6 | `_git_version()` が起動時にgitサブプロセスを3回実行 | 共有配置時の起動遅延要因 |

B1・B4は同じ原因（ハートビートの応答を`.catch(()=>{})`で捨てている）で、
**すでに信号は届いているのに使っていない**状態。

### 2.3 アプリ固有値の散在（仕様書ステップ2の未実施）

| 値 | 散在箇所 |
|---|---|
| ポート`5029` | `start_app.bat`, `app.py`(2箇所), `static/js/base.js` |
| 表示名`測定伝送システム` | `templates/index.html`(3箇所), `base.js`(2箇所), `list-view.js` |

## 4. 設計判断

### 4.1 配置形態が未定・混在への対応

種類ごとに扱いを変え、**どちらの配置でも安全**にする。

| 種類 | 置き場所 | 理由 |
|---|---|---|
| ログ・pycache・runtime・work | **必ず** `%LOCALAPPDATA%\WaveLog\` | 共有配置でも端末間で衝突しない。仕様書2.7の主目的 |
| `master.sqlite3`（マスタ） | 設定で指定可。既定は現状維持（アプリ直下`db/`） | 全社共通マスタとして共有したい可能性があるため、強制移動しない |
| `records.sqlite3`（測定バックアップ） | 設定で指定可。既定は現状維持 | 本来は端末ローカルが正しいが、既存データがあるため移行を強制しない |

加えて、起動時にアプリ本体の位置を判定し、**UNCパスやネットワークドライブ上に
`records.sqlite3` がある場合は警告をログに記録**する。配置形態が決まった時点で
設定1つで切り替えられる状態にしておく。

> SQLiteをSMB共有上で複数端末から書き込むとロックが正しく効かず破損し得る。
> 共有配置に決まった場合は `records.sqlite3` のローカル化が必須になる。

### 4.2 起動待機表示の実現方式（検証済み）

サーバー起動前でも表示できる必要があるため、待機画面は `file://` の
ローカルHTMLとして開く。ただし `file://` から `http://127.0.0.1` への
`fetch` はCORSで読めないため、**script要素による生存確認**（JSONP相当）を使う。

```
loading.html (file://)
  └─ <script src="http://127.0.0.1:5029/api/ready.js?cb=...">
       └─ 応答: wavelogReady({"app":"wavelog","ready":true,"version":"...","pid":...})
```

- サーバー未起動なら `onerror` → 一定間隔で再試行（表示は「接続を確認中…」）
- 応答が返ったら**アプリ識別情報を検証**してから本体URLへ遷移
- 規定回数を超えたら「起動できません」＋確認すべきログの場所を表示

**Playwrightで実証済み**: 待機画面を先に開き、4秒後にサーバーを起動する
順序でも、待機画面が識別情報 `{"app":"wavelog","ready":true,...}` を
正しく受け取ることを確認した。

この方式は仕様書2.2（起動待機表示）と2.3（起動完了の確認・アプリ識別情報の検証）を
同時に満たし、**起動順序に依存しない**ため 2.1のP0バグも根本的に消える。

### 4.3 アプリ固有値の集約

`app/config.py` に集約する。

```
APP_ID          = 'wavelog'          # 識別子（多重起動判定・ready.js検証・ローカル領域名）
APP_NAME        = '測定伝送システム'   # 表示名
PORT            = 5029
LOCAL_DIR_NAME  = 'WaveLog'          # %LOCALAPPDATA% 配下の名前
```

フロントエンドへは `/api/build` 経由で渡し、HTML/JSへの直接埋め込みを無くす。

## 6. フェーズ計画

### Phase 0 — 起動バグの緊急修正【単独リリース】

実害が出ている 2.1 を最短で止める。仕様書2.2/2.3の中核だけを先行実装する。

- `loading.html` を追加（`file://` から起動、script要素で生存確認）
- `/api/ready.js` を追加（アプリ識別情報を返す）
- `start_app.bat` を修正: **ブラウザではなく `loading.html` を開く**
- 待機画面に経過時間・起動段階・失敗時の確認先を表示

**効果**: 起動レース・90秒自決・起動待機表示なし が同時に解消。
**リスク**: 既存の業務コードに触れないため極小。

### Phase 1 — 起動基盤の骨格

仕様書ステップ3「業務機能を作り込む前に基盤を成立させる」に対応。
**この段階では `app.py` の中身は動かさない**（`server.py` が読み込んで実行するだけ）。

- `app/config.py` — アプリ固有値の集約（ポート・表示名の散在を解消）
- `app/logging_setup.py` — ログ初期化（launcher / app の2系統）
- `app/watchdog.py` — ウォッチドッグを `app.py` から分離
- `start_app.py` / `launch_guard.py` / `server.py` / `process_manager.py`
- `Start.vbs`（通常起動）/ `start.bat`（診断起動）/ `stop.bat`（明示停止）
- 多重起動の防止（ロックファイル + ポート確認 + アプリ識別）
- **接続断の画面表示**: ハートビート応答を使い、切断時にバナー表示と再読込操作を提示（B1・B4の解消）

### Phase 2 — 実行時ファイルのローカル配置

- `%LOCALAPPDATA%\WaveLog\` 配下の作成と `app/paths.py` による解決
- `PYTHONPYCACHEPREFIX` で `__pycache__` をローカル領域へ
- DBパスの設定化 + 共有配置の検出と警告（4.1）
- 既存データは**移動しない**（後方互換の `resolve_local_db` を維持）

### Phase 3 — バックエンド／フロントエンドの再編

最も回帰リスクが高いため、**移動と改変を必ず別コミットに分ける**。

1. `backend/` → `app/` へ移動（import パスの変更のみ・ロジック不変）
2. `templates/` `static/` → `app/` 配下へ移動（`url_for` が吸収）
3. `app.py` の業務APIを `routes/` へ分離（受付とロジックの分離はまだしない）
4. `routes/` から `services/` へ業務ロジックを抽出
5. `masters.py`（50KB）を `routes/masters.py` + `repositories/master_repo.py` へ分割

各手順ごとに回帰テスト一式（現状 PASS=115 / FAIL=6）を実行し、
**既知の6件以外に失敗が増えないこと**を確認してから次へ進む。

### Phase 4 — docs / tests の整備

- 回帰テストを scratchpad から `tests/` へ移植（配布ZIPには含めない）
- `ARCHITECTURE.md` を新構成へ全面更新
- 障害時の確認手順を `docs/` に追加（ログの場所・よくある失敗と対処）

## 7. 進め方の原則

1. **移動と改変を同じコミットに混ぜない。** 移動だけのコミットは差分が
   「ファイル名の変更」に見え、レビューと切り戻しが容易になる。
2. **各フェーズごとに回帰テスト一式を実行**し、既知6件以外の失敗が
   増えていないことを確認する。
3. **実データを保護する。** テスト実行前に `db/*.sqlite3` を退避し、
   実行後に戻して行数を照合する（過去にテストが実データを汚染した経緯あり）。
4. **各フェーズで `APP_VERSION` を上げ、`CHANGELOG` へ追記**する。
5. **`start_app.bat` はCP932で保存**する（`CLAUDE.md` の規約）。
   `Start.vbs` / `stop.bat` も同様。
6. 仕様書の項目を省略・統合する場合は、**その項目が解決していた問題を
   別の方法で解決できるか**を確認する（仕様書8章）。

## 8. 完成条件

仕様書8章の5点をWaveLogの言葉に置き換えたもの。

- [ ] 利用者は `Start.vbs` だけを知っていればよい
- [ ] 起動中・起動失敗・接続断が、それぞれ画面上で区別して見える
- [ ] 「起動しない」と言われた時に、ログだけで原因の切り分けができる
- [ ] 実行時ファイルが共有側のアプリ本体を汚さない
- [ ] 業務機能の追加が起動処理へ影響しない
