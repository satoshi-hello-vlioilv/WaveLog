## 1. 構造の候補（推奨順・各項目に評価関数）

### 3-18. 色のリテラルをトークンへ（残り）【小〜中】
- **評価関数**: 非トークン行の色リテラル **758** → `#fff`／`transparent`／紙の `--rp-*` を除いて **0**
  （上限は `tests/fixtures/color_baseline.json`・下げる方向だけ）。
- **やること**: 残りは「値が同じトークンが無い」色なので、**役割名（`--sc-…`／`--rp-…` など）を
  足してから**置く。色の意味を決める作業になる。`tests/visual/run.sh compare` で見た目が変わらないことを
  確かめる——**撮り比べの床を先に測る**（同じコードで2回撮っても 47枚中11枚・最大1,767画素ずれる・§9.353）。
- 機械で置けるぶん（1,110→758）は済み（[§9.350](decisions/9.350.md)）。

### 3-19. 部品の族を減らす（残り）【中・見た目が変わるので要確認】
- **評価関数**: タブ／段／セグメントのクラス族 約40 → **3**（`.wl-tabs`＝並列／`.wl-steps`＝順番あり／
  `.wl-seg`＝切替）＋画面固有は中身のクラスだけ。いまこの3つは**CSSにもHTMLにも1件も無い**。
- **含むもの**: 画面の 4-3 ⑩「タブの流儀が3種類」（測定の番号付き段・共通設定の下線タブ・印刷プレビューの3段）
  ——「順番がある＝番号付き」「並列＝下線」の2種に固定する。
- **注意**: 共通クラスを要素へ付ける段は**寸法が揃う＝見た目が変わる**。**揃えること自体を目的にしない**
  ——動かす前に「読む人に何が良くなるか」を言い、変わる値を**撮った範囲の外まで全部**数えて見せる
  （[§9.449](decisions/9.449.md)。メニューで一度却下された）。
- 選択中の見た目を束ねる段（CSSだけ）は済み（[§9.353](decisions/9.353.md)）。メニュー族は `.wl-menu` の1つ（[§9.448](decisions/9.448.md)）。

### 3-22. 長い関数を段ごとに切り出す【中】
- **評価関数**: 80行超の関数の数を上限固定で下げる。いまの上位:

  | 関数 | 場所 | 行数 |
  |---|---|---|
  | `bindFieldBuilders` | `master/master-report.js` | 568 |
  | `renderGridInner` | `list/list-view.js` | 516 |
  | `renderEntryRow` | `schedule/schedule-view.js` | 402 |
  | `renderOpModal` | `master/master-opdata.js` | 394 |
  | `buildOneFieldControl` | `master/master-maint.js` | 320 |
  | `_expand_plan_with` | `backend/schedule_calc.py` | 約310 |

- **やること**: `renderGridInner` は**既に §番号のコメントで11の段に区切られている**（列の準備→並び→書式→
  式→列幅→行番号の桁→揃え→…）。段ごとに関数へ切り出すだけで振る舞いは変わらない。`bindFieldBuilders`・
  `renderOpModal`・`buildOneFieldControl` は型（`type`）ごとの `switch` なので、型→組み立て関数の登録表へ。
- **やらない**: `schedule-view.js` を機械的に割ること（踏襲）。

### 3-7. 画面の骨組みHTMLをJS文字列から出す【中】
- **評価関数**: `ensurePanel` のような「HTML文字列を組み立てるだけの関数」**9本**（最大は `schedule-view.js` の
  約360行）→ `<template id="tpl-…">` を `WL.panel(id)` で複製する形へ。JSの中のHTML文字列のバイト数を数えて減らす。
  いま `index.html` の `<template>` は0件。
- **理由**: §9.211 ③・§9.266 で「テンプレートリテラルの中のコメントにバッククォートを書いて画面が組み上がら
  なくなった」が2度。HTMLがHTMLとして置いてあればこの事故の種が消え、CSSとの対応も読める。
  `<template>` は不活性なので起動の描画コストは増えない。

### 3-14. 配信の軽量化【小・任意】
- **評価関数**: 初回の `<script>` 要求 **39本** → 1本（`/css/app.css` と同じく `/js/app.js?t=` へ連結）／
  配信バイト **約4.56MB** → コメントを配信時に落として約6割（ソースは触らない）。
- 効果は初回と版上げ直後だけ（`immutable` キャッシュ済み・§9.97）。優先は低い。

### 長期の方向（今すぐは推奨しない）
- **ES modules**（`<script type="module">`、バンドラ不要・フォルダコピー配布のまま）: 依存が `import` で
  静的に辿れ、読み込み順の契約が消える。画面のJSは全部閉じた（§9.359）ので始める足場はある。
  **新しい画面から1本ずつ**が現実的。過去の非目標は「バンドラ・フレームワーク・TS」であって
  native module は含まれていない——**ここは判断を仰ぎたい点**。

## 3. 推奨する順番

```
構造（振る舞い不変・各1コミット）: 3-18 色（残り）→ 3-22 長い関数 → 3-7 骨組みHTML → 3-14 配信（任意）
構造（見た目が変わる・要確認）:    3-19 部品の族（4-3 ⑩ を含む）
画面（都度確認・1つずつ）:          20 → 22 → ⑥ → 19 → ⑫・25 → 26・27 → ⑦・⑧ → ⑭・⑯
```

**やらないこと**（踏襲）: バンドラ・フレームワーク・TS・型注釈の一斉導入、
`schedule-view.js` の機械的分割、`window.*` の一斉移設、§番号の振り直し、全件テストの並列化。

**分からないこと**: 実機の見え方（撮影は Linux の Chromium・1920×1080。利用者の 2160×1440・125% では
1728×1152 相当）と、現場での操作頻度（19・26 の「要確認」はここに依る）。⑭ がいまも切れるかは測っていない。
